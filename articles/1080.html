TypeScript 7.0 正式發佈：Go 重寫帶來最高 12 倍速度提升

2026 年 7 月 8 日，微軟正式發佈 TypeScript 7.0。這個版本的里程碑意義在於：整個編譯器用 Go 語言從頭重寫，完整構建速度提升 8 到 12 倍，同時內存佔用也顯著降低。

爲什麼用 Go 重寫

TypeScript 最初由 TypeScript 自身編寫（自舉編譯器），經過十多年的發展積累了龐大的代碼量。隨着前端項目規模不斷增長，編譯速度成爲開發者最頻繁遇到的瓶頸，尤其在大型 monorepo 中，一次完整類型檢查可能需要數分鐘。

微軟團隊在 2025 年啓動了原生重寫計劃，目標是利用現代多核 CPU 的並行計算能力。Go 語言的共享內存多線程模型天然適合這個需求。重寫過程中，團隊儘可能保持原有代碼結構和邏輯不變，確保新舊編譯器產出的類型檢查結果完全一致。

TypeScript 7 帶來了三個關鍵變化：

- **原生代碼執行速度**：Go 編譯爲原生二進制，不再依賴 Node.js 運行時

- **共享內存多線程**：解析、類型檢查、代碼生成可以並行執行

- **全新 watch 模式**：基於 Parcel bundler 的文件監視器，跨平臺更穩定

新增並行控制參數

TypeScript 7 引入了兩個實驗性參數來精細控制並行度：

--checkers N

控制類型檢查器的工作線程數，默認爲 4。在 CPU 核心較多的機器上可以調高。例如使用 --checkers 8 時，各項目加速比進一步提升：

代價是內存佔用增加，因爲每個類型檢查器 worker 會維護自己的類型信息視圖。在 CI 環境（CPU 核心少、內存有限）中，可以將 --checkers 調低到 1 來避免不必要的開銷。

--builders N

控制項目引用（project references）的並行構建器數量，適合 monorepo 場景。--builders 與 --checkers 有乘積效應：--checkers 4 --builders 4 意味着最多 16 個類型檢查線程同時運行，可能過於激進。

--singleThreaded

完全關閉並行化，解析、類型檢查、代碼生成全部在單線程中執行。適用於調試、與 TypeScript 6 性能對比、外部編排並行構建、或資源極度受限的環境。

與 TypeScript 6 共存方案

TypeScript 7.0 目前尚未公開編譯器 API（預計 7.1 版本提供）。對於 typescript-eslint 等需要程序化訪問編譯器的工具，微軟提供了兼容方案。

新的 @typescript/typescript6 包導出 tsc6 可執行文件和 TypeScript 6.0 的完整 API。通過 npm alias 可以讓兩個版本在同一項目中共存：

{
  "devDependencies": {
    "@typescript/native": "npm:typescript@^7.0.2",
    "typescript": "npm:@typescript/typescript6@^6.0.2"
  }
}

这样，依赖 typescript 包的工具（如 typescript-eslint）继续使用 6.0 API，而 npx tsc 直接使用 7.0。

Vue、Svelte 等嵌入式語言工具鏈因依賴編譯器 API 集成，目前仍需使用舊版 TypeScript。

企業級實踐反饋

多家公司在正式發佈前參與了測試：

- **Slack**：CI 類型檢查時間從 7.5 分鐘降到 1.25 分鐘，合併隊列等待時間減少 40%。此前編輯器加載慢到幾乎不可用，工程師只能依賴 CI 做完整類型檢查

- **Canva**：編輯器首次報錯時間從 58 秒降到 4.8 秒

- **Vanta**：最大項目獲得 9 倍加速

- **PowerBI**：工程師在 rename 功能尚未支持時就將其設爲默認體驗

微软内部参与测试的团队包括 Loop、Office、Teams、Xbox。外部合作公司包括 Bloomberg、Figma、Google、Linear、Miro、Notion、Sentry、Slack、Vercel 等。

TypeScript 7 的 --watch 模式完全重建，基於 Parcel bundler 的文件監視器實現跨平臺高效監視。Go 標準庫不提供內置文件監視 API，團隊評估了多個第三方庫後選擇自建方案，解決了穩定性和跨平臺兼容問題。
