GitHub 用 Copilot 智能體將 Copilot 運行時從 TypeScript 遷移到 83 萬行 Rust

內容機器翻譯自第三方媒體（GitHub Blog），僅供參考，以原文為準。

AI 導讀

GitHub 工程師 Stephen Toub 覆盤用 Copilot 智能體在約 14.5 周內將 Copilot agent runtime 從 TypeScript/Node.js 全量重寫為 832,378 行生產 Rust，AI 智能體完成大部分代碼，共 128 個 PR 增量合入 main 並持續發佈。

推薦理由

當事工程師覆盤用 AI 智能體在數月內將 Copilot 運行時遷往 Rust 的全過程，策略、迴歸樣本和成本數據對同類遷移有直接參考價值。

正文

GitHub Copilot CLI、GitHub Copilot app 和 GitHub Copilot SDK 全都由 Copilot agent runtime 提供支持，這是一個可以嵌入到應用程序和服務中的智能體運行框架。它最初是用 TypeScript 編寫、運行在 Node.js 和 V8 JavaScript 引擎之上，服務於如今被稱為 GitHub Copilot cloud agent（CCA）的產品，而隨着該運行時及其能力快速擴展，它一直沿用着這套技術棧。

如今，這一切已經改變。藉助 GitHub Copilot app 和 Copilot CLI，我們將該運行時完全重寫為超過 800,000 行生產級 Rust 代碼。AI 智能體編寫了其中大部分代碼，橫跨 128 個 pull request，這些 PR 陸續合入 main 並逐步發佈，而不是等到最後一次性切換。

少數不可避免的迴歸問題也在過程中被迅速發現並修復，同時運行時的性能提升了好幾個數量級。一個在智能體出現之前需要一整個開發團隊花上一兩年才能完成的項目，如今主要由一名開發者僅用幾個月就完成了，而團隊其他成員在此期間還在持續大幅擴展該運行時的能力和覆蓋範圍。

為什麼我們需要移植

Copilot 智能體運行時不僅僅是 Copilot CLI 背後的引擎。它還支撐着越來越多的 Microsoft、GitHub 以及生態系統解決方案，對於其中每一個而言，從架構上看，AI 支持都是圍繞同一個運行時構建的外殼，再加上該解決方案所需的定製化內容。這不僅包括 GitHub Copilot CLI 和 GitHub Copilot 應用，還包括最新發布的 VS Code、Visual Studio、CCA、Copilot Code Review（CCR）、Copilot Cowork、Copilot Studio，以及 Excel、Outlook、PowerPoint、Word……還有更多。

這些是非常不同的產品，它們中沒有哪一個想要、也不應該需要去實現生產級智能體 harness 所包含的一切。它們想要的是全部的智能、安全、可靠性和性能，並且希望這些能夠被共享，這樣一處修復就能修復所有產品。上一段中列出的大多數產品最初都實現了自己的智能體循環，但此後已將其替換為 GitHub Copilot SDK，後者是進入 Copilot 智能體運行時的入口。

這樣做使它們能夠專注於自身的核心業務價值，而把細節交給運行時處理。考慮到行業的節奏，以及所採用的智能體循環需要在激烈競爭中始終保持最佳水準，這一點就更加重要。

所以，共享運行時，很好。問題在於被共享之物的本質。

如果我們看一下這個 CLI，它在邏輯上就是一個構建在智能體循環之上的終端 UI（TUI）。實際情況是，整個技術棧都是用 TypeScript 實現的，使用 Node.js 作為框架、V8 作為執行引擎，並用 Ink 和 React 來做 UI。

對於一個 TUI 應用來説，這是相當合理的選擇；TypeScript 和 Node.js 門檻低、易於上手，能實現非常快速的應用開發。而且對於控制枱應用的需求而言，它在啓動速度、響應性、吞吐量和內存消耗方面的性能影響也是合理的。

但遺憾的是，當你考慮到這套實現要被用在其他環境中、面對其他約束、並且需要滿足諸如快速啓動和因低內存開銷而帶來的出色服務器密度等要求時，這些性能表現就遠沒有那麼合理了。

CLI 及其運行時的架構也加劇了這裏的挑戰。整個行業跑得極快，在這種背景下，真正聰明的人會為了交付速度和市場覆蓋而做決策。Copilot CLI 最初是快速編寫併發布的，在這樣做的時候，TUI 和運行時相當緊密地交織在一起，而不是被分離成離散的層。後來當需要一個 SDK 來以編程方式訪問該運行時時，由於各層之間沒有清晰的分離，人們做出了一個務實的決定：把 SDK 疊加在 CLI 之上，儘管從邏輯上講你會期望相反的架構。CLI 不再只能通過用户在命令行提供的命令來訪問，而是被更新為一種可以無頭運行的模式，從 stdin 讀取類似的命令並將響應寫入 stdout。隨後可以使用 JSON-RPC 協議，將來自外部進程的函數調用與 CLI 之間進行編組。這樣 SDK 就可以嵌入到任意的消費程序中，這些程序會生成一個 CLI 進程，在進程外託管智能體循環，而 SDK 則通過這種 JSON-RPC 機制調用遠程進程中的函數。很巧妙。能快速出門。很靈活。但對於那些消費類應用的性能（啓動、內存、吞吐量）和可靠性來説並不理想。從 SDK 創建一個新的 CopilotClient 意味着要再生成一個進程：

const client = new CopilotClient();
await client.start(); // spawns the CLI as a subprocess
const session = await client.createSession({
    /* ... */
});

這個過程需要啓動並託管 Node 和 V8。這意味着要解析 CLI 中由 TypeScript 代碼生成的大量 JavaScript，為其生成字節碼，並可能在後續的 JIT 層級中優化熱點代碼。這意味着要承擔與 V8 相關的全部內存開銷。

這意味着要繼承 Node 的線程模型，而該模型默認會迫使我們把所有 CPU 密集型工作串行化。這意味着僅僅為了進行函數調用，就不得不進行強制性的跨進程通信。這意味着每一種語言的每一個 SDK 使用者，都要附帶 Node.js 或一個包含 V8 的打包二進制文件。

這意味着 C#、Python、Go、Java 和 Rust 的 SDK 都要為每個客户端額外付出整整一個語言運行時的代價，最低工作集大約在 100 MB 量級，而這個運行時對其應用而言別無他用。這意味着每一個事件、每一條消息，以及每一次抽象會話文件系統的讀寫，都要跨越進程邊界。

這意味着 Node 的一次崩潰會連帶整個會話一起崩潰。這也意味着任何部署它的人，至少都要監督、監控和調試兩個進程。

相反，我們想要一個運行時：

  • 它不包含 TUI，TUI 是它自己的庫，TUI 以及其他應用和服務可以乾淨地分層構建在其之上。
  • 以依賴極少、開銷極低的語言實現。
  • 以能夠乾淨地嵌入進程內、而非被迫置於進程外的方式實現。
  • 以在性能、可擴展性和可靠性方面具備頂尖特性的語言實現。
  • 用一種非常適合互操作的語言實現，從而能夠通過各技術棧的外部函數接口（FFI）機制，被全部六種 Copilot SDK 語言版本（C#、TypeScript、Python、Rust、Go、Java）乾淨地使用。
  • 用一套提供更現代安全態勢的工具鏈實現，供應鏈風險更低，並且對構造即正確（correct-by-construction）代碼有更好的支持。

基於以上所有理由，以及一些較軟性的理由（例如團隊經驗和行業方向），我們選擇了 Rust。這絕不意味着每一個大型 TypeScript 程序都應該改成 Rust。我們的需求強調通過 C ABI 進行嵌入、低啓動開銷和穩態開銷，以及可預測的資源使用。Rust 讓這些目標成為可能，代價是帶來了其他複雜性，例如我們必須顯式地表示生命週期和共享狀態（後文討論的生命週期迴歸問題正凸顯了這一影響）。合適的目標語言確實因應用而異。

隨後開展了兩項關鍵且相關的任務：

  1. 將 TUI 專屬代碼與運行時分離，使前者嚴格分層構建於後者之上，更具體地説，嚴格分層構建於 SDK 的公開接口之上。如今，CLI 仍在若干處直接調用運行時內部實現；將其完全遷移到 SDK 的接口之上仍是進行中的工作。
  2. 將該運行時層 100% 移植到 Rust，最終形成一個純原生二進制文件，對外暴露 C ABI 供所有語言前端在進程內調用，同時提供一個基於 stdin/stdout 或基於 socket 的服務器，以備仍需進程外調用的情況。

本文主要討論第二點：將運行時移植到 Rust。

之前的樣子

2026 年 5 月初的初步移植計劃估計該運行時大約有 130,000 行 TypeScript 代碼。就界定範圍而言，這一初步測量相當準確，但事實證明，它在兩個關鍵方面也極具誤導性。在移植的同時：

  1. 仍封裝在 TUI 層中的部分正被下推到運行時層。最初在估算中被忽略的整個組件以及相當大比例的代碼，隨後又被認為與移植相關。
  2. 提交的 Pull Request 帶來了大量新增 TypeScript 代碼，不斷推高倉庫中 TypeScript 的總量。數十名藉助智能體輔助的開發者每週合併數百個 Pull Request。

把所有因素都算進去，我估計大約有 430,000 行生產環境 TypeScript 代碼最終經過了這次移植。這些同樣的因素也讓人難以看清過程中的進展：直到接近尾聲時，生產環境 TypeScript 的代碼量看起來仍相對穩定，甚至略有增長，因為移植的速度一直勉強跟上新進來的工作。

這一點更加令人困惑，因為在這段時間裏，除了移植工作之外，還有新進來的 Rust 代碼；在移植工作早期，新進來的代碼更可能以 TypeScript 為主，而到了後期，則更可能以 Rust 為主。

在移植過程中，運行時接收了約 300,000 行生產環境的 TypeScript 代碼，同時移除了約 430,000 行；而約 1,200,000 行生產環境的 Rust 代碼進入，約 365,000 行離開。換句話説，上圖中 TypeScript 行數表面上的穩定，實際上掩蓋了大量的 TypeScript 代碼變動。

原地移植策略

該圖表還凸顯了這次移植方式的一個重要方面：原地進行。

對於這種規模的改寫，主要有兩種方法：

  1. 大爆炸式。新的 Rust 運行時作為完整的替代方案進行開發，然後在準備就緒時一次性整體替換。這種大爆炸式切換有兩種變體。a. 全員停工。在改寫進行期間，所有人停止在 main 分支上的其他工作，改寫工作在 main 中完成。b. 並行開發。改寫在一個功能分支中進行，同時主分支上的工作繼續進行，改寫工作不斷嘗試跟上併合並主分支的變更。
  2. 原地進行。這是以逐組件移植的方式完成的，運行時被一塊一塊地增量重寫。這種原地方式也有兩種變體。a. 原子替換。每一塊都從 TypeScript 原子性地切換為 Rust，剩餘的 TypeScript 與新的 Rust 之間的互操作提供了連續性。隨着時間推移，生產運行時中 TypeScript 越來越少，Rust 越來越多，直到有一天，不再有 TypeScript，只有 Rust。b. A/B。與其在組件被移植後就刪除它們，不如將 TypeScript 和 Rust 組件都作為可熱插拔的選項加以維護，一旦信心趨於平穩，就刪除 TypeScript。

出於多種原因，我們選擇了方案 2a：

  • 沒有人會經歷工作中斷。主分支繼續保持活躍。每一位未直接參與移植的開發者都可以照常繼續工作，只有當他們在長時間內一直在推進的某個 pull request 恰好觸及了同時被移植的代碼時才會受到影響，在這種情況下，他們需要 rebase，並讓他們的智能體幫助只移植他們正在推進中的改動。
  • 運行時的主分支始終可發佈。每個 pull request 都用一層調用 Rust 的薄墊片替換現有的 TypeScript 實現，並在一次原子性變更中刪除舊代碼。新代碼會立即在原地被實際運行。
  • 重寫是增量式且可審查的。每個 pull request 只移植單個組件或切片，因此變更範圍更小，diff 也更容易審查，無論是人工、智能體還是兩者兼有。
  • 大多數移植都相當小且自成一體，從而最大限度地減少了與併發 pull request 之間的偏移。在某些情況下，當 TypeScript 組件過於龐大時，可以先將它們重構為更易於移植的組件。
  • 所有現有的端到端測試，涵蓋 CLI 和 SDK，在每一步都針對新的 Rust 代碼運行，這給了我們信心和大量的驗證。如果某個 pull request 導致必需的測試失敗，它就不會被合入。

我們也避開了 2b 方案的一個變體，即同時維護同一組件的多個版本。過去幾個月裏，每週都有數百個 pull request 被合併進倉庫，代碼庫在不斷演進，而且速度很快。讓同一份代碼以兩種不同語言、兩套不同依賴庫的形式存在，會帶來極大的複雜性。而且其中一些組件並非完全隔離；有些在邏輯上是獨立的，其餘系統可以通過簡單的 API 訪問它們，但另一些則有大量牽連，要讓這張圖按組件熱插拔簡直是一場噩夢。最有可能從謹慎的並行切換中獲益的子系統，恰恰是並行最難的那些。例如，會話編排並不是一個純函數，不能靠某個實驗開關用 if/else 去調用兩個不同版本。它持有可變狀態，雙向驅動回調，並貫穿幾乎所有其他子系統，因此“兩個都跑並對比”意味着要維護兩份分叉的副本——一份承載對話狀態與服務的組件副本，還要祈禱它們能在數百次併發編輯中保持同步。讓一個組件難以移植的那種耦合，也正是讓它幾乎不可能在不引入比避免的更多回歸的情況下進行影子運行的那種耦合。能夠以這種方式切換所帶來的好處，主要在於獲得信心，而我們也可以通過其他方式獲得信心。

驗證也通過增量式發佈來完成。如果採用一次性切換的方式，我們會把所有內容放在一個長期分支中，移植整個運行時，然後一次性切換。這意味着使用者會一次性體驗到所有移植的代碼行，包括在倉庫內測試中漏掉的所有迴歸問題。以增量方式分批發布變更——這裏兩個組件、那裏一個組件——使我們能夠在已部署的構建中獲得最後一公里的驗證，並伴隨真實的使用者使用（通常是 Microsoft 和 GitHub 內部的第一方使用者），同時將回歸風險降到最低。在大約十四周半的移植窗口期內，main 發佈了 135 個版本，其中包括 100 個預發佈版本和 35 個穩定版本，平均每天約 1.3 個版本。每天也大約有 1.3 個移植 pull request 被創建，因此每個版本都攜帶一組規模小且可確知的已移植組件（我們通常嘗試先在預發佈版本中發佈移植，但並非總能成功）。在最近七天的 npm 採樣中，預發佈版本僅佔下載量的 10.5%，這表明在監控反饋渠道以發現故障信號並在下一個預發佈版本中迅速修復期間，初始暴露面相對有限。所報告的問題更容易與已知的近期變更相關聯，也更容易定位根因並快速修復。通過這種方式，在較長時間內以增量方式進行移植實際上是一種優勢而非阻礙（也就是説，更快並不總是更好）。到 8 月 21 日，運行時已 100% 為生產 Rust：832,378 行生產 Rust 代碼和 468,689 行 Rust 單元測試，此外還有 174,675 行 E2E TypeScript 測試。獨立的 GitHub Copilot SDK 倉庫又增加了約 130,000 行 E2E 測試代碼，涵蓋 Node.js、Python、Go、C#、Rust 和 Java。

開始上手

在全力投入之前，我們先建立了信心並驗證了可行性。我們首先提交了兩個 pull request，搭建了 Rust 工作區、工具鏈、lint 規則、CI、構建流水線和編碼規範，隨後引入了運行時 crate 以及代碼生成和互操作模式，同時移植了一批純邏輯原語——這些原語是特意挑選的，因為它們沒有 I/O 或共享狀態，並且已有完善的測試。

只有在這些合併之後，第一個主要移植 pull request 才將三個無副作用的輔助函數走完了完整流程。這些起到了試點發布的作用，把關於倉庫佈局、FFI、打包、測試和審查的假設轉化為約定，供後續規模大得多的移植工作複用。

基本上，我們對整套機制進行了端到端測試。計劃繼續按照從葉到根的順序推進工作，以純輔助函數、內容排除、shell 工具和會話文件系統操作來建立翻譯和測試模式。隨後是有狀態子系統，工具、hooks、模型客户端和 MCP 則構建在這些基礎之上。

早期的移植工作，即那些小型葉子組件，推進得很快。但更大的子系統並不是以單個原子步驟完成遷移的；例如，MCP 支持經歷了七個專門的 pull request 才逐步推進，而工具則通過一個由六部分組成的系列逐步推進，之後還需要額外的工作來遷移編排邏輯並淘汰剩餘的 TypeScript。Hooks、auth、telemetry、plugins、settings 和 persistence 也走了類似的路徑。

實際上，有用的移植單元並不總是“一個組件”。它往往是一次穿越相關行為區域的浪潮：先遷移純邏輯，再遷移狀態歸屬，然後遷移編排，接着移除回退邏輯，最後在臨時互操作層消失後簡化 Rust 代碼。

互操作

在這次移植中，涉及互操作的主要有兩個層面：

  1. 臨時內部互操作。每當一個函數被移植到 Rust，該函數都需要能夠被調用初始 TypeScript 函數的任何 TypeScript 代碼所調用。同樣，我們也需要讓 Rust 函數能夠調用 TypeScript 回調。這種互操作需求屬於實現細節，且極其多變。隨着 Rust 內部接口面積的增長，所需的 TypeScript 墊片數量也隨之增長，因為它們與需要從 TypeScript 調用的 Rust 方法一一對應。當那些調用方被移植到 Rust 後，現有的墊片層就會被刪除，並換上新的層。最終，當我們到達運行時庫的公共入口點時，墊片就消失了。
  2. SDK 層面。所有 SDK 庫都需要能夠架設在運行時之上並暴露其功能。在移植前的世界裏，這是通過一個雙向 JSON-RPC 層來暴露運行時實現的：SDK 將函數調用請求作為 JSON-RPC 方法調用負載發送，運行時解析請求並調用相關 API，然後通過同一傳輸通道將結果發回，供 SDK 解析並返回。反方向同樣存在；運行時需要能夠回調 SDK 客户端，例如用於鈎子通知和權限請求，這些在 SDK 客户端中以回調形式呈現，使用各語言中被視為慣用的語言特性（例如 C# 中的委託）。

我們通過 napi-rs 項目的 napi Rust crate 實現了第（1）點，該 crate 的存在就是為了用 Rust 構建 Node 原生插件。你只需給一個函數標註 #[napi]，napi-rs 宏就會生成 N-API 註冊膠水代碼，使該函數可從 JavaScript 調用，並在生成的 index.d.ts 中為其生成 TypeScript 聲明。一個同步的 Rust 函數會變成普通的 JavaScript 函數，一個 async fn 會變成返回 promise 的 JavaScript 函數，而標註了 #[napi(object)] 的結構體會在另一側變成普通對象。

流量還必須雙向流動。許多已移植的組件暫時依賴於尚未移植的東西，因此 Rust 需要回調到 TypeScript，例如 Rust 中的工具實現向仍是 TypeScript 的模型層請求推理，或觸發一個 hook，或為它想要運行的命令請求權限決策。

napi-rs 通過“線程安全函數”來處理這一點，它讓運行在 Tokio 工作線程上的 Rust 代碼能夠回調到 Node 主線程上的 JavaScript 回調。Node 安裝一次回調，Rust 持有它，並在需要反向調用時隨時調用它。

每一個這樣的回調從構造上就是臨時的：回調之所以存在，只是因為另一端的東西仍是 TypeScript，而當那個東西被移植後，它就會被刪除。

這個臨時接縫在 8 月 3 日達到峯值，有 2,019 個內部 N-API 導出和 3,356 個 TypeScript 調用點。完成時，運行時完全由 Rust 構成，因此沒有內部互操作：0 個臨時內部 N-API 導出和 0 個 TypeScript 調用點留存。（我前面提到過，CLI 仍然對運行時有一些內部訪問，我們正在努力移除；那些導出不在此處計數。）

第二層互操作層，即 SDK 表面，是兩者中永久性的那一層。Copilot SDK 面向六種語言發佈：TypeScript、Python、Go、C#、Java 和 Rust。它們全都使用相同的雙向 JSON-RPC 契約，最初它們都以相同的方式接入它：以無頭模式將 Copilot CLI 作為子進程啓動，並通過管道或套接字與之通信。

在移植期間，這仍然是默認方式。這也意味着任何語言的 SDK 使用者都要隨附或定位一個完整的 Node 實現，在每一個事件和每一條消息上都要付出一次進程跳轉的代價，並且要監督兩個進程而不是一個。

將運行時移植到 Rust 正是讓另一個選項變得可行的原因。所發佈的 runtime.node 是一個普通的平台共享庫（.node 擴展是 Node.js 原生插件的約定；其底層是一個 .dll、.so 或 .dylib），而它現在為同一個引擎提供了兩扇前門。一扇是 napi 門，Node 進程將其作為原生插件加載；這是 CLI 的路徑（目前……未來，意圖是它將完全走 SDK 路徑）。另一扇是 C ABI 門，任何語言都可以將其加載到自己的進程中並通過 FFI 調用。同一個進程內運行時通過每種語言的原生互操作機制被選用：

Rust 重寫與進程內、進程外託管方式的選擇是兩個相互獨立的維度。已完成的 Rust 運行時同時支持兩者：它既可以運行在 SDK 使用方的進程內，也可以運行在現有 JSON-RPC 服務器邊界之後。目前這些進程內入口點屬於選擇性啓用，因為我們還在逐步建立與使用方應用共享同一進程、進而共享同一故障邊界的信心。

傳輸層之上的一切仍保持相同的 SDK API：會話、事件、工具、權限和回調並不關心它們的 JSON-RPC 字節是通過管道還是函數調用傳遞的。

第二扇門的有趣之處在於它的規模。它只導出了 19 個函數：4 個用於服務器生命週期，4 個用於會話註冊與配置，8 個用於連接，還有 3 個用於嵌入式宿主。在這些函數背後，共享契約目前包含 364 條分發路由：其中 340 條可由 SDK 使用方調用，另有 24 條以相反方向運行，作為運行時到 SDK 的回調。

napi 這扇門則大得多，需要為每一條分發路由都提供函數。C ABI 這扇門是基於分發的：API 方法根本不會獲得導出，而是以 JSON-RPC 字節的形式寫入連接中傳輸，結果、事件以及服務器到客户端的請求則通過宿主提供的回調返回。

新增、修改或移除一個 API 方法只會觸及引擎的分發表，而絕不會觸及 ABI。SDK 只需一次性綁定這 19 個入口點，就能通過它們動態觸達整個仍在不斷增長的 API 表面。

這就引出了一個顯而易見的問題：在一次不再跨越進程邊界的調用中，為什麼仍然存在 JSON-RPC？

答案是，這讓進程內託管成為即插即用，而非重寫。每個 SDK 都已經有了一個可用的 JSON-RPC 客户端，具備分幀、請求與響應關聯，以及處理服務器到客户端方向的處理程序。將 FFI 作為該客户端底層的又一種傳輸方式掛載上去，就把字節路徑從管道或套接字轉移到了函數調用，而上層的一切保持不變。

六個 SDK 以增量式、可選啓用的傳輸方式獲得了進程內託管，現有的傳輸方式則保持不變。如果我們改為為每個 API 方法定義一個帶類型的 C 函數，那麼每個 SDK 都需要第二層綁定，每個新增的 API 方法都需要再多六個綁定，而 ABI 也會變成一個我們必須對其進行版本管理的二進制兼容性表面。

對於真正處於遠程的運行時——無論是跨越子進程邊界還是通過 TCP——我們仍然需要 JSON-RPC。在進程內保持相同的協議，意味着只需維護一套雙向 API 和分發系統，而不必為遠程連接維護 JSON-RPC、再為本地連接維護一套按方法劃分的 FFI 接口。

這是一個實實在在的權衡，而不是一個顯而易見的決定。我們避免了進程跳轉，但每次調用仍然要付出 JSON-RPC 的開銷。對於以推理為主的工作負載，與模型往返相比，這種序列化開銷通常微不足道。在高吞吐的本地工作負載中它仍然可測量，但如今還不足以證明值得在六個 SDK 綁定中重複實現數百個方法。

而且這是一個我們日後可以輕鬆修改的決定，只要性能需求真的出現。載荷編碼是兩端之間的私有細節，把 JSON 換成 MessagePack 之類更緊湊的格式，不會改變任何一個已聲明的導出。按方法劃分的類型化導出也可以日後為熱路徑添加，調用同一個引擎和同一批處理器，而無需替換字節通道——該通道仍將是流式傳輸、服務端到客户端請求，以及那些極少調用的長尾方法的底層基礎，為這些方法定製導出毫無收益。

一切都關乎緩存

大語言模型服務商通常對輸入 token（你發送給它們的內容）和輸出 token（它們返回給你的內容）分別按不同費率計費。計費之所以常以 token 為單位，是因為 token 能較好地近似完成推理所需的計算量：對於每個輸入 token，模型必須讀取它、將其納入內部表示，並在決定下一個 token 的計算中加以使用。

不過，服務商往往支持緩存這些計算的結果，這樣一來，如果某個提示詞的相同前綴已經被處理過，服務商就可以複用緩存中的中間計算結果，而不必從頭重新計算。這降低了處理這些 token 的成本，而節省下來的費用可以傳遞給用户。因此，輸入 token 通常會公佈多種費率，其中包括從緩存中讀取的輸入 token 的費率。

折扣力度非常大！服務商通常對緩存命中按 90% 的折扣計費，例如某服務商可能對 100 萬輸入 token 收費 $2.00，而對 100 萬緩存輸入讀取 token 僅收費 $0.20。換句話説，你非常非常需要維護好提示詞緩存，這樣你的賬單就能少一個數量級。

這次移植工作的數據表明，我們在這方面做得很好。提示詞緩存命中率為 96.22%：緩存讀取量除以所有輸入側 token 總量（緩存讀取加緩存寫入加全新輸入）。緩存寫入佔 3.07%，全新輸入佔 0.71%。這並非偶然。GitHub Copilot 專門塑造了智能體循環，以維護一個長而穩定的前綴（先是系統提示詞，然後是工具定義，再是累積的對話），因此每一輪都向模型已經處理過的上下文追加內容。

上下文中昂貴的部分只需支付一次，之後每次調用都以低一個數量級的成本重新讀取。這也正是長時間自主會話在經濟上能夠成立的原因。一次三百小時的移植，如果在數萬次調用中的每一次都從頭重新讀取整個不斷增長的上下文，其成本將與我們看到的相差一個數量級。

智能體框架開發者花費大量精力試圖避免破壞提示詞緩存，而模型廠商也經常發佈新功能來幫助他們做到這一點。

上下文壓縮（Compaction）則講述了另一個相輔相成的故事。在所有移植會話中，GitHub Copilot 自動壓縮上下文 5,116 次（即會話填滿上下文窗口後，為了繼續運行而自我總結的時刻）。那個單獨的 sessions-infrastructure 移植 pull request 在其持續多天的生命週期中壓縮了 647 次，而有一個小型移植則從未壓縮過一次。

持續數百小時的自主工作之所以可能，正是因為智能體能夠一遍又一遍地回收其工作記憶而不丟失線索。這數千次總結中的每一次，都是一個有損交接本可能悄然讓移植脱軌的節點，而大多數情況下並沒有。Copilot 的子智能體在最小化壓縮方面也起到了很大作用。

每個子智能體都擁有自己的上下文，因此父會話可以有效地提出問題，讓子智能體去計算答案並在此過程中消耗相當多的上下文，然後只把答案報告回父會話。父會話的上下文無需被所有這些中間信息所影響。

上面所説的“大多數情況下並沒有”，在會話日誌中清晰可見。我讓 Copilot 將每一次成功的壓縮與其前後至少各有 20 次工具調用的工作配對。這產生了約 4,000 個可比較的窗口。智能體在壓縮前 20 次工具調用中所做的事情，與壓縮後所做的事情在規模上看起來相似（探索：壓縮前 46.5%，壓縮後 48.1%；修改：壓縮前 8.4%，壓縮後 6.0%；驗證：壓縮前 4.7%，壓縮後 4.0%；失敗：壓縮前 1.0%，壓縮後 1.5%）。

如果壓縮經常丟失思維線索，我們會預期壓縮後一側明顯偏向重新定位，出現閲讀量激增而編輯量驟降，因為智能體在重新發現自己在哪、應該做什麼。然而，實際上只出現了朝那個方向的輕微偏移。

是的，靜態分析有幫助

有一個流行的説法認為，Rust 是 AI 生成代碼格外理想的目標，因為 Rust 嚴格的編譯器能捕捉到模型出錯的地方。這些會話日誌讓我們得以檢驗這一理論，至少對於類似這次移植工作的任務而言。

直接驗證命令的結果捕獲了 8,678 次 rustc 錯誤代碼的出現。四個最大的診斷類別覆蓋了 84%：

  • 37%：名稱與導入解析，其中以 E0425 為主（“cannot find value in this scope”）
  • 22%：缺失的方法或字段
  • 14%：類型不匹配
  • 11%：未滿足的 trait 約束

這些全都是普通的接線問題：某個名稱輸出略有偏差、某個簽名對不上、某個字段被重命名了、某個抽象尚未實現。這類錯誤正是批量翻譯容易且不經意間產生的，也正是編譯器能極快捕捉到的。

但請注意這份清單裏缺少的東西：任何真正屬於 Rust 特有的內容。這四個類別中的每一個都是最基礎的靜態類型檢查，C#、Java 或 Go 編譯器同樣能全部捕獲，其中好幾項還能給出更友好的診斷信息，而且速度都要快得多。如果這就是把智能體引向 Rust 的理由，那它實際上是把智能體引向任何靜態類型語言的理由。一個強類型編譯器和/或具備出色靜態分析與 lint 能力的語言，確實非常適合這類工作，智能體可以把它當作快速反饋迴路。在 4,478 次直接 cargo check 運行中（更嚴格的結果匹配器捕獲到了結果），87.1% 返回乾淨結果，這正是以小增量編輯並不斷重新編譯所得到的效果。

相比之下，所有權、借用和生命週期錯誤加起來僅佔已編碼診斷的 1.7%。借用檢查器——這個在每一場關於 Rust 難學的討論中佔據主導地位的東西——只是一個安靜的後台存在。編譯器幾乎把所有報錯精力都花在了無聊的機械性錯誤上。

模型選擇

GitHub Copilot 允許單個會話在對話中途切換模型，也允許不同會話運行不同的模型，因此模型選擇變成了按切片（per-slice）做出的決策。日誌中出現了兩種不同類型的模型決策。在主線程上，也就是驅動每個端口的那條線程，由我們來選擇模型和推理強度。而在會話內部，當智能體啓動子智能體或子會話去探索或攻克一項有邊界的任務時，則由負責編排的模型來選擇這些模型。

對於子智能體而言，模型組合看起來略有不同，因為是由智能體而非人類來優化吞吐量和成本，而不是做出最困難的判斷。它最常生成的子智能體運行在 Claude Opus 4.8、GPT-5.6 Sol、Claude Haiku 4.5 和 GPT-5.5 上，其次是 Gemini 3.1 Pro 和 Claude Opus 5。然而，至少在移植進行的那段時間，有三個頻繁使用的智能體定義固定了它們的模型選擇（explore 和 task 使用 Claude Haiku，research 使用 Claude Sonnet），因此這一用量中有相當一部分是由子智能體的選擇決定的，而不是單獨選擇模型的結果。

與智能體集群協作

GitHub Copilot 應用支持可視化活躍的拉取請求會話、查看每個會話的狀態，並在它們之間輕鬆切換，這使其非常適合管理移植工作所固有的大量併發任務。但真正讓它出彩的一點，是它能夠讓會話與其他會話進行交互。

一個會話可以創建其他會話，並且可以在其他會話運行時向它們發送消息。每個會話，無論是父會話還是子會話，都擁有自己的工作樹、自己的分支和自己的智能體循環；它獨立於創建它的會話，而不是在其中運行的東西。這與子智能體不同，子智能體在父級自己的工作區內運行，並將其答案交回父級的上下文中。兩者都是對不同用途有用的構造。

舉一個會話可能創建其他會話的例子，最困難的移植之一針對的是 session.ts 文件。這個文件有機地增長到了約 30,000 行 TypeScript。它代表了會話的骨幹，實際上橫向貫穿整個運行時，幾乎與每一個組件相互觸碰、相互影響，處於狀態、事件、工具、模型、鈎子和入口點訪問的中心。因此，我把它留到了移植過程的接近尾聲，從技術棧底部向上、跨越所有垂直方向推進，直到它們全部在 session.ts 處走到盡頭。接手它的移植會話並沒有一上來就直接動手寫 Rust。它最初的五十六分鐘都在閲讀，在創建任何東西之前進行了 122 次工具調用，構建出這個文件實際擁有什麼、接縫在哪裏的圖景。直到那時它才開始委派，把這個文件按邏輯拆分，並將切片委派給子會話。在整個 25 小時的運行中，它自己進行了 222 次 shell 調用、205 次文件查看和 197 次 ripgrep 搜索，這還不算它的子會話所做的一切。

那就是 15 個子會話，每一個都是獨立的分支，擁有自己的工作樹和獨立的智能體，全部由頂層的父會話隱式創建。父會話在大約三個小時內分七波創建了它們：第一波創建了五個，第二波在大約二十分鐘後創建了另外兩個，然後又在二十分鐘後創建了另外兩個，接着在接下來的兩個小時裏零散地創建單個和成對的會話。

模型選擇是按切片逐一決定的：15 箇中有 10 個運行在 GPT-5.6 Sol 上，5 個運行在 Claude Opus 4.8 上。全部 15 個都在 GitHub Copilot 的 autopilot 模式下啓動，該模式允許會話朝着某個目標持續推進，而不必在每一步都停下來等待批准。

啓動提示詞的中位數長度約為 1,100 個字符，足以承載歸屬邊界和各項約束，但又短到讓子會話必須自行摸索出實現路徑。我向父智能體發出提示，隨後是父智能體——而非人類——為每個子會話撰寫那些啓動提示詞。

除了這 15 個子會話之外，同一個父會話還動用了五個子智能體：三個 explore 智能體與第一波並行觸發，一個 code-review，以及一個 rubber-duck。這些子智能體負責探究問題，並把父智能體在決定下一步該做什麼之前、其上下文中所需的答案反饋回去。子智能體讓父智能體無需耗費自己的上下文窗口去推導，就能獲得經過深入思考的答案。

相比之下，子會話則着手進行實際的移植工作——這些工作會產生 diff，並且需要與其他並行移植者隔離。子會話的工作涉及倉庫中 140 個不同的文件，其中 120 個文件恰好只被一個會話觸及。那 20 個存在爭用的文件都是樞紐文件，比如 session.ts 本身。但每個會話都在自己的工作樹中工作，因此能夠不受兄弟會話幹擾地推進。當然，父會話為此在協調上付出了代價。它花費了大量精力與子會話溝通，充當信息中介，輪詢它們的狀態 60 次，併發送了 89 條協調消息。當子會話各自宣佈完成時，父會話將它們的提交 cherry-pick 到自己的分支中並解決衝突。這些合併也並非特別乾淨，父智能體花了相當多的時間來調和這些編輯。

我們可以在時間線上看到這一點，其中展示了父會話及其大多數子會話。

注意那些大的空檔。我在進行這次移植工作的同時還在旅行，不得不在多個時間點合上筆記本電腦。（我隨後改變了工作流程，加入了可以遠程接入的雲端虛擬機。）

這些並行的子會話對那台筆記本電腦造成了顯著影響。有一段時間，併發移植進行得非常順利。隨後，同一台機器上的全部 15 個併發智能體各自嘗試構建和測試，我那可憐的筆記本電腦直接卡死了。我向父會話發出提示，讓它轉告其子會話，必須全部停止構建和測試。父會話把這一約束向外傳達，它們所幸終止了構建，隨後以最低的 CPU 活動繼續工作。我隨後更新了自己的常駐指令，要求子智能體和子會話在移植期間避免大型構建和測試運行，改為只由父智能體來執行這些操作。

後來我又更進一步，把一個原本普通的聊天會話變成了八個獨立移植會話的構建調度器。提示詞簡單得令人尷尬：向每個打開的會話發送一條策略，要求儘可能避免 CPU 密集型的構建和測試，規定在必須構建時需向本會話請求許可，並充當閘門，一次只向一個會話發放構建權限。

基本上，我把這個聊天會話變成了一個智能體互斥鎖。這個閘門維護着明確的持有者和隊列，並通過各會話原本就用於協調代碼的同一套跨會話消息機制，一次只授予一個租約。那些請求租約但被拒絕的會話，往往會在此期間做其他工作來等待，比如從自己的待辦清單裏挑事情做。

這個 session.ts 端口還牽涉到我在整個運行時移植過程中所目睹的最酷、最令人唏噓、也無疑最出人意料的一次交互。正如我提到的，我們主要採用自底向上的方式來做移植，這也是為什麼 session.ts——它實際上位於所有其他組件之上——是最後移植的組件之一。始終位於 session.ts 之上的，只有運行時的所有入口點，也就是從 SDK 暴露出來、並出現在前面討論過的分發表中的那些公共函數。這樣的函數有數百個。雖然我知道其中許多會立即調用到 session.ts，但我想搶先推進移植工作，於是在啓動 session.ts 會話之後，我又啓動了一個會話來移植所有入口點。我告訴它在 session.ts 邊界處停下。我估摸着可能會有一些白費的工作，在 rebase 時也需要投入一些精力或消耗一些 token，但這樣會加速整體移植。然後我就去睡覺了。再然後……它們找到了彼此。

我給入口點會話寫的啓動提示詞確實告訴了它，會話移植和六個組件移植正在併發運行，因為我想讓它知道自己的邊界，以及應當避免移植哪些內容，從而儘可能減少衝突。顯然，我的提示詞起了反效果。剛過四分鐘，在盤點完入口路徑、並大概對它們的重疊程度形成了判斷之後，它調用了一個應用內置的 orchestrate 技能，該技能的作用是協調跨會話的工作。從那裏開始：

  1. 入口點會話枚舉了每一個活躍會話，並向那些它認為存在重疊的會話發送了消息。
  2. session.ts 會話用一個 2,001 字符的清單作了回答，標題為“關於 stephentoub-port-session-to-rust 的具體重疊”
  3. entrypoints 會話讀取了 session.ts 會話的工作樹，以確認它剛剛被告知的內容（我猜是“信任但要驗證”）。
  4. entrypoints 會話詢問 session.ts 會話是否準備好協調其 760 個文件的 diff。
  5. session.ts 會話基本上讓它別來煩自己：“還沒準備好提交/集成。”
  6. entrypoints 會話接着又問了同樣的問題三次，每次它都從 session.ts 會話那裏得到同樣的回答。
  7. 就在這時，entrypoints 會話決定不再在意 session.ts 會話怎麼想，直接伸手進入它的工作樹，抓取了另一個會話的所有更改，併合併到了自己的裏面。
  8. 然後兩個會話就各自愉快地繼續下去了。

我從這次交互中有幾點收穫：

  1. 明確表達意圖很重要。啓動提示詞列出了其他正在運行的會話，這樣這個會話就會知道哪些不要碰。但我沒有把“不要碰”這部分説清楚，所以我沒有阻止智能體去做某件事，反而鼓勵了它去做。我需要在意圖和指導上表達得更加明確。
  2. 你提供的任何東西，都可能被智能體判定為適用。這個orchestrate技能隨 GitHub Copilot 應用一起提供，它自我描述為用於並行運行獨立的工作流。我的提示詞中完全沒有提到它。模型自己發現了自身所處的情況，將其與該描述進行匹配，然後加載了它。你所暴露的能力集合，就是你可能得到的行為集合，包括在你從未設想過的情境中。
  3. 對等方需要一個裁決者。兩個會話都無法強制對方。當session.ts會話四次表示尚未準備好集成時，這一拒絕沒有任何分量，因此願意單方面行動的會話默認獲勝。針對相鄰代碼的並行會話需要一個指定的協調者，或者需要一個人，而這兩個會話兩者皆無。
  4. “自主運行”需要對超出你自己分支範圍的決策設置例外。我真正的意思是“不要因為設計細節來叫醒我”。它（並非不合理地）理解為吞併一個對等方也在範圍內。再説一次，我本應在我的指導中説得更明確。
  5. 這裏的根本原因是我自己。我同時以自頂向下和自底向上的方式劃分這項工作，而這兩個方向在中間相遇於代碼庫中連接最密集的那個文件。我太貪心，想要向前推進。上述一切都由此而來。

謝天謝地，這整個交互是一個有趣的異類。在整個運行時移植工作中，大多數葉子組件的移植都是簡單的單會話任務。較大的子系統往往涉及多個子會話和子智能體。不過，這些部分在移植過程中如何參與，差異很大。

模型編排層的移植——即真正與提供商通信的那一層——很好地展示了其中一種模式。它的主會話運行了 42 個掛鐘小時，啓動了 126 個子智能體。最繁忙時，有 22 個同時在工作。然而，大多數時間裏，只有主智能體在運行，然後時不時地會在某個時間窗口內生成大量子智能體。

那張圖中有三點很突出。第一，幾乎所有代碼生成都在前 12 小時內完成；之後一天的工作全是驗證。第二，底行的顏色從左到右變化，從以藍色和綠色為主（閲讀、構建）轉變為以藍色和橙色為主（閲讀、審查）；這在邏輯上説得通，但能在實踐中看到它還是很不錯的。第三，那個例子——以及更普遍地這種模式——各階段之間有非常清晰的分離。擴展運行時的移植則是一個反例。

它花了 88 小時而不是 42 小時，並且結構非常不同：

  • 寫作和審查顯著重疊。在前一個例子中，工作是高度瀑布式的（先代碼生成，再審查），而在這裏，審查在寫作停止之前很久就開始了，兩者在大部分工作時間內並行推進並重疊。
  • 最下面一行的顏色分佈則雜亂無章。 在模型編排中，顏色從綠色變為橙色，對應着從編寫到檢查的過渡；而這一行從頭到尾都是閲讀、構建和審查的混合。在 88 小時的會話中，閲讀調用中間的一半分佈在 49 小時的時間跨度內，編寫分佈在 33 小時內，審查分佈在 27 小時內。每個類別都散佈在整個運行過程的大部分時間裏。
  • 空閒被推遲到了最後。 整個集群在前 56 小時內幾乎不間斷地工作。
  • 比例仍然吻合。 這裏編寫 Rust 佔工具調用的 2%，那邊佔 1%；閲讀佔 44%，那邊佔 57%；審查佔 23%，那邊佔 27%。兩個會話對待完成的工作內容看法一致，只是發生的時間不同。

末尾那些空白的切片也直觀地反映了一個在這個智能體編程時代越來越普遍的問題：等待審批。團隊中的某個人和/或某個智能體審查代碼並留下反饋，然後有一段短暫的活動期，智能體處理反饋並讓 CI 重新變綠，接着又是更多的等待，如此反覆，直到最終我們得到那個令人多巴胺飆升的批准印章。

這兩個例子各自代表了一種主導模式。大約四分之一的會話看起來更像模型編排那個會話，而四分之三看起來像擴展運行時那個。乾淨利落的階段推進反而是例外；常見的情況是智能體自始至終都在規劃、編寫和審查。

大規模代碼審查

前面圖表中體現出的對審查的高度關注，很大程度上源於我明確的提示。我創建了一個簡單的“提示詞即技能”，我稱之為 rust-rebase-review（此外還有我們已經合併到倉庫中的通用 Rust 編碼技能）。由於變更湧入速度很快，其中許多還相互衝突，我需要頻繁地 rebase。通過自定義指令，我鼓勵 harness 在流程中的適當時機調用這個技能，同時我也會不時手動調用它。這個提示詞隨着時間推移有所演變，但大致是以下這個版本的變體：

Squash into a single commit, then rebase on the latest in origin/main, resolving all conflicts, and force push. As part of rebasing, pay extra special attention to anything that has changed, been added, been removed, and ensure that logic is all ported over to the corresponding Rust code correctly. Always do the rebasing yourself / in the main agent; do not spawn a subagent for it.

Then enter a review/fix loop where you launch a subagent per opus 5, gpt-5.6-sol, and grok 4.6.

- That subagent should do a line-by-line comparison of the old TypeScript and the new Rust, confirming behavioral equality.
- Look for anything introducing any kind of incompatibility; our goal is to move this code into Rust with as close as is possible to 100% the same semantics. If you hit anything questionable, ask me about it.
- We want to ensure we're writing as efficient and idiomatic Rust code as we can; look for opportunities to simplify, to use routines like from the memchr crate to optimize searches instead of open-coded loops, avoid unnecessary allocation, use traits for reuse and loose coupling, etc.
- Ensure that all defunct TypeScript code (e.g. code that has been fully ported, tests that are now no longer necessary because they're duplicative, unnecessary napi shims, etc.) has been deleted.
- Ensure that we've ported as much code as possible, e.g. if there's any TypeScript remaining in touched files and that TypeScript is more than just a shim, that's a red flag. If new TypeScript that's not just a super thin shim is being added, that's a red flag. Look for any callers of TypeScript shims to see whether those callers can instead be ported to Rust, pushing the boundary as far as reasonably possible. Our goal is to soon get to 100% Rust in the runtime layer.
- Validate that no E2E tests have been deleted or changed. Such changes are an indication of a porting bug.

If a review surfaces issues, validate them, and then if there are any to fix, fix them, and iterate to do another full review. Continue iterating with reviewing/fixing until all reviews come back clean. After every set of changes in response to review feedback, commit and push so that CI validation runs concurrently with subsequent reviews.

Don't bother running full test suites; that'll be handled in CI. Try to minimize CPU-consuming efforts to the bare minimum, as we'll likely have many operations happening concurrently.

在頻繁 rebase 的情況下，湧入的變更很容易被意外丟失。但我們發現原地原子替換帶來了一個意想不到的好處：在添加對應 Rust 代碼的同時刪除 TypeScript 代碼，我們實際上隱式地製造了與 rebase 引入的、針對該 TypeScript 的變更之間的衝突：一個分支修改它，另一個分支刪除它。這保證了我們會注意到對已移植代碼的變更，而不需要為每一行湧入的代碼去判斷它是否可能觸及了此前已移植的代碼。

我自己的審查當然只是所執行的智能體審查中的一部分。除了每次提交都會運行的 CCR 之外，團隊還有多個專門的代碼審查機器人，每個都有自己的方法和提示詞，在每次提交時運行並提供詳細反饋。所有這些最終都會變成 pull request 上的評論，然後需要逐一處理。幸運的是，處理所有這些智能體反饋也可以（大部分）由智能體來完成。

在本次評審中，我聚焦於架構、設計、約定和方法。智能體負責做詳盡的新舊對比；測試和靜態分析檢查可機械驗證的屬性；人類評審者則專注於架構、API 契約、風險，以及其他各層所暴露出的任何可疑之處。

我選定了目標架構，決定了哪些行為至關重要，劃分了工作，解決了模糊的權衡取捨，評判了證據，人工審查了高風險區域，審查了智能體對反饋的回應，並做出了最終的合併決策。智能體改變了一名工程師所能監督的代碼量。它們並沒有消除對這樣一名工程師的需求：他理解整個系統，並能為方向、護欄和發佈背書。

自動化內循環

GitHub Copilot 應用是這項工作的核心。它管理着大量併發的活躍會話，使得在它們之間切換變得很容易，並且每個會話都攜帶着所有相關的配對上下文（關聯的終端窗口、瀏覽器窗口、畫布等等）。這裏最重要的功能是智能體合併：

Agent merge 是內置於該應用中的一個循環（CLI 也通過 /pr auto 提供了這一功能）。它會按定時器觸發，或響應外部刺激（比如來自 GitHub 的 CI 完成通知或審查評論），屆時應用會查看發生了什麼變化。如果留下了審查評論，它會調用智能體來決定是拒絕該評論，還是接受並處理它（同時回覆，並註明是自動化在響應）。如果測試失敗，它會下載日誌、調查失敗原因並修復 bug。如果出現衝突，它會調用智能體進行合併或 rebase。實際上，它把我們作為人類開發者都會做的這個循環自動化了：推動我們的 pull request 走向“全綠”、獲得批准，並最終合併。

Agent merge 處理了每一個移植 pull request。不過在大多數情況下，我們並沒有走到真正的“合併”那一步。智能體會修復所有 CI 失敗、處理並回復所有評論，並確保所有衝突都得到解決。在合併之前，我會抽查智能體實際做了什麼，尤其是它如何處理反饋。我是否不同意它對審查者的某些回覆？所應用修復的總體方向是否可取且合理？對於這些移植，我通常會保留最後那一項不勾選。

最後一個複選框不止一次發揮了作用。在一次合併循環中，移植過程刪除了一個暴露給 SDK 的函數。我們倉庫的 schema 兼容性 CI 環節恰好履行了職責並失敗了。智能體的回應是給倉庫打上 schema-break-ok 自動化標籤，這是讓檢查通過的逃生通道。在合併前審查這個 pull request 時，我問了那個顯而易見的問題：“schema 破壞是什麼？你給這個 pull request 加了 schema-break-ok 標籤；為什麼這樣沒問題？”它並不沒問題。這個方法存在於 main 上；移植過程只是把它弄丟了。我稱這是不可接受的迴歸，並告訴智能體用 Rust 把它完整恢復回來。二十一秒後，豁免被移除，該方法以原生 Rust 實現被恢復。

我們既在局部也在全局層面回應失敗，修復個別案例，但隨後也修復系統，使它們更不容易再次發生。我們不斷演進提供給編碼和審查智能體的指令，以進一步降低這些問題在未來移植 pull request 中再次發生的可能性。我們把會話日誌轉化為評估。在某些情況下，我們實際上利用學到的經驗來改進運行時本身，通過調整提示詞、工具描述或 autopilot 的運作方式。

一次遷移，兩件事

語言重寫幾乎從來不只是語言重寫。運行時依賴的每一個庫也都必須被替換，而且與我們在 Rust 代碼中編寫並擁有的部分不同，這些替換並非由我們來做忠實還原。有些是同一理念換了個名字。有些需要好幾個 crate 才能覆蓋一個 npm 包曾經完成的工作。還有少數根本沒有可接受的現成答案，只能手工編寫（由智能體完成）。

CLI 和運行時目前位於同一個倉庫中，共享一個 package.json。在移植過程中，我們移除了約 60 個 npm 依賴，因為它們只被已移植到 Rust 的運行時代碼所使用。這只是一個移除數量的下限，因為有些包雖然被替換用於運行時，但 CLI 仍然需要它們。例如，zod 是一個 TypeScript 模式聲明與驗證庫，CLI 和運行時都在使用它。隨着 Rust 移植的推進，運行時現在使用 serde、schemars 和 jsonschema 的組合來滿足相同的用途，但 zod 仍然因為 CLI 的緣故留在清單中。

有很多例子是一個 npm 包變成了一個做同樣工作的 crate。js-tiktoken 變成了 tiktoken-rs，具有相同的 o200k_base 編碼。ignore 變成了同名 crate，具有相同的 gitignore 語義。minimatch 變成了 globset，fast-myers-diff 變成了 similar，dompurify 變成了 ammonia，而 github/keytar 變成了 keyring。

在其他情況下，我們無法將包與 crate 一一對應地替換。相反，一個包變成了多個 crate，或者多個包合併為更少的 crate。依賴工作的大部分都花在了這裏。八個 opentelemetry/* 包變成了四個 crate，外加一個手寫的跟蹤器狀態機和文件導出器。三個 Web 內容包——mozilla/readability、linkedom 和 turndown——變成了兩個 crate：readability 和 htmd。sharp、image-size、file-type 變成了 image 和 imagesize。以此類推。還有五個案例，我們完全用自定義實現替換了 npm 包。

有多少 unsafe？

人們關於智能體編寫的 Rust 代碼提出的另一個問題是，其中有多少悄悄放棄了安全保證。Rust 的安全性是一種可以用關鍵字關閉的屬性，因此當智能體遇到無法滿足的借用檢查時，就有一個顯而易見的逃生通道。在整個 runtime crate 中，我們現在有 158 個 unsafe 塊，僅分佈在 36 個文件中（與之相伴的還有 26 個 unsafe fn 聲明、26 個 unsafe extern 塊，以及 9 個 unsafe impl trait 實現）。重要的是，其中每一個都與外部組件的互操作有關。

C ABI 代碼塊是 SDK 宿主進入的前門，因此它們會從調用方接收原始指針和長度，而 Rust 編譯器對這些調用方沒有任何控制權。Windows 和 POSIX 代碼塊是系統調用：註冊表讀取、憑據握手、進程樹、sysconf。SQLite 是一個 C 庫。動態庫加載是 dlopen，從構造上就不可能安全，哪怕僅僅因為解析出的符號可能並非你期望的函數。進程環境 unsafe 代碼塊之所以存在，是因為 Rust 2024 將多線程進程中對進程全局環境狀態的修改視為不安全操作。這些 unsafe 代碼塊中的每一個都標記了 Rust 所提供保證真正終止的地方：另一側是 C 函數、系統調用、來自外部運行時的指針，或進程全局的宿主狀態。

有用的特性在於，unsafe 讓我們所擁有的 Rust 代碼中所有這些位置都可審計。TypeScript 運行時中的等價代碼恰好跨越了相同的邊界，穿過 Node 的 C++ 內部實現和原生 npm 包，而我們的源碼中沒有任何東西標記出受檢查的世界在哪裏終止。當然，這並不是交付系統中每一個安全邊界的完整清單：依賴項、構建工具、C 庫、安全封裝以及規格錯誤的 FFI 契約仍然可能包含或暴露不安全代碼。

unsafe 在哪些地方被使用的細節很有意思，但我更感興趣的是它沒有在哪些地方被使用。它沒有被用在模型客户端中、MCP 層中、智能體層中或提示詞層中。而且移植工作中已知的迴歸問題，沒有一個涉及 unsafe 塊。

迴歸問題

移植代碼很容易。讓它正確卻很難。而對於像 Copilot 智能體運行時這樣龐大且複雜的代碼庫，迴歸問題是意料之中的。

到 2026 年 9 月 14 日，我們已經追蹤了數十個已知的移植迴歸問題，全部已修復。大多數是正確性 bug，還有一小部分是性能迴歸。這些是在從零編寫的約 832,000 行生產 Rust 代碼的基礎上出現的。

當然，並非所有這些迴歸問題都發布了。有些在倉庫中開發時就被發現了。另一些出現在預發佈版本中，但在進入穩定版本之前就被修復了。還有一些進入了穩定版本，通常是因為它們足夠不起眼，以至於在一輪或多輪預發佈使用中都未被發現。

當然，這並非為零，而且我百分之百確信，實際數量比我們所知道的還要多。這些是我們注意到的或被報告出來的，但如此規模的遷移絕對還帶出了另外一些，它們足夠安靜，以至於至今還沒有人踩到。就像一般的 bug 一樣，我預計隨着技術棧更偏遠的角落被在真實環境中猛烈地反覆使用，我們會繼續發現零星的邊角案例迴歸問題。

絕對數量其實也沒那麼重要。更重要的是所有這些問題的“原因”，這樣我們才能從中吸取教訓，避免將來重蹈覆轍。幾乎所有的正確性迴歸都落在三大類中：新代碼實現了不同的行為契約；狀態、所有權或生命週期行為發生了變化；或者遷移的某一部分被遺漏、只部分應用，或在 rebase 中丟失了。還有一小部分來自宿主或互操作邊界處的要求，甚至來自那些自信地驗證了錯誤行為的測試。這些類別在若干反覆出現的模式中變得更加具體：

語義模糊。若干迴歸問題源於源語言未明確表達的行為。TypeScript 只有一種 number 類型；Rust 則要求在多種類型中做出選擇，包括某個值是否可以為小數。而智能體猜錯了。概念上屬於整數的字段變成了 f64，於是 Rust 將諸如 42.0 這樣的值序列化，而不是 42：像 Go 和 C# 這類強類型 SDK 無法將倉庫 ID 反序列化為 int64，並拒絕了 hook 時間戳和任務時長。反方向上，某個智能體將 timeToFirstTokenMs 聲明為 i64，但流式路徑卻輸出了諸如 5446.712845 這樣的值，導致已寫入的會話無法讀取、無法恢復。還有一個更隱蔽的案例與類型無關：event.error || "Unknown error" 變成了 .unwrap_or("Unknown error")。JavaScript 的 || 會替換空字符串；Rust 的 unwrap_or 則保留它，因此一個空的子智能體錯誤仍然保持為空。哎。

環境行為。另一個反覆出現的來源是 JavaScript 或 Node 在不可見的情況下提供的行為。配額代碼使用了 toLocaleDateString，它會繼承宿主時區；而 Rust 需要顯式傳入該時區。但儘管 Intl.DateTimeFormat().resolvedOptions().timeZone 的類型標註為 string，它卻可能返回 undefined，而 napi 無法將其轉換為 Rust 的 String，從而導致模型列表加載失敗。在另一處，將環境變量的讀取從某個 await 之前移到之後，意味着等待期間宿主的變化可能會改變結果。一個原生插件加載器調用 process.report.getReport() 僅僅是為了識別平台，但在 Windows 上這會遵循 _NT_SYMBOL_PATH，並可能在渲染 CLI 之前花費數分鐘下載 PDB。其他環境輸入還包括工作目錄、倉庫身份、PATH 以及會話認證。將所有權移入 Rust 需要決定何時捕獲每一項、如何攜帶它，以及何時刷新它。

只移植了一對中的一半。若干迴歸問題源於成對操作失去同步。一次輪次上限檢查更新了原生註冊表的終止狀態，但沒有取消進程內的模型循環，導致又有一個請求逃逸出去。在另一處，任務完成被持久化併發出，但沒有投射到活動會話狀態中，因此 Autopilot 在完成任務後仍繼續運行。

阻塞主線程。 CLI 仍然從 Node 的單線程事件循環驅動 Rust 運行時，因此跨 napi 邊界的同步工作會凍結 UI。/chronicle reindex 以這種方式解析了數百個會話文件，導致渲染和輸入被阻塞近一分鐘。將導出改為 async 並把工作移到阻塞線程池線程後解決了問題。一次審計又發現了幾個可能阻塞的入口點，由此形成了一條長期規則：真正幹活的 napi 導出必須是異步的，並在必要時使用 spawn_blocking。

窗口閃爍。 在 Windows 上，生成子進程時如果不帶 CREATE_NO_WINDOW，會短暫彈出一個控制枱窗口。Node.js 運行時此前通過猴子補丁修改了進程生成邏輯以添加該標誌，從而對移植智能體隱藏了這一要求；Rust 替代實現遺漏了它。一次審計又修復了兩處額外的進程生成點，不過這些是原本就存在的遺漏，而非移植引入的迴歸，我們隨後將該規則加入了 copilot 指令。

生命週期管理。 最大的一類問題涉及生命週期、釋放、所有權、順序或競態。將狀態移入 Rust 後，TypeScript 往往持有一個指向存儲於原生表中實例的不透明句柄。與對象引用不同，該句柄的生命週期可能長於實例本身。一個 hook 在請求中途被釋放，導致一個 tool_use 塊成為孤兒，卡住了對話，因為模型 API 要求有匹配的結果。一個 shell 在“已宣告”和“已啓動”之間被取消，泄漏了一個孤兒進程，使會話保持活躍。一個沙箱開關更新了一個代數計數器，卻沒有更新其原生對應物，導致 shell 卡在“重新配置中”。

被忽視的功能。另一組問題涉及移植過程中直接遺漏的功能。有一處移植省略了 SDK 回調，並刪除了對應的端到端測試，這促使團隊制定了一條新規則：智能體未經明確同意不得修改 E2E 測試。一次會話中止保留了原生那一半，卻丟失了用於中斷等待工具返回的輪次所需的進程內取消能力。SDK 替換內置工具搜索的能力取決於啓用開關、面向模型的描述和 schema，以及將執行路由到 SDK 回調。這次移植把這三樣全丟了（一致性萬歲？），悄無聲息地把某個使用方的自然語言搜索替換成了正則表達式搜索。

不同庫，不同主張。還有幾處迴歸源於用更嚴格的 Rust 等價實現替換 JavaScript 庫或 API。當時，Rust MCP SDK（rmcp）會對格式錯誤的 JSON-RPC 輸入做出響應，而 TypeScript SDK 則不會。面對一個用更多格式錯誤輸出回應錯誤的服務器，這種禮貌變成了無限循環，導致啓動卡死。不同生態系統中相關的庫很少表現完全一致。

擦肩而過。少數迴歸源於分支漂移或 rebase。在一個每週有數百個 pull request 的倉庫裏，一個開了好幾天的會話會不斷累積變更和衝突。這次移植需要數千次 rebase；即便成功率非常高，也仍會有失敗。

還有那些慢吞吞的傢伙。最後一組在功能上是正確的，但速度更慢。有些迴歸丟失了已有的效率優化，比如記憶化、完全異步等待，或有界日誌流式傳輸。另一些則在 Rust-TypeScript 邊界引入了遷移特有的開銷：冗餘序列化、加鎖、輪詢、無界原生併發，以及原生到宿主側的跨界調用。這些並不是後續可以優化的機會點；每一項都是移植過程中引入的性能退化。有一次只讀掃描把 260 MB 的事件日誌做了深拷貝，而不是借用它。在持續的事件流量下，另一個實現只完成了所請求通道刷新的一小部分，同時為每個事件保留一個異步句柄，直到 V8 耗盡堆內存。

幾十個迴歸聽起來很多。但在一項生成了超過 800,000 行代碼的移植中，坦白説，我驚訝且欣慰的是我們沒有遇到多一個數量級的迴歸。我們還可以通過觀察公開的 github/copilot-cli 和 github/copilot-sdk 倉庫中 issue 的趨勢，來瞭解這些問題是否被廣泛“感知”到。在這裏，我們將 1 月到 8 月期間開啓的 issue 分類為質量相關，條件是它們帶有 bug 標籤，或者標題中使用了常見的故障術語，如“bug”“regression”“crash”“hang”“timeout”“broken”或“incorrect”。與移植工作進行期間及之後相比，這些水平與移植工作之前基本沒有變化：

只要能編譯，就能編譯

前面我提到了一個流行的梗：Rust 因其嚴格的編譯器而非常適合 AI 生成的代碼。還有一個相關的流行 Rust 梗：如果代碼能編譯，它就是正確的。並非如此。我們已知的迴歸問題清單對此給出了很好的回應：語料庫中的每一個迴歸問題都被合併到了 main，這意味着它們都成功編譯了。編譯器接受了這些有 bug 的版本，因為對編譯器而言，它們每一個都是合法的 Rust。

編譯器可以證明某個 f64 被一致地使用。但它無法知道倉庫 ID 必須序列化為整數，也無法知道一個以尾部 .0 序列化的時間戳會被線路另一端的每一個強類型 SDK 拒絕。編譯器可以防止它所能看到的代碼中出現未同步的數據競爭，但它無法阻止一個完全同步的狀態機編碼出錯誤的狀態。一個隊列可以被鎖保護，卻仍然讓兩個發送方各自認定對方會將其排空。事件可以在線程之間安全傳遞，卻仍然以錯誤的順序到達。一個同步的 napi 函數可以是內存安全的，卻仍然阻塞 Node 的主線程長達一分鐘。編譯從定義上講也幾乎無法檢測到那些不存在的東西。當一次 rebase 悄悄移除了一個防護及其測試，或者當一個進程啓動器忘記了抑制控制枱窗口彈出的 Windows 標誌時，編譯器不會提出異議。它也對每次讀取都克隆一份 250 MB 的事件日誌沒有任何意見。編譯器檢查的是你寫的程序在內部是否自洽。它無法檢查你是否寫完了整個程序、是否保留了舊的契約、是否按正確的順序調用、是否滿足了宿主未明説的要求，或者是否以可接受的成本完成了工作。

這絕不是反對 Rust 編譯器的論據。與任何靜態類型語言一樣，編譯器消除了一大類機械性錯誤，併為智能體提供了一個極其有用的內循環。但“只要能編譯，就是正確的”只有當作笑話時才有用。

性能，性能，還是性能

那麼，這一切換來了什麼？這次移植刻意保持了行為不變。它並非要重新設計算法或修復 bug；事實上，我反覆把智能體從機會主義的優化方向上推開，因為同時改變語言和行為會讓你很難判斷究竟是哪一個把你搞壞了。不過，這次重寫的一個關鍵目標確實是性能和可擴展性（此外還有可靠性等因素）。

當人們問我為什麼要用 Rust 重寫運行時，我的回答往往是這樣的：“我並不是要轉向 Rust，我是要擺脱 Node.js 和 V8。”這一轉變確實顯著提升了我們的性能表現。

在移植前後，我通過 C# SDK 對運行時的多個場景進行了基準測試（TypeScript、Python、Go、C#、Java 和 Rust SDK 都通過相同的傳輸架構接入同一個引擎）。基線是移植前的 SDK 和 CLI 構建版本，其中 TypeScript 運行時由 Node 託管，並通過 stdio 訪問。

8 月 21 日的結果使用的是 Rust 運行時，既作為進程外服務器，也通過 FFI 在進程內加載。這是對交付系統的端到端比較，而非試圖隔離語言變更所帶來的影響；同一時期還落地了其他改動，因此這些數字需要打些折扣來看。

每個計時的輪次都發往運行在 localhost 上的一個確定性聊天補全服務器，產生固定的小規模響應。換句話説，這些數字刻意剔除了模型推理和網絡延遲。它們衡量的是我們所改變的那部分：客户端啓動、進程啓動、會話創建、事件處理、持久化、拆除等。

“客户端、會話、單輪”這個數字是最容易直觀感受到的。它指的是創建一個客户端、創建一個會話、執行單輪交互，然後拆除一切。進程外開銷的很大一部分來自啓動 Node、初始化 V8，以及在第一輪交互開始之前加載、解析併為由 TypeScript 代碼生成的 JavaScript 應用生成字節碼。Rust 運行時消除了這些 Node/V8 和 JavaScript 加載成本。

“1,000 次單輪會話生命週期”壓力測試代表了我們可以構建的東西發生了階躍式變化。它使用單個共享客户端，測量運行 100 個併發流水線的表現，每個流水線創建一個會話、完成一次完整的模型輪次、銷燬會話，並連續執行十次。移植前的 TypeScript CLI 每秒完成 7.55 次這樣的生命週期。Rust 進程外完成 57.45 次。Rust 進程內完成 120.0 次。

這是一個特定於工作負載的結果；Rust 運行時並非普遍“快 15.9 倍”。但這恰恰是服務器託管方關心的工作負載：許多獨立會話共享一個運行時。而且掛鐘時間並沒有把工作隱藏到另一個核心上。在對同一 100×10 工作負載進行的單獨資源採樣中，移植前的進程樹消耗了 312 秒的累計 CPU。Rust 配置消耗了約 110 秒。這是託管方可以用於更多會話的 CPU 容量。

內存數據也講述了同樣的故事，同時附上那個老生常談的警告：內存指標極易被誤用。觀察十客户端批處理期間新增的常駐私有內存，移植前的進程樹峯值比基線高出 1,383 MB。Rust 進程外方案峯值僅為 247 MB。而 Rust 進程內方案為 126 MB，少了一個數量級。雖然這些數字當然會因用途和機器而異，但它們觸及了核心目標：一台機器上的服務可以承載多得多的客户端和會話，之後內存、進程數或 CPU 才會成為限制性資源。

最棒的是，這還只是基線移植。大部分實現仍然由忠實轉寫為 Rust 的 TypeScript 風格算法構成。我們尚未開展新的所有權模型、併發模型和進程內架構所支持的廣泛重新設計工作。在優化工作開始之前，就能讓一個進程內客户端完成創建、一個完整的單輪會話和銷燬僅需約 55 毫秒，將共享客户端推至每秒 120 次單輪會話生命週期，並將實測的十客户端內存增量削減 91%，這是一個非常好的起點。

移植的代價

那麼……這一切在金錢上花了多少？請鼓掌……

我在所有移植工作上的 token 消耗總計約 1363 億 token，其中包括約 1306 億緩存輸入讀取 token、約 42 億緩存輸入寫入 token、約 9 億全新輸入 token，以及約 6 億輸出 token。所有這些 token 的賬單金額約為 $120,000。

當然，這些 token 並不會自己花掉。使用開發者大量時間來引導這些智能體的成本也應計入其中。不過，我並沒有把所有時間都投入到這個項目上。智能體式開發很大程度上是“趕緊提交然後等待”；提交一個提示詞，讓編碼智能體自行其是，時不時查看一下以便可能引導它，但在它完成之前，去做其他事情。

這意味着開發者不再一次只處理一個編碼任務；他們把等待時間重疊起來，從而能夠同時處理許多事情。在移植窗口期內，這些 Rust 移植 PR 約佔我向所有貢獻倉庫提交的 PR 的 20%。如果我們粗略估計 PR 的佔比近似於我所花時間的佔比，那大約相當於三週專門用於移植的時間。

換句話説，這次移植工作的大致賬單約為 120,000 美元的歸屬 token 支出，外加三週的開發者時間。

話雖如此，端到端的 Rust 遷移並非完全由一位開發者完成；這是一項團隊協作的成果。@stevesandersonms提供了napi-oop的設計與實現，即臨時的進程外互操作性層，以及六個 SDK FFI 實現中的五個，@edburns提供了第六個。@roji實現了 SDK 的打包，以便正確發佈和使用 Rust 二進制文件。@caarlos0一直在幫助將 Rust 代碼拆分為許多小的子 crate，以緩解開始變得棘手的構建時間問題，而@criemen則幫助改進了資源緩存，以加速 CI 和本地構建。@devm33、@examon、@MRayermannMSFT、@dereklegenzoff以及其他人為無數 pull request 的審查和批准提供了幫助。而所有為 copilot-agent-runtime 倉庫做出貢獻的人，在世界於他們腳下發生鉅變之時，始終給予了支持與配合。

經驗教訓

這次經歷強化了幾條超越本次重寫本身的經驗教訓。以下是我們下次會帶入的一些做法：

  • 目標必須被清晰、完整地陳述出來。 我們早期的指令過於模糊。“把 XYZ 組件移植到 Rust”被理解成只處理熱路徑，或者只處理邏輯部分，而智能體一再把 I/O 和編排視為超出範圍。一旦我們明確説明最終狀態是一個由 100% Rust 代碼庫構建的原生二進制文件，即便我們想保留也沒有任何留給 TypeScript 的執行環境，它們就變得擅長得多，能夠自主地朝着這個目標推進。
  • 端到端測試絕對、毫無疑問地至關重要。 除了一個例外，所有涉及功能缺失的迴歸，以及許多其他迴歸，都是由於缺乏足夠的端到端測試造成的。對於任何此類性質的移植，你都必須擁有可用於驗證移植正確性的測試，而且這些測試本身不能在移植過程中被重寫，否則你就會失去你的判定基準。我們這次移植工作的初始計劃就指出了這一點，並指出我們需要在開始移植之前大幅改善我們的 E2E 測試狀況。我們做到了，但做得還不夠。我們確信，如果在開始移植之前增加更多的 E2E 測試，真正專注於確保大多數有意義的行為都被它們覆蓋，我們一路上的迴歸會比實際出現的更少。
  • 保護判定基準免受智能體影響。 不能允許改動實現的智能體同時通過削弱測試、更新快照、提高兼容性基線或套用逃生艙標籤來悄悄重新定義正確性，至少不能在缺乏監督的情況下這樣做。儘可能讓行為契約保持獨立，把敏感的護欄置於單獨的所有權或審批之下，並用具有不同失效模式的檢查層層疊加，這樣單一個錯誤就不足以讓一次重大回歸上線。
  • 先翻譯，再重新設計。 保持行為不變並沿用現有算法，可以讓同時變動的變量數量保持在可控範圍內。一旦舊實現和過渡期的腳手架被清除，就可以在一個穩定的基線上重新設計歸屬關係、併發和性能。我曾幾次偏離這一原則——出於不安分，或難以對同事説不，或堅信這次情況不同——事後看來，每一次我都後悔。每一次偏離都比堅持原路線付出了更多的迴歸問題、更多的時間或更多的 token。
  • 把反覆出現的失敗轉化為未來的成功。 AI 智能體會偏離正軌：當它們偏離時，要從中學習。當某種失敗模式出現兩次時，它就應該被寫入常駐指令、可複用技能、評測、受保護的基線，或者 harness 本身。
  • 當智能體進入循環時，開發者的內循環更重要，而不是更不重要。 對於我們開發者來説，我們生活和呼吸都在內循環中——我們能多快做出改動、構建、測試、迭代。當其中的工具鏈環節耗時過長時，我們會感到沮喪。人們很容易認為，當智能體在做更底層的工作時，這一點就不再適用。但事實恰恰相反，它更加適用。AI 智能體完成這些任務中思考和編寫代碼的部分極其迅速，但它們仍然需要構建，仍然需要測試。而且，隨着它們在思考和編寫上花的時間更少、在快速驗證的內循環中花的時間更多，它們用於構建和測試的時間佔比實際上在增加。花一些時間在前期優化內循環，並針對多件事情同時發生的情況來優化它（例如，就像你同時在多個 worktree 中處理多個任務一樣）。你日後會感謝自己做了這項投資。

接下來是什麼？

它成功了。五月時還完全是 TypeScript 的執行運行時，到了八月已經完全是 Rust，而且整個過程持續交付給真實用户，而不是在最後以一次令人膽戰心驚的整體切換落地。

我並沒有簡單地讓一個 AI 智能體“把整個代碼庫從 TypeScript 移植到 Rust”。即便這是整個行業的發展方向，我們也絕對還沒到那一步。相反，智能體讓一整類項目變得可行。在一個運行中的系統裏就地重寫，產出數十萬行生產級 Rust 代碼，main，由一名工程師在團隊支持下完成——這在智能體出現之前是不會被批准的提案。那需要一整個團隊和一兩年的時間，它還要與那個團隊本可以交付的每一項功能競爭，而且它會輸（説實話，也應該輸）。智能體把成本降到了讓這個項目變得可行的程度。

這次移植本身已經完成：運行時的生產實現 100% 是 Rust，臨時的內部 TypeScript/N-API 接縫已經移除。不過，我們仍有許多想做的事：進一步改進構建系統和開發者內循環、清理移植後的結構、圍繞 Rust 的所有權與併發模型重新設計，以及追求進一步的性能提升。

這次移植是一次翻譯，而且是有意為之（也是以此為目標促成的），我們儘可能讓行為保持接近 100% 一致，而不是趁機修復額外的 bug、重構組件，或進一步提升性能和可擴展性（超出重寫本身自然帶來的部分）。在微觀層面，大部分代碼已是地道的 Rust，但在宏觀層面，仍有相當多最初用 TypeScript 編寫的算法披着 Rust 的語法外衣。

如今這些算法底層的約束已經改變，重新審視這些決策，才是真正有意思的收益所在。

最讓我興奮的是這次移植所開啓的可能性。SDK 現在可以直接加載進六種語言中任意一種的宿主進程，依賴鏈中不再有 Node.js 或 V8，也不需要再監督第二個進程——而這正是我們從採用該 SDK 的合作伙伴那裏聽到的最常見的單一摩擦點。

運行時實例的成本只有過去的零頭，意味着宿主在耗盡機器資源之前可以運行多得多的併發會話。而且運行時現在可以去到 Node.js 永遠無法跟隨的地方，覆蓋從雲端到桌面、到設備、再到嵌入式系統的整個譜系。這些都不是終點。它是我們如今得以在其之上構建 GitHub Copilot 未來的基礎，而在三個月裏看着智能體重寫運行它們自己的那個引擎之後，我很期待看到它能走多遠。
