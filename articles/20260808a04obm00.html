今年 3 月，Token Maxxing 興起，一些公司甚至擔心工程師用 AI 太少，紛紛搞起了內部員工的 Token 消耗排行榜。

到了 6 月，公司們紛紛出臺預算上限、動態配額和審批機制，掉頭轉向 Token Minimizing。短短幾個月，沒有產生 ROI 的 Token 用量變成財務系統裏的警報。

這場急轉彎，恰好印證了**「十字路口」年初與真格基金管理合夥人戴雨森的** ——他把 2026 概括爲 **The Year of R**，並將商業回報 Return 放在第一位，企業會開始追問在 AI 上投資的 Return。

3 月 16 日，在 GTC 上把數據中心描述爲生產 Token 的“AI 工廠”。三天後，黃仁勳做客 All-In 播客，把這套 Token 經濟學推演到工程師身上。他說，如果一名年薪 50 萬美元的工程師，一年的 Token 消耗不到 25 萬美元，會令他深感不安。在他看來，這就像芯片設計師放着 CAD 不用，卻只用紙和筆。

在 Meta 內部，這場競賽有了一塊真實的記分牌。

一名 Meta 員工自發搭建 Claudeonomics，把 8.5 萬個內部賬戶的用量彙總成一張 Top 250 榜單。榜單不展示代碼是否發佈、產品是否上線，只根據 Token 用量授予「Token Legend」「Cache Wizard」「Session Immortal」等稱號。The Information 的計算頁顯示，榜首員工 30 天消耗了 3,285 億 Token，按默認模型組合和公開定價折算約 180 萬美元，相當於黃仁勳所說年度標準的 7 倍。

排行榜把 AI 採用變成了一場荒誕的“生產力表演”。

一名微軟員工向 Pragmatic Engineer 表示，他會讓 AI 重讀已有文檔、起草不會落地的原型，只爲避免顯得“用得太少”。Salesforce 則把這種隱形壓力直接搬到桌面上。Mac 桌面組件每 15 分鐘更新個人 Token 支出，顯示 Claude Code 和 Cursor 的最低消費目標，員工還能查看同事花了多少。

同一套激勵也出現在國內。今年 3 月，有員工在脈脈社區上爆料，騰訊爲員工配置年均價值約 22 萬元的 Token 資源。到了 3 月底，部分業務開始統計並排名 Token 用量。一些員工擔心消耗不夠，開始搭建沒有實際意義的工作流，讓 Agent 反覆執行任務，甚至“接私活”，只爲不在用量上落後。

排行榜在鼓勵消耗，財務系統裏的另一張表已經先報了警。

傳統 SaaS 多按席位收費，預算大致等於人數乘以單價。Agent 把這項相對固定的許可支出變成了波動的使用量支出：一項任務可能觸發多次模型調用，攜帶不斷增長的上下文，並在規劃、生成、檢查和重寫之間反覆循環。賬單隨任務複雜度、模型選擇、上下文長度和重試次數波動，不再只跟人數走。

4 月中旬，Uber 首席技術官 Praveen Neppalli Naga 公開透露，公司僅用四個月便耗盡了全年的 AI 預算，部分重度用戶每月產生的 AI 賬單高達 2,000 美元。

一個月後，Uber 首席運營官 Andrew Macdonald 在 Rapid Response 播客中承認，Uber 上一季度約 25% 的代碼提交來自 Claude Code，但並不意味着也多交付了 25% 真正有用的消費者功能。他補充，產出可能確實增加了，只是這條聯繫尚未建立。當他詢問高級工程負責人，究竟有多少原本被擱置的項目因生產力提升而進入開發清單，對方仍無法給出答案。

6 月 2 日，Uber 因預算告急開始踩下剎車，將 Claude Code、Cursor 等 AI 編程工具的月額度設爲每人每個工具 1,500 美元。

兩天後，這一轉向出現在科技圈外。

零售巨頭沃爾瑪把內部 AI 工具 Code Puppy 從不限量使用改爲固定 Token 配額。據 Business Insider 報道，這款工具能讓員工通過自然語言自行開發軟件，過去一年間，用戶從約 1,000 人增至 7.5 萬人，採購、供應鏈、門店經理乃至按小時計薪的兼職員工都在使用，非工程師用戶已與工程師相當。Token 治理從軟件工程預算進入大型企業的日常運營。

賬單衝擊也可能在用量沒有增長時發生。同樣在 6 月，一家 B2B 客服初創公司 Pylon 在超過 Anthropic Team 的 150 個席位後，需要遷移至 Enterprise，Token 改爲按標準 API 價格另行計費。CEO Marty Kausas 稱，這會讓公司的 Anthropic 年化賬單從 40 萬美元飆升至 140 萬美元，幾乎一夜增加 3.5 倍。Pylon 隨後要求客服團隊追加 Token 必須經過審批。他認爲工程團隊使用最強模型“顯然值得”，但其他崗位的回報並不明確：

國內大廠也沿着同一方向調整。據《經濟觀察報》報道，6 月，騰訊多個業務線員工的 Token 額度均有下降。混元大模型團隊的員工月額度約 7,000 元，優圖實驗室約 5,250 元，另有騰訊娛樂外包員工透露自己的月額度只有 1,000 元。額度先進入部門池，再由管理者根據業務需要動態分配，有需求可以“舉手申請”。

額度縮減後，有員工調侃，“以前每天上班唯一要做的，就是狠狠鞭撻 Workbuddy；現在每天都要緊張地檢查一下 Token 看板，生怕把它累着。”也有人感慨，“由奢入儉難，自己已經回不去古法編程了”……

限額能止住賬單，卻回答不了錢該花在哪。企業需要把這張賬單繼續追蹤到任務與交付結果上。

7 月，Business Insider 援引 UBS 分析師的報告稱，在近期與數十位企業 IT 高管的交流中，約 60% 的受訪企業已經採取不同程度的管控措施來收緊 AI 支出。分析師把它描述爲一個“健康的問題”：企業並沒有停止部署 AI，Token 優化正在從預算超支後的應急措施變成持續性的工程紀律。

理想情況下，覈算口徑大致是 Token ROI = 可驗證的業務增量 ÷（模型成本 + 人工複覈 + 重試/返工 + 工程治理成本）。但截至目前，公開實踐中還沒有一套被多家企業共同採用的標準。分子這側，取決於各家的業務口徑，很難有統一算法，不過已經有公司在朝這個方向逼近；分母這側更確定，多數企業從這裏入手，在任務和工作流層面進行覈算。

部分企業開始自建覈算機制，服務商也把類似能力做成標準化工具。

Shopify 通過統一的大模型調用網關、用量看板和異常告警，按團隊、項目和個人歸集支出。單個用戶一天的 Token 支出超過 250 美元會觸發人工覆盤，但高用量只會啓動調查，不會直接被判定爲浪費。

GitHub 與 Amazon 則試圖把 AI 的使用與工程交付放在一起觀察。

GitHub 7 月推出的 Copilot 使用指標影響面板按照 AI 採用程度將用戶分組，比較合併的代碼變更請求數量、合併速度和每日代碼產出。

Amazon CloudWatch 的 Coding Agent Insights 更進一步，把 Token 用量與成本按模型、部門、團隊和個人歸集，與代碼提交、活躍編程時間、建議接受率放進同一個面板。

看板能回答誰花了多少 Token，還不能回答這些換回了什麼。代碼行數、提交次數、合併速度和建議接受率，依然停留在工程活動層。企業要繼續往下追問的，是 AI 生成的代碼有沒有進入生產環境，有沒有留在代碼庫裏，又真正替代了多少人類工作。

Amazon 用於評估 AI 編程工具的指標之一是 normalized deployments，即標準化後的部署量。它把 AI 採用與團隊的部署速度放在一起分析，同時觀察回滾和人工干預。Token 消耗和代碼生成量都不能直接記作產出；代碼進入部署流程，並經受住生產質量檢驗，纔算一次有效交付。

Cursor 觀察的是 keep rate：Agent 生成的代碼在一段時間後有多少仍留在代碼庫中。一次生成被開發者接受，只能說明它暫時可用；如果很快又被刪除或重寫，這部分消耗很難算作穩定回報。過去九個月，Cursor 一直用代碼保留率和用戶滿意度評估模型更新與 Agent 工作流調整。

Cognition 走得更遠。Devin 會評估每個已完成任務是否產生了有效結果，再估算同一項工作交給人類工程師需要多少時間。沒有合併的代碼變更，或者被判定爲無效的任務，不計入有效產出。節省的工程時間隨後被折算爲金額，與企業的實際支出進行比較。

這三種口徑仍不能完整代表業務 ROI。代碼上線不等於產生收入，節省工時也不意味着這些時間一定被重新投入到高價值工作。但它們把企業的觀察對象從“AI 跑了多少”推進到了“最終留下了什麼”——是否上線、是否留存、是否節省了真實的人力。

有了這層結果口徑，企業可以根據任務的質量要求、失敗成本和預期價值，決定哪些請求交給輕量模型，哪些值得調用最強模型。

在 Artificial Analysis 的最新綜合測評中，國產模型 Kimi K3、Qwen 3.8 已經進入接近前沿模型的智能區間，但完成基準任務的平均成本明顯低於 Claude Opus 5、GPT-5.6 Sol 等高價模型；DeepSeek V4 Flash 則處在成本更低的一端，爲通過企業內部質量驗證的常規任務提供了更便宜的選擇。

模型選擇變多後，分配本身成了新的管理問題。缺少自動路由時，最熟悉或最強的模型仍會成爲昂貴的默認項。

騰訊雲 AI 網關給出了一張直觀的示意圖。用戶請求進入網關後，系統先識別它屬於代碼、數學、翻譯、簡單問答還是複雜推理，再將任務交給專項模型、輕量模型或旗艦模型。無法可靠識別或模型出現異常時，請求會回退到默認服務。

這套路由邏輯也在成爲雲平臺的標準配置。Amazon Bedrock、Microsoft Foundry 和 Google Vertex AI 都允許企業根據任務特徵，在質量與成本之間動態分配請求。

在 Coding 工具層，Cursor 也於 7 月 22 日推出 Router。它會結合請求內容、上下文、任務複雜度和所屬領域，在 Intelligence、Balance 和 Cost 三種模式下選擇模型。據 Cursor 官方披露，在覆蓋數百萬請求的在線 A/B 測試中，Router 在保持前沿水平質量的同時節省了約 60% 的成本。

模型路由決定任務交給哪個模型，工作流設計則影響完成任務需要攜帶多少上下文、調用多少工具、經歷多少輪循環。兩者共同決定最終的 Token 支出。

隨着模型能力增強，一個問題開始變得具體：這些約束是能力不足時的補丁，還是與能力無關的工程紀律？

7 月 25 日，Claude Code 團隊的核心工程師 Thariq Shihipar 公開了一組數字：

他給出的原因是「過度約束」。當他們閱讀自己內部使用 Claude Code 的轉錄記錄時，發現單個請求中出現了多條相互衝突的指令，比如“酌情添加文檔”或“不要添加註釋”，而往往 Claude 需要先分辨這些矛盾，才能決定怎麼做。

這些限制曾經是爲了避免最壞情況而必要的，但團隊現在發現，可以讓模型依賴周圍的上下文和判斷來做出決策。他把這輪調整概括爲以下幾組前後對照。

其中一組是從「給 Claude 定規則」到「讓 Claude 自己判斷」：過去系統提示詞寫明“默認不寫註釋，絕不寫多段落文檔字符串或多行註釋塊”，現在只留一句“讓它讀起來像周圍的代碼一樣：匹配其註釋密度、命名風格和慣用表達”。

另一組是從「把所有內容都前置」到「採用漸進披露」：代碼評審與驗證被移進各自的 Skill，由 Claude 按需調用；部分工具改爲延遲加載，Agent 在使用前必須通過 ToolSearch 搜索其完整定義。

漸進披露不只出現在模型廠商一側。Matt Pocock 那套在 GitHub 社區爆火的 Skill 庫已積累超過 20 萬星標，其中 The Main Flow 這條主工作流把從想法到交付的過程拆成五個階段，每個階段對應一個 Skill。

想法還模糊時，先用 /grill-with-docs 接受追問，並把確認下來的決定記進文檔；與 Agent 達成共識後，用 /to-spec 把對話變成一份書面規格；要開始動手，就交給 /to-tickets 拆成 Agent 能獨立完成的小模塊；進入編碼，用 /implement 按測試先行的方式把規格變成代碼；改動完成後，由 /code-review 對照團隊標準和規格文檔審一遍差異。

五個 Skill 各自只在自己的階段被調用，這正是 Thariq 所說的漸進披露：上下文不必一次鋪滿，需要時再加載。兩人在這一點上並無分歧，關鍵在於約束本身。

Pocock 這條鏈仍在給模型定下硬規則，/implement 要求測試先行，/to-tickets 要求按用戶功能垂直切分，明確禁止先把數據庫建完再寫後端。理由是，模型會習慣性地按技術分層推進，或在實現時走捷徑。

兩種做法沒有孰優孰劣。在 Thariq 那裏，約束是能力不足時的補丁，模型強了就該拆掉；在 Pocock 那裏，它是與能力無關的紀律，已經寫進一套正在被使用的流程。

從獎勵消耗到限制預算，企業僅用幾個月便完成了一輪 AI 成本校準。

回到前文那個覈算口徑：Token ROI = 可驗證的業務增量 ÷（模型成本 + 人工複覈 + 重試/返工 + 工程治理成本）。

其中，模型成本最清楚，調用與輸出的價格都寫在各家的官方頁面上；人工複覈難以準確計量，但工作流設計得當時理論上會下降；重試和返工同理，約束到位能夠減少，具體減少了多少，企業正通過統一網關、用量看板建立歸因；而工程治理成本，正是 Thariq 和 Pocock 各自在做文章的地方。

我們不斷追問的 Return，不僅是業務增長；如何降低模型成本、人工複覈、重試返工和治理成本，同樣值得企業優化。

企业 AI 正从 Tokenmaxxing 转向 Token ROI maxxing。
