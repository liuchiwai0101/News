你平時用電腦，是通過鼠標點擊圖標、菜單來操作的，這叫**圖形界面（GUI）**。而**終端（Terminal）**是另一種操作電腦的方式 —— 通過輸入文字命令來告訴電腦做什麼。

打個比方：圖形界面就像在餐廳看着菜單點菜（點什麼有什麼），終端就像直接跟廚師說你想喫什麼（更靈活，但需要知道怎麼"說"）。

AI編程工具（如Claude Code）幾乎全部運行在終端中，所以掌握基本的終端操作是第一步。

- 按下鍵盤上的 `Win + R`鍵（Win 是鍵盤左下角帶 Windows 標誌的鍵）

- 在彈出的"運行"對話框中輸入 `powershell`

- 按回車鍵

或者更簡單的方式：

- 在桌面底部的搜索欄中搜索"PowerShell"

- 点击"Windows PowerShell"打开

**macOS 用户：**

- 按下 `Command + 空格`打开 Spotlight 搜索

- 输入 `Terminal`或"终端"

- 按回車鍵打開

提示：打開終端後你會看到一個黑色（或白色）的窗口，裏面有一個閃爍的光標等待你輸入命令。不要怕，它不會因爲你輸錯命令就爆炸 —— 最多給你一個報錯信息而已。

以下是你需要掌握的最基本的終端命令。打開終端，跟着一起敲：

**1. pwd —— 查看當前位置（我在哪？）**

# 通用命令（macOS/Linux直接输入，Windows PowerShell也支持）
$ pwd

預期輸出：

# Windows 輸出類似：
C:\Users\你的用戶名
# macOS 輸出類似：
/Users/你的用戶名

這就像你在商場裏，看一下腳下的地圖上"您在此處"的標記。

**2. ls（macOS/Linux）或 dir（Windows）—— 查看当前目录有什么**

# macOS / Linux
$ ls
# Windows PowerShell（ls也可以用，但dir是经典命令）
$ dir

預期輸出：

Desktop    Documents   Downloads   Pictures   Videos
桌面       文档       下载       图片      视频

就像打開一個文件夾，看看裏面有什麼東西。

**3. cd —— 進入某個目錄（走到某個位置）**

# 進入"桌面"文件夾
$ cd Desktop
# 返回上一級目錄
$ cd ..
# 直接回到用戶主目錄
$ cd ~

cd 是 “change directory” 的缩写，就是"换个地方"的意思。

**4. mkdir —— 創建新文件夾**

# 創建一個名爲 my-project 的文件夾
$ mkdir my-project
# 驗證：查看是否創建成功
$ ls

預期輸出中應該能看到 my-project 文件夾。

**5. clear —— 清屏（屏幕太亂了，清理一下）**

$ clear

驗證：在終端中依次執行以下命令，確認你能正常操作：$ pwd $ mkdir ai-coding-test $ cd ai-coding-test $ pwd $ cd ..如果每條命令都能正常執行且沒有報錯，恭喜你，終端入門完成！

在正式上手工具之前，我們需要先建立"認知地圖"。這就像學開車之前要先了解交通規則一樣 —— 你不需要成爲交通工程師，但至少要知道紅燈停綠燈行、靠右行駛這些基本概念。

**傳統編程**是你一行一行地"手寫"代碼，告訴計算機每一步該怎麼做。你需要掌握編程語言的語法、理解算法、記住各種API —— 學習曲線陡峭且耗時漫長。

**AI輔助編程**則完全不同。你用自然語言（中文或英文都行）描述"你想要什麼"，AI幫你把它變成可運行的代碼。你的角色從"打字員"變成了"指揮官"。

打個比方：傳統編程就像你自己從頭學做一道紅燒肉 —— 要學買菜、備料、掌握火候；AI編程就像你請了一個專業廚師 —— 你只需要說"我想喫紅燒肉，少放糖，多放一點八角"，廚師幫你做出來，你嘗一口覺得太鹹了，再說"減少一些鹽"就行。

提示：AI編程不是"不需要懂任何技術"，而是大幅降低了入門門檻。隨着你的使用越來越深入，你會自然而然地積累技術知識。這個過程是"邊用邊學"，而非傳統的"先學後用"。

AI編程並不是突然出現的，它經歷了一個清晰的演進過程：

**第一階段：智能補全時代（2020-2022）**

代表产品：GitHub Copilot、TabNine

就像手機輸入法的聯想功能 —— 你打了幾個字，它猜你接下來要打什麼。這個階段的AI只能幫你補全一行或幾行代碼，依然需要你自己動手寫大部分代碼。

**第二階段：對話式編程時代（2023-2024）**

代表产品：ChatGPT、Claude.ai

AI進化成了一個"編程顧問"。你可以用自然語言問它"怎麼寫一個排序算法"，它會給你一段完整的代碼。但問題是：你需要自己把代碼複製到項目中、自己處理各種細節，AI並不瞭解你的項目全貌。

**第三階段：智能體編程時代（2024 至今）** ← 我們現在就在這裏

代表产品：Claude Code、Cursor Agent、Qoder、Codex

這是一個質的飛躍！AI從"回答問題"進化到了"完成任務"。你告訴它"給我的項目添加一個用戶登錄功能"，它會**自己**去讀你的項目代碼，**自己**創建需要的文件，**自己**寫代碼，**自己**運行測試 —— 全程自主完成。

這就像從"問路人"（對話式）變成了"請了一個代駕"（智能體）—— 你只需要說目的地，它自己開車到。

**第四階段：協作工程時代（正在形成）**

多個AI智能體組成"團隊"，各司其職 —— 一個負責設計架構、一個負責寫代碼、一個負責測試、一個負責審查代碼質量。人類的角色進一步上升爲"項目總監"。

你不需要成爲AI專家，但理解以下幾個核心概念會幫你更好地使用AI工具：

**Token化：AI怎麼"閱讀"代碼**

AI不是像人一樣一個字一個字地讀代碼，它把文本切成一個個小塊，叫做 **Token**。

例如，Hello World 会被切成 Hello 和 World 两个 Token。中文的 你好世界 可能被切成 你好 和 世界 两个 Token，也可能被切成更多个。

爲什麼這個概念重要？因爲**AI的計費和能力限制都以 Token 爲單位**。你發送的內容越長，消耗的 Token 越多，費用越高。

提示：簡單記住這個換算關係 —— 1 個 Token ≈ 4 個英文字符 ≈ 1-2 箇中文字符。一篇 1000 字的中文文章大約是 500-1000 個 Token。

**上下文窗口：AI的"工作記憶"**

上下文窗口是AI一次能"記住"的內容量。這就像你的辦公桌大小 —— 桌子越大，能同時攤開的文件越多。

對於AI編程來說，上下文窗口越大越好 —— 因爲AI需要同時"看到"更多項目代碼才能做出合理的修改。Claude、Gemini、GPT 等主流模型都在持續擴大上下文窗口。

**概率生成：爲什麼AI有時會"胡說八道"**

AI生成內容的本質是**預測概率最高的下一個詞**。大多數時候它預測得很準，但有時候它會"一本正經地胡說八道" —— 這被稱爲**“幻覺”（Hallucination）**。

例如，AI可能信心滿滿地告訴你某個函數的用法，但這個函數根本不存在。這就像一個知識淵博但偶爾會編故事的朋友 —— 大部分時候值得信賴，但關鍵信息你需要自己驗證。

避坑：永遠不要100%信任AI生成的代碼。尤其是涉及數據庫操作、用戶認證、支付邏輯等關鍵代碼時，一定要仔細檢查。"信任但驗證"是AI編程的黃金法則。

**Vibe Coding** 是 AI 大牛 Andrej Karpathy（前OpenAI/Tesla AI主管）在2025年初提出的概念。他的原话是：

“完全沉浸在氛圍中，擁抱指數級增長，忘記代碼的存在。”

翻譯成大白話就是：**不要糾結代碼的每一個細節，跟着感覺走，讓AI幫你實現想法**。

Vibe Coding 的核心原則：

- **意圖優先**：先描述你想要什麼效果，而不是告訴AI怎麼寫代碼

- **快速迭代**：不追求一次完美，擁抱"生成 → 測試 → 修正"的循環

- **信任但驗證**：相信AI的能力，但始終檢查關鍵邏輯

- **上下文經營**：持續維護和優化提供給AI的背景信息

**Vibe Coding 适用场景：**

- 原型開發、概念驗證（快速把想法變成可運行的東西）

- 個人項目、學習項目（試錯成本低）

- 探索性編程（不確定最終效果，邊做邊看）

- UI/前端開發（可視化反饋快，容易判斷好不好）

**Vibe Coding 需謹慎的場景：**

- 注意： 生產環境的核心繫統（銀行、醫療等）

- 注意： 安全敏感代碼（認證、加密等）

- 注意： 性能極致要求的場景

提示：Vibe Coding 不等於"亂來"。它的精髓在於改變你的關注點—— 從關注"代碼怎麼寫"轉向關注"產品好不好用"。

Vibe Coding 對於做小項目、快速原型非常好用，但當項目變大變複雜時，純粹的"跟着感覺走"會遇到麻煩：

- **代碼質量不可控**：AI可能寫出能跑但很亂的代碼，積累成"技術債務"

- **前後矛盾**：AI在不同對話中可能給出相互衝突的實現方式

- **缺乏全局視角**：AI可能只關注當前的小任務，忽略對整體架構的影響

- **難以協作**：沒有統一規範時，多個人（或多次會話）的代碼風格各異

這就像建房子 —— 自己搭一個小木屋可以隨意發揮（Vibe Coding），但要建一棟大樓就必須有圖紙、有規範、有質檢（Agentic Engineering）。

在AI編程的語境中，**智能體（Agent） 是一個能夠自主完成任務**的AI系統。它和普通的AI聊天有什麼區別？

一個智能體的工作循環是 **感知 → 推理 → 行動 → 反饋**：

   ┌─────────────────────────────────┐
   │                         │
   ▼                         │
  感知（读取项目代码、理解需求）      │
   │                         │
   ▼                         │
  推理（分析问题、制定计划）         │
   │                         │
   ▼                         │
  行动（修改文件、运行命令、安装依赖）   │
   │                         │
   ▼                         │
  反馈（检查结果、发现新问题）──────────┘

Claude Code 就是一個典型的編程智能體 —— 你告訴它"幫我添加一個用戶註冊功能"，它會自己讀懂項目代碼，自己創建文件，自己寫代碼並運行測試。

當一個智能體不夠用時（比如項目特別複雜），可以讓多個智能體協作，各司其職。就像一個公司不是一個人幹所有事 —— 有產品經理、有程序員、有測試員、有設計師。

**領導者-執行者模式（Leader-Worker）**

一個"老闆"Agent負責拆分任務和協調，多個"員工"Agent負責執行具體任務。

               ┌──────────┐
               │ 领导Agent │ ← 你的需求
               │（规划分配）│
               └──┬───┬───┘
                  │   │
           ┌────────┘   └────────┐
           ▼                ▼
      ┌──────────┐        ┌──────────┐
      │编码Agent  │        │测试Agent  │
      │（写代码）  │        │（写测试）  │
      └──────────┘        └──────────┘

Qoder 就是這種模式的典型代表 —— 有 Leader（指揮官）、Coding（開發者）、Research（研究員）、Verify（測試員）等多個 Agent 角色。

**管道式協作（Pipeline）**

Agent按順序接力，就像工廠流水線：

需求分析Agent → 架構設計Agent → 代碼實現Agent → 測試Agent → 部署Agent

**对等协作（Peer-to-Peer）**

多個Agent平等地互相審查，就像同事之間互相Code Review。

提示：對於初學者來說，你暫時只需要瞭解這些概念。在實際使用中，Claude Code 是一個單智能體工具（一個Agent幫你做所有事），已經能完成大多數項目。當項目足夠複雜時，再考慮 Qoder 等多智能體方案。

優秀的AI編程智能體不會一股腦地把所有代碼寫出來，它會像一個經驗豐富的程序員一樣，先思考再行動：

**Plan-Act-Observe-Reflect 循环：**

1. Plan（規劃）：   "要完成登錄功能，我需要做這些事......"
2. Act（行動）：   "先創建數據庫用戶表......"
3. Observe（觀察）："創建成功了，但發現少了一個字段......"
4. Reflect（反思）："我需要修改表結構，加上郵箱字段......"
5. 回到 Plan：     "好的，現在繼續下一步......"

**任務分解原則 —— MECE：**

MECE（Mutually Exclusive, Collectively Exhaustive）是一個管理諮詢中常用的概念，意思是"相互獨立，完全窮盡"。

舉個例子，把"構建一個博客系統"分解爲：

構建博客系統
├── 1. 用戶系統（註冊、登錄、個人資料）
├── 2. 文章系統（創建、編輯、刪除、列表）
├── 3. 評論系統（發表、刪除、回覆）
├── 4. 分類標籤（創建分類、打標籤、按分類篩選）
└── 5. 部署上線（打包、配置服務器、域名）

這5個子任務之間互不重疊（相互獨立），合在一起覆蓋了博客系統的全部功能（完全窮盡）。

提示：在使用 Claude Code 時，最佳實踐是先讓AI制定計劃，你確認後再執行。而不是一上來就讓它開始寫代碼。這個習慣會大幅減少返工。

你有沒有過這種經歷：在淘寶買衣服時，你描述"我要一件好看的衣服"，結果收到的和你想的完全不一樣？這就是**溝通不精準**導致的。

AI編程也是一樣。如果你告訴AI"幫我做一個網站"，它可能做出一個和你期望完全不同的東西。“垃圾進，垃圾出” —— 模糊的需求必然導致不準確的結果。

**規範（Specification）就是你和AI之間的"合同"**，它明確地寫清楚：

- 要做什麼（功能需求）

- 怎麼做（技術方案）

- 做到什麼程度（質量標準）

有了這份"合同"，AI才能精準地理解你的意圖。

**PRD（Product Requirements Document，产品需求文档）**描述的是"要做什么"。

**用戶故事（User Story）格式：**

作爲一個 [角色]，
我希望 [功能]，
以便 [價值/目的]。

例如：

作爲一個博客讀者，
我希望能按標籤篩選文章，
以便快速找到我感興趣的內容。

**验收标准（Acceptance Criteria）格式：**

Given（前提條件）：系統中有20篇文章，其中5篇標記了"Python"標籤
When（操作）：用戶點擊"Python"標籤
Then（預期結果）：頁面只顯示這5篇標記了"Python"標籤的文章

**用AI輔助生成PRD的Prompt：**

這是一個非常實用的技巧 —— 你可以讓AI幫你把模糊的想法變成結構化的需求文檔：

我想做一個個人書籤管理工具。
請幫我生成一份完整的PRD文檔，包含：
1. 項目概述（一句話描述）
2. 目標用戶
3. 核心功能列表（按優先級排列：Must Have / Should Have / Nice to Have）
4. 每個功能的用戶故事和驗收標準
5. 非功能需求（性能、安全、兼容性）
請用Markdown格式輸出。

提示：在第五部分的項目實操中，我們會完整演示如何用這個方法生成PRD文檔。

**SPEC（Technical Specification，技術規範文檔）**描述的是"怎麼做"。

一個完整的SPEC文檔包含：

**讓AI從PRD自動生成SPEC的Prompt：**

基於以下PRD文檔，請生成對應的技術規範文檔（SPEC）：
[粘貼你的PRD內容]
要求：
1. 推薦技術選型並說明理由
2. 設計完整的數據模型（包含字段類型和關係）
3. 列出所有API接口（RESTful風格）
4. 給出建議的項目目錄結構

質量規範定義了"做到什麼程度算合格"：

- **編碼規範**：代碼風格統一、命名規則、註釋要求

- **測試規範**：需要覆蓋哪些測試場景

- **安全規範**：輸入驗證、認證授權、數據保護

提示：對於初學者來說，不需要一開始就寫完美的規範文檔。從簡單的PRD開始，隨着項目變複雜再逐步完善。規範的核心價值在於 ——讓你和AI的溝通更精準。

建議在項目根目錄下創建一個 specs/ 文件夾，統一管理規範文件：

my-project/
├── specs/
│   ├── PRD.md         # 产品需求文档
│   ├── SPEC.md         # 技术规范
│   ├── ARCHITECTURE.md   # 架构设计
│   └── API.md         # API 接口文档
├── src/              # 源代码
├── CLAUDE.md          # 给Claude Code的项目说明（详见第二部分）
└── package.json

規範文件最大的價值之一是 —— **可以直接作爲AI工具的上下文輸入**。當你把 SPEC.md 的內容提供給 Claude Code 時，它就能精準地按照你的技術方案來寫代碼。

**參數量：模型的"大腦"大小**

你可能聽說過"7B模型"、“70B模型"這樣的說法。這裏的 B 是 Billion（十億）的縮寫，指的是模型的參數數量。簡單理解：參數越多，模型越"聰明”，但也越慢、越貴。

提示：參數量不是唯一標準。訓練數據的質量、訓練方法的優化同樣重要。有些小參數模型經過精細調優後，在特定任務上可以媲美大模型。

**上下文窗口：再次強調的核心概念**

對AI編程來說，上下文窗口直接決定了AI能"看到"你項目中多少代碼。窗口越大，AI對項目的理解越全面，生成的代碼越準確。

4K Token   ≈ 一個文件      → 只能看到當前文件
32K Token  ≈ 幾個文件      → 能看到相關的幾個文件
128K Token ≈ 一個小項目    → 能理解整個小項目
200K Token ≈ 一箇中型項目   → 許多主力模型的長上下文起點
1M Token   ≈ 一個大型項目   → Claude / Gemini / GPT 等旗艦模型的超長上下文級別

**Token 計費：你的"油費"**

使用AI模型就像開車需要加油 —— Token 就是你的"油"，用多少付多少。

費用 = 輸入Token數 × 輸入單價 + 輸出Token數 × 輸出單價

**Temperature：AI的"创造性开关"**

Temperature 是一個 0-1 之間的參數，控制AI回覆的"隨機性"：

- **Temperature = 0**：每次給出幾乎相同的答案（最確定性）→ 適合代碼生成

- **Temperature = 1**：每次答案都不同（最隨機）→ 適合創意寫作

提示：編寫代碼時，通常不需要手動調整 Temperature。Claude Code 默認使用適合編程的低 Temperature 值。

Claude Code 是 Anthropic 公司推出的 **AI 編程智能體**。它最經典的入口是終端 CLI，現在也提供 IDE、Desktop、Web 等形態。它能夠讀取項目代碼、修改文件、運行命令、安裝依賴 —— 就像你僱了一個 24 小時在線的遠程程序員，你用自然語言告訴它做什麼，它自己動手幹活。

*圖：Claude Code 核心能力架構 —— AI大腦接收你的指令，通過四大能力模塊操控項目*

**Claude Code 是什么？**

如果把AI編程工具比作不同的交通工具：

- ChatGPT/Claude.ai 就像**公交車**—— 你問路，它告訴你怎麼走，但你得自己走

- Cursor 就像**共享單車**—— 你騎着它走，它幫你指路和加速

- Claude Code 就像**出租車**—— 你說目的地，它自己開到

Claude Code 的核心特點：

**Claude Code vs Claude.ai 的核心区别：**

提示：Claude Code 和 Claude.ai 都使用 Claude 系列模型，核心區別在於“交互方式”和“工具權限”。Claude Code 給了 AI “手” —— 讓它能在你授權後直接觸碰項目文件和開發工具。

要理解 Claude Code 與你以前用過的 ChatGPT、Claude.ai 的本質差別，必須先弄懂一個機制 —— **LLM Loop（大模型循環）**。

**對話式 AI（ChatGPT/Claude.ai）的工作方式**：你問一句 → 它答一句 → 結束。如果答案不滿意，你再問一次。**主動權一直在你手裏**，AI 只是個"高級回答機器"。

**Claude Code 的工作方式**：你下達一個目標 → cc 自己拆解步驟 → 自己調用工具 → 看結果 → 決定下一步 → 再調用工具 → ……一直循環到任務完成。**主動權交給了 AI**。這個不斷"思考-行動-觀察-再思考"的循環，就叫 **LLM Loop**。

*图：LLM Loop —— Claude Code 的自主循环机制*

這就是爲什麼我們把 cc 稱爲 **Agent（智能體）** 而不是 Chatbot（聊天機器人）。也正因爲如此：

- 你可以給 cc 一個**模糊的高層目標**（如"幫我做一個番茄鍾"），它會自己一步步推進

- cc 在執行過程中**會自我糾錯**——某條命令報錯了，它會讀錯誤信息，調整方案再試

- 注意： cc **不一定每一步都問你**，所以在它"撒丫子跑"之前，你要給好上下文（CLAUDE.md、Skills、計劃等）

關鍵認知：cc 是一整套"程序+模型"的組合，底層的大模型其實可以替換——這也是爲什麼後面我們能用 DeepSeek、千問、GLM 等國產模型來驅動 cc。是這套 Loop 機制 + Harness 工程，讓 cc 比單純的對話式 AI 強大得多。

很多人對 Claude Code 有個誤解：以爲它會像其他 AI 工具一樣，需要先把項目代碼上傳到服務器建立“索引”。**事實上，Claude Code 不需要任何預先的代碼庫索引。**

官方把這種機制叫做 **Agentic Search（智能體式檢索）**，它的工作方式和**一個人類工程師冷啓動一個項目完全一樣**：

*圖：Agentic Search——像人一樣按需讀取代碼庫*

**與傳統 RAG/向量檢索的本質區別：**

關鍵意義：這意味着 Claude Code天生適合活躍代碼庫——它不依賴一份可能過期的預建索引，也不需要 IT 部門部署向量數據庫。但它讀取到的相關文件內容仍會作爲上下文發送給模型服務，所以處理敏感代碼時依然要遵守公司安全規範。

官方反覆強調一個觀點：**決定 Claude Code 表現的，不只是背後的模型，還有圍繞模型搭建的“腳手架 Harness”。**

理解方式：模型能力決定下限，項目上下文、工具權限、規則文件和工作流決定上限。實際生產中，圍繞模型搭建的工具生態會顯著影響最終表現。

選擇AI編程方案時，**工具和模型要一起考慮**——就像買車不能只看車架不看發動機。以下是根據不同預算和需求，經過大量實戰驗證的最優組合：

**性能组：Claude Code + Claude 模型**

這是目前綜合體驗最好的組合。Claude Code 的 Agent 能力 + Claude 模型的代碼理解能力，兩者深度適配。缺點是需要國際支付方式，且按量付費需要留意用量。

適合：有國際信用卡的學生/開發者，對代碼質量要求高。

**免费组：Codex CLI + ChatGPT/Codex 账号额度**

Codex CLI 可以通過 ChatGPT 賬號或 API Key 使用，具體額度取決於你的賬號套餐和官方策略。Codex CLI 開源透明，沙箱和審批機制清晰，適合低成本入門。缺點是不同地區、套餐和時間段的可用額度可能變化。

適合：想零成本入門 AI 編程的新手。

**性价比组：Claude Code + GLM Coding Plan**

智譜的 Anthropic 兼容接口做得比較完整，三個模型槽位（Opus/Sonnet/Haiku）可自動映射到 GLM 系列，免去手動配置的麻煩。套餐價格、額度和高峯期倍率會調整，正式購買前以智譜官網爲準。

適合：國內大多數開發者，不想折騰配置、追求穩定省心。

**极客组：Claude Code + DeepSeek V4 Pro**

DeepSeek 官方提供了 Claude Code 的 Anthropic 兼容接入方式，當前文檔示例使用 deepseek-v4-pro[1m]，並可把輕量任務映射到 deepseek-v4-flash。價格通常較低，但需要自己配置端點、Key 和環境變量，並按官方文檔覈對最新模型名。

適合：動手能力強、追求極致性價比的學生和個人開發者。

選型建議：新手推薦從性價比組（GLM Coding Plan）或免費組（Codex CLI）開始，零風險體驗。等熟悉了再升級到性能組。

**雙工具流（推薦）**：Claude Code（後端/架構/數據庫）+ Cursor（前端/UI細節）

**国内友好组合**：Trae + DeepSeek API

全程無需代理，Trae 的 IDE 體驗接近 Cursor，DeepSeek 提供高性價比的模型能力。

中轉服務本質上就是一個"代理"，幫你把請求轉發給 Anthropic，再把結果返回。你在 Claude Code 中需要做的就是把"目的地地址"從 Anthropic 官方改成中轉服務。

**Step 1：獲取中轉服務的信息**

在 0.3.2 節你已經註冊了中轉服務，現在需要兩個關鍵信息：

API Base URL：中轉服務的地址（每個服務商不同）
API Key：在中轉服務上創建的 Key（不是 Anthropic 官方的 Key）

**以 OpenRouter 为例：**

API Base URL: https://openrouter.ai/api/v1
API Key: sk-or-v1-你的OpenRouter-Key

**Step 2：設置環境變量**

Claude Code 通过 ANTHROPIC_BASE_URL 环境变量来指定API地址。

**Windows 用户（PowerShell）：**

# 临时设置（当前窗口有效）
$env:ANTHROPIC_BASE_URL = "https://openrouter.ai/api/v1"
$env:ANTHROPIC_API_KEY = "sk-or-v1-你的中转服务Key"
# 永久设置（推荐）
[System.Environment]::SetEnvironmentVariable("ANTHROPIC_BASE_URL", "https://openrouter.ai/api/v1", "User")
[System.Environment]::SetEnvironmentVariable("ANTHROPIC_API_KEY", "sk-or-v1-你的中转服务Key", "User")

**macOS / Linux 用户：**

# 编辑 shell 配置文件
$ vim ~/.zshrc  # 或你喜欢的编辑器
# 在文件末尾添加以下两行：

CLAUDE.md 是 Claude Code 中**最重要的配置文件之一**。它就像你給新來的實習生寫的"項目入職手冊" —— 告訴AI這個項目的背景、技術棧、編碼規範和當前進度。

**兩個官方推薦的創建姿勢：**

- `/init`創建項目級- `claude`後輸入- `/init`，cc 會自動掃描項目並生成一份 CLAUDE.md 初稿，你再調整。官方建議：- **項目有一定規模再**（太空它掃不出什麼東西）。- `/init`效果更好

- `/memory`編輯全局級- `/memory`選擇“全局 CLAUDE.md”，會用默認編輯器打開該文件供你修改。- **修改全局後需重啓 cc 才生效。**

**最佳實踐：**

- **保持更新**：項目級 CLAUDE.md 應該是動態的——項目加了功能、踩了坑，就同步更新

- **足夠具體**：技術棧寫明具體版本號，目錄結構要與實際一致

- **寫明禁忌**：把"不要做什麼"也寫清楚（如"不要修改數據庫遷移文件"）

- **適度簡潔**：不要寫成論文，AI需要的是關鍵信息而非贅述

- **只放"頂層不變原則"**：隨着實踐你會發現，CLAUDE.md 不該塞太多。卡帕西發佈的「claude.skills」幾百行通用規則就能拿 10 萬+ Star——寫點 “頂層、不變、須嚴守" 的東西就夠了。`https://github.com/multica-ai/andrej-karpathy-skills`

如果說 CLAUDE.md 是**你主動立下的規矩**，那 Auto Memory 就是 **cc 在幹活過程中默默記下的設計筆記**。你沒顯式寫進 CLAUDE.md 的習慣、反饋、項目踩坑，會被一個後臺 agent 靜靜記錄。

**Auto Memory 會記哪幾類東西：**

**使用手感（重要）：**

- 它只在當前項目生效（文件存在項目目錄下），換項目需重新積累

- 啓用後 cc 不會每次都把所有記憶全部加載進上下文，只會讀一份 `memory.md`索引——**遇到具體問題纔去讀對應的子文件**，佔 token 很少

- 隨時可以用快捷鍵 `Ctrl+O`在會話中查看實際被調用過的記憶內容

- 記錯了就跟它說：“忘掉剛剛說的不喜歡深色主題”，它會自己刪掉

提示：

一句話區分 CLAUDE.md vs Auto Memory：CLAUDE.md 是第一優先級、全量注入的明規則；Auto Memory 是第二優先級、按需注入的隱規則。兩者配合，cc 越用越懂你。

除了上面兩層，你還可以仿照 Skill 的"**漸進式披露**"機制爲 cc 手動打造一套**專項參考文檔**。

**應用場景**：某些東西不適合全部塞進 CLAUDE.md（太長、太專門），但 cc 需要的時候必須能查到。比如做個產品，你希望：

- **品牌視覺規範**：顏色、字體、間距 →- `docs/brand-visual.md`

- **产品文本风格**：语调、术语表 →- `docs/copywriting-style.md`

- **API 约定**：请求响应格式、错误码 →- `docs/api-conventions.md`

然後在 CLAUDE.md 里加上指引：

## 外部參考文檔
- 修改前端視覺、調顏色、調間距時 → 必讀 `docs/brand-visual.md`
- 寫產品文案、按鈕文字、提示語時 → 必讀 `docs/copywriting-style.md`
- 寫 API 、定義返回格式時 → 必讀 `docs/api-conventions.md`

這樣 cc 只在"需要的時候"纔去讀完整文檔，既保證了準確性，又不佔多餘上下文。

Claude Code 的三層記憶體系：第一層 CLAUDE.md（你主動寫，全量加載）→ 第二層 Auto Memory（cc 自己記，按需讀取）→ 第三層自建參考文檔（你寫，cc 遇到對應任務纔讀）。

本質認知：agent 的所有"記憶"，本質上都是在合適的時候向大模型注入壓縮過的上下文。粗暴點說 —— 這些記憶機制本質上還是提示詞工程，只不過由 cc 幫你組織了層次。

<code>/compact</code> —— 上下文压缩（必须掌握）

這是解決”用久了 AI 變笨”的核心武器。用 cc 一段時間會發現回答變慢、質量下降——這是因爲你聊的每句話、它讀的每個文件、它執行的每個操作的結果，都在擠佔上下文空間。模型上下文雖然有 200K，但實際有效比例只有 60%-80%，且會隨上下文增多能力下降。腦子裏塞多了東西，它就容易把握不住重點。

心法：寧可”多/clear幾次重新介紹背景”，也不要”一直聊一直聊”。每個/clear都是給 AI 一次重新聚焦的機會。

<code>/rewind</code> —— “后悔药”（双击 ESC 快捷启动）

注意：

默認的 Claude Code 是什麼都能做、什麼都不知道的通用助手。通用不是好事。

**allow 白名單**：日常安全操作，不應該每次都問——讀文件、寫源碼、跑測試、git 日常命令。

配完之後：日常操作零彈窗，危險操作自動封堵。

注意：allow 按你的工具鏈改——用 yarn 就加Bash(yarn *)，用 bun 就加Bash(bun *)。deny 那幾行建議原樣留着，它們是安全底線。

**Q1：安装时报 ENOENT: no such file or directory**

- **原因**：npm 緩存損壞

- **解决**：运行- `npm cache clean --force`，然后重新安装

**Q2：安裝成功但 claude 命令找不到**

- **原因**：npm 全局安裝路徑未加入系統 PATH

- **解決**：運行- `npm config get prefix`，將輸出的路徑加入系統 PATH 環境變量

**Q3：Windows 上報"無法加載文件，因爲在此係統上禁止運行腳本"**

- **原因**：PowerShell 執行策略限制

- **解决**：以管理员身份打开 PowerShell，运行- `Set-ExecutionPolicy RemoteSigned`

**Q4：启动后提示 Invalid API Key**

- **原因**：API Key 配置錯誤或過期

- **解决**：检查环境变量- `ANTHROPIC_API_KEY`是否正确设置。用- `echo $ANTHROPIC_API_KEY`（macOS）或- `echo $env:ANTHROPIC_API_KEY`（PowerShell）验证

import sqlite3
import os
from finance.models import DEFAULT_CATEGORIES, Record
DB_DIR = os.path.join(os.path.expanduser("~"), ".finance-cli")
DB_PATH = os.path.join(DB_DIR, "data.db")
def _get_conn():
   """获取数据库连接"""
   os.makedirs(DB_DIR, exist_ok=True)
   conn = sqlite3.connect(DB_PATH)
   conn.row_factory = sqlite3.Row  # 让查询结果可以像字典一样取值
   return conn
def init_db():
   """初始化数据库：建表 + 写入默认分类"""
   conn = _get_conn()
   cursor = conn.cursor()
   cursor.execute("""
      CREATE TABLE IF NOT EXISTS categories (
         id INTEGER PRIMARY KEY AUTOINCREMENT,
         name TEXT NOT NULL UNIQUE
      )
   """)
   cursor.execute("""
      CREATE TABLE IF NOT EXISTS records (
         id INTEGER PRIMARY KEY AUTOINCREMENT,
         amount REAL NOT NULL,
         category_id INTEGER NOT NULL,
         record_date TEXT NOT NULL,
         note TEXT DEFAULT '',
         created_at TEXT DEFAULT (datetime('now', 'localtime')),
         FOREIGN KEY (category_id) REFERENCES categories(id)
      )
   """)
   for cat_name in DEFAULT_CATEGORIES:
      cursor.execute(
         "INSERT OR IGNORE INTO categories (name) VALUES (?)", (cat_name,)
      )
   conn.commit()
   conn.close()
def add_record(amount: float, category_name: str, date: str, note: str = "") -> int:
   """添加一笔账目，返回新记录的 ID"""
   conn = _get_conn()
   cursor = conn.cursor()
   # 先查分类 ID
   cursor.execute("SELECT id FROM categories WHERE name = ?", (category_name,))
   row = cursor.fetchone()
   if row is None:
      conn.close()
      raise ValueError(f"未知分类：{category_name}。可用分类：{', '.join(DEFAULT_CATEGORIES)}")
   category_id = row["id"]
   cursor.execute(
      "INSERT INTO records (amount, category_id, record_date, note) VALUES (?, ?, ?, ?)",
      (amount, category_id, date, note)
   )
   new_id = cursor.lastrowid
   conn.commit()
   conn.close()
   return new_id

還記得 Part 4 開頭的 Harness 七層框架嗎？Skill 是其中的**第三層**，也是最重要的一層：它把專業知識變成 cc 在需要時按需調用的"外接大腦"。大模型再聰明，也不可能把所有領域的最佳實踐都塞進訓練數據。但有了 Skill，你可以——這正是它如此重要的原因。

**Skill（技能）** 是一個**封裝了特定能力的可複用指令集**。

打個比方：你每次做一道菜，都要從頭回憶配料和步驟，很容易忘這忘那。但如果你把菜譜寫下來，下次照着做就行了，還能分享給別人。Skill 就是給AI寫的"菜譜" —— 把一個複雜的任務標準化、流程化，讓AI每次都能按照固定的高質量標準執行。

**Skill vs 单次 Prompt：**

- **一致性**：確保AI每次執行都遵循相同標準（不會這次用Tab縮進，下次用空格）

- **效率**：複雜流程一鍵觸發，無需每次重寫Prompt

- **可複用**：跨項目、跨團隊共享最佳實踐

- **可迭代**：持續優化和升級，越用越好

很多人以爲 Skill 就是一個 Markdown 文件，其實不是。**一個完整的 Skill 是一個目錄**，可以包含多種類型的文件，就像一個"能力包"。

打個比方：如果把 Skill 比作一本食譜，那麼：

- **SKILL.md**就是食譜本身（菜名、步驟、注意事項）

- **scripts/**就是配套的廚房小工具（削皮刀、量杯 —— 封裝好的輔助腳本）

- **resources/**就是附贈的食材包和調料配比表（模板、示例數據、配置）

- **references/**就是食譜末尾的"參考書目"（營養學標準、食品安全規範 —— AI 可隨時查閱的參考資料）

**標準 Skill 目錄結構：**

skill-xxx/               # Skill 根目录（命名规范：小写+短横线）
├── SKILL.md              # 核心：技能描述文件（必选）
├── scripts/              # 辅助脚本目录（可选）
│   ├── helper.py          # Python 辅助脚本
│   └── utils.js           # JavaScript 工具函数
├── resources/            # 配套资源目录（可选）
│   ├── template/          # 模板文件（如代码模板、报告模板）
│   ├── examples/          # 示例文件（如输入/输出示例数据）
│   └── config/            # 配置文件（如规则定义、默认参数）
├── references/            # 参考文档目录（可选）
│   ├── best-practices.md    # 最佳实践文档
│   ├── api-docs.md         # API 参考文档
│   └── standards.md        # 行业/团队编码规范
└── requirements.txt        # 依赖声明（可选，列出脚本需要的第三方包）

提示：Skill 的核心是SKILL.md，其餘文件均爲輔助。如果你的 Skill 只需要一份指令說明，只放一個SKILL.md就夠了。但當 Skill 涉及複雜邏輯（如數據處理、格式轉換）時，配上scripts/、resources/和references/會大幅提升 Skill 的能力和可維護性。

**各組成部分詳解：**

**1. SKILL.md（必選）—— 技能的"說明書"**

這是 Skill 的核心載體。它包含兩部分：頭部的**元數據（Frontmatter） 和正文的具體指令**。

---
# 元數據（Frontmatter，YAML 格式）
name: react-component-generator   # 技能名稱（唯一標識）
version: 1.0                  # 技能版本
description: 根據需求生成符合項目規範的 React 組件文件集  # 技能簡介
trigger: ["創建組件", "新建React組件", "生成組件"]      # 觸發關鍵詞
tools: ["typescript", "react"]    # 依賴工具
author: your-name              # 技能作者
---
# React 組件生成器
## 執行步驟
1. 確認組件名稱和功能需求
2. 在 src/components/{componentName}/ 目錄下創建文件
3. 按照 resources/template/ 中的模板生成代碼
4. 運行 scripts/validate.js 驗證組件結構
## 輸出規範
- 所有文件創建完成後，報告創建的文件列表
- 給出組件的使用示例代碼
## 錯誤處理
- 如果目錄已存在，提示用戶確認是否覆蓋
- 如果缺少依賴包，提示安裝命令
## 示例
給一個完整的輸入→輸出示例。

注意：Frontmatter（元數據）是可選的，很多簡單的 Skill 可以省略它。但如果你的 Skill 需要被 Agent 系統自動發現和匹配，Frontmatter 中的trigger和description就非常重要 —— Agent 啓動時只讀取元數據，只有當用戶任務匹配觸發條件時，纔會加載完整指令。這種"漸進式披露"的設計可以節省上下文窗口空間。

**2. scripts/（可选）—— 辅助脚本**

當 Skill 需要執行復雜邏輯時（如數據預處理、文件批量操作、格式驗證），把這些邏輯封裝到腳本中比寫在 SKILL.md 裏更清晰：

# scripts/helper.py —— 辅助脚本示例
def fill_missing_value(df, column, strategy="mean"):
   """缺失值填充：把复杂逻辑封装成函数，SKILL.md 中只需调用即可"""
   if strategy == "mean":
      df[column].fillna(df[column].mean(), inplace=True)
   elif strategy == "empty":
      df[column].fillna("", inplace=True)
   return df

**3. resources/（可选）—— 配套资源**

- `template/`：存放代碼模板、文檔模板。例如 React 組件的標準結構模板，AI 可以基於模板快速生成代碼

- `examples/`：存放輸入/輸出示例。幫助 AI 理解"好的輸出長什麼樣"

- `config/`：存放配置文件（JSON/YAML），定義規則和參數，避免在 SKILL.md 中硬編碼

**4. references/（可选）—— 参考文档**

與 resources/ 不同，references/ 存放的不是"模板和配置"，而是 **AI 執行任務時可以查閱的知識性文檔**。比如：

- 編碼規範文檔（團隊的代碼風格指南）

- 安全審計標準（如 OWASP Top 10 清單）

- API 文檔（第三方服務的接口說明）

- 技術選型文檔（爲什麼用 A 不用 B 的決策記錄）

提示：references/和resources/的區別可以這樣理解 ——resources/是"生產材料"（模板、配置，直接用於生成輸出），references/是"參考書"（規範、標準、文檔，用於指導 AI 做出正確決策）。

**5. requirements.txt（可选）—— 依赖声明**

如果 scripts/ 中的腳本依賴第三方庫，在這裏聲明，方便部署時一鍵安裝：

pandas>=2.0.0
openpyxl>=3.1.0

- 你是否經常給AI寫**類似的Prompt**？→ 把它變成Skill

# React 组件生成器
## 触发条件
当用户要求创建新的 React 组件时使用此 Skill。
## 输入参数

const fs = require('fs');
const path = require('path');
function validateComponent(componentName) {
  const dir = path.join('src/components', componentName);
  const requiredFiles = ['index.tsx', 'types.ts'];
  const missing = [];
  requiredFiles.forEach(file => {
   if (!fs.existsSync(path.join(dir, file))) {
     missing.push(file);
   }
  });
  if (missing.length > 0) {
   console.error(` 组件 ${componentName} 缺少文件: ${missing.join(', ')}`);
   return false;
  }
  console.log(` 组件 ${componentName} 结构验证通过`);
  return true;
}

  description String     @default("")

  image      String     @default("")

  updatedAt   DateTime   @updatedAt
  cartItems   CartItem[]
  orderItems  OrderItem[]

**爲什麼下單要用數據庫事務？**

下單涉及三個操作：創建訂單 + 扣減庫存 + 清空購物車。這三個操作必須**要麼全做，要麼全不做**。如果創建了訂單但庫存扣減失敗了——用戶付了錢但庫存沒減，後續會超賣。

Prisma 的事務寫法：

const order = await prisma.$transaction(async (tx) => {
  // 1. 创建订单
  const newOrder = await tx.order.create({ data: { ... } });
  // 2. 扣减库存
  await tx.product.update({ where: { id }, data: { stock: { decrement: qty } } });
  // 3. 清空购物车
  await tx.cartItem.deleteMany({ where: { userId } });
  return newOrder;
});
// 如果任何一步失败，前面已执行的操作会自动回滚

前面幾部分我們重點學習了 Claude Code、Skills、MCP 和項目實戰。到了這一部分，我們換一個視角：用 OpenAI 的 Codex Desktop 來理解“桌面 Agent”到底能幫我們做什麼。

不要把 Codex 只理解成一個聊天窗口。它更像是運行在你電腦旁邊的執行型助手：能讀項目文件、調用終端、創建文檔、部署網站、連接外部服務，也能在你授權後完成一些跨軟件的操作。本章的重點不是把每個按鈕背下來，而是建立一套使用桌面 Agent 的工作習慣。

Codex 和 Claude Code 都屬於編程 Agent，但二者的側重點不完全一樣。Claude Code 以終端開發工作流起家，現在也有 IDE、Desktop 和 Web 入口，適合深度編碼、代碼審查、複雜重構；Codex Desktop 更強調圖形界面、本地項目管理、插件連接和日常自動化，對零基礎用戶更友好。

實際選型可以簡單一點：

- **剛入門，害怕終端**：優先從 Codex Desktop 開始。

- **已經在做工程項目**：Claude Code 和 Codex 可以一起用，一個偏深度開發，一個偏日常執行。

- **要處理文件、部署、安裝軟件、定時任務**：Codex Desktop 的桌面形態會更順手。

- **要做複雜代碼設計和長鏈路重構**：Claude Code 的工程化體驗通常更適合。

不必糾結“只能選誰”。Agent 工具之間不是互斥關係，關鍵是讓不同工具承擔它擅長的工作。

使用 Codex Desktop 需要 ChatGPT 賬號。免費賬號通常也可以體驗，但額度和能力會受限制；付費套餐的可用額度更多，適合高頻使用。具體價格、額度和模型名稱會隨官方策略變化，正式使用前以 OpenAI 頁面顯示爲準。

官方下載入口：

https://chatgpt.com/codex/download

下載完成後按安裝嚮導操作即可。首次啓動時，系統可能會詢問你的主要用途，例如日常辦公、學習或編程。這個選擇只是爲了初始化體驗，不需要太緊張，後面可以繼續調整。

Codex Desktop 的界面大體可以分成三塊：

第一次打開時，不需要把所有入口都研究一遍。建議先創建一個測試項目，用一個無風險的小任務熟悉流程，例如“幫我整理這個文件夾裏的 Markdown 文件標題”。桌面 Agent 的學習方式和傳統軟件不同，邊交代任務邊觀察它如何申請權限、如何拆解步驟，會比單純看菜單更快。

Codex 能讀寫本地文件、執行命令、連接插件，所以權限設置非常重要。它不是普通聊天機器人，而是可能真正改變你電腦文件狀態的執行工具。

新手建議從**自動審查模式**開始。它能減少頻繁彈窗，又不會完全放開高風險操作。對於公司代碼、客戶資料、生產配置等重要目錄，建議切換到更謹慎的模式，並在執行前要求 Codex 先給出計劃。

一個好習慣是：

先讓 Codex 說明它準備讀哪些文件、改哪些文件、執行哪些命令，再讓它動手。

Codex Desktop 的“項目”本質上對應你電腦上的一個文件夾。你選擇了某個文件夾，它才能在授權範圍內讀取、分析和修改裏面的內容。

進入項目工作區後，Codex 會把該文件夾視爲當前任務的主要上下文。它可以根據文件內容回答問題，也可以生成、移動、重命名或修改文件。

適合練習的任務包括：

- 批量整理課程資料文件名

- 把零散筆記合併成一份 Markdown 文檔

- 根據圖片或視頻素材生成清單

- 檢查項目目錄結構是否混亂

- 把已有文檔改寫成更適合發佈的版本

建議一開始用副本文件夾測試，確認行爲符合預期後，再讓 Codex 處理正式資料。

一個項目裏可以並行存在多個會話。你可以讓一個會話分析需求，讓另一個會話整理文檔，也可以把不同任務拆開，避免上下文互相干擾。

不過，並行不等於隨意。涉及同一批文件的任務，最好避免同時修改，否則容易出現覆蓋或衝突。更穩妥的做法是：一個會話負責寫，另一個會話只負責審查或給建議。

Codex 在項目中生成的 Markdown、圖片、PDF、PPT、代碼文件等，都會保存到你的本地文件夾裏。這一點很關鍵：它不是隻在聊天記錄裏給你一段文本，而是能把結果變成真實文件。

記住一句話：項目文件夾既是 Codex 的工作臺，也是它能看見的主要上下文。

Codex 可以在你授權後運行終端命令。對非技術用戶來說，這個能力尤其有價值，因爲很多開發環境配置、依賴安裝和部署操作，本質上都是一串命令。

例如你可以直接說：

請檢查我電腦上是否已經安裝 Node.js 和 Git。如果沒有，請給出安裝方案，確認後再執行。

相比直接說“幫我安裝”，更推薦加上“先檢查、再說明、確認後執行”。這樣你可以知道它準備做什麼，也能避免重複安裝或裝錯版本。

當你想安裝某個新工具、CLI 或 Agent 時，可以讓 Codex 先搜索官方文檔，再根據系統環境選擇安裝方式。例如：

幫我安裝 Hermes。請優先查官方倉庫或官方文檔，安裝後驗證版本，並告訴我啓動方式。

這個提示詞比單純一句“幫我裝一下”更可靠，因爲它明確要求了來源、驗證和交付結果。

對於不太知名的工具，最好把 GitHub 倉庫、官網文檔或安裝說明鏈接直接發給 Codex。這樣能減少它誤判同名項目的概率。

這是我要安裝的 Skill 倉庫鏈接：xxx。請閱讀 README，說明安裝位置和啓用方式，確認後再修改我的配置。

Codex 支持同時運行多個任務，但不建議把多個會寫同一目錄的任務同時放出去。可以並行的任務通常有這些：

- 一個任務安裝工具，另一個任務閱讀文檔

- 一個任務生成方案，另一個任務做資料整理

- 一個任務部署項目，另一個任務準備發佈文案

涉及同一份代碼或同一批文件時，先排隊，再執行，會更穩。

對話越長，模型需要攜帶的歷史信息越多。Codex 會用界面上的上下文指示器提醒你當前會話的佔用情況。當上下文接近上限時，它可能會自動壓縮歷史。

一個任務完成後，也可以主動讓它總結當前狀態：

請把當前項目進展、已修改文件、未完成事項和下一步建議壓縮成一份簡短摘要。

如果界面支持斜槓命令，也可以使用對應的壓縮或狀態命令。命令名稱可能會隨版本變化，按你當前客戶端顯示爲準。

額度通常可以在設置或狀態面板中查看。有些版本也支持在對話中通過狀態命令顯示當前會話的上下文、短週期額度和週期額度。

這裏要注意兩點：

- 複雜任務、長上下文、高速模式或高推理強度通常會消耗更多額度。

- 額度、刷新週期和套餐權益會變化，不建議在教程裏寫死太多數字。

日常文件整理、文檔改寫、簡單腳本，可以選擇默認或中等智能程度。涉及架構設計、複雜調試、跨文件重構時，再提高模型能力或推理強度。

一個實用原則是：

低風險任務追求速度，高風險任務追求可解釋和可確認。

Codex 的持久記憶可以分成兩類：一類是你主動寫下來的規則，另一類是系統自動總結的記憶。對教程學習者來說，最值得掌握的是 agents.md。

全局規則適合存放跨項目都適用的偏好，例如：

- 默認使用中文回答。
- 修改文件前先說明計劃。
- 重要操作前先列出影響範圍。
- 文檔改寫時保留原意，不製造未經確認的數據。

這些規則相當於你對 Codex 的長期工作約定。寫得越清楚，後續溝通成本越低。

項目級 agents.md 只服務當前項目，適合記錄技術棧、目錄結構、運行命令、測試方式、提交規範和禁止事項。

推薦在項目初步成型後，讓 Codex 讀取項目並生成一版草稿：

請閱讀當前項目結構，幫我生成一份項目級 agents.md。內容包括技術棧、常用命令、目錄說明、開發約束和測試要求。先給我預覽，不要直接寫入。

審覈通過後再寫入，比一開始憑空寫規則更貼合實際。

自動記憶適合作爲補充，不適合作爲唯一依賴。它可能會根據對話和任務自動總結信息，但觸發時機、記錄內容和召回方式不一定完全可控。

明確、穩定、重要的要求，仍然建議寫進 agents.md；臨時偏好和低風險背景，可以交給自動記憶輔助。

做複雜任務時，不要急着讓 Codex 直接寫文件。先進入計劃模式，讓它把需求拆開、列出步驟、說明風險，再決定是否執行。

你可以創建一個空項目，輸入：

我想做一個個人主頁。請先用計劃模式和我確認目標用戶、內容模塊、視覺風格、技術棧和部署方式，不要立刻寫代碼。

Codex 通常會追問你一些選擇題或開放問題，例如頁面內容、風格偏好、是否需要響應式、是否部署等。你確認方案後，它再開始初始化項目。

當 Codex 生成過程中方向不對，不需要等它全部做完再說。你可以直接補充：

當前風格太像營銷頁了，請改成更像作品集：少用大段宣傳語，多展示項目和聯繫方式。

很多時候，反饋會在下一輪工具調用前被加入上下文。這樣既保留了當前進度，也能及時修正方向。

如果前半段討論很有價值，但後面走偏了，可以從某條回覆 Fork 出一個新會話。它相當於從歷史分岔點重新開始，適合保留前面已經整理好的需求、方案和約束。

前端項目尤其適合使用內置預覽。你可以邊看頁面邊提出修改意見，有些版本還支持直接在預覽區域批註具體元素。

修改頁面時，儘量給 Codex 可執行的反饋：

- “按鈕太靠下，移動到首屏右上角”

- “移動端標題換行不好看，請調整字號和寬度”

- “這張圖與主題不符，請換成更貼近產品的圖片”

比起“優化一下”，這類反饋更容易得到穩定結果。

插件的作用，是讓 Codex 連接外部平臺和工具。不同版本、賬號和系統環境下可見插件可能不同，但常見方向大致包括部署、瀏覽器操作、代碼託管和外部應用連接。

以前端項目爲例，可以讓 Codex 先檢查構建命令，再連接部署平臺：

請檢查這個項目是否可以部署到 Netlify。先運行構建驗證，說明需要的環境變量和部署步驟，確認後再連接插件執行部署。

部署完成後，讓它返回訪問鏈接、構建日誌摘要和後續維護建議。

瀏覽器能力很適合做網頁驗證、後臺配置、資料蒐集和表單測試。但涉及賬號、付款、刪除、提交審批等敏感動作時，一定要求 Codex 停下來讓你確認。

可以加一條長期規則：

凡是涉及登錄、付款、刪除、發佈、提交表單的操作，必須先說明影響並等待我確認。

Skills 是把可複用流程沉澱下來的機制。前面我們已經詳細講過 Skills，在 Codex 中也可以用類似思路：把高頻、穩定、步驟清晰的任務封裝成技能。

適合做成 Skill 的任務包括：

- 每週生成技術資訊摘要

- 把課堂錄音整理成講義

- 檢查前端頁面的響應式問題

- 根據固定模板生成項目週報

- 按統一標準潤色課程文檔

創建 Skill 有兩種常用路徑。

**第一種：先描述目標，讓 Codex 幫你起草。**

我想創建一個“課程文檔潤色”Skill，用於把口語稿改成正式教程。請先和我確認輸入、輸出、規則和示例。

**第二種：先跑通一次真實任務，再沉澱。**

這種方式更推薦。因爲你已經知道流程中哪些步驟有效、哪些檢查必須保留，生成出來的 Skill 會更實用。

MCP 可以理解爲讓 Agent 連接外部數據源或工具服務的一種協議。對於初學者，不需要一開始就深入配置細節，先知道它解決什麼問題即可：當 Codex 需要訪問某個外部知識庫、數據庫、文檔系統或業務工具時，MCP 可能就是連接方式之一。

安裝 MCP 時建議遵循三個原則：

- 優先使用官方文檔或可信倉庫。

- 安裝前讓 Codex 說明配置文件位置、權限範圍和憑據保存方式。

- 安裝後用一個最小任務驗證是否真的連通。

示例提示詞：

請根據這個 MCP 官方文檔幫我完成配置。先說明它會訪問哪些數據、需要哪些密鑰、配置會寫到哪裏，等我確認後再執行。

自動化任務的價值，不是“定個鬧鐘讓 AI 說一句話”，而是把一套可重複流程交給 Agent 定時執行。

例如：

- 每週一彙總 GitHub 趨勢項目，生成中文推薦稿

- 每天早上檢查網站是否可訪問，並整理異常日誌

- 每三天彙總課程資料文件夾，生成新增內容清單

- 每週生成一次學習進度報告

你可以在自動化面板裏手動創建，通常需要填寫任務提示詞、觸發時間、模型和推理強度。

也可以直接在對話中描述：

請幫我創建一個自動化任務：每週一上午 9 點，讀取我的項目資料文件夾，生成一份本週新增資料摘要。創建前先展示任務內容、執行頻率和輸出格式。

自動化任務要特別注意邊界：它會在你不盯着屏幕的時候運行，所以提示詞必須寫清楚輸入來源、允許做什麼、禁止做什麼、結果發到哪裏。

部分版本支持通過 ChatGPT 手機 App 連接電腦上的 Codex，從手機端發起任務。這個能力適合臨時下發輕量任務，例如讓家裏電腦繼續整理資料、檢查項目狀態或生成草稿。

一般流程是：

- 手機 ChatGPT 和電腦 Codex 都更新到支持該功能的版本。

- 在手機端進入 Codex 入口。

- 按提示完成電腦端配對。

- 在電腦上確認允許該設備遠程控制。

遠程控制的便利性很高，但也意味着風險更高。建議只對可信設備開啓，並避免在手機端隨手發起刪除、部署、付款、批量修改等高影響操作。

這一部分我們從“會安裝”走到了“會安排任務”。Codex Desktop 的核心能力可以壓縮成這張表：

學完本章，請記住兩件事。

第一，Codex 不是“更會聊天的搜索框”，而是可以在你電腦上執行任務的工作代理。它能節省時間，也需要你設定邊界。

第二，使用 Agent 的能力不只在於會提問，更在於會管理：給清楚的目標，提供必要上下文，要求它先計劃，執行中及時糾偏，最後驗收結果。你越會管理任務，AI 編程工具越能發揮價值。
