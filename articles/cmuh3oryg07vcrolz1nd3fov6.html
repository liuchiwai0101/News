GitHub 如何通過遷移 CSS Modules 將 SSR 時間降低 55%

內容機器翻譯自第三方媒體（GitHub Blog），僅供參考，以原文為準。

AI 導讀

GitHub 工程師 Josh Black 覆盤將 Primer 設計系統從 CSS-in-JS 遷移到 CSS Modules 的歷程。截至 2024 年 12 月 Primer 全部組件遷移完成，服務端渲染時間減少 55%，組件初始化時間減少 25%。

推薦理由

原文給出大廠從 CSS-in-JS 遷移到 CSS Modules 的完整路徑和量化收益，可遷移到類似的前端架構改造。

正文

Primer Design System 支撐着如今你在 GitHub 上看到的許多體驗。從按鈕到橫幅再到麪包屑導航，這些基礎組件必須在各種場景下都具備可訪問性、靈活性和高性能。

早在 2023 年，某些頁面上的組件數量開始激增。這給我們現有的 CSS-in-JS 方案帶來了若干與性能相關的挑戰：

  • 由於樣式在客户端初始化，初始頁面加載耗時更長
  • 隨着樣式收集從客户端轉移，服務端渲染性能下降
  • 隨着頁面上組件數量的增長，樣式更新逐漸失控

很明顯，Primer 團隊需要從根源上解決這個問題。我們需要找到一種替代方案，徹底避免當前方案所面臨的客户端和服務端開銷。最重要的是，我們選擇的任何替代方案都必須以在遷移期間不會對 GitHub 造成任何破壞的方式運作。

引入 CSS（Modules）

Primer 團隊找到了一個滿足我們所有標準的解決方案：CSS Modules。這種格式讓我們能夠做我們最喜歡的事情之一：編寫並使用原生 CSS 特性，同時仍然保留我們從 CSS-in-JS 中所期望的一定程度的同置與封裝。

使用 CSS Modules，樣式會與組件的 JavaScript 源碼一起寫在同一個 CSS 文件中。它還允許我們默認將所有類名視為局部作用域，從而避免全局選擇器可能帶來的一些衝突和難題。這種形式也消除了對任何客户端或服務端運行時行為的需求。相反，樣式會被彙總進 CSS 樣式表，作為頁面 HTML 的一部分一併發送。

然而，這一方案與我們當時採用的 CSS-in-JS 方案截然不同。這一變更需要更新每一個 Primer 組件，以及 GitHub 中每一個使用該技術編寫的組件。所幸，設計系統正是大規模推行這類變更的完美載體。

逐步邁向 CSS Modules

轉向 CSS Modules 的形勢已經明朗。Primer 團隊需要為其每個組件交付更新，將它們從 CSS-in-JS 遷移到 CSS Modules。與此同時，我們對這些組件所做的更新不能破壞 GitHub 中的任何使用。最後，我們用於 CSS-in-JS 的底層技術也必須繼續對 GitHub 中當前正在使用它的任何組件保持可用。

在這些約束條件下，我們決定採用增量遷移策略，使我們能夠安全地發佈組件更新而不至於引發混亂。對於每個組件，我們的計劃是：

  • 新增一個文件，將現有樣式轉換為 CSS Modules
  • 將該組件添加到一個功能開關中，用於在新舊樣式之間切換
  • 利用現有的視覺迴歸測試來驗證我們的 CSS-in-JS 方案與 CSS Modules 之間的快照是否完全一致
  • 逐步向我們的團隊、然後是 GitHub 員工、最後向所有 GitHub 用户推出該功能開關，以便在此過程中及時發現任何問題

這一流程形成了一個強大的反饋閉環，隨着 Primer 持續將這些變更交付到 GitHub，問題在流程早期就被標記出來。功能開關的使用讓我們能夠安全地完成這次遷移，同時為我們提供了關於 CSS Modules 性能收益的清晰信號。

到 2024 年 12 月，Primer 中的所有組件都已通過這一流程遷移到 CSS Modules。我們在各個方面都看到了性能提升，尤其是：

  • 頁面服務端渲染時間減少了 55%
  • 頁面上組件的初始化時間減少了 25%

在 Primer 中開展這項工作帶來了明顯的性能提升，於是我們開始思考，在 GitHub 的其他部分進行這些轉換是否也能獲得類似的性能收益。同樣地，我們還需要多久才能最終在全公司範圍內放棄對 CSS-in-JS 的支持？

在 GitHub 告別 CSS-in-JS

從 Primer 中移除我們的 CSS-in-JS 方案，最棘手的部分之一在於 sx prop 的使用。這個 prop 曾是為 Primer 組件設置樣式和進行自定義的方式。團隊可以提供一個內聯對象來自定義組件的方方面面。它代表了 CSS-in-JS 最好的一面，也代表了最糟的一面：

  • 出色的 TypeScript 支持，並與我們的 Design Tokens 集成
  • 與組件同處一地，因此一切都集中在一個地方
  • 由於用於 sx 的內聯對象具有動態特性，運行時開銷很高
  • 隨着頁面上使用 sx 的組件數量增長，擴展變得困難

因此，我們擺脱 CSS-in-JS 之旅的第一步，就是減少 sx 在 GitHub 各處的使用。這讓我們能夠立即提升性能，效果類似於我們遷移 Primer 組件時所獲得的收益。它也為我們從產品中徹底移除 CSS-in-JS 做好了完美鋪墊。

Primer 的雙重性

需要注意的是，雖然設計系統本身已正式停用，styled-components但 GitHub 代碼庫本身的大部分內容卻並非如此。由於sxprops 多年來一直是 GitHub 事實上的樣式標準，我們面臨着數千個sxprops 需要遷移，之後才能考慮將 GitHub 遷移到這套簡潔全新的@primer/react版本上，而該版本不再依賴styled-components.

那麼……我們是如何在完成如此龐大工作量的同時，還提升了信心並降低了風險？答案是：並非一蹴而就。

最初的 CSS 遷移比我們對外透露的要更微妙一些：除了將組件遷移到 CSS modules、通過功能開關在生產環境中測試並逐步灰度發佈之外，我們還在一個名為 @primer/styled-react 的傳遞性庫中創建了“包裝”組件。這個包的整個目的，是讓 sx 的用法能夠進入新遷移的組件中。這樣一來，GitHub UI 代碼庫中使用該 prop 的實例，可以通過 @primer/styled-react 導入同一個組件來繼續使用它們，與此同時，對於那些不需要該 prop 的場景，我們則通過直接從 @primer/react 導入獲得了性能收益。

Styled Box Zero

遷移過程的下一階段如下：

  • On a package-by-package basis:
    • 將所有 sx 用法翻譯為等效的 CSS modules 文件。這包括交叉引用（參見 遷移到 CSS 變量）
    • 將 @primer/styled-react 導入替換為 @primer/react 導入
    • 在預生產環境中測試
    • 部署

説來也巧，就在我們準備着手這項浩大工程之際，styled-components維護模式 被宣佈了，這進一步印證了我們正朝着正確的方向邁進。

這項工作於 2025 年 4 月啓動，待遷移的 sxprops 峯值約為 7,760 個；直到 2026 年 5 月我們才看到它最終落地。起初，我們內部一位出色的開發者 Ian Sanders 創建了一個 VS Code 插件，用於輔助逐個 prop 的遷移。我們還在內部開發了一個類似的 codemod，並用它來遷移 GitHub 代碼庫中的整個文件。這項工作雖然需要一些人工監督和仔細驗證，但大部分是自動化的。8 名工程師輪班工作，在 6 個月的時間裏遷移了 6,419 個 props，觀察到服務端渲染時間性能提升幅度從 1% 到某些頁面的 22% 不等。

在 GitHub 的另一側，Copilot 的能力正呈指數級增長。AI 變得越來越聰明、越來越強大；在這項工作仍在進行期間，我們發佈了 Copilot coding agent 和 Copilot code review。

等到我們重新拾起這項工作時，已經是 2026 年 4 月，局面已大不相同；我們得以在三週內將 sxprops 從 895 個降到 0 個，靠的是一名工程師組成的團隊、不屈不撓的決心，以及大量 Copilot 編程智能體。

主題之爭

這是個大日子：我們終於完成了sx那些橫亙在我們與徹底styled-components移除之間的遷移工作，歷經數年之久……我們終於可以清理掉這些依賴，轉向其他更令人興奮的工作了，對吧？錯！

GitHub 支持七種不同的主題，它們全都提供高對比度模式變體。而這一切的實現，靠的正是你猜到的那個東西——styled-components。在我們考慮移除這些依賴之前，首先需要把主題系統解耦。

現在，這件事並沒有聽起來那麼嚴重。我們的主題變量一直是通過 @primer/css 包在 CSS 中定義的，而且我們在 2025 年底遷移 @primer/react 時就已經為非樣式化的主題化做了前瞻性規劃。我們需要移除的是由 styled-components 啓用的 JavaScript 用法和工具函數。於是，我們又一次投入了工作。

到這一步你應該已經熟悉套路了：執行遷移、逐步推出、為一切加上功能開關。兩個月後，期間經歷了一些小波折，我們終於可以全面移除依賴了；我們甚至為此也加了功能開關。小心駛得萬年船。

結局好，一切都好

截至 2026 年 6 月，GitHub 已 100% 運行在 CSS modules 之上。我們設置的各項防護措施使我們能夠安全地推出重大架構變更、在生產環境中進行壓力測試、高效地捕獲錯誤、調整方向並修復問題，最終讓我們成功達成目標，並在此過程中實現了顯著的性能提升。

起初看似一次 CSS 遷移的工作，最終演變為對 GitHub 如何大規模地設計樣式、應用主題和交付 UI 的一次漸進式重新平台化。到最終，我們不僅從 dotcom 中移除了 sx、styled-components 和 styled-system，而且在整個過程中沒有讓 GitHub 出現故障。提升產品的性能、用户體驗和愉悦感，始終是 GitHub 全體成員最關注的事情。
