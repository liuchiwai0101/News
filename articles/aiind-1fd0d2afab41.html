正文

2026 年，智能體將在企業級應用中取得哪些實質性突破？ 點擊下載 《2026 年 AI 與數據發展預測》白皮書，獲悉專家一手前瞻，搶先擁抱新的工作方式！

過去幾年，企業 AI 技術棧已演變成一個高度複雜，卻又碎片化且難以管理的生態系統。如今，這一技術棧涵蓋了向量數據庫、監控系統、Pipeline 調優等各類組件，並通過編程 Agent、嵌入式 Agent，以及與企業系統對接的模型上下文協議（MCP）服務器相互連接。支撐這一切的模型組合也在不斷變化，幾乎每隔幾周就會更新一次。不同團隊按照各自的節奏引入技術棧中的不同組件，可能由此產生管理和治理缺口，進而影響安全性。

在這樣一個割裂的環境中，很少有企業能夠掌握足夠全面的上下文信息，準確回答貫穿各個層面的基本問題：我們正在調用哪些模型？誰在調用這些模型？它們正在執行什麼操作？相關成本又是多少？

面對這種情況，企業的本能反應往往是加強限制，但這並非可行的長期解決方案。限制員工使用 AI 的能力，只會促使他們轉向未經批准的 AI 工具，從而進一步放大風險。

這一缺口的根源並非工具問題，而是缺少一個關鍵層。現代 AI 技術棧需要一個控制節點，位於每個 AI 客户端與其所訪問的企業系統之間。Cortex AI Gateway（已進入公開預覽階段）通過充當這一集中式控制平面，為現代多元化基礎設施提供所需的統一可見性、治理能力和監督機制。在我們看來，現代企業的 AI 基礎設施技術棧必須具備以下六大要素：

目前，Cortex AI Gateway 已進入公開預覽階段。平台團隊可以通過統一入口授予模型及 MCP 服務器的訪問權限，對支出進行歸因和控制，並瞭解 AI 代表用户執行了哪些操作。應用團隊則可以通過單一端點進行開發。接下來，我們將逐一介紹它如何覆蓋技術棧的各個層面。

Cortex AI Gateway 是 Snowflake 面向企業 AI 基礎設施打造的集中式控制平面。它通過單一端點提供受治理的模型推理、動態模型路由、MCP 工具治理、可觀測性、安全護欄和成本控制能力，讓平台團隊能夠統一查看組織內所有 AI 客户端和 Agent 的運行情況。

統一且受治理的模型推理：讓 Agent 通過單一端點訪問模型

隨着 AI 技術棧不斷擴展，最先暴露的問題之一就是模型訪問路徑過多：一名工程師將編程 Agent 配置為連接某家模型提供商，平台團隊又將應用程序接入另一家，還有其他人通過腳本調用第三家。每條訪問路徑都有獨立的憑證、日誌和賬單。

Cortex AI Gateway 將這些訪問路徑整合為單一端點。它為 OpenAI、Grok、GLM、Gemini、Llama、Mistral 和 DeepSeek 模型實現了 Chat Completions API，併為 Claude 實現了 Messages API。這兩種協議已成為模型服務領域的主流標準。流式傳輸、工具調用、結構化輸出、Prompt 緩存、圖像輸入和推理等功能，都能以與原生接口相同的方式運行。因此，要讓現有客户端接入 Cortex AI Gateway，只需配置一個新的 base URL 和一個 token。對 OpenAI Responses API 的支持也即將推出。以下示例展示了使用 Cortex AI Gateway 配置 OpenCode 所需的全部設置：

為了進一步簡化編程 Agent 與 Cortex AI Gateway 的集成，Snowflake CLI 將能夠自動完成流量經由 Gateway 路由的相關配置。只需一條命令，即可從當前有效的 Snowflake 連接中讀取憑證，將其注入編程 Agent 的配置文件，並啓動 Agent，使其流量通過 Cortex AI Gateway 進行路由。例如，現在使用 Snowflake CLI 啓動 OpenCode，只需運行 snow ai opencode 即可。

Cortex AI Gateway 中的動態模型路由：為每項任務選擇合適的模型

大多數團隊習慣於使用單一前沿模型處理所有任務。這是一個合理的起點，但隨着應用規模擴大，成本也會變得高昂。Agent 執行的很多步驟實際上只是文件編輯、格式調整和信息查詢，成本更低的模型同樣能夠以相當的質量和準確性完成這些任務。

即將通過 Cortex AI Gateway 開放私有預覽的動態模型路由功能，能夠在 Agent 執行任務的每個步驟中，從可用模型裏選擇能夠可靠完成當前任務、且成本最低的模型。Snowflake 研究團隊對這一功能進行了微調，使低複雜度和重複性任務能夠交由高效模型處理，而需要深度推理的任務則交由前沿模型完成。在一項內部評估中，與僅使用前沿模型的方案相比，該功能在完成 dbt Pipeline 工作負載時，在質量相當的情況下，token 效率最高提升至 3 倍；在另一項獨立的編程測試中，工程團隊在保持 Pull Request 吞吐量不變的同時，將 token 使用量減少了約 25%。這些結果有望轉化為企業實際的成本節省。

動態路由與手動選擇模型遵循相同的治理規則。系統只會使用經過批准的模型，遵守現有的數據駐留設置，並記錄每一次路由決策，使合規團隊能夠查看具體由哪個模型處理了哪項請求。由於路由邏輯位於 Cortex AI Gateway，而非各個應用程序內部，因此 Snowflake 可以隨着模型價格和性能的變化不斷調整路由決策，無須修改 Agent 配置。

開源模型在這裏同樣發揮着重要作用。在使用 Snowflake CoCo 作為 Agent 測試框架的 ADE-bench 評測中，DeepSeek-V4-Flash 取得了 74.4% 的成績，超過了我們測試的領先專有模型。GLM-5.3 也即將進入私有預覽階段，而其前代模型 GLM-5.2 在 ADE-bench 評測中取得了 66% 的成績，同時也是該基準測試中 token 消耗量最低的模型，這正是高吞吐量工作負載所需要的特性。Snowflake 在其安全邊界內提供這些模型的服務，因此推理可以在受治理的數據附近執行，並受到現有 RBAC 和審計追蹤機制的統一管理。

一旦 Agent 能夠調用工具，它就成為了企業系統中的一個執行主體，而 MCP 讓這種能力的實現變得異常簡單。員工每安裝一個未經管理的 MCP 服務器，就相當於為生產系統增加了一條新的訪問路徑，而使用這條路徑的軟件會在運行時自行決定如何利用其獲得的訪問權限。這是一種影子 IT，只不過這些未經授權的軟件還能夠讀取生產數據庫，並修改企業 SaaS 系統中的記錄。

API Gateway 需要判斷的是：某個客户端是否有權訪問指定端點。工具網關則必須回答另一個問題：此時此刻，這個 Agent 是否有權代表該用户執行這次工具調用？

在 Snowflake 收購 Natoma 之後，Cortex AI Gateway 中的 Tools 功能為這一問題提供瞭解決方案。該功能目前處於私有預覽階段，內置了一個經過篩選的 MCP 服務器目錄，包含超過 100 個 MCP 服務器，並已為用户處理好各服務器的 OAuth 授權，有助於減少 MCP 服務器無序擴張的問題。

管理員可以選擇啓用特定工具、所有當前已發佈的工具，或所有當前及未來發布的工具。未啓用的工具對客户端不可見，也無法被調用。因此，被禁止的能力通常根本不會向客户端暴露，而非等到實際調用時才返回失敗。系統還可以記錄工具調用日誌，將同一個 Prompt 觸發的完整 Agent 執行過程串聯為連續的操作序列。工具調用還會將 Span 寫入與模型推理相同的 Trace 表，從而使單條 Trace 同時覆蓋推理過程和實際操作。

這套審計追蹤機制能夠幫助防範針對工具層的特定攻擊。工具投毒（Tool Poisoning）、工具遮蔽（Tool Shadowing）以及 Rug Pull 攻擊，都可能在終端用户毫無察覺的情況下發生。例如，在 Rug Pull 攻擊中，已經獲得批准的服務器可能悄悄將工具定義更新為惡意內容，而客户端會自動獲取這些變更。此類攻擊在設計上很難被終端用户發現，但對於記錄每項工具定義和每次調用的系統而言，它們並非不可見。

當企業被問及有哪些 Agent 正在訪問其系統時，大多數情況下，能夠給出的真實答案往往來自一份已經過時的 Agent 清單表格。我們開展的一項調查也印證了這一現象：約三分之一的受訪客户使用自行開發的內部儀錶板來實現 Agent 可觀測性。

雲安全聯盟（Cloud Security Alliance）的一項調查發現，在過去一年中，82% 的組織至少發現過一個此前不為安全或 IT 團隊所知的 AI Agent 或自主工作流。此外，根據《2026 年數據泄露成本報告》，影子 AI 使用率較高的組織平均數據泄露成本達到 539 萬美元，而在發生數據泄露的組織中，有 43% 受到影子 AI 事件的影響。
