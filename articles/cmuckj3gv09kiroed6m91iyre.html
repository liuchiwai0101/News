transformers 支持直接加載 GGUF 量化模型，本地推理性能接近 llama.cpp

內容機器翻譯自第三方媒體（Hugging Face），僅供參考，以原文為準。

AI 導讀

Hugging Face 宣佈 transformers 支持直接運行 GGUF 量化模型，通過 from_pretrained 傳入 gguf_file 即可加載 Hub 上的 GGUF checkpoint，並複用 ggml 的 Metal 內核。

推薦理由

官方宣佈 transformers 直接加載 GGUF，給出在 Apple Silicon 上接近 llama.cpp 的實測吞吐和加載方法，可幫助本地推理用户選擇工作流。

正文

我們正在為在 transformers 中高效運行 GGUF 模型添加支持

，這樣你就可以通過熟悉的 transformers API，使用適配你筆記本電腦內存大小的檢查點。從 Hub 上挑選一個 GGUF，用

from_pretrained

加載它，然後就可以在你自己的機器上開始生成了。

GGUF 由 llama.cpp 團隊開發，是一種廣泛用於本地推理的格式。該團隊還在 Hub 上的 ggml-org 下分享了量化檢查點。Unsloth、LM Studio Community 和 bartowski 等發佈者也提供了多種量化級別、開箱即用的 GGUF 檢查點，用户可以選擇適合自己機器的版本。GGUF 模型已被下載數百萬次。

我們也希望讓這些模型能更輕鬆地通過 transformers 在本地運行。兼容性只有在模型運行體驗良好時才有意義。為了讓性能接近 llama.cpp，我們通過 kernels 庫複用了其底層的 ggml 內核，並減少了 generate 中的開銷。我們最初的重點是在 Apple Silicon 上進行本地推理，從 Qwen3.5 架構開始。

什麼是 GGUF 文件格式？

GGUF 將模型權重和元數據（包括 tokenizer 信息和可選的聊天模板）打包在一個文件中。它支持不同的量化級別，讓你可以用一定的精度換取更小的內存佔用。諸如 Q4_K_M 之類的變體混合了張量精度，大部分權重使用 4-bit，同時對敏感張量保持更高精度。

以下是量化如何改變 Unsloth 的 Qwen3.5-4B 文件大小的：

GGUF 變體文件大小權衡
BF168.42 GB未量化參考版本
Q6_K3.53 GB精度高於更小的變體
Q5_K_M3.14 GB在體積與精度之間取得折中
Q4_K_M2.74 GB本地推理的實用起點

我們建議從 Q4_K_M 開始，如果你有更多可用內存，再嘗試 Q5_K_M 或 Q6_K。更激進的量化有助於讓更大的模型裝得下，但質量上的權衡取決於模型和任務。請在你實際希望模型完成的工作上對它進行評估。Hub 的 GGUF 文檔介紹了可用的量化類型。

使用 transformers 加載 GGUF

要開始使用，你需要：

  • 一台 Apple Silicon Mac。
  • 一個受已發佈的 ggml-quantization 內核構建 支持的 PyTorch 版本，通常是最近的兩個 PyTorch 版本。
  • 最新版本的 transformers（目前為 main 分支，直到下一個版本發佈）以及一個兼容版本的 kernels。
pip install -U "git+https://github.com/huggingface/transformers.git" kernels

要加載 GGUF 模型，請將其 Hub model_id 和文件名作為 gguf_file 傳給 from_pretrained。

無需額外配置：當權重以打包形式保留在 Metal 上時，transformers 會自動加載兼容的 ggml/Metal 層內核，並使用ggml-org/ggml-attn作為注意力實現。如果無法獲取該內核，模型會回退到"sdpa"並給出警告，而你始終可以通過顯式傳入"sdpa"來強制使用attn_implementation="sdpa"。有關更多加載選項，請參閲GGUF 文檔。

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "unsloth/Qwen3.5-4B-GGUF"
filename = "Qwen3.5-4B-Q4_K_M.gguf"

tokenizer = AutoTokenizer.from_pretrained(model_id, gguf_file=filename)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    gguf_file=filename
)

這是唯一一個 GGUF 專屬的步驟。之後的一切都是標準的 transformers API：

messages = [{"role": "user", "content": "Explain why the sky is blue in a few sentences."}]
inputs = tokenizer.apply_chat_template(
    messages,
    tokenize=True,
    add_generation_prompt=True,
    return_dict=True,
    return_tensors="pt",
).to(model.device)

with torch.inference_mode():
    outputs = model.generate(**inputs, max_new_tokens=256)

print(tokenizer.decode(outputs[0], skip_special_tokens=True))

如果沒有兼容的量化 kernel，加載器會回退到對模型進行反量化，並佔用更多內存。

用你偏好的接口來部署 GGUF

你也可以在 transformers serve 中使用同一個 checkpoint，它會暴露一個兼容 OpenAI 的 API：

pip install -U "transformers[serving] @ git+https://github.com/huggingface/transformers.git" kernels

transformers serve "unsloth/Qwen3.5-4B-GGUF:Qwen3.5-4B-Q4_K_M.gguf"

model 參數使用 <model_id>:<filename>.gguf：冒號之前是 Hub 倉庫（unsloth/Qwen3.5-4B-GGUF），冒號之後是要加載的文件（Qwen3.5-4B-Q4_K_M.gguf）。這樣可以從一個可能包含多個量化版本的倉庫中選定某個特定的量化。

對於聊天模板支持思考的模型，添加 --reasoning off 可跳過思考，添加 --reasoning on 可啓用思考。默認值 --reasoning auto 遵循聊天模板的默認設置。詳情請參閲 推理選項。

你可以通過添加一個自定義的兼容 OpenAI 的提供商來連接諸如 Jan 或 Pi 這樣的客户端，設置如下：

設置值
Base URLhttp://localhost:8000/v1
模型 IDunsloth/Qwen3.5-4B-GGUF:Qwen3.5-4B-Q4_K_M.gguf

transformers 在你的 Mac 上運行模型，而客户端提供對話界面。其他支持該 API 的客户端也可以使用同一個端點。

與 llama.cpp 進行基準對比

我們衡量本地推理性能的參照是 llama.cpp。下面的對比聚焦於三個 GGUF 檢查點：一個小型稠密模型、一個較大的稠密模型，以及一個混合專家模型。

llama.cpp 一列的數據來自 llama-bench 工具（構建版本 5f55650a7，發佈版 b10200，來自 ggml 0.18.0 的 Metal 後端），以 llama-bench -m <file> -p 0 -n 128 -r 3 方式運行，它報告的是 tg128：在 128 個解碼 token 上的 token 生成速率，取三次重複的平均值，且不包含提示詞處理。transformers 一列則是 generate 從 12 個 token 的提示詞生成同樣的 128 個 token，取三次預熱運行中的最佳值，並且包含預填充。

在 MacBook Pro M2 Max、32 GB 統一內存、macOS 26.6、PyTorch 2.12.1、kernels 0.17.0、接通電源的條件下測得。

基準測試腳本

import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id, filename = "unsloth/Qwen3.5-4B-GGUF", "Qwen3.5-4B-Q4_K_M.gguf"

model = AutoModelForCausalLM.from_pretrained(model_id, gguf_file=filename)
tokenizer = AutoTokenizer.from_pretrained(model_id, gguf_file=filename)
inputs = tokenizer("The capital of France is Paris. The capital of Germany is", return_tensors="pt")
inputs = inputs.to(model.device)


with torch.inference_mode():
    model.generate(**inputs, max_new_tokens=8, min_new_tokens=8, do_sample=False)  
    torch.mps.synchronize()
    for _ in range(3):
        time.sleep(90)  
        start = time.perf_counter()
        model.generate(**inputs, max_new_tokens=128, min_new_tokens=128, do_sample=False)
        torch.mps.synchronize()
        print(f"{128 / (time.perf_counter() - start):.1f} tok/s")

另一列的情況：

llama-bench -hf unsloth/Qwen3.5-4B-GGUF:Q4_K_M -p 0 -n 128 -r 3

在全部三個檢查點上，Transformers 都接近 llama.cpp。圖表使用的是上文所述的同一批測量數據；它並不意味着基準測試條件完全相同，因為 Transformers 的測量包含預填充，而 llama-bench 報告的是僅解碼吞吐量。

transformers 與 llama.cpp

當 GGML 和 llama.cpp 加入 Hugging Face 時，我們描述了它們互補的角色：llama.cpp 為本地推理提供基礎，而 transformers 為模型定義提供基礎。GGUF 支持讓這兩者更加緊密地結合在一起。

當你的優先目標是高效的本地推理時，llama.cpp 仍然是我們推薦的引擎。 其專用運行時、內存管理以及廣泛的硬件支持都是圍繞這一目標構建的。這一集成讓開發者可以方便地在 transformers 中使用相同的 GGUF 檢查點：

  • 在 Python 和 PyTorch 中試驗 GGUF。 使用 hook 檢查中間激活值，修改模型的前向傳播，或使用熟悉的 PyTorch 工具原型化自定義層。
  • 評估 GGUF 模型。 使用你現有的 transformers 評估工作流來衡量量化檢查點的質量。
  • 驗證 GGUF 轉換。 對於我們開發者而言，在 transformers 中加載原始檢查點及其 GGUF 轉換版本，可以更容易地檢查權重是否正確轉換，同時考慮量化誤差。
  • 嘗試新的解碼思路。 使用自定義 logits 處理器和停止條件配合 generate，或用 Python 編寫你自己的生成循環。
  • 從 GGUF 檢查點進行微調。 將權重反量化，然後繼續使用標準的 transformers 訓練工作流。

對於最後一種情況，請使用 GgufConfig(dequantize=True)：

import torch
from transformers import AutoModelForCausalLM, GgufConfig

model = AutoModelForCausalLM.from_pretrained(
    "unsloth/Qwen3.5-4B-GGUF",
    gguf_file="Qwen3.5-4B-Q4_K_M.gguf",
    quantization_config=GgufConfig(dequantize=True),
    dtype=torch.bfloat16,
)

超越 GGUF：為更多模型提供 ggml 內核

更大的機會在於將 ggml 的性能帶給 llama.cpp 不支持的模型。

transformers 已經提供了這些架構的 PyTorch 實現。藉助 PyTorch 中可用的 ggml 內核和量化方案，我們可以着手加速其支持的操作，而無需先在 llama.cpp 中實現整個模型。這對於新架構、研究模型以及可能永遠不會獲得專門 llama.cpp 實現的自定義變體尤其有用。

這一機會超越了 GGUF 格式本身。內核作用於張量；它並不要求整個模型都來自 GGUF 文件。相同的構建模塊可以集成到其他 transformers 模型和加載工作流中。這也為其他模態開闢了道路：計算機視覺模型、音頻模型和多模態模型可以複用兼容的注意力、歸一化和矩陣乘法內核，而無需先在 llama.cpp 中擁有完整實現。每個架構仍然需要集成和驗證；這裏的初始 GGUF 示例涵蓋的是文本生成。

使用 Python 和 PyTorch 實現快速本地推理

我們還希望展示，在將模型和生成循環都保留在 Python 中的情況下，我們能走多遠。有了合適的 kernel 和高效的生成循環，Python 和 PyTorch 能夠提供強勁的本地推理性能。kernel 負責處理繁重的計算，而生成循環則通過避免不必要的同步來讓 GPU 保持忙碌。

我們的重點是讓 eager 執行變得快速，而無需依賴 torch.compile。對於交互式使用，我們希望快速啓動並獲得穩定的 token 流，不出現編譯暫停，也不會在輸入形狀變化時重新編譯。這項工作的兩個主要組成部分是 kernel 和 generate 本身。

複用 ggml 的 Metal kernel

kernel 是在 GPU 上執行某種運算的小型程序。PyTorch 提供通用實現；專用 kernel 可以完成更少的工作、合併多個運算，或直接以存儲格式讀取量化權重。

kernels 庫讓我們能夠在 Hub 上分發 ggml Metal kernel 的兼容構建版本，並從 transformers 中調用它們。這將 ggml 的工作成果引入 PyTorch 模型，而無需用單獨的推理運行時來替換該模型。

Kernel它的作用
ggml-quantization為矩陣運算讀取打包的量化權重，包括 MoE 模型中被選中的專家。它避免了在每次解碼操作前展開整個權重矩陣。
ggml-norm融合歸一化操作，包括 Qwen3.5 和 Qwen3.8 使用的零中心 RMSNorm。
ggml-attn為提示詞處理和 token 解碼提供 ggml 的 Metal flash attention。
ggml-gated-delta-net加速 Qwen3.5 和 Qwen3.8 混合架構線性注意力層中使用的門控 delta 網絡。
topk為 MoE 模型中的每個 token 選擇專家，結合了 softmax 和 top-k 路由。這是我們自己的 Metal 實現。

前四個包構建在 ggml 的內核之上；top-k 內核解決了 MoE 路由中的另一個瓶頸。它們共同減少了每個生成 token 所需的 GPU 工作量。

為了展示層內核的貢獻，我們將相同的打包 GGUF 檢查點在啓用與不啓用這些內核的情況下進行了對比。兩種配置中量化內核都保持啓用：禁用它也會改變權重的表示方式，從而衡量的是另一種不同的權衡。

讓 CPU 與 GPU 協同工作

更快的內核只有在 GPU 有活可干時才有幫助。在生成過程中，CPU 負責調度 GPU 操作，並控制產生下一個 token 的循環。從 GPU 讀回結果會迫使 CPU 等待排隊的操作完成。即便每個 token 只重複一次很小的等待，也會明顯降低吞吐量。

在 generate 中，有兩項改動解決了這一問題，它們為所有 transformers 模型帶來了改進（而不僅僅是在運行 GGUF 文件時）：

  • 儘早移除不必要的注意力掩碼（#48814）。[ 當受支持的僅解碼器輸入沒有填充時，其全為 1 的填充掩碼可以在生成開始時移除。下游的注意力代碼不再需要反覆檢查該掩碼以判斷是否可以跳過它。因果注意力仍然得到保留。
  • 延遲停止檢查（#47975）。[ 在受支持的路徑上，generate 會異步複製停止決策，並在下一步消費它。CPU 可以在 GPU 運行的同時繼續調度工作。流式 token 也採用相同的方式，並且任何超出停止條件的額外步驟都會從結果中移除。

這些改動改進了模型周圍的生成循環，因此其價值不僅限於 GGUF。它們與內核層面的工作相輔相成：內核降低了單個運算的成本，而更少的同步點則讓 CPU 調度與 GPU 執行得以重疊。

這些測量保持所有層內核啓用；柱狀圖隔離出的僅是生成循環中的改動。

當前侷限與後續步驟

最初的目標是在 Apple Silicon 上實現單輪交互式對話。有幾點邊界需要留意：

  • 目前打包推理路徑僅支持 MPS。通過反量化導入 GGUF 仍是一個獨立選項；支持該文件格式並不意味着打包內核在每台設備上都可用。
  • 填充與批處理仍需完善。無填充輸入可受益於上文所述的掩碼優化。帶填充的批次無法走同樣的捷徑，性能可能更低。我們希望將這項工作擴展到 MPS 上的 generate_batch。
  • 架構覆蓋範圍有限。打包加載器目前覆蓋 Qwen3.5 的稠密與 MoE 架構，包括兼容的 Qwen3.8 檢查點。添加對其他架構的支持相對直接，我們將逐步擴大覆蓋範圍。

如果你有一個想在 transformers 中使用的 GGUF 模型，請提交一個 issue，附上 checkpoint 和你的使用場景。這將幫助我們優先支持大家正在本地運行的模型。
