推薦理由

官方介紹 Projects 的三項核心能力，並給出內部使用數據，讀者可據此判斷它適合什麼規模的工作。

正文

今天，我們在 Cursor 中推出 Projects。Projects 讓你能夠承接更大規模的工作，比如一個功能、一次遷移或一個完整的應用。它能在數月的工作中保持上下文，將任務委派給數千個子智能體，並在無需提示的情況下執行週期性工作。

今年 2 月，我們闡述了關於軟件開發第三紀元的願景，在那個紀元裏，成群的智能體將承接完整的工作。Projects 正是這一願景的具體實現。通過向上提升一層抽象，它讓開發者從管理智能體中解放出來，轉而直接指揮工作本身。

在 Cursor，我們已經使用 Projects 數月之久，完成了諸如運行涉及數百個 PR 的遷移、保持設計系統一致性，以及發佈 Projects 本身等工作。我們發現它是一個顯著的生產力倍增器：新用户合併的 PR 數量增加了 30%，而主要使用 Projects 的用户合併的 PR 數量則是六倍。

通過一個協調者指揮數千個智能體

你通過與 Project 的協調者智能體對話來管理它。協調者本身不編寫代碼，而是指揮其他編寫代碼的智能體。由於它負責委派而非執行，因此它永遠不會被阻塞，並且始終能對指令做出響應。

有三項核心能力讓 Projects 成為可能：

默認雲端運行，需要時本地運行。 一個 Project 運行在它自己的計算機上，因此合上你的筆記本電腦也不會讓它停止。這讓一個 Project 能夠並行運行比你的筆記本電腦所能支持的更多子智能體。當某些東西需要在你的機器上測試時，協調者會啓動一個本地智能體在那裏運行它。

共享上下文。 你不應該每次開始一項任務時都要重新讓一個智能體熟悉情況。每個 Project 都維護一組文件，這些文件會在其智能體所使用的每一台雲端和本地機器之間同步。智能體會添加研究內容和產物，以及它們對代碼庫的瞭解和你偏好的工作方式。例如，如果一個智能體弄清楚瞭如何測試某個服務，那麼未來每一個智能體都可以使用這些説明。這些上下文會隨着 Project 一起成長，使協調者隨時間推移變得更加高效。

訂閲。 協調者可以監視一個 Slack 頻道、按計劃運行，或跟蹤你所有的 PR，修復 CI，並在它們打開或合併時採取行動。這樣它就能根據檢測到的信號採取行動，而無需等待你來提示它。

我們在 Cursor 如何使用 Projects

三種模式涵蓋了我們工程師使用 Projects 所做的大部分事情。

功能開發

大多數工程師會為一個規模可觀的工作創建一個 Project。一個功能通常始於智能體研究系統，並將它們瞭解到的情況記錄為共享上下文。隨後，協調者會制定計劃，並派出智能體並行實現和測試該功能的不同部分。

隨着每一輪反饋，Project 會逐漸瞭解你的架構和偏好。當功能準備好試用時，協調者可以在你的電腦上啓動一個智能體並在本地運行它。功能發佈後，同一個 Project 可以監控日誌並處理 bug 報告，同時掌握最初決策背後的完整上下文。

遷移

Project 對於那種容易開始、卻難以完成的遷移尤其有用。在 Cursor，我們曾用它們來採用新框架，並在數百個 PR 中替換樣式系統。

你與協調者一起制定一套安全的方案，然後它會在整個代碼庫中逐步應用這套方案。早期，你會仔細審查每一個 PR。隨着修復逐漸站得住腳，你的審查會減少，而協調者會自行持續推進整個遷移。

園藝

Project 非常適合處理那些永遠不會真正結束的工作，比如維護代碼質量或監控迴歸。你可以讓協調者跟進新的 PR、監聽 Slack 中的 bug 報告，或按計劃運行，一旦有新工作出現它就會採取行動。

我們團隊的一位工程師就是這樣運行一個設計系統 Project 的。起初，這位工程師會審查每一處修復，並糾正它做錯的地方。現在，協調器會掃描每一個新的 PR，提取屬於設計系統的組件，並且每當同一個錯誤出現兩次時，就添加一條 lint 規則。這個 Project 有望每天處理 20 到 100 個 PR，因此協調器負責組織工作，而工程師則在需要關注的地方進行檢查。

開始使用 Projects

Projects 目前處於 beta 階段，從今天起向所有用户逐步推出。從左側導航欄啓動一個 Project，描述你想要構建的內容，協調器就會接手處理。它最適合那些會跨越單次對話而長期存在的工作，無論是一個包含多個 PR 的功能、一次遷移，還是你希望在你離開時也能處理的任務。
