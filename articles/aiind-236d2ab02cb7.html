AI Agent 越用越貴？如何藉助可觀測性平衡性能、質量與成本 ｜ 技術趨勢

正文

2026 年，智能體將在企業級應用中取得哪些實質性突破？ 點擊下載 《2026 年 AI 與數據發展預測》白皮書，獲悉專家一手前瞻，搶先擁抱新的工作方式！

AI 智能體正在改變可觀測性領域的格局，同時也帶來了響應質量和 AI 支出方面的新挑戰。即使智能體在執行請求時沒有出現錯誤，仍可能檢索到錯誤的信息，或生成質量不佳的響應。多步驟工作流可能涉及多次提示詞輸入、工具調用、信息檢索、重試和模型生成，因此很難確定質量從哪個環節開始下降，以及哪些因素推動了 Token 消耗和成本增長。此外，智能體產生的遙測數據比傳統應用請求更多，進一步增加了保留調查所需數據的成本和複雜性。為了控制成本，團隊往往不得不對遙測數據進行採樣或直接丟棄部分數據，導致最需要這些數據進行問題排查時，反而面臨信息缺失。

Snowflake Observe 即將推出的 Agent Observability（智能體可觀測性） 功能（即將開放私有預覽），旨在應對這些新興挑戰。通過追蹤交互過程，並將智能體行為與成本和質量關聯起來，該功能能夠幫助團隊監控、調試和改進 AI 智能體及大語言模型應用。

Agent Observability 將提供團隊調試智能體交互所需的埋點採集能力、指標、工具和用户界面，幫助團隊定位性能與質量問題、識別 AI 支出的驅動因素，並改善業務成果。Observe 原生構建於 Snowflake 之上，旨在以經濟高效的方式大規模保留和分析智能體遙測數據。團隊可以進一步將這些運行信號與 Snowflake 上的業務數據關聯起來，瞭解哪些智能體和工作流能夠產生切實的業務成果，改進表現不佳的部分，並將 AI 投資引導至最能創造價值的領域。

使用可選的兼容 OpenTelemetry 的 SDK 或現有埋點方式採集智能體數據： 使用遵循新興 OpenTelemetry （OTel）生成式 AI 語義約定的 SDK，捕獲提示詞、模型生成結果、檢索操作、工具調用、Token 使用量和會話 ID。該 SDK 已通過測試和驗證，支持 LangChain、Anthropic Agents SDK 和 OpenAI Agents SDK。團隊也可以自行對智能體進行埋點，或使用自定義框架，再通過 OTLP 端點將符合規範的追蹤數據發送至 Observe；

通過智能體探索器（Agent Explorer）搜索和調試對話： 跨追蹤記錄、會話和對話進行搜索，檢查智能體的行為、調用了哪些工具，以及故障或異常響應從何處開始出現；

監控性能、使用情況和成本： 分析從智能體追蹤數據中提取的指標，包括延遲、錯誤和成本；

對生產流量開展在線大語言模型裁判評估（LLM-as-judge）： 識別模型幻覺、安全護欄失效及低質量響應。將評估結果與底層跨度（Span）和追蹤記錄（Trace）關聯起來，持續監控質量變化；

追蹤離線評估結果： 將現有開發和測試工作流中的評估結果作為追蹤數據或指標發送至 Observe，以便進行可視化分析；

通過編程方式查詢遙測數據 ： 使用 API，從第三方智能體和自動化工作流中查詢追蹤記錄、指標和在線評估結果。

隨着企業部署更多智能體並擴展應用場景，理解這些智能體所需的遙測數據也在快速增長。這種增長源於智能體交互本身的結構特點。智能體追蹤記錄會記錄一次交互背後的完整步驟，包括模型調用、信息檢索、工具調用、重試和中間輸出。這意味着，與傳統應用的追蹤記錄相比，智能體追蹤記錄的持續時間更長、單個跨度包含的數據量更大，產生的跨度數量也更多。

這給許多團隊帶來了數據方面的挑戰。他們需要保留足夠的細節，以便重建重要的交互過程，但保留如此大量的遙測數據可能顯著增加可觀測性成本。一些團隊已經開始擔憂，持續增長的數據量將迫使他們對數據進行採樣或丟棄部分數據，從而在問題調查中留下信息缺口。

Observe 專為高吞吐量、複雜事件數據而構建，其底層架構使 Agent Observability 能夠保留和查詢高保真度的智能體遙測數據。

完整保留長時間運行的追蹤記錄和對話： Observe 將其 應用性能監控產品 採用的事件驅動方法擴展至智能體交互，將跨度作為事件存儲，並通過追蹤 ID 和對話 ID 進行查詢，使延遲到達的跨度和較長的時間間隔仍能納入完整的交互記錄；

查詢包含豐富上下文的大型跨度數據： Snowflake 原生支持複雜的半結構化事件數據，使 Observe 非常適合存儲和查詢提示詞、模型響應、檢索到的上下文，以及工具輸入和輸出，同時保留具有價值的細節信息；

以經濟高效的方式保留持續增長的遙測數據： 雲對象存儲旨在以更低的成本存儲詳細的智能體遙測數據，而 Observe 的遙測湖倉基礎架構（Telemetry Lakehouse Foundation）將存儲與計算分離，使團隊能夠保留更多數據，並根據搜索、分析和調試需求獨立擴展計算資源。

當智能體產生質量不佳的結果時，最終響應通常無法反映問題的全貌。工程師需要了解智能體接收到的上下文、執行模型調用、信息檢索、工具調用和重試的順序、每個步驟產生的中間輸出，以及工作流從哪個環節開始偏離預期結果。

客户向我們反饋，這些信息通常分散在應用程序、智能體框架、模型提供商和支持服務中。一些團隊在請求離開自身環境後便失去了可見性，導致用户對延遲、錯誤或異常行為的投訴，可能演變成耗時數小時甚至數天的問題調查。他們需要一種能夠在同一平台上追蹤和調試端到端智能體工作流的方法。

Observe 旨在捕獲這些交互背後的上下文，並按照對話、會話、追蹤記錄和單個跨度，組織成面向智能體的不同視圖。藉助智能體探索器（Agent Explorer），團隊可以利用已捕獲的屬性搜索智能體交互，並從對話逐層深入到底層追蹤記錄。他們能夠檢查提示詞、模型生成結果、檢索到的上下文、工具活動和重試過程，從而確定故障或異常響應最初出現的位置。

追蹤視圖重建模型調用和工具活動的執行順序及耗時，同時展示每個跨度中捕獲的提示詞、響應和屬性

延遲或錯誤的響應可能源於智能體工作流內部，例如模型處理、信息檢索、工具使用或編排環節，也可能由支持該工作流的應用程序、服務或基礎設施組件中的問題引起。Observe 的上下文圖譜（Context Graph）將智能體遙測數據與相關應用程序、服務、API、數據庫和基礎設施連接起來，幫助團隊關聯智能體跨度與上下游依賴關係，從而避免孤立地分析智能體工作流。

傳統可觀測性可以顯示某個請求是否快速且無錯誤地完成，卻無法判斷響應是否準確、相關或有用。對於非確定性系統，質量需要成為生產環境中可衡量的指標。

Observe 支持針對生產環境追蹤數據開展 在線大語言模型裁判評估 ，並將評估結果轉化為可持續監控的指標。由於每項評估結果都與底層交互相關聯，工程師能夠將質量問題追溯至提示詞、檢索到的上下文、工具選擇、支持服務或模型響應，並評估相關調整是否改善了生產環境中的實際表現。

評估視圖（Evaluations）追蹤準確性、相關性、幻覺率和指令遵循情況等生產環境質量指標，包括評估分數及其隨時間的變化
