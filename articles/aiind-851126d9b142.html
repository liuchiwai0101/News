給 AI 騰內存？Discord 拋棄Electron，省70%內存還秒開：Windows應用該跟進了

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

近日，Discord 聯合創始人兼 CTO Stanislav Vishnevskiy 在 X 上宣佈，Discord 正將客户端遷移至 Rust，桌面端將移除 Electron，移動端也將放棄 React Native。他展示的 Windows 任務管理器截圖顯示，新客户端以“Discord Phoenix”的名稱運行，內存佔用約 290.2MB。相比之下，現有 Windows 客户端在加入多個服務器後，內存佔用很容易達到 1GB 甚至更高。Vishnevskiy 隨後補充稱，截圖中的客户端同時運行着兩個賬户。

“新版 Discord 客户端內存佔用更低，這還只是其中一點。點擊操作流暢無比，我再也回不去了。看看啓動速度就知道了。”Vishnevskiy 展示了新版客户端的效果：

之後，有網友詢問網頁客户端的變化，Vishnevskiy 回答道，“我們會有一個 HTML 渲染器，但邏輯系統將採用 WASM 而非 JS。”

目前，Discord 尚未公佈正式上線時間，只表示希望儘快開放用户測試。

“恭喜你們終於發現 Vibe Coding 了。”有網友在 Vishnevskiy 帖子下評論，他沒有正面回應。不過，Discord 工程副總裁 Mark Smith 早在 3 月份就公開介紹過公司的內部 AI 開發平台 Vibeyard。按照他的説法，Discord 員工過去需要幾天甚至幾周才能交付一款內部應用，如今通過 Claude、CLAUDE.md、GitHub Actions 和 Cloudflare 基礎設施，約兩分鐘就能完成部署。

因此，對於這次重構，大部分人認為是 AI Coding, 不過官方沒有明確這一説法。

2025 年 10 月，Discord 針對 Windows 客户端啓動專項排查。到當年 12 月，團隊已經修復至少 9 項與內存泄漏、死鎖、緩衝區溢出等有關的問題，還增加了遙測和內存分析工具。

但問題並沒有徹底解決。Discord 披露，客户端正常使用時內存通常低於 1GB，部分用户卻會遭遇超過 4GB 的異常佔用。一些問題甚至涉及操作系統、驅動程序和硬件，團隊需要與外部合作伙伴共同定位。

經過一輪修復，Discord 將內存佔用的 P95 降低了約 5%，但對於長期運行、頻繁切換頻道和服務器的用户來説，這還遠遠不夠。

2025 年底，Discord 工程團隊在 Reddit 解釋了這項特殊的性能實驗。當 Windows 客户端內存佔用超過 4GB 時，程序可以在用户離開電腦後自行重啓，以緩解持續增長的內存壓力。為了避免幹擾用户，Discord 設置了嚴格的觸發條件：客户端必須運行至少一小時、用户處於離開狀態、沒有進行語音通話，每天也只能重啓一次。團隊希望藉此緩解部分用户的內存壓力，同時收集更多異常數據。

Discord 當時明確表示，這只是臨時措施，不是解決內存問題的長久之計。

當時，這項決定在社區引發了討論。一些用户認可 Discord 主動處理問題，但也有人認為，一款聊天軟件需要靠自動重啓控制內存，本身就足以説明客户端的性能問題已經相當嚴重。

隨後，Discord 繼續沿着原有技術路線優化。今年 9 月 8 日，Discord 公佈了一輪性能改進：桌面端升級至 Electron 42，調整部分調用方式後，CPU 佔用中位數下降約 17%，但內存佔用中位數反而增加約 4%。

移動端也進行了類似的優化。React Native 版本升級後，Android 和 iOS 應用的平均 CPU 佔用下降約 5%，平均啓動時間縮短約 5%。

這些數據説明，Discord 並非沒有嘗試過優化 Electron，也不是因為一次性能問題突然決定重寫客户端。相反，團隊已經持續投入大量工作，但在原有架構下，不同性能指標之間仍然存在取捨。

對於 Discord 這樣的產品，問題尤其敏感。它經常在用户運行遊戲、直播或共享屏幕時保持後台在線。聊天客户端多消耗的 CPU 和內存資源，可能直接擠佔遊戲和其他應用的運行空間。

Discord 拿出了一套更徹底的方案：放棄 Electron，用 Rust 重寫整個客户端。

Vishnevskiy 表示，公司早在 2018 年就開始採用 Rust。目前 Discord 的大量基礎設施、語音技術和部分現有客户端代碼已經使用 Rust 開發，將整個客户端遷移過去一直是團隊希望實現的目標。

早在 2020 年，Discord 還專門發表過一篇工程文章，解釋為什麼將一項核心後端服務從 Go 遷移至 Rust。這項服務名為 Read States，負責記錄用户讀過哪些頻道和消息。Discord 需要處理數十億條已讀狀態，服務每秒涉及大量緩存更新和數據庫寫入，屬於典型的高頻訪問場景。

當時的 Go 版本大多數時候運行很快，但幾乎每隔兩分鐘就會出現一次明顯的延遲峯值。工程團隊排查後發現，問題與垃圾回收器（GC）掃描大型 LRU 緩存有關。

Discord 嘗試過調整垃圾回收參數、縮小緩存規模等辦法，但縮小緩存又會導致更多數據需要從數據庫讀取，反而影響尾延遲。團隊最終決定用 Rust 重寫這項服務。

Rust 通過所有權機制在編譯階段管理內存訪問，不依賴傳統垃圾回收器。遷移後，緩存中的對象可以在不再使用時及時釋放，原有的週期性垃圾回收延遲問題也得到解決。Discord 還利用 Rust 版本進一步調整了緩存結構和容量，提高了服務整體性能。

不過，這次遷移並不是毫無代價。Discord 當時也提到，早期 Rust 異步編程生態還不夠成熟，開發團隊需要解決額外的技術問題。對於規模較大的系統，語言遷移需要考慮的遠不只是運行效率。
