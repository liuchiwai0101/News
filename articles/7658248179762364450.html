一個基於 Module Federation 的微前端框架，核心 500 行搞定沙箱隔離、CSS 作用域和生命週期管理。

爲什麼又要造一個微前端框架？

市面上的微前端方案已經不少了——qiankun、micro-app、wujie、Module Federation 原生方案……每個都有自己的設計哲學。但我們在實際生產項目中遇到了幾個痛點：

- **qiankun 的沙箱性能開銷**：每次子應用切換都要完整的- `activate`/- `deactivate`，對於需要頻繁切換的多標籤頁場景不夠絲滑

- **CSS 隔離方案的特異性污染**：Shadow DOM 太封閉，CSS Modules 需要改造代碼，BEM 命名約定靠人工遵守

- **子應用運行時"被污染"**：大多數方案要求子應用引入框架特定的 SDK，子應用不再純淨

- **路由衝突**：多個子應用共存時，- `popstate`事件會同時觸發所有活躍子應用的路由器

於是我們提取了生產環境中的核心模塊，做成了 PavilionMfe——**一個運行時只有 5 個包、子應用零依賴的微前端框架**。

設計原則很明確：**底層包零依賴**，上層按需組合。sandbox、bridge、tabs 三個包可以獨立使用，router 依賴它們提供完整的路由調度能力，runtime 是聚合層通過 MF Remote 確保單例，vite 僅構建時起作用。

核心設計：用 500 行代碼解決四個難題

1. JS 沙箱：棧式副作用追蹤

傳統的 Proxy 沙箱（如 qiankun）需要爲每個子應用創建獨立的 window 代理，開銷不小。PavilionMfe 的思路不同：**不隔離 window，而是追蹤和清理副作用**。

// 核心实现：模块级 activeStack + 一次性全局补丁
const activeStack: Sandbox[] = []
let globalsPatched = false
function patchGlobals(void {
  if (globalsPatched) return  // 只执行一次
  globalsPatched = true
  globalThis.setTimeout = ((handler, timeout, ...args) => {
    const id = origSetTimeout(handler, timeout, ...args)
    const active = activeStack[activeStack.length - 1]
    if (active) active._timeouts.add(id)  // 归属于栈顶沙箱
    return id
  }) as any
  // 同理拦截 setInterval / addEventListener / removeEventListener
}

核心思路：

- `activeStack`是模塊級的數組，記錄當前活躍的沙箱棧

- `patchGlobals()`- **只执行一次**，拦截- `setTimeout`/- `setInterval`/- `addEventListener`/- `removeEventListener`

- 每個副作用被分配到**棧頂沙箱**——天然支持多實例併發

- `deactivate()`时自动清理所有归属于该沙箱的 timers / listeners / globals

const sandbox = new Sandbox('my-app')
sandbox.activate()    // 推入栈顶，开始追踪
// ... 子应用运行，setTimeout/addEventListener 自动追踪
sandbox.deactivate()  // 弹出栈，清除 3 个 timer、2 个 interval、5 个 listener

2. CSS 作用域：`:where()` 的零特異性魔法

CSS 隔離最頭疼的是**特異性問題**。假設你給子應用加了一個 .app 前綴：

/* 加了前缀后特异性变了！ */
.pavilion-demo .card { color: red; }  /* 特异性 0,2,0 */
.card { color: blue; }               /* 特异性 0,1,0 — 被覆盖了 */

PavilionMfe 的解决方案是使用 :where() 伪类：

/* 输入 */
.card { color: red; }
@keyframes fadeIn { from { opacity: 0; } }
/* PostCSS 输出 — :where() 零特异性 */
:where(.pavilion-mfe-demo-app) .card { color: red; }
@keyframes pavilion-mfe-demo-app-fadeIn { from { opacity: 0; } }

:where() 的關鍵特性：**它包裹的選擇器不貢獻任何特異性**。所以：

- 作用域後的 `.card`仍然是`0,1,0`，不會覆蓋庫的默認樣式

- 子應用開發者不需要改變任何 CSS 書寫習慣

- `@keyframes`名稱也自動前綴化，防止動畫名衝突

PostCSS 插件實現只有 130 行，構建時運行，子應用零感知。

3. 路由隔離：popstate 代理攔截

多個子應用共存的場景下，瀏覽器前進/後退會觸發 **所有** 子應用的 popstate 監聽器。PavilionMfe 的做法是**代理攔截**：

// sandbox 的 addEventListener 补丁中
if (type === 'popstate' && routeMatcher) {
  const appCode = active.appCode
  const proxyHandler = (event: Event) => {
    // 只有当前子应用的路由匹配时，才触发原 handler
    if (routeMatcher(appCode, location.pathname)) {
      handler(event)
    } else {
      // 非活跃子应用：仅记录日志，不触发
      console.log('popstate-blocked', appCode, location.pathname)
    }
  }
  active._listeners.push({ target: globalThis, type, handler: proxyHandler })
  origAddEventListener(type, proxyHandler)
}

每個子應用的 popstate 監聽器被替換爲一個代理——只有當 routeMatcher 判定當前路徑屬於該子應用時，纔會真正觸發回調。非活躍子應用完全不會收到導航事件，從源頭避免路由衝突。

日誌中你可以清楚看到攔截過程：

4. Keep-Alive 緩存：不銷燬框架實例

大型子應用（Element Plus 組件庫 + 業務代碼）的初始化可能耗時數百毫秒。在多標籤頁場景下反覆銷燬重建體驗很差。

const pavilionMfeRouter = createPavilionMfeRouter({
  apps: [{
    name: 'demo-app',
    keepAlive: true,  // 开启缓存
    // ...
  }],
  maxCache: 5,  // 全局 LRU 驱逐上限
})

緩存策略的精細設計：

- **切換離開**：只隱藏 DOM（- `display: none`），- **不銷燬框架實例**，沙箱也不 deactivate

- **切換回來**：- `display: block`，- **跳過 mount()**，狀態完整保留（表單數據、滾動位置等）

- **LRU 驅逐**：超過- `maxCache`時，最早緩存的子應用纔會完整執行- `deactivate() + unmount()`

状态机增加 CACHED 状态：

MOUNTED → (unmount/离开) → CACHED → (restore/回来) → MOUNTED

子應用的極簡契約

子應用只需要導出一個對象——**三個生命週期函數，零框架依賴**：

// main.ts — Vue 3 子应用
export default {
  mount: async (ctx, el) => {
    const app = createApp(App)
    app.use(router)
    app.mount(el)
    return () => app.unmount()  // 返回清理函数
  },
  unmount: async (ctx, el) => {
    el.innerHTML = ''
  },
}
// 独立运行时自启动
if (!window.__PAVILION_MFE_ENV__) {
  createApp(App).use(router).mount('#app')
}

對於 Vue 2、React 也是同樣的模式，只需改變框架調用方式。關鍵是 mount 返回一個清理函數，框架在合適的時機調用它。

對比其他方案

PavilionMfe 的優勢在於：

- **子應用完全純淨**：運行時不含任何- `@pavilion-mfe/*`代碼

- **構建工具只支持 Vite**：享受 ESM 原生 + MF 的極致性能

- **包體積小**：核心 5 個包，底層零依賴

侷限：

- 僅支持 Vite 構建（不支持 Webpack）

- Module Federation 的共享依賴配置需要一定學習成本

- 浏览器兼容性依赖 `:where()`（Chrome 88+）

適用場景

PavilionMfe 特别适合：

- **管理後臺類應用**：多標籤頁、頻繁切換子應用

- **Vite 技術棧團隊**：和 Vite 生態深度整合

- **多團隊協作**：子應用獨立倉庫、獨立發佈，零耦合

- **多框架混合**：同一主應用中運行 Vue 2、Vue 3、React 子應用

結語

PavilionMfe 的設計哲學是**"子應用不感知框架"**。我們相信好的微前端方案應該像瀏覽器一樣——你不需要知道自己在 iframe 裏運行，框架也無權侵入你的代碼。

核心 500 行搞定沙箱，130 行搞定 CSS 作用域，300 行搞定路由調度。在追求"小而美"的路上，我們用 :where() 替代了重型的 Shadow DOM，用棧式追蹤替代了 Proxy 代理，用 popstate 代理替代了路由劫持。

如果你也在維護一個多團隊的管理後臺，不妨試試 PavilionMfe。
