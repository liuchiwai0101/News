React useEvent Hook：告别过期闭包的稳定回调 (2026)

掘金· 8月15日 周六 · 查看原文 ↗
本文為原文轉錄（繁體中文，簡體已自動轉繁），版權歸原媒體所有；內容機器翻譯自第三方媒體，僅供參考，以原文為準。

每個 React 開發者遲早都會走到同一個岔路口。你寫了一個讀取 state 的事件處理函數，把它傳給子組件或 effect，然後必須二選一：要麼保持內聯函數原樣，看着每次渲染都產生一個新引用——React.memo 失效、effect 反覆執行、監聽器反覆重新訂閱；要麼用 useCallback 包起來，開始玩依賴數組打地鼠——漏掉一個依賴，處理函數看到的就是三次渲染之前的 state。

第二種失敗模式有個名字——**過期閉包（stale closure）**——它大概是生產代碼裏最常見的 React bug。解決方案也有個名字：useEvent，源自 2022 年的官方 React RFC，今天可以直接用 @reactuses/core 裏的 useEvent。它給你一個**引用在渲染之間永不變化**、但函數體**總能讀到最新 state 和 props** 的函數。岔路口的兩邊，全都要。

本文涵蓋它的 API、讓這一切成立的三行實現技巧、與 useCallback 及 React 19.2 內置 useEffectEvent 的對比、真實使用模式，以及必須遵守的一條規則（不要在渲染期間調用它）。TypeScript 優先。

三十秒看懂問題

這就是 bug 製造機。一個聊天組件定時把當前草稿文本發送心跳：

function Composer({ roomId }: { roomId: string }) {
  const [draft, setDraft] = useState('');
  useEffect(() => {
    const id = setInterval(() => {
      sendHeartbeat(roomId, draft); // ⚠️ 哪个 draft？
    }, 3000);
    return () => clearInterval(id);
  }, [roomId]); // 故意省略 draft——我们不想重置定时器
  return <textarea value={draft} onChange={e => setDraft(e.target.value)} />;
}

interval 閉包捕獲的是 effect 運行時的那個 draft——空字符串。此後每次心跳發的都是 ''。把 draft 加進依賴數組，閉包倒是新鮮了，但定時器會在**每次按鍵**時銷燬重建。useCallback 幫不上忙：它有一模一樣的依賴數組，所以逼你做一模一樣的選擇——要麼值過期，要麼引用不停變。

你真正想要的，是一個在組件生命週期內*始終是同一個東西*、但觸發時*讀到當前值*的函數。這就是 useEvent：

import { useEvent } from '@reactuses/core';
function Composer({ roomId }: { roomId: string }) {
  const [draft, setDraft] = useState('');
  const beat = useEvent(() => {
    sendHeartbeat(roomId, draft); // ✅ 永远是最新的 draft 和 roomId
  });
  useEffect(() => {
    const id = setInterval(beat, 3000);
    return () => clearInterval(id);
  }, [beat]); // beat 永不变化——effect 只运行一次
  return <textarea value={draft} onChange={e => setDraft(e.target.value)} />;
}

beat 在每次渲染中引用完全相同，所以 effect 只運行一次，定時器在打字過程中穩如泰山。當它觸發時，通過最新一次渲染的閉包讀取 draft。依賴數組甚至是誠實的——beat 列在裏面，只是它恰好穩定。

完整 API

幾乎沒有學習成本：

const stableFn = useEvent(fn);

- `fn`- `this`也一样。

- `stableFn`- `fn`完全相同，但引用在組件生命週期內固定不變。

类型是精确的，不是 (...args: any[]) => any：

const format = useEvent((n: number, unit: string) => `${n}${unit}`);
format(3, 'px');   // ✅ string
format('3', 'px'); // ❌ 类型错误

開發環境下，如果傳入的不是函數，會在控制檯打印 useEvent expected parameter is a function, got …，而不是悄悄失敗。

內部實現原理

整個實現短到一杯咖啡就能讀完，而且每一行都有它的道理：

export const useEvent = <T extends Fn>(fn: T) => {
  const handlerRef = useRef(fn);
  useIsomorphicLayoutEffect(() => {
    handlerRef.current = fn;
  }, [fn]);
  return useCallback((...args) => {
    const fn = handlerRef.current;
    return fn(...args);
  }, []) as T;
};

三個值得注意的細節：

-

**用 ref 攜帶最新閉包。**每次渲染都產生一個捕獲最新 state 的新`fn`；effect 把它存進`handlerRef`。返回的包裝函數——用空依賴數組只 memoize 一次——在*調用時*而非渲染時讀取`handlerRef.current`。外殼穩定，內核新鮮。

-

**ref 在 layout effect 裏更新，而不是普通 effect。**`useIsomorphicLayoutEffect`在 DOM 變更後同步執行，早於瀏覽器繪製、也早於被動的`useEffect`回調。如果 ref 在普通`useEffect`裏更新，這個間隙中觸發的任何事件——或同一次 commit 中更早運行的其他 effect——調用包裝函數時就會命中上一次渲染的閉包。layout 時機堵上了這個窗口。

-

**Isomorphic 意味着 SSR 安全。**服務端使用`useLayoutEffect`會打印 hydration 警告；`useIsomorphicLayoutEffect`在 SSR 時換成`useEffect`，瀏覽器裏再換回真傢伙。沒有警告，你的代碼也不用做特殊處理。

如果這個 ref 持有技巧看着眼熟，那是因爲它和 useLatest 是同一個思路——useEvent 本質上就是 useLatest 加一個穩定的可調用外殼。想在某個現有回調裏*讀取*最新值時用 useLatest；當回調本身就是你要到處傳遞的東西時用 useEvent。

useEvent vs useCallback

它們解決的是不同的問題，對比一下兩者都更清楚：

「渲染期間」這一行是真正的分界線。useCallback 的結果是個普通值——你可以在渲染時調用它來計算 JSX。useEvent 的包裝函數讀取的 ref 只保證在 commit *之後*是最新的，渲染期間調用可能觀察到上一次渲染的 state（也違反了 RFC 謹慎設計的併發渲染契約）。經驗法則不言自明：**如果函數是響應某件事而觸發的——點擊、定時、消息——用 useEvent；如果它在渲染期間計算東西——用 useCallback。**

useEvent vs React 官方的 useEffectEvent

2022 年的 RFC 最終被取代：React 把這個想法以 useEffectEvent 的形式發佈，自 React 19.2 起穩定。如果你在 19.2+ 上，應該瞭解兩者的關係：

- `useEffectEvent`刻意收窄了範圍。- *effect 內部*調用（ESLint 規則強制執行），也不能傳給其他組件或 Hook。React 團隊把它限定在他們認爲萬無一失的那一種模式：在 effect 裏讀最新值而不重新觸發 effect。

- `useEvent`覆蓋更寬的場景。- `useEffectEvent`的 linter 全都會拒絕——恰恰是用戶態- `useEvent`的用武之地。代價是更寬的場景包含了上面那個渲染期調用的坑，紀律從 linter 轉移到了- *你*身上。

- **兩者可以共存。**React 19.2+ 上 effect 內部用- `useEffectEvent`，跨組件邊界的穩定引用用- `useEvent`；19.2 以下則全部用- `useEvent`——那裏根本沒有- `useEffectEvent`。

使用模式

不破壞 React.memo 的處理函數 prop

經典的列表行場景——memoized 的行組件照樣重渲染，因爲父組件每次渲染都重新創建 onSelect：

const Row = React.memo(function Row({ item, onSelect }: RowProps) {
  return (
    <li onClick={() => onSelect(item.id)} className="row">
      {item.label}
    </li>
  );
});
function List({ items }: { items: Item[] }) {
  const [selected, setSelected] = useState<string[]>([]);
  const handleSelect = useEvent((id: string) => {
    // 读到最新的 selected，没有依赖数组要维护
    setSelected(selected.includes(id)
      ? selected.filter(s => s !== id)
      : [...selected, id]);
  });
  return (
    <ul>
      {items.map(item => (
        <Row key={item.id} item={item} onSelect={handleSelect} />
      ))}
    </ul>
  );
}

handleSelect 每次渲染都是同一個引用，React.memo 才真正 memo 得起來。換 useCallback 的話，你要麼把 selected 列進依賴（引用變來變去，memo 白費），要麼到處用函數式更新（這裏還行，一旦處理函數要讀兩份 state 就沒轍了）。

永不重新訂閱的訂閱

WebSocket、EventSource、SDK——任何僅僅因爲閉包過期就要拆掉連接重建的地方，都很難堪：

function usePriceFeed(symbol: string, threshold: number) {
  const [price, setPrice] = useState(0);
  const onMessage = useEvent((e: MessageEvent) => {
    const next = JSON.parse(e.data).price as number;
    setPrice(next);
    if (next > threshold) notify(symbol, next); // 永远是最新的 threshold
  });
  useEffect(() => {
    const ws = new WebSocket(`wss://feed.example.com/${symbol}`);
    ws.addEventListener('message', onMessage);
    return () => ws.close();
  }, [symbol, onMessage]); // 只有 symbol 变化才重连
  return price;
}

socket 在 symbol 變化時重連——這是正當理由——而 threshold 變化時絕不重連。注意：對於普通 DOM 目標，useEventListener 內部已經做了這件事（它用 useLatest 包住你的 handler），所以只有當訂閱管道由*你自己*掌管時才需要 useEvent。

定時器——或者直接用庫裏現成的

上面的心跳例子太常見了，@reactuses/core 直接內置瞭解法：useInterval 讓回調保持新鮮而不重啓定時器——它自己的實現就構建在 useEvent 和 useLatest 之上。useTimeout、useDebounceFn、useThrottleFn 也是同樣的故事：過期閉包防護是內置的，所以在自己動手接 useEvent 之前，先看看你要造的 Hook 是不是已經存在了。

傳給命令式組件的穩定回調

圖表庫、地圖 SDK、編輯器通常在構造時接收處理函數：

function Editor({ docId }: { docId: string }) {
  const [dirty, setDirty] = useState(false);
  const handleSave = useEvent((content: string) => {
    saveDocument(docId, content); // 最新的 docId
    setDirty(false);
  });
  useEffect(() => {
    const editor = createEditor('#mount', { onSave: handleSave });
    return () => editor.destroy();
  }, [handleSave]); // 稳定 → 编辑器只创建一次
  return <div id="mount" data-dirty={dirty} />;
}

僅僅因爲 docId 在閉包裏換了個引用就重建一個重量級編輯器——這正是 useEvent 要消滅的浪費。

兩條規則

只有兩條，都是 ref 更新時機的直接推論：

- **不要在渲染期間調用返回的函數。**它屬於事件處理、effect、定時器、回調——commit 之後才觸發的東西。渲染期間，ref 可能還指向上一次的閉包。

- **不要用它對 effect 撒謊。**如果一個 effect 確實- *應該*在某個值變化時重新運行（比如篩選條件變化時重新請求數據），用- `useEvent`包住邏輯來讓 linter 閉嘴，等於埋掉了一個真實依賴。- `useEvent`是「讀最新值、不重新觸發」；它不是依賴數組的萬能靜音鍵。

要點回顧

- `useEvent`返回一個引用永久不變、閉包永遠新鮮的函數- `useCallback`逼你二選一的那兩樣東西。

- **技巧是一個在 layout effect 裏更新的 ref**，加一個只 memoize 一次、調用時纔讀 ref 的包裝函數。- `useIsomorphicLayoutEffect`保證 SSR 安全。

- **渲染期間的值用**永遠不要在渲染期間調用- `useCallback`，事後觸發的處理函數用- `useEvent`。- `useEvent`的函數。

- **React 19.2+ 上，**且有 linter 保駕；跨組件、跨庫邊界傳遞的穩定處理函數則交給- `useEffectEvent`覆蓋 effect 內部的場景- `useEvent`。

- **先查庫裏有沒有現成的**——- `useEventListener`、- `useInterval`、- `useDebounceFn`等等都已內置過期閉包防護。
