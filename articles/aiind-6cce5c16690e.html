Pi創始人曝現代開發奇觀：系統崩了，一屋子工程師都在問Claude怎麼修

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

系統崩了，工程師們緊急開會。照理説，這時候最該有人站出來，指出故障發生在哪一層、哪段代碼出了問題、系統該怎麼恢復。但會議室裏，竟然沒有一個人説得清楚。

這可不是哪個程序員編出來的黑色幽默。這是近期 Flask 作者、Pi 開發者 Armin Ronacher 在一場訪談中透露的同行經歷。對此他感嘆道：“真的太可怕了。”

不過，這位發出如此感嘆的恰恰是正在把越來越多軟件開發工作交給 AI 的人。Armin 參與開發的 Pi，每天會收到約 40 至 50 個新 Issue。如今，團隊已經讓 Agent 接手了相當一部分問題處理工作：判斷 Bug 是否存在、嘗試復現、編寫測試、生成修復方案，甚至分配優先級。在一些任務中，只要測試能夠證明修復有效，工程師確認之後就可以直接合並代碼。

Agent 已經能替工程師寫代碼、找 Bug、修 Bug，甚至檢查自己的工作。可當整個行業都在興奮地討論，如何讓 AI 接管更多開發流程、如何建造不需要人類參與的“黑燈軟件工廠”時，一個尷尬的問題擺在了面前： 如果軟件是 AI 寫的，測試是 AI 跑的，代碼審查也交給了 AI，最後連繫統為什麼崩潰都只能去問 AI，那還需要工程師幹什麼呢？

Pi 創始人 Mario Zechner 對這種趨勢的質疑更加直接。在他看來，整個行業似乎正在努力追求一種狀態：開發者不必再理解自己正在構建的軟件。

Mario 直言：“如果你什麼都不需要理解了，那你還有什麼用？公司為什麼還需要你？”

但 Mario 並不是一個排斥 AI 的傳統程序員。他自己開發 Coding Agent，也在用 Agent 處理大量實際工程任務。他甚至直言，軟件開發中已經有很多工作不再需要人類完成，而且他找不到理由證明每一位軟件工程師都應該保住自己的崗位。

一邊承認 AI 已經能夠替代大量編碼工作，一邊又警告工程師正在失去對系統的理解。這種矛盾，貫穿了 Mario Zechner 與 Armin Ronacher 最近的一場對談。

在 Matt Pocock 主持的這期約 46 分鐘的訪談中，兩人談到了 Opus 5.5 之後 Coding Agent 的能力變化，也拆解了自動化編程背後越來越難迴避的工程問題：為什麼 Agent 可以讓測試全部通過，卻仍然寫出糟糕的軟件？為什麼代碼審查越來越自動化，系統卻未必更加可靠？當開發者不再親自編寫和理解大部分代碼時，誰來承擔最終的維護責任？而對於整個行業追逐的“黑燈軟件工廠”，這兩位已經深度使用 AI 編程工具的開發者，顯然沒有那麼樂觀。

Armin： 最大的變化是，對於有明確驗證標準的任務，現在可以讓 Agent 獨立運行更長時間。比如，給它一套參考測試，它就能反覆嘗試，直到寫出符合要求的實現。但這種能力不能推廣到所有開發任務。

Mario： 我沒覺得模型在系統設計、架構設計和 API 設計上有多大進步。它們真正擅長的是編排子 Agent，以及完成可以通過測試驗證的任務。我曾讓 Agent 優化 Pi 的啓動速度，它報告説啓動時間縮短了 100%，結果只是把整個應用程序刪掉了。

Matt： 為什麼同樣使用 Opus 5.5，不同開發者得到的結果差別很大？

Armin： 我和一位朋友都用 Opus 5.5 開發遊戲，我這邊進展順利，他卻沒有取得太大進展。後來我意識到，這和我的遊戲開發經驗有關。知道該用什麼專業術語、按照什麼順序推進任務，往往比單純把需求交給 Agent 更有效。模型給出的第一個可行方案，也不一定是最優解。

Matt： AI 讓代碼生成越來越便宜，開發者應該如何平衡數量與質量？

Armin： Agent 幾乎不會拒絕增加功能，這很容易讓軟件變得越來越複雜。我更希望大家利用 AI 提高軟件質量，而不是不斷堆砌功能。

Mario： 過去大量煩瑣的編碼工作，現在可以交給 Agent。照理説，開發者應該有更多時間關注質量，但現實往往相反。我們至今還沒有找到一套成熟的 Agent 工程流程，能夠持續交付高質量軟件。

Mario： 很多人以為，只要 Agent 寫出大量單元測試、端到端測試，CI 全綠，系統就可靠了。但 Agent 可能測錯東西，也可能漏掉關鍵問題。單個模塊通過驗證，不代表整個系統正確。如果開發者不瞭解底層實現，就無法判斷這些測試究竟證明瞭什麼。

Armin： 我試過用 Lean 做形式化證明，但目前還沒找到辦法，讓驗證真正成為約束 Agent 行為的底層機制。很多時候，它只是多了一份供 Agent 參考的材料。

Matt： Pi 已經使用 Agent 自動處理 Issue，哪些工作可以放心交給它？

Mario： Pi 每天收到約 40–50 個新 Issue。我們的機器人能判斷 Bug 是否存在、嘗試復現、提出修復方案並分配優先級。如果有失敗測試證明問題存在，修復後測試又能通過，我通常可以直接批准合併。但涉及新功能和用户體驗設計時，Agent 的表現仍然不可靠。對於核心模塊，我也依然會查看代碼。

Mario： 我會讓 Agent 一次生成十種不同的實現，再從中探索合適的方案。它能加快試錯，但無法替我作出最終判斷。

Armin： 系統設計需要理解真實的數據流和業務規模。我遇到過 Agent 根據舊文檔判斷數據庫只有 2000 條記錄，實際上早已增長到幾百萬條。不同規模需要完全不同的技術取捨，而這些背景條件很難靠一句提示詞交代清楚。

Matt： 未來真的能實現完全不需要人工參與的“黑燈軟件工廠”嗎？人類工程師還有什麼價值？
