馬斯克喊話“真男人自己管理內存”，三十年系統老將警告：Rust 也攔不住 AI 製造複雜性

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

11 月 10 日，面對網友“為什麼用 C/C++ 重寫，之前用的是 Rust 嗎”的追問，Elon Musk 用這句話回應了 xAI 的技術選擇。

四年前，他還公開表示自己是 Rust 的擁躉，認為 Discord 的實踐證明了它的擴展能力。不過，他當時也保留了一個判斷：在專用硬件上追求極致性能，精煉的 C 代碼配合定製編譯器，依然無可匹敵。

如今，隨着他宣佈棄用 JAX/SGLang、用 C/C++ 從零重寫強化學習與推理技術棧，這場關於性能、內存管理和語言選擇的爭論，又被推到了台前。

在 DTrace 聯合作者、Oxide 聯合創始人 Bryan Cantrill 看來，Rust 的價值，恰恰要放回過去幾十年積累的工程負擔中理解。許多語言為了讓開發者更輕鬆，把複雜性藏進運行時：寫代碼時少操一點心，部署之後卻要為垃圾回收、運行時錯誤和難以預測的性能付出代價。當這些軟件成為下一層系統的地基，過去的便利就可能變成後來者無法繞開的技術債。Rust 受到追捧，一個重要原因就是它嘗試扭轉這筆交易：要求開發者提前想清楚所有權和內存關係，用開發階段的約束，換取運行時的安全與可靠。

到了 AI 編程時代，這種約束反而更有價值。LLM 可以反覆修改代碼，編譯器則不斷指出問題，Rust 陡峭的學習曲線由此顯露出另一面。不過 Cantrill 的警告也正在這裏：Rust 可以攔住一部分錯誤，卻攔不住 LLM 源源不斷地製造複雜性。一個系統可以通過編譯、符合內存安全要求，同時充滿多餘的模塊、層層疊加的抽象，以及永遠做不完的“改進”。

人會因為腦子裝不下整個系統，設法讓它更簡單；LLM 卻沒有同樣的壓力。你讓它精簡，它可能再派一萬個 Agent 來“優化”。Steve Yegge 的軟件工廠 Gas Town 就陷入了這樣的循環：原本要替人開發軟件，最後卻只顧着開發自己。按照 Yegge 的自述，Opus 4.7 總覺得“再做兩件事就好”，不斷修改 Gas Town 本身，始終無法進入真正幹活的狀態。工廠一直在擴建，卻遲遲不肯開工；代碼越堆越多，Token 越燒越貴，最終把自己拖垮了。

在 Cantrill 看來，這暴露了 AI 編程更深的風險：模型可以不停寫、不停改，甚至把“簡化系統”也變成一輪新的擴建。Rust 能檢查內存使用是否安全，卻無法替人判斷，這座工廠究竟還缺一塊磚，還是早就該停止施工。

先給大家一點背景，我在 Sun Microsystems——一家現在已經不存在的計算機公司幹了 14 年，之後我去了一家雲計算先驅公司 Joyent，它在 2016 年被三星收購。然後我們在 2019 年創辦了 Oxide。這就是我整個職業生涯的跨度。

我入行那會兒，用事後諸葛亮的眼光看，幾乎算是史前時代。那時候大家都覺得面向對象就是未來，但語言對它的支持糟糕透頂。那是 Java 出現之前，只有 C++。如果你覺得現在的 C++ 很糟，那你真該看看九十年代的 C++，更是爛到令人髮指。

我職業生涯是從 C 起步的，1996 年那會兒沒人覺得 C 是未來，但我想寫的操作系統內核軟件，毫無疑問只有 C 可用。但軟件世界的其他地方不是這麼想的，訴求都集中在語言上：怎麼讓軟件更容易寫？怎麼讓更多人能寫軟件？

這些訴求聽起來都很合理，我們確實希望軟件更平民化：一門心思優化開發體驗，降低了認知門檻，讓開發者不必懂那麼多。從彙編和 C 那個年代走出來，這聽着很值得稱道。可這些東西全都是一筆隱性交易：我們讓開發者更輕鬆了，卻讓運維者難受得多。這個張力，從我九十年代寫 C++ 的時候就埋下了，在今天的 LLM 時代又以一種全新的方式冒了出來。

垃圾回收（Garbage Colletction）就是絕佳例子。垃圾回收讓開發者省事，可一旦真要運維這套軟件，麻煩就來了，它會伴隨軟件的整個生命週期。我一個從顯式內存分配年代長大的人，都覺得這事有點荒唐：我們居然要把“什麼時候要內存、什麼時候用完”這種負擔從工程師身上卸下來。拜託，這又不是分裂原子。我想要點內存，用完了，還給你，這不難吧？可不行，太“難”了。

這對某些軟件確實很棒，但對基礎設施類軟件，那些要承載其他軟件、要扛負載的軟件，就是跟你對着幹。我認識的那些在垃圾回收語言裏寫數據庫的人，首先，我為你感到難過，你花了大量時間去“討好”垃圾回收器：有一塊自認為沒人引用的垃圾，拼命希望垃圾回收能發現它，不然垃圾回收就會 stop the world，給你帶來延遲。更糟的是，你以為那是垃圾，其實不是，你手裏還攥着引用。寫過 JavaScript 的都懂，用閉包太容易創建出你看不見的對象引用了。然後你罵垃圾回收不停地跑，其實它根本沒在回收垃圾，它現在是個堆掃描器，純屬南轅北轍。

動態類型也一樣。不用預先定義類型、運行時再確定，對開發來説很爽。如果你從靜態類型語言轉到 JavaScript，那感覺就像進了裸體營地。你從小穿慣了衣服，突然大家都把衣服脱了，一開始是有點刺激，但人穿衣服是有原因的。動態類型也許讓某些軟件開發更容易，但現在你在生產環境遇到的問題，本該是編譯錯誤，比如本來只是個手誤把屬性拼錯了，現在卻要在運行時爆出來，這就是為什麼沒人該用 Node.js 寫基礎設施軟件。

還有 M:N 線程，我希望大家都不認識這東西。它號稱“你能創建幾百萬個線程”，你真去創建幾百萬個，一切都卡死了，又是那種為了遷就開發者、卻讓系統更難理解的東西。

異常也是。在代碼深處動態拋異常，感覺很好，不用擔心錯誤處理了。可一旦真出了錯，異常就像草叢裏的蛇，很難正確處理。尤其 JavaScript 裏，如果異常是因為屬性拼錯導致的類型錯誤，你根本不知道該怎麼處理。

ORM（對象關係映射），“我們想讓訪問數據庫超級簡單”，對開發者很棒，開發速度飛快，甚至都不用知道自己是在跟數據庫打交道。可真正在生產裏處理這攤子的人心想：我就知道，他們不知道自己面對的是數據庫。我這輩子花了太多時間在生產環境裏調試別人的代碼，總覺得這世界有一種因果失衡：一定有人制造的 bug 遠多於他們調試的 bug。等你遇到這些人，很難開口説“嘿，我讀過你很多代碼，順便問一句，你知道那些東西全都是數據庫查詢嗎？”這也情有可原，因為抽象就是不讓你知道，好讓你開發得更快，但代價是引入了所有這些複雜性。

RPC（遠程過程調用），幾乎從定義上就是個壞主意：你有個遠程的函數調用，然後説“別擔心你要走網絡，就當調個函數”，這讓你一不小心就造出一個病態系統。

這些都是抽象稍微出了問題的例子，所以讓咱們聊聊抽象，因為抽象正是軟件的全部。我們看不見它、聞不到它，卻對什麼是乾淨的抽象有很強的審美。一個好抽象能讓我們造出非凡的東西，緊湊到人們甚至不知道自己被抽象掉了。這跟 ORM 那種“不知道”不是一回事：好抽象是無縫到根本看不見，不會在生產環境裏引發湧現行為；壞抽象則會泄漏、會爆炸，產出的系統極其脆弱。

當你在開發階段為開發者過度優化，想把開發者從現實和後果中屏蔽出去時，幾乎不可避免地會造出一個泄漏的抽象，而收拾它的人是運維。

垃圾回收就是最好的例子。它本來不該泄漏，前提是我們真的永遠不用操心它。但每個 Java 性能問題最後都是“你得換個垃圾回收器”，或者“換個算法”。我們簡直是在搞降神會，從替代垃圾回收器的超自然世界裏召喚靈魂，這就是恐怖地泄漏的抽象。它對很多系統沒問題，但當我們試圖構建基礎設施，那種我們在其上構建更多軟件的軟件，它就會壞得很慘。

壞了，它們就引入複雜性。複雜性和抽象是軟件工程的一對偶極子。好的抽象把我們蒸餾到問題剩下的本質複雜性上，壞的抽象誘發偶然複雜性。真正的問題在於，複雜性不只是累積，它還會爆炸：壞抽象誘發的偶然複雜性會變成下一層必須處理的本質複雜性。你的壞抽象創造了一個糟糕宇宙的新規則，而我們發現自己就困在裏面。

舉個非常具體的例子：基本輸入輸出系統（BIOS），它是系統裏非常底層的固件，後來演變成 UEFI。x86 或者 ARM 系統啓動時，就會執行這段固件。這挺讓人失望，因為 ARM 本來根本不需要模擬這套行為。如果你在實現一項技術，想取代一個你覺得比你走得更遠的技術，千萬不要假設圍繞它運轉的複雜性就是本質複雜性。ARM 那幫人覺得，我們 ARM 也必須有 UEFI BIOS，這玩意兒是本質複雜性。才不是，它是偶然複雜性，你其實根本不需要它。但當每個人都用的時候，你就會覺得它不可協商。我們日常要處理的大量複雜性都像是不容置疑的本質複雜性，但其中很多其實是過去選擇造成的偶然複雜性。
