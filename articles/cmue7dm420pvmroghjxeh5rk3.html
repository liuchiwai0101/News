Anthropic 前線工程師分享 AI 驅動代碼現代化項目的六步準備方法

推薦理由

來自 Anthropic 前線工程師的實戰總結，把智能體驅動的代碼現代化拆成可落地的六步組織流程。

正文

在我們的Notes from the Field系列中，Anthropic 的前線部署工程師分享源自真實客户部署的最佳實踐。在本文中，我們分享管理大型代碼現代化項目的經驗。

代碼現代化曾經被劃定為耗時數年、全員投入的工程，如今可以在幾個月（甚至幾周）內完成，但兩側的組織性工作往往依然如故。

例如，對關鍵銀行系統的每一次變更都必須經過變更管理、審查和審批。這是一套穩健的流程，因為監管機構、審計人員和業務方都要求如此。

正是這些流程讓關鍵系統值得信賴，而它們建立在這樣一個假設之上：每一次變更由人編寫，每一個 diff 由人審查。一旦智能體加速了變更的編寫，瓶頸就從產出變更轉移到圍繞變更調動整個組織。

本文涵蓋企業在現代化真正開展之前必須完成的工作：定義何為完成、一次變更必須攜帶哪些證據、經過認證的變更將如何進入生產環境，以及必須預先準備哪些環節才能讓整個流程得以啓動。

我們將這一過程拆解為六個步驟：

  1. 定義目標：現代化後的代碼必須具備的技術棧和行為。
  2. 創建證書：變更必須滿足哪些條件，才能被視為在目標狀態下是正確的。
  3. 設定晉升策略：已認證的變更以何種路徑、按其產出速度進入生產環境。
  4. 落實前置條件：環境、CI/CD、評審能力以及審批。
  5. 構建並完善智能體工作流：定製的 Claude Code 動態工作流，將現代化改造分配到許多更小的並行子智能體工作流中，由它們產出變更。這一工作流圍繞目標、證書和晉升策略構建。
  6. 運行現代化改造：在代碼庫的一小部分上端到端驗證該工作流，然後再擴大規模。

第 1 步：定義目標

目標是現代化改造的最終狀態。期望的最終狀態決定了你正在做的是下表中詳述的三種現代化改造中的哪一種。

確定現代化改造類型

類型它是什麼選擇時機目標是
升級同技術棧的版本升級（例如 C++11 → C++20）。技術棧本身沒問題，但版本已經落後：運行時已停止維護、安全漏洞未修補、依賴項無法再升級。一個運行時版本和包集合。
改造跨技術棧重寫，同時保持行為不變（例如 COBOL → Java）。技術棧是需要解決的問題，而行為是可信賴的。升級所需的一切，外加新代碼必須遵循的語言、框架和架構約定。
重新構想在新架構上進行全新重建，並修改行為。行為需要與代碼一同改變。改造所需的一切，外加新系統的書面行為規格説明。

決定進行哪種類型的現代化改造，往往會在組織內部引發爭論。根據我們的經驗，最貼近生產環境的人希望在不改變行為的前提下替換技術棧，以控制風險（轉型式現代化改造）。另一方則通常是長期與這套代碼庫共處的工程師，他們希望借現代化改造來償還技術債務，此外還有其他業務相關方，想藉此機會提出新的需求（重構式現代化改造）。

這兩種立場都合理，但如果這個問題懸而未決，它日後就會重新浮現，演變成一場關於某項改動是否“正確”的爭論。就選擇哪條路徑達成共識，會在初期增加一些摩擦，但能讓整個項目推進得更順暢。

梳理代碼庫並創建行為規格説明

理解當前系統通常是定義目標的一個不錯的起點。提取舊代碼實際做了什麼，並建立一份當前行為的清單，就能輕鬆判斷哪些部分應當修改或捨棄，從而確定這次現代化改造是轉型式還是重構式。這往往還能揭示出未知的業務邏輯和邊緣情況。

Claude 可以通過梳理依賴關係，併為那些沒人記得是誰構建的工作流程編寫文檔，來完成其中大量的探查工作。代碼現代化插件的assess、map和extract-rules命令能夠挖掘業務規則，並附上可供工程師隨後審查的來源引用。

然而，僅靠 Claude 的發現可能無法完整呈現遺留系統的全部行為。與業務用户和開發人員的訪談，以及內部文檔，可以填補這些空白。上下文收集在前期可能需要花一些時間，但上下文的質量會決定該工作流後續所做的每一項決策。

對於重新構想（reimagine）而言，定義目標需要額外的工作：應當寫下詳細的行為規格説明，並與用户群體達成一致。

來自代碼現代化插件的一個交互式依賴關係圖示例。

確立項目的合理性與目標

在定義目標的同時，組織還應考慮這項現代化究竟為何值得開展。對遺留系統進行現代化可以減少持續的維護和運營成本，然而，根據我們的經驗，降低成本並非大多數現代化項目的主導目標。

降低風險往往是最重要的現代化收益。在討論是否要開展該項目時，不妨考慮一下不進行現代化所帶來的風險。

例如，一個帶有未修補漏洞的系統可能意味着一次網絡入侵，或一次嚴重到足以讓企業本身陷入險境的停機。不再受支持的運行時，或理解該系統的工程師群體不斷萎縮，都會加劇這一風險。

像 Claude Code 這樣的智能體編程工具已經縮短了現代化改造的時間線，但預算仍然難以估算，這導致了惰性。我們已經公開了一些大規模現代化改造的成本，其他人也是如此。這些可以作為粗略的基線，我們在本指南底部還提供了關於預算預測的額外指導。

啓動這些項目的主要挑戰通常在於建立內部共識，並獲得擁有該系統的團隊以及依賴該系統的團隊的承諾。構建商業論證並設定項目目標——通常是在領導層層面——會讓這一過程變得更容易。這也有助於為後續的證書和推廣政策中的權衡取捨提供錨點。當利益相關方對一項變更可以承載多少風險存在分歧時，不進行現代化改造的風險就是制衡力量。

第 2 步：定義證書

證書是每一項現代化改造變更都必須滿足的一組條件或測試。選擇那些能提供最強累積證據、證明該變更相對於目標是正確的條件。

每個條件都應該能夠在無需人工介入的情況下進行檢查，這樣智能體工作流就可以對變更進行迭代，直到它滿足證書要求；如果無法滿足，則將其標記出來供人工審查。

證書中包含哪些內容取決於目標，但通常會從以下列表中選取：

  • 原始測試套件通過
  • 現代化改造期間編寫的 Claude 生成測試全部通過
  • 測試覆蓋率滿足約定的閾值
  • 性能基準保持在約定的範圍內
  • 由 Claude 在各自全新的上下文窗口中進行的獨立對抗性審查未發現阻塞性問題
  • 對於用户界面，Claude 驅動的計算機使用未發現迴歸問題
  • 當前版本與目標版本對相同輸入產生相同輸出，輸入可以是實時的、錄製的或 Claude 生成的
  • 持久化狀態和傳輸格式在當前版本與目標版本之間可往返轉換
  • 變更在預發佈環境中運行約定的一段時間，錯誤率、延遲或告警均無迴歸
  • 靜態分析和安全掃描未發現新的問題
  • 對於編譯型目標，構建乾淨且類型檢查通過
與將負責審查和推動變更進入生產環境的人員共同編寫證書。在證書和智能體工作流仍在設計階段時，就引入當前依賴該代碼庫的開發者、用户群體和業務負責人。

他們的專業判斷塑造了證書所衡量的內容，而他們的早期參與正是當變更進入評審階段時贏得他們認可的原因。對最終證書的一個良好檢驗是：他們是否願意僅憑證書中的證據就放心合併。如果他們從中看到了自己的標準，那麼第 3 步中的推廣策略就可以更寬鬆。

證書對照什麼進行檢查、以及如何檢查，取決於現代化改造的類型。

  • 對於提升式現代化改造，對標的是原始代碼庫，原始測試套件可以作為證書的核心。
  • 對於轉換式現代化改造，對標的同樣是原始代碼庫，但原始測試套件很少能在新棧上運行。取而代之，生產流量回放、新舊系統之間的差分測試，以及生產環境並行部署承擔了大部分工作。
  • 對於重構式現代化改造，證書錨定在行為規格説明上。這是最困難的情況。規格説明不如現有系統那樣客觀、可供差分對比，因此涉及更大程度的模型判斷，這可能導致結果更加多變。在這裏，證書依賴於根據規格説明編寫的測試、由 Claude 進行的獨立對抗性審查（對照規格説明檢查每一項變更），以及在新系統保留舊系統行為之處進行的差分檢查。要預期隨着規格説明的澄清而修訂證書：規格説明中的缺口會首先在這裏暴露出來。

舊系統往往測試覆蓋率低、測試不穩定，且幾乎沒有遙測數據。定義證書的一部分工作就是識別這些缺口。如果支撐一份強有力的證書會很困難，那麼在這一步最有用的做法之一，就是用 Claude 來構建缺失的證據，無論是搭建一個與生產環境平行的環境、構建回放測試框架，還是編寫更多測試。

第 3 步：設定晉升策略

智能體產生變更的速度，遠超任何人類團隊逐條 diff 審查的速度。晉升策略是一條分級審查路徑——提前書面寫明並達成一致——它規定了針對某項變更的人工審查深度，從而讓現代化工作能在可接受的時間線內完成。

與證書一樣，這一步要與審查人員共同推進，並儘可能將其融入你組織現有的變更管理流程。具體細節會因組織和其所面臨的風險權衡而異，但有幾條規則放之四海而皆準：

  • 按影響範圍和智能體置信度對變更分級。如果你的組織已有自己的變更或風險分類，就沿用它的。對關鍵路徑保留完整的人工審查。
  • 從源頭修復反覆出現的標記。對隨時間推移被標記的變更進行分組和分析。當同類型的標記反覆出現時，應在智能體工作流或證書中修復其根因，而不是逐一審查每一條。
  • 與評審人員共同設計輸出格式。就哪些信息和格式能讓評審最快完成達成一致，以及哪些信號比其他信號更能帶來信心。讓他們在第 5 步中評審早期樣本輸出。
  • 高效分配 SME 時間。SME 不會閲讀每一份最終 diff，但他們的判斷仍然是稀缺的輸入。讓他們能夠直接跳到最高風險層級中的變更，以及每個層級中被標記的智能體決策，而無需費力翻閲大量 diff。這樣，少量專家工時就能覆蓋風險最高的那些變更。

這些規則中有許多通過在項目早期就讓 SME 參與，將他們的工時前置投入。他們的反饋會在全面現代化開始之前，就校準證書和智能體工作流。

他們對樣本的簽字確認，也會成為在信心較高之處採用更輕量評審路徑的進一步依據。這與傳統的非智能體模式正好相反——在那種模式下，評審發生在最後。

一項變更從生成到上線的路徑。

晉升策略還應反映該現代化項目在速度與評審深度之間所處的位置。一個正在趕硬性截止日期的現代化項目——例如某個運行時即將失去支持——需要更快的策略，採用更輕量的人工評審，並明確同意每項變更承擔更多風險。

在更長的時間線上進行現代化改造，可以承擔更深入的人工審查和更緩慢的切換。利益相關方會根據自身的風險偏好和約束條件，落在這一光譜的不同位置上，因此值得在工作開始之前就將其確定下來。

在受監管的環境中，對任何變更採取較輕量的人工審查路徑都可能引發切實的不安。個別審批人會猶豫是否簽字批准，因為他們承擔着不良變更的風險，而管理層則承擔着系統老化的更大風險。

根據我們的經驗，最好讓晉升策略的指令來自組織最高層。最好也事先就此達成一致，這樣進入生產環境的 bug 的責任就是共同承擔的，而不是被歸咎於批准該變更的人。

所有這些仍然取決於一份足夠詳細的證書，使其能夠作為真正的證據，也取決於審查者是否足夠理解 Claude 是如何得出某項變更的，從而能夠信任它。

第 4 步：將前置條件落實到位

這一步的許多工作要經由現代化改造之外的團隊來推進：主機所需的平台或基礎設施團隊、負責測試容量的 QA 或發佈工程團隊、負責審批的安全與合規團隊。這些團隊通常各自都有自己的待辦事項或審批流程，所以要儘早開啓溝通——一旦你明確了需求就馬上開始，往往在第 1 步到第 3 步還在進行時就要着手。

環境

  • 一台專用的遠程主機，用於運行該工作流，並讓 Claude 能夠訪問代碼庫及其他相關來源
  • 按證書要求測試容量
  • 任何能強化證書的東西：生產遙測數據、與生產並行的環境，或用於回放的生產數據

代碼庫與 CI/CD

  • 一份代碼庫的依賴關係圖，以構建和編譯日誌、導入分析或運行時追蹤為依據。注意：該插件的 map 命令是一個不錯的起點，但取決於代碼庫的規模和年代，可能需要做更多的前期工作
  • 作為目標定義的一部分，對任何依賴項或軟件包的既定處理方式
  • 如有需要，一個可隨時加入 CI/CD 的兼容性檢查
  • 如果你是在原地進行現代化改造，一份商定好的代碼凍結策略
  • 一份面向在職開發者的溝通計劃，涵蓋任何代碼凍結和新的兼容性要求

團隊與評審

  • 依賴該代碼庫的其他團隊就他們如何參與達成一致，例如簽署證書或在晉升政策下進行審查，並預留審查者時間

安全與合規

  • 為 Claude Code 批准一條用於源代碼的模型訪問路徑
  • 為智能體工作流實施最小權限訪問：僅可寫入現代化分支，且無生產環境憑證
  • 從現代化分支中清除或掩蔽密鑰和 PII
  • 每項變更均可追溯，且 PR 關聯到智能體記錄和證書證據
  • 對新依賴項進行許可證和漏洞檢查

第 5 步：構建並完善智能體工作流

使用 Claude Code 開發一套定製化的動態工作流，用於對代碼庫進行現代化改造。

我們建議從代碼現代化插件開始，並把工作流可能需要的一切都放到文件系統上或通過 MCP 提供，讓 Claude 能夠訪問。這包括目標、證書、晉升策略、代碼庫、文檔，以及證書所需的任何數據源或工具。你也可以把本文作為上下文提供給 Claude。這就構成了該項目的核心知識庫。

有了這些基礎，構建現代化工作流就是容易的部分了。讓領域專家（SME）按需審查 Claude 的工作，包括任何針對特定代碼庫的技能或提取出的規則，然後再讓下游環節依賴它們。

通過將其應用於代碼庫的一小部分來完善你所構建的內容，由領域專家審查它產生的變更、智能體的流程，以及證書已滿足的證據。

當問題浮現時，你應該修改工作流，而不是修改每一處變更。目標是確信：一旦規模化，變更幾乎在所有地方都能滿足證書要求，審查者也會願意按照晉升策略進行合併。

第 6 步：運行現代化

首先，在代碼庫的一小部分上端到端地完成現代化，包括通過晉升策略審查並落地這些變更。趁代價還低時修復任何不奏效的地方，重複這一過程直到你有信心，然後再擴展到整個代碼庫。

雖然“轉換式”和“重新構想式”現代化都涉及在現有系統之外構建目標系統、待完成後一次性切換，但“提升式”現代化還有第二種選擇：在開發持續進行的同時，直接在線上代碼庫上原地現代化。

當系統無法停機，或者代碼庫變化太快、難以為單獨的現代化副本保持同步時，這通常是首選方案。在這種情況下，我們看到行之有效的做法是：從葉子節點向內將代碼庫拆分為邏輯分區；一次凍結並現代化一個分區；並對 CI/CD 設置門禁，使新提交無法在某個分區完成現代化後將其回退。

關於成本的一點説明

我們經常被問到，這樣一次現代化改造會消耗多少 token。每次現代化改造的情況各不相同，但主要的成本驅動因素包括：

  • 代碼庫中有多少部分需要閲讀，而不是修改；
  • 認證流程涉及的工作量有多大（在受監管環境中，驗證通常比編寫變更佔據更大的比重）；
  • 認證要求編寫多少新測試以及修復多少測試；以及
  • 在運行進行期間，其他團隊在你周圍合併代碼會帶來多少協調工作。
在對代碼庫的一小部分完成現代化改造時，測量 token 用量，並據此推算整個運行過程的消耗。將試點無法覆蓋的任何內容——例如在實時代碼庫上進行的對賬——視為未知項。這樣你就能估算出完整現代化改造的成本下限。

試點的測量結果還能揭示在哪些環節可以針對成本優化你的智能體工作流。找出工作流中消耗 token 最多的部分，並思考如何讓它們更高效。把計算密集型的驗證信號移到更廉價的關卡之後，使其只在更簡單的檢查通過後才運行。

對於證書能夠完整校驗的機械性、大批量工作，考慮使用 Sonnet 這類兼顧成本與能力的模型。將更智能的模型留給困難的轉換以及驗證正確性的對抗性審查。

當較便宜的模型無法滿足證書要求時，你也可以升級到更昂貴的模型，但在試點期間要仔細分析重試率，因為多次廉價嘗試的成本可能超過一次昂貴嘗試。如果你讓 Claude 同時訪問工作流和試點數據，它就能與你一起完成其中大部分分析。

超越現代化改造

現代化改造後的代碼庫只是其中一項產出。其他產出還包括：生成它的工作流、一份寫明何為正確的書面證書、一套你的變更管理流程已經接受的晉升策略，以及每一次落地變更的證據鏈。把這套操作手冊固化為可複用的資產，這樣在下一次升級或重寫時，這套模式就已經就位。
