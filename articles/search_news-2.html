第 9 篇給知識庫裝了 OpenClaw，第 10 篇裝上了 Hermes。到這一步，你已經在用別人做好的 AI 工具了。

但用着用着，你會發現一件事。

插件市場裏那幾百個插件，沒一個完全合你心意。你要的「把 PDF 拖進去，自動提取摘要、打標籤、寫進 Frontmatter」，要麼沒有，要麼湊合能用但缺個關鍵功能。

以前到這一步就卡死了。你不會 TypeScript，不會寫插件，連 JavaScript 都看不懂。

現在不一樣了。你不需要會寫代碼，你只需要會提需求。Claude Code 和 Codex 這兩個 AI 編碼 Agent，能聽懂人話，自己動手寫代碼。

這篇講怎麼用它們，給 Obsidian 造你自己的工具。

一、先明白一件事：你不是在學編程，是在指揮

很多人一聽「用 AI 寫代碼」就發怵，覺得還是得先學 Python。

不用。

你要做的轉變，是把自己從「寫代碼的人」變成「提需求的人」。

想象你請了個程序員，他坐在你旁邊，聽得懂中文，幹活飛快，還不要工資。你要做的就是把需求說清楚。AI 編碼 Agent 就是那個程序員。

區別在於，你跟他說話要更講究一點。人跟人說話，說一半對方能猜。AI 不行，它會把你的話當真。你說得越具體，它幹得越準。

這就是整篇文章的心法，記好這一句：**你的價值在需求，不在代碼。**

二、1+N 優先：先造小工具，再造大插件

第 5 篇講標籤系統的時候提過 1+N。造工具這件事，同樣適用。

1 是那個核心的東西，比如一個完整的 Obsidian 插件。N 是圍繞它的零碎腳本。

很多人的第一反應是，讓 AI 直接寫個插件，一步到位。

別。

插件是重武器。要配置 manifest.json，要處理 Obsidian API，要處理各種邊緣情況。第一次就讓 AI 寫插件，大概率翻車，而且翻車了你都不知道錯在哪。

正確順序是反過來的：

**先用 AI 寫幾個輕量級腳本，跑通你的工作流。腳本驗證沒問題了，再讓 AI 把邏輯封裝成插件。**

舉個例子。你想做「文獻自動入庫」。先別讓 AI 寫插件，讓它寫個 Python 腳本，能掃描文件夾、提取 PDF 摘要、寫進 Frontmatter。這個腳本跑通了，你的需求就清晰了。這時候再讓它封裝成插件，成功率完全不一樣。

腳本是草稿，插件是成稿。沒人會直接交草稿當成稿。

選哪個 Agent

兩個主流選擇，Claude Code 和 Codex。簡單對比：

我的習慣是，活兒越明確越給 Codex，活兒越模糊越給 Claude Code。批量重命名 500 個文件，這種破事 Codex 一把梭。設計一個插件的數據結構，這種需要來回討論的，交給 Claude Code。

三、實戰：造一個「文獻自動入庫」流水線

場景定死：你是個研究生，每天下載 PDF 論文，丟進 Obsidian 的00-Inbox。你想要的效果是，論文自動生成摘要，自動打標籤，自動寫進 Frontmatter，然後挪到100-筆記/文獻/下。

四步走。

Step 1：先規劃，別急着寫代碼

打開 Claude Code，進 Plan 模式（終端裏按兩次 Shift+Tab）。

把這段話丟給它：

你是一個 Obsidian 插件開發專家。

我的知識庫在 D:\wiki\knowledge-vault，結構如下：

00-Inbox 是臨時收件箱，100-筆記 是核心筆記區，裏面有文獻子目錄。

我想實現：把 PDF 論文拖進 00-Inbox 後，自動提取摘要、

打標籤、寫進 Frontmatter，再移到 100-筆記/文獻/。

先不要寫代碼。先幫我規劃：

1. 這個功能用腳本還是插件實現更合適？

2. 如果需要讀取 PDF，怎麼提取文字和摘要？

3. 打標籤的規則怎麼定？

4. 移動文件時怎麼處理雙鏈引用？

請給出設計方案，並說明每一步的風險。

Plan 模式的好處是，它只輸出方案，不動你的文件。你看了方案覺得不對，直接說，改到滿意爲止。

這一步千萬別省。規劃半小時，後面省三天。

Step 2：輕量腳本先行（N 落地）

方案確認了，先用 Codex 寫個獨立 Python 腳本。

把需求說得越死越好：

寫一個 Python 腳本，功能如下：

1. 扫描 D:\wiki\knowledge-vault\00-Inbox 下的所有 .pdf 文件

2. 用 pymupdf 提取每篇 PDF 的標題、作者、摘要

3. 生成一篇 Markdown 筆記，格式：

title: <論文標題>

authors: <作者>

tags: [文獻, 待整理]

source: <PDF 文件名>

4. 筆記寫到 100-筆記/文獻/ 目錄

5. 處理完的 PDF 移動到 00-Inbox/已處理/

6. 所有操作寫日誌到 logs/import.log

不要修改任何已有文件，只創建新文件。

注意最後一句。這句是保命的，後面避坑部分細說。

腳本跑一遍，看結果。摘要提取得準不準，標籤打得合不合理，路徑對不對。這一輪迭代全在腳本層面，成本極低，改起來也快。

Step 3：封裝成插件（1 落地）

腳本穩定了，需求已經驗證過了。這時候讓 Claude Code 把它變成真正的 Obsidian 插件。

把剛纔這個腳本的邏輯封裝成 Obsidian 插件：

1. 用 TypeScript 重寫，遵守 Obsidian 插件規範

2. 配置 manifest.json，id 用 literature-importer

3. 添加一個命令「導入文獻」，點擊後掃描 Inbox 並執行導入

4. 設置頁允許配置 Inbox 路徑、目標目錄、標籤規則

5. 保留腳本的日誌功能，寫入 vault 的 .obsidian/logs/

6. 關鍵：所有操作只創建新文件，不修改、不刪除已有文件

它自己會建目錄結構，自己寫 manifest.json，自己處理 Obsidian API 的坑。你只需要最後驗證。

Step 4：讓 AI 自己測自己

插件寫完別急着用。讓 Codex 生成測試用例：

給這個插件寫測試用例，覆蓋以下場景：

1. 空 Inbox，什麼都不該發生

2. 正常 PDF，筆記生成且格式正確

3. 損壞的 PDF，應該報錯但不中斷其他文件處理

4. 目標目錄已存在同名筆記，應該跳過而不是覆蓋

5. Frontmatter 为空的情况

用 pytest 寫，跑一遍，告訴我哪些用例失敗了。

讓 AI 寫測試，本質是讓 AI 自己審自己。它能發現很多你根本想不到的邊緣情況。

四、避坑指南（這篇的重點）

工具造出來了，坑也來了。這四個坑我全踩過，寫下來你繞開。

坑 1：上下文污染

你的知識庫可能有幾百上千個 Markdown 文件。如果你讓 Agent 讀整個 Vault，它的上下文窗口直接爆掉，然後開始胡言亂語，把不相關的筆記內容混進來。

對策很簡單，幹活之前把範圍圈死：

只读取 D:\wiki\knowledge-vault\00-Inbox 目录，

不要掃描其他目錄，不要讀取 200 篇以上的文件。坑 2：CLAUDE.md 越寫越長

CLAUDE.md 是給 AI 看的項目規則文件，每次會話自動加載。很多人什麼規則都往裏塞，最後塞成一本幾百行的字典。

規則超過 1500 行，說明架構出了問題，不是規則不夠，是設計亂了。

正確做法是分層。全局規則放根目錄的 CLAUDE.md，只管「不許刪除文件、備份優先」這種鐵律。某個子目錄的特殊規則，放子目錄自己的 CLAUDE.md。各管各的，互不干擾。

坑 3：AI 誤刪你的筆記

這是最要命的一個。AI 有讀寫權限，一個錯誤的 delete 操作，你的筆記就沒了。

三條防線，按順序：

第一，**明確規則**。在 CLAUDE.md 裏寫死：

鐵律

- 禁止刪除任何 .md 文件

- 禁止修改原始資料（raw/ 和 00-Inbox/）

- 所有整理操作必須創建新文件

- 高風險操作（刪除、覆蓋、移動）前必須詢問用戶

第二，**權限控制**。Claude Code 支持權限模式，把工作區限制在指定目錄：

只允許寫工作區內的文件

claude --permission-mode workspace-write

高風險操作需要人工確認

claude --permission-mode acceptEdits --approval-policy on-request

第三，**備份**。動手前先備份 Vault。Obsidian 官方同步或者 Git 都行，一天一次自動提交，出事了隨時回滾。

坑 4：不規劃就動手

最貴的錯誤是讓 AI 直接生成代碼，生成完發現方向錯了，全部推翻重來。

四步工作流記死：**探索 規劃 執行 驗證**。每一步都確認了再進下一步。AI 編代碼不貴，貴的是返工。

五、一條額外提醒：增量更新

讓 AI 改你的筆記庫，最安全的姿勢是「只加不減」。

我有個原則，跟 AI 說整理任務時，永遠加一句「創建新文件，不要修改原文件」。整理完你覺得對的，手動把舊的刪了。這樣哪怕 AI 理解錯了，你的原始數據也毫髮無損。

這個習慣救過我一次。有次讓 Agent「整理」我的文獻筆記，它把我一篇三千字的筆記壓縮成了一百字摘要。幸虧原始文件還在，恢復回來就沒事。

從那天起，我所有自動化任務的默認策略都是 append-only。新內容只追加，舊內容不碰。

六、收個尾

這四篇下來，你的 Obsidian 從靜態知識庫，到有手（OpenClaw）、有腦（Hermes）、能造工具（本篇），已經是個完整體系了。

但造工具這條路，說實話不適合所有人。折騰環境、調權限、看日誌，這些對非程序員來說還是有點門檻。

下一篇我們換條路。講講 WorkBuddy 這種輕量 Agent，不用寫代碼，不用配環境，說一句話它就能幫你整理知識庫。適合不想折騰的人。
