Nuxt 4.5 发布：Vite 8 + Rspack 2 重构构建层，Nuxt 3 将于 8 月底停止支持

掘金· 8月13日 周四 · 查看原文 ↗
本文為原文轉錄（繁體中文，簡體已自動轉繁），版權歸原媒體所有；內容機器翻譯自第三方媒體，僅供參考，以原文為準。

我們組一個React中後臺項目，跑了三年多了，452個模塊。Webpack 5打包一次生產環境接近兩分鐘，CI排隊的時候看着進度條，總覺得在浪費生命。 上週刷GitHub看到Rspack已經2.1.7了，release note裏寫了不少性能優化，我尋思趁這周需求間隙試試。官方文檔看起來挺清爽的：改個配置文件名，換幾個loader，完事。半天就夠了吧。 結果折騰了兩天。文檔寫得挺清楚，但坑都在文檔沒寫的地方。

SWC替換Babel，上來就給我一棒子

配置文件改名那步确实没啥好说的，<code>webpack.config.js</code> 改成 <code>rspack.config.js</code>，<code>webpack</code> 换成 <code>@rspack/core</code>，内置插件名字换一换，五分钟搞定。跑 <code>npx rspack build</code>，直接就开始编译了，没报错。
然后我把 <code>babel-loader</code> 换成 <code>builtin:swc-loader</code>，按照文档的示例改了改配置：
// 改之前
{
  test: /.(j|t)sx?$/,
  loader: 'babel-loader',
  options: {
    presets: [
      '@babel/preset-env',
      '@babel/preset-react',
      '@babel/preset-typescript'
    ],
    plugins: [
      '@babel/plugin-proposal-decorators',
      'babel-plugin-styled-components'
    ]
  }
}
// 改之后（第一版，有问题的）
{
  test: /.(j|t)sx?$/,
  loader: 'builtin:swc-loader',
  options: {
    jsc: {
      parser: {
        syntax: 'typescript',
        tsx: true,
        decorators: true
      },
      transform: {
        react: { runtime: 'automatic' },
        legacyDecorator: true
      }
    }
  }
}

編譯炸了。報錯大概長這樣：

Error: Expected ';', '}' or <EOF>
   ,- src/utils/legacy-parser.ts:42:15
   |
42 |   const result = arr?.filter(x => x != null)
   |                  ^

可選鏈 ?. 報語法錯誤？？我第一反應是項目裏是不是有什麼奇怪的語法沒注意到，檢查了一圈發現不是。然後我以爲是 SWC 配置哪裏寫錯了，試了好幾種寫法，改 parser、改 target、改 transform，折騰了一個多小時都不行。

最后去翻 Rspack 的 issues 才搞明白：builtin:swc-loader 的 syntax: 'typescript' 并不会自动开启所有 ES 新特性的解析。Babel 的 @babel/preset-env 默认就处理可选链、空值合并这些，但 SWC 不会，得在 jsc 配置里显式指定 target：

// 最终能用的版本
{
  test: /.(j|t)sx?$/,
  loader: 'builtin:swc-loader',
  options: {
    jsc: {
      parser: {
        syntax: 'typescript',
        tsx: true,
        decorators: true
      },
      transform: {
        react: { runtime: 'automatic' },
        legacyDecorator: true
      },
      target: 'es2020'  // 加上这行就好了
    }
  }
}

結果還沒完。我們項目裏有一些 .js 文件也用了 decorators（別問爲什麼，三年前的代碼，什麼妖魔鬼怪都有），TypeScript parser 不認 JS 文件裏的 decorators。又得給 .js 單獨寫一條規則：

{
  test: /.js$/,
  loader: 'builtin:swc-loader',
  options: {
    jsc: {
      parser: { syntax: 'ecmascript', decorators: true },
      transform: { legacyDecorator: true }
    }
  }
}

光這一個 loader 就搞了我大半天。Babel 時代 @babel/preset-env 一把梭的日子一去不復返了。SWC 配置粒度更細，但你得真的知道自己在配什麼。

另外 babel-plugin-styled-components 這個——SWC 裏沒有直接對應的插件。我們項目裏用 styled-components 不多，趁這個機會直接遷到 CSS Modules 了。如果你們項目裏 styled-components 用得重，這個遷移成本得額外算。

CSS Modules全炸了，差點回滾

Loader 搞完之後編譯總算過了。心想最難的應該搞定了，跑起來看看效果吧。 頁面出來了。然後我差點沒認出來——所有樣式都亂了。 我們在 Webpack 裏 CSS Modules 用的 [local]_[hash:8] 命名：

// Webpack的配置
{
  loader: 'css-loader',
  options: {
    modules: {
      localIdentName: '[local]_[hash:8]'
    }
  }
}

我一開始在 Rspack 裏這麼寫的：

// 有问题的版本
{
  test: /.module.css$/,
  use: [rspack.CssExtractRspackPlugin.loader, 'css-loader'],
  type: 'css/module'
}

問題出在 type: 'css/module' 走的是 Rspack 內置的 CSS Modules 處理，它用的是自己的默認命名規則，完全忽略了 css-loader 裏的 localIdentName。兩種機制不能混用，我當時不知道，配置寫上去跟沒寫一樣。

搞到第二天下午還沒搞定的時候，我一度想把配置回滾了，先不遷了。後來靜下心來翻 Rspack 文檔裏 CSS 那章，才發現內置方式要把命名配置放在 module.parser 裏：

// 最终正确的版本
module: {
  parser: {
    'css/module': {
      exports: 'local',
      localIdentName: '[local]_[hash:8]'
    }
  },
  rules: [
    {
      test: /.module.css$/,
      type: 'css/module',
      use: [rspack.CssExtractRspackPlugin.loader]
    }
  ]
}

改完樣式恢復了。哦對，還有一點——如果你的項目不是用 .module.css 後綴區分，而是在 webpack 裏配 modules: { auto: true } 按文件名自動識別的，Rspack 的 auto 行爲和 Webpack 不完全一致，這塊得多測試。

剩下的坑不大但都挺煩人

<code>copy-webpack-plugin</code> 换成 <code>rspack.CopyRspackPlugin</code>，配置格式基本一样，这个倒丝滑。<code>fork-ts-checker-webpack-plugin</code> 换成 <code>ts-checker-rspack-plugin</code>，注意 Rspack 2.x 推荐搭配 TypeScript 7 使用，我们还在 TS 5.x，暂时兼容但最好计划升级。
<code>thread-loader</code> 和 <code>cache-loader</code> 直接删掉就行——Rspack 本身就是 Rust 多线程编译，内置持久化缓存，这俩在 Webpack 时代用来加速的 loader 在这反而拖后腿。<code>webpack-dev-server</code> 换成 <code>rspack serve</code>，代理配置大部分兼容，但 <code>historyApiFallback</code> 的 <code>rewrites</code> 函数传参方式有点不一样，踩了一下。
对了还有 <code>import.meta.env</code>——我一开始看 2.1.6 的 changelog 说支持了，正高兴呢，结果 2.1.7 又给 revert 了。老老实实用 <code>DefinePlugin</code> 吧。

遷移完的感受

冷啓動從38秒降到6秒左右，HMR從400多毫秒降到不到100毫秒，生產構建從快兩分鐘降到15秒上下。內存從將近2G降到600多M。 冷啓動那個提升說實話感知不強，等6秒反正也會去倒杯水。但 HMR 是實打實的體感變化——改一行代碼頁面上幾乎是即時反饋，之前那400毫秒的延遲其實每次都在打斷思路。CI 構建時間縮短對發佈節奏的提升也是真的，push 完基本就能部署了。

值不值得遷，得看你自己的情況。我們項目是 Webpack 5，450多個模塊，構建兩分鐘，遷完確實爽。如果你項目規模差不多，我覺得可以試試。但如果你還在 Webpack 4，先升到5吧，Rspack對4的loader兼容性更差，遷移成本會高不少。已經在用Vite的就別折騰了，Rspack的優勢是Webpack存量項目的平滑遷移，跟Vite不在一個賽道。

最後一個建議：遷之前先把你那個 Webpack 配置理一遍。我們那個配置文件三年裏好幾個人往上疊，裏面有不少已經沒用的 loader。趁遷移清理一遍，比翻譯一份臃腫的配置省事得多。
