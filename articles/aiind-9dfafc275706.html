GitLab 19.5 發佈，將智能體開發納入可治理的 DevOps 平台能力

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

GitLab 19.5 於 10 月 15 日發佈，將智能體軟件開發和治理作為平台核心： GitLab MCP 服務器正式可用，同時擴展了外部 AI 智能體與 GitLab 交互的方式。

該版本允許 Claude Code 、 Cursor 等兼容 MCP 的工具訪問更多 GitLab 工具目錄，並調用 GitLab Duo Agent Platform 的智能體和工作流。與此同時，GitLab 增加了對外部智能體的治理控制，讓安全團隊能夠了解哪些智能體正在被使用、誰在使用、針對哪些項目。

正式可用的 GitLab MCP 服務器通過 Model Context Protocol 為智能體開放 GitLab 平台能力。新增工具允許智能體發現群組、檢查單個 CI/CD 構件文件，以及啓動或監控 GitLab Duo 智能體和工作流。管理員還可以選擇暴露哪些 MCP 工具集，從而減少不必要的工具以及它們佔用的上下文。

為智能體提供所有可用工具會增加上下文消耗，也會增加模型可能執行的操作數量。工具集篩選是一種輕量化的最小權限代理設計方案。

GitLab.com 還引入了 MCP 速率限制：免費版用户每分鐘 60 次請求，Premium 和 Ultimate 用户每分鐘 600 次，重連與重試請求同樣計入限額。

更重要的新增功能之一是將 外部連接智能體 納入 GitLab 的 AI 治理範圍。

此前， AI 治理儀表盤 主要關注 GitLab Duo Agent Platform 的智能體。GitLab 19.5 允許通過 GitLab CLI 連接 Claude Code、Cursor 和 Codex 等工具。配置完成後，組織可以記錄符合條件的智能體會話，包括用户、智能體、項目和時間信息，這些活動會與 GitLab 自身的智能體一起顯示。審計事件還可以流式傳輸到 SIEM 系統。

這不只是提供一個 MCP 端點，而是邁出了重要一步：連通性提供能力，而治理決定了這種能力能否在組織規模下安全使用。

GitLab Duo CLI 新增了自動模式，允許智能體執行工具而無需為每個 Shell 命令、Git 操作或 MCP 調用請求批准。該功能默認關閉，可在實例、群組和項目級別進行控制，明確標記為“始終拒絕”（Always Deny）的工具仍會被阻止。

/goal 命令也正式可用。開發者只需描述一個開放式目標，GitLab Duo 就會交由受治理的流程完成代碼實現與結果核驗。

這些功能共同推動 GitLab 向智能體驅動開發模式演進：開發者只需要表達意圖，由智能體在開發環境中自動執行多步任務。

這使得治理控制變得越來越重要：智能體的自主性越高，依賴人工批准每個單獨操作就越不現實。

該版本同時正式發佈 GitLab Secrets Manager 。它基於 OpenBao 構建，與現有 GitLab 群組和項目權限集成，將密鑰作用範圍限定於需要它們的任務內，併為密鑰操作生成審計事件。

GitLab 還擴展了安全配置模板能力，企業可以統一配置密鑰檢測（Secret Detection）、靜態應用安全檢測（SAST）的參數，例如排除路徑、分析器鏡像、全歷史掃描等，不必在每個項目的 CI/CD 文件中重複配置。

這些能力加強了對智能體可能訪問的代碼庫、憑證和流水線的控制，與智能體功能形成互補。

GitLab 的發展方向和 GitHub 策略越來越相似：把 代碼智能體變稱軟件生命週期的參與方 。但 GitLab 的側重點是將外部智能體接入自身現有的 DevSecOps 治理體系。

GitHub 的生態受益於 GitHub Copilot 和編碼智能體的廣泛覆蓋，而 Cursor 和 Claude Code 等工具更側重開發者的本地環境。GitLab 的 MCP 方案則試圖讓 DevOps 平台可被智能體訪問，包括代碼庫、議題、流水線、構件以及 GitLab 原生智能體。

GitLab 關注的競爭焦點正在從“哪個編碼助手生成的代碼更好”轉向“哪個平台能為自主智能體執行工程工作提供最安全、最有用的環境”。
