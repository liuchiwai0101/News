正文

我們如何用 Python 改造應用存儲平台 Habitat，以應對前所未有的增長。

作者：Jon Lee、Chaomin Yu 和 Ben Ries，技術團隊成員

每一款 OpenAI 產品都依賴於快速、可靠的數據訪問，無論是用户登錄、查看其 Codex 設置，還是在 ChatGPT 中開啓一段新對話。這些操作中的每一個，在產品能夠響應之前，都可能需要許多次獨立的數據查詢。如果這些請求很慢，產品就會顯得很慢。如果這些請求失敗，產品就會徹底停止工作。

Habitat 是我們構建的在線存儲平台，讓 OpenAI 產品能夠快速、可靠地訪問所需信息。Habitat 現在每秒處理超過 7000 萬次請求，支撐着每週超過 10 億人使用的產品，覆蓋近 40 個地理區域。兩年前，Habitat 還只是一個連接到單一數據庫的簡單 Python 客户端庫。如今，它已是一個複雜的分佈式系統，服務於超過 500 PB 的數據。

在這一規模上構建和運營基礎設施絕非易事，但也並非特別具有挑戰性。真正讓我們的情況獨一無二的是，我們不得不以空前的速度擴展，以支撐驚人的用户增長和產品需求，同時還要構建一個成熟的平台。通常情況下，系統工程師會按照 10 倍規模來構建，並希望它能支撐幾年，同時為下一個 10 倍做準備。而在我們的情況中，過去三年我們每年都實現了超過 10 倍的增長。因此，構建和運營 Habitat 的過程是一系列戰術決策和排序：從最低層級理解每個組件，以儘可能從現有技術棧中榨取更多性能，同時抵禦存儲和計算容量的緊缺，為基礎性投入爭取時間。

隨着 OpenAI 的發展，Habitat 也必須隨之成長：首先要可靠到足以承載關鍵業務的產品流量，然後要快到足以服務全球用户，最後還要能夠嫺熟地支撐超大規模運行。本文是關於我們如何擴展在線存儲的兩部分系列文章中的第一篇。在這篇文章中，我們將分享 Habitat 是如何演進的，我們為什麼把它從一個庫轉變為一個服務，以及我們如何將一個用不常見的服務棧語言——Python——編寫的服務，擴展為一個可靠的存儲平台層。

在後續文章中，我們將詳細講述我們如何實現大規模下的多租户可靠性、我們優化讀取性能的分層策略，以及我們如何擴展與 Azure Cosmos DB 的合作關係，以可靠地應對前所未有的需求。

什麼是 Habitat？

Habitat 源於一個簡單的想法：產品工程師不應該需要操心數據庫管理。Habitat 於 2024 年年中起步，最初只是一個與 ChatGPT 主服務器交互的小型 Python 庫。它支持一小組操作，這些操作在底層映射到數據庫應用 Azure Cosmos DB。

這個庫的職責是為產品團隊提供一種簡單的方式來存儲和檢索數據，而無需掌握底層的細節。Habitat 負責處理必要的工作：判斷涉及的是哪種數據、數據應該來自哪裏（或去往哪裏）、該請求是否被允許，等等。

產品工程師無需關心 schema 查找、路由、授權、加密、序列化、請求塑形和連接池。他們甚至無需考慮數據來自哪裏：Azure Cosmos DB、緩存，還是其他類型的存儲。

這個 Python 庫運行良好，Habitat 在 OpenAI 的產品工程師中得到了快速採用，儘管並沒有任何集中的推動來促使大家放棄使用自助式 Postgres 和 Azure Cosmos DB。

隨着產品需求的演變，產品開發者甚至可以輕鬆地為這個共享庫添加諸如客户端緩存、壓縮或加密等功能支持。

構建一個服務，以更好地支持多個複雜產品

到 2025 年中期，Habitat 作為客户端側實現已經達到了極限。隨着 Habitat 層變得越來越複雜，OpenAI 的服務數量不斷增加，向後兼容的協議變更已經變得不可行。

在一個案例中，我們希望將最關鍵的數據集遷移到一組按區域分佈的 Azure Cosmos DB 賬户上，以縮小任何單一區域故障的影響範圍。進行這一變更需要在客户端中引入額外的路由邏輯，將其隱藏在功能開關之後，確保它推廣到所有客户端，然後再啓用該功能開關。

跨數十個服務協調部署，並與每個團隊逐一推進上線，花了數天時間。在啓用之前，我們意識到需要引入一些影子流量機制，以確保分片邏輯正確無誤。這又花了幾天才完成部署。修復一個我們後來發現並不正確的 bug？又是幾天。最終，我們準備好啓用該開關，結果其中一個團隊因無關原因將他們的服務回滾到了一個此前有 bug 的客户端版本，導致了我們一直努力避免的故障。

客户端庫的變更需要在數十個服務之間進行復雜的協調，這一過程被證明越來越脆弱、低效，且容易發生運維故障。為了減少未來部署中的這種運維擴散，我們決定將 Habitat 拆分為一個獨立服務。

通過將存儲邏輯解耦為一個獨立服務，我們建立了一個統一的控制點，用於部署、可觀測性和平台增強。我們不再需要管理碎片化的更新，而是可以集中實施改進，讓每個 OpenAI 產品立即受益。

集中式服務還為我們提供了一個單一卡點，以提供最強的數據安全和隱私原語。Habitat 服務是我們集中執行訪問控制策略、進行審計日誌記錄，以及限制對 Azure Cosmos DB 等底層存儲資源訪問的地方。Habitat 在保護用户數據和防止來自外部、內部及智能體行為者的未授權訪問方面發揮着關鍵作用。

大規模啓動一個 Python 服務

我們知道需要一個服務，但還不想完全從 Python 遷移出去，即便 Python 作為服務會帶來額外的開銷。與本地庫執行相比，用 Python 跑高吞吐服務會增加網絡延遲，並帶來可觀的 CPU 和內存擴容成本。此外，我們意識到 Python 的低效在 100 倍規模下將無法接受，最終幾乎必然要重寫。

不過，我們把這視為一次戰略性的技術債引入。當時我們的首要目標不是成本或資源優化，而是為產品開發者解除阻塞、實現平台穩定性。通過在短期內接受 Python 服務的性能取捨，我們得以優先處理更緊迫的挑戰、建立核心 API，並搭建起穩健的基礎設施。

我們還做了一次經過盤算的押注：我們自己的編碼模型快速進步，會在未來簡化技術路徑。我們賭的是，等到必須徹底遷離 Python 時，Codex 和 GPT 能讓這次遷移變得可行。這個賭注最終被證明是對的。

從性能角度看，把 Habitat 作為 Python 服務來運行並非最優，但卻是必要的選擇。Python 讓我們能快速推進，但這並不意味着我們可以不顧一切、接受明顯更差的延遲。當用户的平均請求會觸發數百次數據庫調用時，用户感受到的是最慢的那次數據庫調用。我們發現，在這一規模下運行 Python 服務的主要挑戰，就在於管理這些尾部延遲。

追蹤 asyncio 延遲

Asyncio 幫助 Python 併發執行 I/O 密集型工作負載，但無法繞過 Python GIL 提供 CPU 並行能力。除了 I/O 密集型的請求代理之外，Habitat 還承擔大量 CPU 密集型職責和後台任務：路由、壓縮、加密、校驗和計算、下游健康檢查、請求影子複製以及對沖請求。

由於我們的服務中存在如此多的 CPU 密集型工作負載和後台任務，asyncio 調度延遲很容易成為尾部請求延遲的主要因素。在為初始服務上線進行調優之前，我們在 p99 及以上延遲的請求鏈路追蹤中看到，雖然下游存儲響應很快，但請求經常停滯在等待負責解析響應的協程被重新調度上。

對於 OpenAI 的 Python 服務，我們發現，除了測量內存、CPU、網絡和磁盤使用率的標準利用率與飽和度指標之外，同樣關鍵的是還要監控 asyncio 事件循環及其繁忙程度，並據此進行調優。

通過定期調度後台任務並記錄預期執行時間與實際執行時間之間的差值，我們能夠以實證方式實時測量事件循環的調度延遲。在高利用率下，當存在大量高開銷任務時，即使每個進程的併發請求數量適中，也足以產生顯著的調度抖動，最高可達數百毫秒，在某些邊緣情況下甚至可達數秒。

因此，我們只能讓每個進程僅處理少量併發請求，轉而大規模擴展 Python 工作進程的數量。

降低功能開關配置中的尾部延遲

在服務最初上線時，我們通過線上服務的 CPU 性能剖析發現了一個導致 asyncio 高延遲（以及由此產生的高尾部延遲）的根本原因：通過 Statsig（一款用於管理功能開關、並可用於運行 A/B 測試等功能的工具）對功能開關配置進行週期性的 JSON 解析。

默認情況下，Statsig 被配置為每分鐘輪詢一次刷新後的配置，且沒有抖動，而該配置包含了所有服務中的每一條生產規則。另外，在架構上還做出了一項決策：每個 pod 運行最多 8 個 Python 進程，以提高 CPU 使用率並提供更低的延遲。兩者疊加意味着，每分鐘每個 pod 都會出現某個時刻，其所有工作進程都停止處理正在進行的請求，轉而將 CPU 週期花在解析一個巨大的配置文件上。

一旦 CPU 性能剖析幫助我們定位了根本原因，修復就很直接了：部署一個更小的、有針對性的配置，延長刷新間隔，併為這類後台任務添加一些抖動。

負載均衡與連接池管理

為了保持較低的 asyncio 延遲，在服務器進程之間維持良好的請求負載均衡同樣至關重要；如果不加以調優，連接池最終可能會與此背道而馳。

在客户端連接池場景下，一個發起大量併發請求的客户端進程可能只建立少量服務器連接，結果將其全部負載只發送給少數幾個進程。在調整我們的負載均衡方式之前，我們的服務利用率差異很大，一些尾部進程承載的併發請求數量是平均值的 5-10 倍。

我們是在一次偶然事件中發現這一點的：儘管已經停止了那個讓部分服務過載的客户端，仍有一小部分進程在突發流量過去很久之後依然處於降級狀態。事實上，我們注意到這些進程出現了失控式降級，收到的請求越來越多，直到我們重啓它們才恢復。一旦某個 pod 過載，某些行為就會把更多流量釘到那個過載的 pod 上。這是一類我們一些同事在以往工作中非常熟悉的故障：亞穩態故障。

我們懷疑連接池是罪魁禍首，並通過限制最大連接複用時長來驗證這一猜測，結果確實減輕了性能退化，從而確認了我們的排查方向。進一步調查發現，Python 的 aiohttp TCPConnector 默認採用 LIFO 連接複用：最近歸還的連接會被選用於下一個請求。這通常是一個合理的默認行為：複用較新的連接可以讓為應對突發流量而額外創建的連接進入空閒超時，從而降低維護額外連接的開銷。但在我們的場景中，它造成了一種亞穩態故障。在一波請求突發期間，發往較慢的過載服務器的請求會更晚將連接歸還到池中，因此這些連接被後續請求選中的頻率更高，逐漸將更多流量集中到那些本已不堪重負的 pod 上。將連接池修補為使用 FIFO 複用後，打破了這一反饋迴路，甚至降低了我們穩態下的請求方差。

避免下游資源被淹沒

針對低 asyncio 延遲進行調優，再加上擁有如此多的 Python 進程，一個副作用就是：海量的連接非常容易壓垮下游依賴（即所謂的“驚群效應”）。

一次常規的每日部署——如果沒有調優得足夠慢——就可能因連接反覆建立與斷開而引發顯著的 CPU 抖動。或者，一處連接泄漏就可能因佔滿 NAT 網關而拖垮整個網絡。這些問題對其他服務來説也並不罕見，但由於進程數量多了一個數量級，觸發閾值被大幅拉低，往往會佔滿那些客户端在穩態下僅憑純吞吐量並不預期需要處理的網絡相關資源。

我們還依賴 Envoy 來最大化連接扇入。我們用它把 Python 的 HTTP/1 連接升級為 HTTP/2，以利用多路複用，然後將這些連接池化並延長連接生命週期。Envoy 還為我們提供了一個集中位置來實現限流和熔斷，而這些如果在每個獨立的 Python 進程中實現，效果會大打折扣。

為什麼 Habitat 做得更少

我們能夠將 Python 擴展到如此規模的一個原因，是 Habitat 受限的 API，它讓請求成本保持可預測。Habitat 沒有允許客户端構造任意 SQL 查詢——這類查詢可能導致大規模全表掃描或跨多張表的連接——而是暴露了一個簡單的 NoSQL API。缺少強大的 API 是 Habitat 設計中有意做出的權衡。

我們力求針對簡單、可預測、工作量恆定的請求進行優化。根據我們的經驗，這類系統在擴展上要容易得多，也不容易出錯或被誤用。扇出不可預測的請求在運維上很危險：它們會讓隔離和負載均衡變得複雜，並引入延遲懸崖，無論對服務本身還是其客户端來説都難以擴展。

在我們遷移到 Habitat 和 Azure Cosmos DB 之前，OpenAI 的大部分在線數據都存儲在 Postgres 上。當時，審查所有查詢和 schema 變更很容易，可以在發佈到生產環境之前確保它們行為良好、且針對已建索引的數據運行。隨着團隊和產品的增長，這很快變得難以管理，併成為頻繁導致故障的原因——熱路徑上一個開銷高昂的新查詢就能拖垮整個數據庫。

這裏的問題在於成本失衡：編寫開銷高昂、難以運行的 SQL 查詢既便宜又容易。在 Habitat 中，我們避免了這一點，讓開銷高昂的查詢在客户端一側變得極其明顯。不存在可能讓 Habitat 過載的無界查詢，而複雜的 join 和圖遍歷需要產品團隊承擔一部分繁重工作，這有助於從整體上優化出更高效的設計。

Habitat 對外暴露一個 NoSQL API，其建模圍繞客户端定義的對象類型和邊類型，靈感來自 TAO⁠ 。客户端預先定義對象和邊以及它們之間的相互關係，但不定義每種類型的內容。由此產生的關係類似圖，但 Habitat 本身並不支持典型的圖遍歷查詢，只能查詢某個特定對象的直接邊。

我們對這個圖進行分區，使每個對象及其對應的邊在存儲層分區中共置，但我們並未在數據庫層面做出一致努力，將對象與其邊所指向的遠程對象共置。結果是，該模型可以輕鬆分區以實現水平擴展，但圖遍歷效率低下，因為對象之間的任意一次特定跳轉都可能需要從存儲在不同區域的兩個完全不同的 Azure Cosmos DB 賬户中獲取數據。

對於查詢需求更復雜的客户，我們確實通過 Rockset 提供了一個離線的 Habitat 二級視圖。我們使用變更數據捕獲（CDC）將近乎實時地將在線存儲中的變更流式傳輸到隔離的 Rockset 實例。每個客户團隊負責為自己的複雜查詢需求擴展其各自的 Rockset 實例。

這種 Rockset 配置給我們的客户帶來了額外的摩擦，但我們認為在當前這個特定時刻這是正確的權衡：讓簡單查詢成為默認選項，同時為需要複雜查詢的用户提供一個逃生通道。這一設計將我們的在線存儲與讀取密集型的分析和搜索工作負載隔離開來。

從 Python 遷移到 Rust

將 Python 重寫推遲一年，使我們能夠在超高速增長期間專注於更緊迫、更具影響力的挑戰。隨着平台日趨成熟、增長持續加速，並且它已成為 OpenAI 按核心數計算的第二大服務（按 Envoy 部署規模計算為第四大），終於到了告別 Python 的時候。在巔峯時期，Python 曾幫助我們每秒處理超過 2000 萬次請求。

2026 年第二季度，僅憑 2 名工程師、Codex 和 GPT‑5.5，我們就用 Rust 重寫了整個服務。這個新的 Rust 服務目前承載了我們 95% 的生產請求；我們將在未來幾周內徹底棄用 Python。我們的數據顯示，Rust 服務的 CPU 效率是 Python 版本的 6 倍，內存效率是 15 倍，平均延遲和尾部延遲都顯著更低。我們計劃在未來的博客中分享更多經驗。

優化我們的數據庫層：Azure Cosmos DB

這個 Python——如今是 Rust——服務只是 Habitat 的一個側面。在本系列的第二部分中，我們將講述我們如何快速擴展在線存儲以服務超過 10 億 ChatGPT 用户，屆時會談到存儲層，以及 Habitat 如何每秒處理超過 500 PB 的數據和超過 7000 萬次請求。
