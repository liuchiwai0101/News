作者：Addy Osmani

Web 開發者通常將瀏覽器視作一個“黑盒”——它彷彿會施展魔法，將 HTML、CSS 和 JavaScript 轉化爲交互式的 Web 應用。然而事實是，像 Chrome (Chromium)、Firefox (Gecko) 或 Safari (WebKit) 這樣的現代 Web 瀏覽器，是極其複雜的軟件工程傑作。它統籌協調網絡請求、解析並執行代碼、利用 GPU 加速渲染圖形，並通過沙盒進程隔離內容以保障安全。 本文將深入探討現代瀏覽器的工作原理——重點聚焦於 Chromium 的架構與內核，同時也會指出其他瀏覽器引擎的差異之處。我們將探索從網絡棧、解析流水線，到基於 Blink 的渲染流程、基於 V8 的 JavaScript 引擎、模塊加載機制、多進程架構、安全沙盒，以及開發者工具的方方面面。我們的目標是爲開發者提供一份易於理解的指南，揭開瀏覽器幕後運作的神祕面紗。 讓我們開始這場探索瀏覽器內核的旅程吧。 每一次頁面加載，都始於瀏覽器網絡棧從 Web 獲取資源。當你在地址欄輸入 URL 或點擊鏈接時，瀏覽器的 UI 線程（運行在“瀏覽器進程”中）就會發起一次導航請求。 **瀏覽器進程（Browser Process）**是主控進程，負責管理所有其他進程以及瀏覽器的用戶界面。特定網頁標籤頁之外發生的一切，都由瀏覽器進程控制。 主要步驟包括： Content-Type 響應頭或不正確，瀏覽器可能需要對 MIME 類型進行嗅探（Sniffing），以決定如何處理內容。例如，如果響應看起來像 HTML 但未標記爲 HTML，瀏覽器依然會嘗試將其作爲 HTML 處理（依據寬容的 Web 標準）。這裏同樣存在安全措施：網絡層會檢查 Content-Type，並可能攔截可疑的 MIME 錯配或不允許的跨源數據（Chrome 的 CORB 即“跨源讀取阻塞”就是這種機制）。瀏覽器還會向“安全瀏覽（Safe Browsing）”或類似服務發起查詢，以攔截已知的惡意負載。Location 頭），網絡代碼將（在通知 UI 線程後）跟隨重定向，並向新 URL 重新發起請求。只有獲取到包含實際內容的最終響應時，瀏覽器纔會進入內容處理階段。所有這些步驟都發生在網絡棧中。在 Chromium 中，網絡棧運行在專門的**網絡服務（Network Service）**中（作爲 Chrome “服務化”改造的一部分，它現在通常是一個獨立的進程）。瀏覽器進程的網絡線程在底層利用操作系統的網絡 API 協調 Socket 通信的底層工作。重要的是，這種設計意味着渲染器進程（負責執行頁面代碼）無法直接訪問網絡——它必須請求瀏覽器進程代爲獲取資源，這是一個巨大的安全優勢。 現代瀏覽器在網絡階段實現了極其複雜的性能優化： 預加載掃描器 (Preload Scanner)： Chromium 實現了一個精密的預加載掃描器，它會在主解析器之前對 HTML 標記進行分詞（Tokenize）。當主 HTML 解析器被 CSS 或同步 JavaScript 阻塞時，預加載掃描器會繼續掃描原始標記，尋找可以並行獲取的資源（如圖片、腳本和樣式表）。這種機制對現代瀏覽器性能至關重要，且無需開發者干預即可自動運行。需要注意的是，預加載掃描器無法發現通過 JavaScript 注入的資源，這會導致這些資源按順序加載而非併發加載。 Early Hints (HTTP 103)： Early Hints 允許服務器在生成主響應的“思考時間”內，使用 HTTP 103 狀態碼發送資源提示。這使得可以在服務端處理期間提前發送 preconnect（預連接）和 preload（預加載）提示，有望將最大內容繪製（LCP）時間縮短數百毫秒。Early Hints 僅適用於導航請求，支持預連接和預加載指令，但不支持 prefetch（預提取）。 Speculation Rules API（推測規則 API）： 這是一項較新的 Web 標準，允許開發者定義規則，根據用戶的交互模式動態預提取（prefetch）和預渲染（prerender）URL。與傳統的鏈接預提取不同，此 API 可以預渲染整個頁面（包括執行 JavaScript），從而實現近乎瞬間的加載。該 API 在 <script> 標籤內或 HTTP 頭中使用 JSON 語法來指定應推測加載哪些 URL。爲防止濫用，Chrome 設有容量限制，並根據緊急程度設置了不同的閾值。 HTTP/2 與 HTTP/3： 大多數基於 Chromium 的瀏覽器和 Firefox 全面支持 HTTP/2，並且廣泛支持基於 QUIC 的 HTTP/3（Chrome 對支持該協議的站點默認開啓）。這些協議通過支持併發傳輸和降低握手開銷來提升頁面加載速度。從開發者的角度來看，這意味着你可能不再需要使用“雪碧圖（Sprite sheets）”或“域名分片（Domain sharding）”等老舊技巧——瀏覽器已經能在單個連接上高效地並行獲取大量小文件。 資源優先級排序： 瀏覽器還會對某些資源進行優先級排序。通常，HTML 和 CSS 的優先級很高（因爲它們會阻塞渲染），腳本可能是中等（如果正確標記了 defer/async 則可能爲高），圖片通常較低。Chromium 的網絡棧會分配權重，甚至可以取消或推遲某些請求，以優先滿足首次渲染所需的資源。開發者可以使用 <link rel="preload"> 和 Fetch Priority (提取優先級) 來影響資源的優先級。 在網絡階段結束時，瀏覽器拿到了頁面的初始 HTML（假設這是一次 HTML 導航）。此時，Chrome 的瀏覽器進程會選擇一個**渲染器進程（Renderer Process）**來處理這些內容。Chrome 通常會與網絡請求並行（推測性地）啓動一個新的渲染器進程，以便數據到達時隨時待命。這個渲染器進程是隔離的（後文探討多進程架構時會詳述），它將接管解析和渲染頁面的工作。 一旦完全接收到響應（或數據流開始湧入），瀏覽器進程就會提交導航（Commit Navigation）：它向渲染器進程發出信號，讓其接收字節流並開始處理頁面。就在這一刻，地址欄會更新，安全指示器（HTTPS 鎖等）也會針對新站點顯示。現在，舞臺交給了渲染器進程：解析 HTML、加載子資源、執行腳本，並繪製頁面。 當渲染器進程接收到 HTML 內容時，其主線程（Main thread）開始按照 HTML 規範對其進行解析。解析 HTML 的結果是 DOM（文檔對象模型）——一棵代表頁面結構的對象樹。解析是增量的，並且可以與網絡讀取交織進行（瀏覽器以流式方式解析 HTML，因此甚至在整個 HTML 文件下載完畢之前，DOM 就可以開始構建）。 HTML 解析與 DOM 構建： HTML 規範將 HTML 解析定義爲一個具有容錯性的過程。無論標記多麼不規範，解析器都能生成一個 DOM。這意味着，即使你忘記了閉合 </p> 標籤或者標籤嵌套錯誤，解析器也會隱式地修復或調整 DOM 樹使其合法。例如，<p>Hello <div>World</div> 會在 DOM 結構中自動將 <p> 閉合在 <div> 之前。解析器爲 HTML 中的每個標籤或文本創建 DOM 元素和文本節點。每個元素都被放置在一棵反映源碼嵌套關係的樹中。 一個重要的細節是，HTML 解析器在運行過程中可能會遇到需要獲取的資源：例如，遇到 <link rel="stylesheet" href="..."> 會促使瀏覽器（在網絡線程上）請求 CSS 文件；遇到 <img src="..."> 會觸發圖片請求。這些請求與解析並行發生。解析器在加載這些資源時可以繼續解析，但有一個重大例外：腳本。 處理 <script> 標籤： 如果 HTML 解析器遇到一個 <script> 標籤，它會暫停解析，並（在默認情況下）必須先執行完腳本才能繼續。這是因爲腳本可能使用 document.write() 或其他 DOM 操作 API，從而改變頁面結構或後續即將加載的內容。通過在這個時間點立即執行腳本，瀏覽器保證了操作順序與 HTML 的相對位置一致。因此，解析器將腳本移交給 JavaScript 引擎執行，只有當腳本執行完畢（且它所做的任何 DOM 修改生效）後，HTML 解析才能恢復。這種腳本阻塞行爲解釋了爲什麼在 <head> 中引入大型 <script> 文件會拖慢頁面渲染——在腳本下載並運行完畢之前，HTML 解析根本無法繼續。 不過，開發者可以通過屬性來改變這種行爲：在 <script> 標籤上添加 defer 或 async（或使用現代的 ES Module 腳本）可以改變瀏覽器的處理方式： async：腳本文件會被並行下載，一旦準備就緒便立即執行，不暫停 HTML 解析（解析器不等待，且腳本不保證按原有的相對順序執行）。defer：腳本同樣並行下載，但執行會被推遲到 HTML 解析完成之後（並將在稍後按原有的先後順序執行）。<script type="module">）默認也是 defer 的（它們還可以使用 import 語句——後文會單獨講解模塊加載）。使用這些技巧，瀏覽器可以在沒有長停頓的情況下繼續構建 DOM，從而顯著提升頁面加載速度。CSS 解析與 CSSOM： 與 HTML 類似，CSS 文本也必須被解析成瀏覽器能夠操作的結構——通常稱爲 CSSOM（CSS 對象模型）。CSSOM 本質上是應用於文檔的所有樣式（規則、選擇器、屬性）的內部表示。瀏覽器的 CSS 解析器讀取 CSS 文件（或 <style> 塊），將它們轉化爲 CSS 規則列表（內部使用了大量的布隆過濾器等機制來加速樣式解析）。接着，在構建 DOM 的同時（或當 DOM 和 CSSOM 都就緒後），瀏覽器會爲每個 DOM 節點計算樣式。這一步通常被稱爲樣式解析（Style Resolution）或樣式計算（Style Calculation）。瀏覽器將 DOM 和 CSSOM 結合起來，根據層疊規則、繼承和默認樣式，決定每個元素適用哪些 CSS 規則以及最終的“計算樣式（Computed styles）”。其輸出可以被理解爲每個 DOM 節點與其計算樣式（元素最終解析出的 CSS 屬性，如顏色、字體、大小等）的映射。 值得注意的是，即使沒有任何開發者編寫的 CSS，每個元素都有瀏覽器的默認樣式（User-Agent 樣式表）。例如，<h1> 在幾乎所有瀏覽器中都有默認的 font-size 和 margin。瀏覽器內置樣式規則以最低優先級應用，確保頁面有合理的默認呈現。開發者可以在 DevTools 的“Computed (計算樣式)”面板查看元素最終應用了哪些確切的 CSS 屬性。 渲染阻塞行爲： 雖然沒有完全加載完 CSS 時 HTML 依然可以繼續解析，但兩者之間存在“渲染阻塞”關係：瀏覽器通常會等待 CSS 加載完畢後才進行首次渲染（針對位於 <head> 中的 CSS）。這是因爲應用不完整的樣式表會導致“未渲染內容閃爍”（FOUC）。在實踐中，如果一個未標記 async/defer 的 <script> 出現在 CSS <link> 之後，解析器在執行該腳本前，還會額外等待 CSS 加載完成（因爲腳本可能會通過 DOM API 查詢樣式信息）。經驗法則：將樣式錶鏈接放在 <head> 中（它們會阻塞渲染，但早期就需要），將非關鍵或大型腳本加上 defer/async 或放在底部，以免延遲 DOM 解析。 現在瀏覽器已經具備了：(1) 由 HTML 構建的 DOM，(2) 解析後的 CSS 規則 CSSOM，以及 (3) 每個 DOM 節點的計算樣式。這三者構成了下一個階段——“佈局（Layout）”的基礎。但在進入佈局之前，我們先稍作探討 JavaScript 方面：當 JS 引擎（在 Chrome 中是 V8）執行代碼時會發生什麼？我們將在後續小節專門深入探討 V8 內部機制。目前只需知道，腳本在運行時可能會修改 DOM 或 CSSOM。瀏覽器必須響應這些變化，按需重新計算樣式或佈局（如果頻繁進行，會產生性能成本）。 在這個階段，瀏覽器的渲染器進程已經知道了 DOM 的結構以及每個元素的計算樣式。接下來的問題是：這些元素在屏幕上的確切位置在哪裏？它們有多大？這就是佈局（Layout）——有時也稱爲“迴流（Reflow）”——的任務。在這個階段，瀏覽器根據 CSS 規則（普通流、盒模型、Flexbox 或是 Grid 等）和 DOM 層級，計算出每個元素的幾何信息（大小和位置）。 佈局樹的構建： 瀏覽器遍歷 DOM 樹並生成一棵佈局樹 (Layout Tree)（有時被稱爲渲染樹 Render Tree 或 幀樹 Frame Tree）。佈局樹在結構上與 DOM 樹相似，但它會忽略非視覺元素（例如 <script> 或 <meta> 標籤不會產生盒子），並且在需要時可能會將某些元素拆分爲多個盒子（例如，分佈在多行中的內聯元素可能會對應多個佈局盒）。佈局樹中的每個節點都持有該元素的計算樣式，包含其內容（文本或圖片）以及影響佈局的計算屬性（如 width、height、padding 等）。 在佈局過程中，瀏覽器計算每個元素盒子的精確座標（x, y）和尺寸（寬，高）。這涉及 CSS 規範中定義的複雜算法：例如，在普通文檔流中，塊級元素默認自上而下堆疊並佔據整個寬度，而內聯元素在行內流動並按需換行。Flexbox 或 Grid 等現代佈局模式則有其專有的算法。引擎必須考慮字體度量以進行換行（因此文本佈局涉及測量文本排版段落），還必須處理外邊距（Margin）、內邊距（Padding）、邊框（Border）等。這裏存在海量的邊緣情況（如外邊距摺疊、浮動、脫離文檔流的絕對定位元素等），使得佈局成爲一個驚人複雜的計算過程。即使是“簡單”的自上而下佈局，也必須計算依賴於可用寬度和字體大小的文本換行。瀏覽器引擎有專門的團隊進行多年開發，以保證佈局的準確與高效。 關於佈局樹的幾個細節： display: none 的元素會被完全從佈局樹中剔除（不生成任何盒子）。相反，僅僅是不可見（如 visibility: hidden）的元素仍會生成佈局盒（佔據空間），只是稍後不被繪製。::before 或 ::after）如果生成了內容，則會包含在佈局樹中（因爲它們具有視覺盒子）。<p> 元素的佈局節點知道它相對於視口的位置和尺寸，並擁有其內部每行或內聯盒子的子節點。佈局計算： 佈局通常是一個遞歸過程。從根節點（<html> 元素）開始，瀏覽器計算視口（Viewport）的大小，然後在其內部佈局子元素，以此類推。許多元素的尺寸依賴於它的子元素或父元素。佈局算法經常需要對浮動等複雜交互進行多次遍歷，但通常它是單向（自上而下）進行的，必要時會進行回溯。 這一階段結束時，頁面上每個元素的座標和大小都已確定。我們現在可以將頁面概念化爲一堆內部包含文本或圖片的“盒子”。但是，我們還沒有真正在屏幕上畫出任何東西——這就是下一步：繪製。 需要牢記的一個關鍵概念是：佈局是一項昂貴的操作，尤其是頻繁進行時。如果 JavaScript 隨後改變了元素的大小或添加了內容，它可能會強制對部分或全部頁面進行重新佈局 (Relayout)。開發者常聽到要避免**“佈局抖動 (Layout Thrashing)”**的建議（例如在 JS 中修改 DOM 後立即讀取佈局信息，這會強制執行同步重新計算）。瀏覽器會嘗試進行優化，標記佈局樹中“髒（dirty）”的部分，並僅重新計算這些部分。但在最壞的情況下，DOM 樹高層的改變可能需要重新計算整個大頁面的佈局。這就是爲什麼應儘量減少昂貴的樣式/佈局操作以提升性能。 樣式與佈局總結： 從 HTML 和 CSS 出發，瀏覽器構建了： 每個階段都建立在前一個階段之上。如果任意階段發生變化（例如腳本改變了 DOM 或修改了 CSS 屬性），後續階段都可能需要更新。這條影響鏈意味着佈局和繪製依賴於最新的樣式，以此類推。 繪製 (Painting) 是獲取結構化的佈局信息，並在屏幕上實際生成像素的過程。在傳統的認知中，瀏覽器會遍歷佈局樹併爲每個節點發出繪製指令（“在這個座標畫背景，畫文字，畫圖片”）。現代瀏覽器在概念上依然這麼做，但通常會將工作拆分爲多個階段，並利用 GPU 來提升效率。 繪製 / 光柵化 (Rasterization)： 在佈局完成後的渲染器主線程上，Chrome 會通過遍歷佈局樹生成繪製記錄 (Paint records)（或稱爲顯示列表 Display List）。這基本等同於一系列帶有座標的繪製操作指令，就像畫家規劃如何作畫一樣：“在 (x,y) 畫一個寬高爲 W 和 H、填充藍色的矩形，然後在 (x2, y2) 用 XYZ 字體畫‘Hello’文字……”。這個列表是按照正確的 z-index 順序生成的，以確保重疊的元素能正確覆蓋。瀏覽器必須處理層疊上下文 (Stacking contexts) 和透明度等，以獲得正確的順序。 過去，瀏覽器可能只是簡單地按順序直接在屏幕上繪製每個元素。但如果頁面只有部分內容發生變化，這種做法（重繪整個頁面）就會非常低效。因此，現代瀏覽器會將這些繪製指令記錄下來，然後利用合成 (Compositing) 步驟將最終圖像組裝起來，並在此過程中大量應用 GPU 加速。 分層與合成 (Layering and Compositing)： 合成是一種優化策略，即將頁面拆分爲可以獨立處理的多個圖層 (Layers)。例如，一個具有 CSS transform 或動畫的定位元素可能會獲得自己的圖層。圖層就像獨立的“草稿畫布”——瀏覽器可以獨立對每個圖層進行光柵化（將繪製指令轉化爲像素），然後合成器將它們在屏幕上混合在一起，這通常由 GPU 完成。 在 Chromium 的管線中，生成繪製記錄後，會有一個構建圖層樹 (Layer tree) 的步驟。有些圖層是自動創建的（如 <video> 或 <canvas> 元素，或者帶有特定 CSS 屬性的元素會被提升爲圖層），開發者也可以使用 will-change 或 transform 這樣的屬性來顯式提示瀏覽器創建圖層。分層的好處在於：一個圖層上的移動或透明度變化可以直接被“合成”（即只需重新渲染或移動該圖層），而無需重繪整個頁面。然而，過多的圖層會消耗大量內存並增加開銷，因此瀏覽器對此非常謹慎。 確定圖層後，Chrome 主線程將任務移交給合成器線程 (Compositor Thread)。合成器線程運行在渲染器進程中，但獨立於主線程（因此即使 JS 主線程正忙，它也能繼續工作，這對於實現流暢的滾動和動畫至關重要）。合成器線程的工作是提取這些圖層，對它們進行光柵化（將矢量繪圖轉換爲實際的像素位圖），並將它們組裝成幀。 藉助 GPU 的光柵化： 光柵化任務也可以並行分配。在 Chrome 中，合成器線程會將圖層分割成更小的瓦片 (Tiles)（想象 256x256 或 512x512 像素的塊）。然後，它將這些瓦片分派給多個光柵化工作線程（甚至可以跨多個 CPU 核心運行）併發執行。每個工作線程負責一個瓦片——本質上就是針對該區域的繪製指令——並生成位圖（像素數據）。重要的是，Chrome 的圖形庫 Skia 可以利用 CPU 或 GPU 進行光柵化；通常這些線程在 CPU 上渲染像素，然後將其上傳到 GPU 內存中作爲紋理 (Textures)。當所有需要的瓦片都繪製完成後，合成器線程就準備好了一套帶有紋理的圖層。 合成器接着組裝出一個合成器幀 (Compositor frame) —— 這本質上是一條發給瀏覽器進程的消息，其中包含了構成屏幕畫面的所有四邊形（quads/圖層瓦片）、它們的位置等信息。該幀通過 IPC（進程間通信）發送回瀏覽器進程，並最終由瀏覽器的 GPU 進程（Chrome 中專用於訪問 GPU 的進程）接手並在屏幕上顯示。瀏覽器的界面（如標籤欄）同樣也通過合成器幀繪製，在最後一步中混合。GPU 進程接收幀，通過底層 API（OpenGL / DirectX / Metal 等）極快地處理，在屏幕正確位置繪製每個紋理並應用變換。這就是你看到的最終畫面。 當你滾動頁面或觀看動畫時，這條管線的優勢展露無遺。例如，滾動頁面主要只是在較大的頁面紋理上改變視口 (Viewport)。合成器只需移動圖層位置並請求 GPU 繪製進入視口的新部分，主線程完全無需重新繪製任何東西。如果動畫只是一個變換（如移動一個獨佔圖層的元素），合成器線程每幀都能更新該元素的位置並生成新幀，完全不需要主線程參與，也不需要重新運行樣式和佈局計算。這就是爲什麼建議使用**“僅觸發合成 (compositing-only)”**的動畫（如改變 transform 或 opacity，不觸發佈局）——即使主線程正忙，它們也能流暢地以 60 FPS 運行。相反，像動畫 height 這樣的屬性會強制每一幀重新佈局和繪製，如果主線程跟不上，就會導致嚴重的卡頓。 簡言之，Chrome 的渲染管線是：DOM → 樣式 → 佈局 → 繪製（記錄指令） → 分層 → 光柵化（瓦片） → 合成 (GPU)。 Firefox 使用 WebRender 的管線在前半部分類似，但它跳過了顯式構建圖層，而是直接向 GPU 發送顯示列表，由 GPU Shader 處理幾乎所有繪製操作。Safari (WebKit) 同樣使用了多線程合成和基於硬件（Mac 上的 CALayer）的 GPU 渲染。 爲了保證平滑渲染，對於每一個動畫幀（目標是 60fps，即每幀 16.7ms），合成器都會努力產出一幀。如果主線程執行 JavaScript 花了太長時間，合成器可能會跳幀，導致肉眼可見的卡頓。開發者可以使用 requestAnimationFrame 將 JS 更新與幀邊界對齊，從而輔助平滑渲染。 JavaScript 驅動了網頁的交互行爲。在 Chromium 中，V8 引擎負責執行 JavaScript 和 WebAssembly。 <script> 時，V8 首先解析源碼生成抽象語法樹 (AST)。它包含一個輕量級的“預解析器 (Preparser)”，對函數僅做最基礎的合法性驗證（跳過內部實現），直到函數真正被調用時才進行完整解析。V8 隨後使用名爲 Ignition 的解釋器將 AST 轉化爲緊湊的字節碼 (Bytecode)。字節碼啓動快，非常適合縮減頁面初始加載時間。JavaScript 是動態類型的語言，直接解釋執行效率較低。V8 擁有多層即時編譯器 (JIT Compilers)，它的理念是：對執行頻繁的“熱點”代碼投入更多編譯時間進行極度優化，以提升運行速度。 如果在後續執行中，變量的類型打破了原有的優化假設（例如一個一直傳入數字的函數突然傳入了字符串），V8 會執行**“去優化（Deoptimization，或逆優化）”**，退回到未優化的狀態。因此，保持 JavaScript 變量類型的穩定性對於維持極致性能至關重要。 V8 使用被稱爲 Orinoco 的垃圾回收器，它是分代、增量且併發的： 對於開發者來說，現代 GC 的性能已經好到“毫無存在感”，但依然要注意避免在緊湊的循環中創建海量長生命週期的對象。此外，像 document.querySelector 或網絡請求等 Web API 實際上並不是 V8 的一部分，它們是瀏覽器（用 C++ 編寫）通過接口綁定暴露給 V8 引擎調用的。 與傳統的 <script> 標籤不同，ES Modules 擁有獨立的加載和執行模型。 <script type="module">，瀏覽器會把它作爲入口點。它會解析代碼並找出所有的 import 語句，並遞歸地獲取和解析所有依賴的模塊，構建出一張模塊依賴圖 (Dependency graph)。這一過程是異步的，只有當依賴圖徹底就緒後，模塊纔會依據依賴順序（最底層的依賴最先執行）依次運行。import()： 可以在代碼執行期間動態按需加載模塊，它返回一個 Promise。這對“代碼分割（Code-splitting）”極爲有用。import { react } from 'react' 會報錯，因爲 'react' 不是有效 URL。Import Maps（<script type="importmap">）允許開發者在瀏覽器端配置映射表，將包名映射到實際的 CDN 網址。它已經被三大主流瀏覽器全面支持，是目前去打包化（unbundled）開發的基石。現代瀏覽器不再是“單進程”巨獸。Chromium 首創了多進程架構以換取穩定性、安全性和性能隔離。 多進程的優勢： 這構成了瀏覽器最堅固的防線： evil.com。在過去，它們可能在同一個渲染器進程內運行；而現在，Chrome 會將這個跨源的 iframe 拆分到一個獨立的進程中。這兩個進程通過極其複雜的 IPC（進程間通信）機制，在後臺拼裝成用戶眼前的單個網頁。對於開發者，這意味着跨源通信（如 postMessage）實際上跨越了進程邊界，但瀏覽器底層優雅地屏蔽了這些複雜性。代價是，更多的進程帶來了相對更高的內存佔用（約 10-20%）。 Chromium (Chrome/Edge/Blink)、Gecko (Firefox) 和 WebKit (Safari) 這三大引擎在總體宏觀架構上高度趨同，但技術實現上各有千秋： 瞭解瀏覽器的“黑盒”之後，作爲開發者我們可以獲得以下具備指導意義的心智模型： <link rel="preload"> 和 preconnect 幫助預加載掃描器儘早開工。transform 和 opacity 做動畫，它們在“合成器線程”上運行，完全不會被主線程上阻塞的 JavaScript 干擾。Web
