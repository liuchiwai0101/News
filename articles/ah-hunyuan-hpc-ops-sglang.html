一句話結論

腾讯混元开源 HPC-Ops 算子库（GitHub: Tencent/hpc-ops），三大核心算子已合并至 SGLang 主分支，在 8 卡 H20 上将 Hy3-FP8 模型的 TPOT 从 35.33ms 降至 18.09ms（batch size 32），降幅达 48.8%。

三大核心算子

1. Dynamic Attention（动态注意力）

**解決的問題**：連續批處理中，不同生成階段的請求混合在同一批次，短 KV cache 與數萬 token 的長序列混合。傳統靜態 split-KV 調度因固定分割數或固定 chunk 大小，導致短請求的 CTA 提前完成、長請求決定尾部延遲。

**解決方案**：採用持久化內核動態平衡 KV tile 在 CTA 間的分配，每 64 個 token 切一個 tile，長 sequence 跨多個 CTA 執行，短 sequence 只貢獻實際擁有的 tile。任務映射每 decode step 生成一次，跨所有 Transformer 層複用。

**性能**：在極端偏斜場景（1 條 128K + 31 條 4K），動態調度比靜態調度快 2.95 倍，比 FlashInfer/FlashAttention 最佳值平均快 2.25 倍。

2. Router GEMM（精度感知路由矩陣乘）

**解決的問題**：MoE 層的路由器需要 FP32 精度保證 top-k 選擇正確，但 FP32 的 Tensor Core 吞吐遠低於 BF16。

**解決方案**：將 FP32 權重分解爲兩個 BF16 分量（W_high 和 W_low），在單個 kernel 中執行兩次 BF16 矩陣乘，從共享內存加載一次 activation tile，在 FP32 寄存器中累加。最終在 epilogue 中應用 1/256 縮放恢復 FP32 精度。

**性能**：比 FP32 cuBLAS 快 1.30 至 3.22 倍，最大绝对误差仅 0.00177（TF32 cuBLAS 为 0.06464）。

3. Fused MoE（融合專家混合）

**解決的問題**：解碼時每個專家只接收少量 token，expert GEMM 很小且 memory-bound，加上負載不均衡和 gather/量化開銷。

**解決方案**：融合路由索引構建（共享內存計數減少全局原子操作）、Gate-Up GEMM 直接讀取原始 token 跳過獨立 gather、SiLU-and-mul 和 FP8 重量化融合爲單 kernel、佔用優先設計（無 warp 特化）、PDL 鏈式階段重疊下游 kernel 啓動。

**性能**：TP1/EP8 配置下平均加速 1.21 倍，batch size 64 時加速 1.60 倍。
