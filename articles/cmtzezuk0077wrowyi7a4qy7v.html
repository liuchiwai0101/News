Agent 長任務上下文工程解析：用預算控制、壓縮、todo-state 和記憶對抗上下文溢出與目標丟失

內容機器翻譯自第三方媒體（MarkTechPost），僅供參考，以原文為準。

AI 導讀

文章解析 Agent harness 層應對長任務中上下文溢出與目標丟失的四類機制：上下文預算與卸載、壓縮、todo-state 複述和跨會話記憶。

推薦理由

文章把解決長任務中上下文溢出與目標丟失的機制拆成四類，並對照多款主流 Agent 產品的具體實現和閾值，便於讀者遷移到自己的系統。

正文

一個智能體，就其最簡單的形式而言，就是一個在循環中調用工具的大語言模型。這個循環適用於短任務。給它一個運行一小時、調用 200 次工具的任務，它會以兩種可預見的方式崩潰。AWS Samples 自主雲編碼智能體設計指南直接指出了這些問題：淺層智能體會遭遇上下文溢出、被分散注意力（目標丟失），並且無法在長時間內維持狀態。解決這一問題的層不是模型，而是 harness（執行框架），AWS 將其描述為管理除模型之外的一切。

本文深入剖析這一層。壓縮、記憶策略、上下文預算和 todo 狀態，正是將淺層循環轉變為深度智能體的機制。我們來看看 LangChain Deep Agents、Claude Code、Manus、OpenAI Codex 和 Amazon Bedrock AgentCore 各自如何實現這些機制，以及它們實際發佈的閾值。

為什麼更大的窗口解決不了問題

顯而易見的解決方案是更大的上下文窗口。但證據表明，它的幫助比預期要小。Chroma 的上下文腐化報告評估了 18 個大語言模型，包括 GPT-4.1、Claude 4、Gemini 2.5 和 Qwen3，發現隨着輸入長度增長，性能變得越來越不可靠，即使在簡單的檢索任務上也是如此。Anthropic 的上下文工程指南解釋了其機制：注意力機制為 n 個 token 創建 n² 個成對關係，因此每增加一個 token 都會消耗有限的“注意力預算”。上下文是一種收益遞減的資源，而不是一個桶。

對於一個智能體循環來説，這比聽起來還要糟糕。Manus 報告稱，一個典型任務大約需要 50 次工具調用，而輸入與輸出的 token 比例接近 100:1。每一條觀察結果都會進入上下文並留在那裏。最初的指令逐漸漂移到上下文窗口的中部，而這恰恰是召回能力退化的位置。目標丟失不僅僅是模型的一個缺陷。它是在足夠長的任務中，對上下文不加管理所導致的必然結果。

機制 1：上下文預算與卸載

一個 harness 的首要職責，是決定哪些內容根本不進入上下文窗口。Deep Agents 附帶 2 條帶有硬性數字的卸載規則。當一次工具響應超過 20,000 tokens 時，它會被寫入文件系統，並替換為一個文件路徑加上前 10 行的預覽。當會話上下文超過模型窗口的 85% 時，較早的寫入和編輯工具調用——其完整文件內容已經存在於磁盤上——會被截斷為一個指針。只有當卸載再也騰不出空間時，harness 才會退回到摘要壓縮。

Claude Code 對首個提示詞加載之前的內容也施加了同樣的預算管理。自動記憶被限制在前 200 行或 25KB。MCP 工具 schema 默認保持延遲加載，只列出工具名稱，完整 schema 通過工具搜索按需加載。壓縮之後，任何超過 5,000 tokens 的重新讀取文件都會以路徑引用的形式返回，而不是內容本身。Claude Code 文檔中的上下文窗口模擬讓這一收益變得具體可見：一個研究子智能體讀取了 6,100 tokens 的文件，並向父級返回了一個 420 tokens 的結果。

這種子智能體模式是在架構層面做預算控制。Anthropic 的指南指出，每個子智能體可能會在探索中消耗數萬個 token，但只返回一份經過提煉的摘要，通常為 1,000 到 2,000 個 token。AWS AgentCore 的演練正是這樣構建的：一個協調者並行啓動 3 個瀏覽器子智能體，每個都在自己的 MicroVM 中運行，而一個分析師子智能體只接收它們的結構化發現結果。

AWS 報告預期運行時間為 4 到 6 分鐘，並指出順序處理最多會耗時 3 倍。

機制 2：壓縮

當卸載還不夠時，執行框架就會進行總結。壓縮是指將一段接近上下文窗口上限的對話取出、加以總結，並用該摘要重新開啓一個新的上下文。這也正是目標丟失最常發生的地方，因為有損摘要可能會丟掉那條唯一重要的約束。

不同實現在承諾保留什麼內容上各有差異。Claude Code 的壓縮提示詞會保留架構決策、未解決的 bug 和實現細節，同時丟棄冗餘的工具輸出。壓縮完成後，它會立即重新讀取最多 5 個最近修改的文件，重新加載與這些文件匹配的規則，並重新注入被調用的技能正文，每個技能上限為 5,000 個 token，總計上限為 25,000 個。文檔明確指出，對話早期的詳細指令可能會丟失，這正是持久性規則應放在項目根目錄的 CLAUDE.md 中的原因，因為該文件會從磁盤重新注入。用户可以通過 /compact focus on the auth bug fix 來引導這一過程，或通過 /autocompact 來移動觸發點。

Deep Agents 將目標保留變成了一項結構性特性。它的摘要是一份結構化文檔，其中設有專門字段用於記錄會話意圖、所創建的產物以及後續步驟。LangChain 團隊是在強制摘要實驗表明這一改動提升了性能之後才加入這些字段的。完整的原始對話記錄也會寫入文件系統，因此一條被摘要抹去的事實，之後可以由 read_file 恢復。

壓縮也已進入 API 層。OpenAI 的 Responses API 通過 context_management 配合 compact_threshold 提供服務器端壓縮，此外還有一個獨立的 /responses/compact 端點，返回一個經過壓縮的上下文窗口，其中包含一個不透明的加密壓縮項；OpenAI 指示開發者將該返回的窗口原樣傳入下一次調用。OpenAI 表示 Codex 依賴這一機制來維持長時間運行的編碼任務。Claude 開發者平台提供了一個 compact_20260112 上下文管理編輯功能，支持自定義指令，以及一個 pause_after_compaction 選項，用於在模型繼續之前插入內容。當你在那裏編寫自定義指令時，它們會完全取代默認提示詞，因此壓縮提示詞是一件真正的工程產物，而不是一項設置。

機制 3：待辦狀態與複述

壓縮在摘要生成的那一刻保護目標。而待辦狀態則在中間的每一輪對話中保護它。Manus 直白地描述了這個技巧：它的智能體會創建一個 todo.md，並逐步重寫它，逐項勾選完成。重寫列表會把目標複述到上下文的末尾，將全局計劃推入模型近期的注意力範圍，減少“中間迷失”的漂移。無需改變架構。這只是用自然語言來引導模型自身的注意力。

關於待辦狀態的證據並非一邊倒。Deep Agents 默認搭載了一個 write_todos 工具，直到 2026 年 7 月的 v0.7，LangChain 才將 TodoListMiddleware 改為可選啓用，因為其在 3 個任務類別上的評估顯示，禁用待辦後獎勵略好、成本更低。LangChain 仍然建議在長時間多步驟任務、能力較弱的模型以及展示進度的 UI 中重新啓用它。Claude Code 保留一份待辦列表，並在壓縮後從磁盤重新注入計劃模式下編寫的計劃。Anthropic 的指南將這一通用模式稱為結構化筆記：智能體在上下文窗口之外編寫一個 NOTES.md 或 TODO 文件，然後重新加載它。其 Claude Plays Pokémon 示例在數千個遊戲步驟中維護計數，然後在每次上下文重置後讀取自己的筆記，並恢復長達數小時的操作序列。

所有這些背後的模式是：目標作為一個可變產物存在，而不僅僅是歷史中的一條消息。消息會老化並被摘要。一個每隔幾輪就被重寫的文件始終是近期的、始終是簡短的，並且能在任何重置後存活下來。它是否值得每輪的 token 成本，取決於模型和任務長度，而這正是 Deep Agents 評估所測量的內容。

機制 4：跨會話的記憶策略

最後一塊是任務結束後仍然留存的內容。Claude Code 在每次壓縮之後，會從磁盤重新注入項目根目錄的 CLAUDE.md 和自動記憶。AgentCore Memory 會存儲事件，並在後台運行配置好的提取策略，因此協調器可以在下一次運行時調用召回工具，而不必重新研究。

AWS 警告稱，如果未配置至少 1 個提取策略，原始事件雖會被存儲，但不會提取任何內容用於檢索。Anthropic 基於文件的記憶工具在 Claude 平台上起到同樣的作用。

侷限在於，持久化上下文並非沒有代價。我們在二月報道過的蘇黎世聯邦理工學院研究（ETH Zurich study）發現，像 AGENTS.md 這樣的倉庫上下文文件通常不會提升任務成功率，反而會推高推理成本：LLM 生成的文件在 2 個基準上使成本增加了 20% 和 23%，而開發者提交的文件最高增加 19%。每次會話都重新加載的記憶，是對注意力預算的一項長期税收。Claude Code 文檔給出了相應的建議：將 CLAUDE.md 保持在 200 行以內，並把參考資料移入技能或按路徑限定的規則中，僅在需要時加載。

交互式講解：觀看 200K 上下文窗口被填滿

下面的模擬器通過一個 200K token 的窗口運行一項 60 步的遷移任務。切換這 4 種機制，設置壓縮觸發閾值，然後按下運行。當所有機制都關閉時，窗口在任務完成一半之前就會溢出。當卸載、壓縮、待辦事項複述和子智能體委派全部開啓時，同樣的任務能夠完成，且目標仍處於近期注意力之中。token 數量僅為示意；閾值與 Deep Agents 的默認值一致。

測試該框架是否真正守住了目標

上下文管理只有在智能體仍能完成任務並找回它已看不到的細節時才有用。LangChain 正是為此維護了針對性的評測：觸發任務中途摘要並檢查智能體是否繼續朝目標推進的測試，以及事實被摘要掉、必須通過文件系統搜索找回的“大海撈針”用例。

為了生成足夠多的事件來比較不同提示詞變體，團隊在窗口的 10% 到 20% 處觸發摘要，而非默認的 85%，並在 terminal-bench-2 上使用 Claude Sonnet 4.5 以 25% 的觸發閾值來研究其效果。

在 LangChain 看來，需要警惕的失敗是目標漂移：智能體在摘要之後立刻請求澄清，或者錯誤地宣佈任務完成。AgentCore Evaluations 提供了一個目標成功率評估器，可以對相同的 trace 打分。如果你運行了一個框架，卻沒有在測試中強制觸發過一次壓縮，那麼你還不清楚你的摘要提示詞到底丟掉了什麼。

關鍵要點

  • 淺層智能體會因上下文溢出和目標丟失而失敗；修復的關鍵在於執行框架，而非模型本身。
  • 預算優先：Deep Agents 會卸載超過 20,000 tokens 的工具結果，並在窗口使用率達到 85% 時清除舊的編輯內容。
  • 壓縮必須明確説明它保留了哪些內容；Deep Agents 增加了會話意圖和後續步驟字段，Claude Code 則會重新讀取最近 5 個文件。
  • 待辦事項複述能將目標保持在上下文末尾，但 Deep Agents v0.7 的評測表明，這並非沒有代價的收益。
  • 持久記憶會消耗注意力：ETH Zurich 測得，由 LLM 生成的上下文文件會使推理成本增加 20% 至 23%。
