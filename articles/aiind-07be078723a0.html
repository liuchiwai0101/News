30 個 Agent 背後：花椒如何建設可持續演進的企業 AI 能力？

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

今年最大的一個變化是，企業做 Agent 的門檻越來越低，但做出一個能完成任務的 Agent，與讓它在業務中持續穩定運行，還存在一定的距離。因為當 Agent 數量和使用頻率放大後，很多原本不顯眼的問題也會跟着放大。

花椒的 Agent 實踐，提供了一個觀察這種變化的樣本。

花椒直播 CTO、超序 AI 創始人兼 CEO 封冰清，正在同時面對企業 AI 落地的兩類問題：如何讓技術在真實業務中持續運行，以及如何把內部積累轉化為可複用、可持續交付的產品與服務。

超序 AI 是花房集團旗下獨立 AI 品牌，推動 AI 融入企業的生產與業務流程，從具體任務出發，面向細分行業沉澱可複用的解決方案和系統。花椒與花房的內部實踐，為這一探索提供了技術與業務經驗。

從產研自動化起步，到約 30 個 Agent 應用落地，封冰清逐漸形成了一個判斷：企業需要持續積累自己的業務方法、系統連接、權限規則和驗收標準，讓模型與工具能夠不斷升級，並用實際交付結果判斷投入價值。

圍繞這一判斷，InfoQ 與封冰清交流了花椒 Agent 平台的建設經歷：為什麼選擇自研，為什麼又不斷拆分平台職責，如何處理業務與公共內核的邊界，以及從單點提效走向組織協同，還需要補齊哪些工程和管理能力。

今年春節後，“小龍蝦”以近乎瘋狂的速度在全球範圍內躥紅。儘快應用 Agent，成了當時很多企業最迫切的事情。

相比多數企業，花椒顯得十分冷靜。“ 我們認為，企業不應該完全迷戀 Agent 或者 AI，企業落地 Agent 應用前，第一步是要先梳理業務的需求。 ”封冰清提到，花椒的 Agent 實踐，起點是希望技術團隊儘早“上 AI 這條船”： 從產研自動化切入，希望團隊能通過實際應用，真正掌握 AI 能力 。按照他的設想，技術團隊需要儘早掌握 AI 帶來的新工作方式，通過 AI Coding 推動研發提效，並打通從產品需求、設計到開發、測試的完整流程。

但真正做起來後，團隊發現，事情沒有想象中那麼簡單。比如，要讓研發環節實現自動化，上游的產品需求就必須足夠清晰。產品團隊要藉助 Agent 完成需求編寫，同樣需要管理 Skill、Prompt、模型和執行環境。

此外，運行時、執行環境、權限和統計會在不同 Agent 中反覆出現。如果每個應用分別建設，交付、排障和維護成本也會重複發生。團隊因此開始考慮，將這些共性問題沉澱為公共能力，讓業務側集中表達自己的工作方法和任務要求 。 

於是，在 2026 年 3 月份左右，花椒開始調研市面上的 Agent 方案，並最終決定自研一套企業 Agent 平台。 這套平台的目標很明確，把運行時、執行環境、用户權限、統計等共性能力交由平台封裝，讓業務側專注在 Skill、Prompt 和模型選擇上，沉澱自身的工作方法、任務要求和智能能力。 這樣一來，開發一個業務 Agent，就不必每次都從底層基礎設施做起。“做業務 Agent 的人，不必同時成為底層基礎設施專家”，封冰清説道。

從決定自研到第一個版本上線，花椒大概花了一個月的時間。第一個版本已經具備基本的 Agent 管理能力，包括應用創建、Skill 配置、執行環境管理、用户權限和聊天交互等。團隊希望先驗證一個最小閉環：能不能讓業務人員在平台上創建應用、配置能力，並通過對話完成實際工作。

平台搭起來只是第一步，更大的挑戰是如何讓員工真正用起來。在企業內部，很多員工對 Agent 的接受程度並不高，一些員工聽到要做 Agent，第一反應是擔心自己的工作會不會被 AI 取代。花椒落地 Agent 應用的思路是， 先從一線員工最迫切的需求入手，讓大家看到 Agent 到底能解決什麼問題 。

以運營人員的數據查詢工作為例。過去，運營人員查詢主播直播數據或用户充值金額時，需要先打開電腦、連接 VPN、登錄後台，有時還要在多個系統之間來回查找，最後整理信息向負責人彙報。基於這個真實痛點，花椒開發了一個 Agent，並接入辦公軟件。運營人員只需要在辦公軟件裏提問，Agent 就能調用後台數據並給出結果。

這種方式得到了業務部門的認可，也讓團隊進一步意識到，Agent 的交互形式需要服從實際工作。開放問題適合通過對話探索；高頻、規則明確的任務，則更適合提供固定入口、必要字段、任務進度和審核位置。

花椒因此將部分 Agent 從單純的聊天交互轉向工作台形態，並逐步抽象連接器、界面等通用能力。底層運行能力可以共用，業務入口則圍繞各部門的任務和結果責任獨立設計。

目前，花椒已經在業務側和集團中台落地了約 30 個 Agent 應用，覆蓋產研、運營、數據分析、客服、法務、行政以及 GR（政府關係）等多個場景。

在封冰清看來，企業判斷一個方向是否值得落地 AI 應用，需要先想清楚最終拿什麼證明它有用。“部門用了 AI”和“部門的工作變好了”，中間還有一段距離。 真正值得持續投入的方向，應該是 AI 能讓員工把原來的一件工作做得更好，或者讓整個工作流程變得更高效。

比如，AI 生成內容的速度提高了，但審核卻更慢，企業就需要縮小自動化範圍；如果一個流程真正的卡點在審批等待，那麼繼續優化 AI 的生成速度，也無法解決實際問題。這也解釋了，為什麼企業 AI 最終會碰到組織問題。“技術團隊可以實現功能，業務團隊必須提供專業標準、參與驗收。跨部門的目標、資源和責任衝突，需要我去推動，不能留給一個工程師靠調提示詞解決”，封冰清提到。

業務與技術的邊界，是花椒設計 Agent 平台時重點考慮的問題，隨着 Agent 應用越來越多，花椒發現，平台本身也需要做減法。

早期，為了儘快支撐業務落地，Agent 平台承載了很多內容，包括模型接入的 newapi、沙箱、運行環境、用户權限等。有的應用只想調用一次模型，卻也要依賴整套 Agent 機制。此外，花椒的 Agent 平台主要通過 AI Coding 開發，隨着功能不斷增加，模塊間的依賴關係越來越複雜。一次簡單的修改，可能需要 AI 理解大量上下文，團隊還得反覆確認是否影響了其他功能。

為此，花椒開始重新劃分平台的職責，將模型服務、Agent 運行和執行環境等職責逐步分開，避免任何需求都必須套進一套完整 Agent 機制。這種分層設計，也讓修改和測試的影響範圍更加可控，降低平台自身的複雜度。

這段實踐讓團隊更加明確，平台需要同時處理兩類變化：業務方法持續調整，模型、工具與基礎設施也在持續更新。分層要讓應用能夠按任務複雜度選擇能力，也要限制一次修改的影響範圍。簡單任務可以直接調用模型，確定性步驟優先交給程序，需要多步判斷和工具調用時再使用 Agent。

AI Coding 加快了代碼實現，但架構邊界、兼容關係和驗證成本仍需要人來控制。技術負責人需要判斷，每增加一項能力，會給後續修改、測試和維護帶來什麼長期成本。
