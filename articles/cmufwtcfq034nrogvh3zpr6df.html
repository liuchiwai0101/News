GitHub Security Lab 發佈 LLM 驅動的 Fuzzing Taskflow，自動完成 C/C++ 項目模糊測試全流程

內容機器翻譯自第三方媒體（GitHub Blog），僅供參考，以原文為準。

AI 導讀

GitHub Security Lab 的 Antonio Morales 開源了基於 Taskflow Agent 的 Fuzzing Taskflow，指向 GitHub 倉庫即可自動識別入口點、編寫 harness、運行 AFL++、讀取覆蓋報告並分診崩潰。

推薦理由

作者開源了完整的自主模糊測試流水線，並講清覆蓋反饋、結構感知和崩潰分診的設計取捨，C/C++ 維護者可直接複用。

正文

如果你是模糊測試的新手，想先學習基礎知識，請查看我們的 Fuzzing 101 課程：gh.io/fuzzing101 。

持續模糊測試並不是能解決你所有問題的魔法方案。即便是已經在 OSS-Fuzz 中登記多年的項目，仍然可能隱藏着嚴重缺陷，而原因幾乎總是相同的：需要有人持續關注覆蓋率，為那些無人觸及的代碼編寫新的測試樁，並對另一端產生的崩潰進行分診。換句話説，模糊測試仍然需要人在環路中。

所以我不斷問自己的一個自然問題是：這些人工工作中，究竟有多少可以真正交給 LLM 智能體來完成？

正是這個問題促使我構建了 Fuzzing Taskflow，一個面向 C/C++ 項目的自主模糊測試流水線。你只需要把它指向一個 GitHub 倉庫，剩下的它都會完成：識別合適的入口點、分析構建系統、編寫測試樁、運行 AFL++、讀取覆蓋率報告、改進測試樁、對每個崩潰進行分診，併為每個唯一缺陷撰寫漏洞報告，全程無需人工照看。

Fuzzing Taskflow 構建在 GitHub Security Lab Taskflow Agent 之上，這是我們用於編寫 LLM 驅動的安全自動化的框架，因此該流水線被表達為一組由智能體端到端運行的任務流。

在這篇文章中，我將帶你瞭解它的工作原理以及背後的設計決策。讓我們開始吧！

如何運行它

最簡單的運行方式就是前往 https://github.com/GitHubSecurityLab/seclab-taskflows-fuzzing 並啓動一個 codespace。

然後，像這樣運行腳本：

./scripts/fuzzing/run_fuzzing.sh PROJECT

例如：

./scripts/fuzzing/run_fuzzing.sh tukaani-project/xz

就是這樣。參數只是一個 GitHub owner/repo slug。接下來，智能體會自行處理所有前期步驟：

  • 安裝 AFL 等軟件
  • 克隆代碼倉庫
  • 識別代碼中最相關的函數
  • 為這些函數創建模糊測試目標

如果你只想在投入長時間測試活動之前做個快速冒煙測試，就把它指向一個小項目：

./scripts/fuzzing/run_fuzzing.sh DaveGamble/cJSON

運行之前有一點提醒：這個 taskflow 會直接在宿主機上運行 afl-fuzz、clang 以及 由 LLM 選定的任意構建命令，中間沒有容器隔離。一個被提示詞注入的智能體原則上可以做你的用户能做的任何事情。所以請只在一次性環境（例如 Codespace 或一次性虛擬機）中運行它，且不要使用提權權限。

模型選擇

一些前沿模型會對其輸出施加安全護欄。對於模糊測試任務流程，我們默認使用 Claude Sonnet 5，因為它在我們的所有內部測試中都順利通過。你可以通過修改以下文件來選擇其他模型：src/seclab_taskflows_fuzzing/configs/model_config.yaml。

一分鐘瞭解架構

在進入有趣的部分之前，先了解各部分如何組合在一起會有所幫助。共有三層：

  • 一個 shell 驅動腳本（run_fuzzing.sh），將各個流水線階段串聯在一起。
  • 一組 taskflow YAML，每個階段一個，它們本質上就是告訴 LLM 智能體在每個步驟該做什麼的提示詞。
  • 一組 MCP 工具，智能體調用它們來實際完成工作：運行 AFL、編譯 harness、存儲崩潰、讀取覆蓋率報告等等。

我最看重的設計原則是職責的清晰分離：LLM 智能體負責決策，MCP 工具負責執行。智能體決定要 fuzz 什麼、要編寫什麼 harness、接下來要追查哪個覆蓋率缺口。工具只暴露諸如 run_afl_for 或 compile_harness 這樣的原語。智能體從不直接調用 AFL 或 clang；它用這些構建塊組合出流水線。所有狀態都存放在一個 SQLite 數據庫（fuzz_context.db）中，因此各個階段之間從不通過內存傳遞數據，只通過數據庫傳遞。

一個微小但重要的細節：每個 harness 都會被構建兩次。AFL 的邊緣插樁非常適合引導 fuzzer，但對於人類可讀的覆蓋率報告毫無用處。因此每個 harness 都會變成兩個二進制文件：一個 .afl 二進制（用 afl-clang-lto -fsanitize=address,undefined 構建）和一個 .cov 二進制（用 clang -fprofile-instr-generate -fcoverage-mapping 構建）。.afl 二進制負責執行 fuzzing；.cov 二進制隨後回放 AFL 的隊列，以生成真實的源碼行覆蓋率和分支覆蓋率。

覆蓋率反饋循環

這是整條流水線的核心，也是最直接地自動化了我開頭所描述的那套手動工作流程的部分。

如果你曾經嘗試過手動提升 fuzzing 覆蓋率，你就會知道這是一個迭代過程，大致如下：

“檢查覆蓋率”這一步過去由我手動完成，人工閲讀 LCOV 報告，尋找未覆蓋的分支。“提升覆蓋率”這一步同樣由我完成，這次是編寫新的測試框架或構造新的輸入。而 Fuzzing Taskflow 把這兩步都交給了智能體。

每一輪迭代中，對於每個測試框架，智能體會在給定的時間預算內運行 AFL，將隊列針對 .cov 二進制文件重放以獲得真實的覆蓋率報告，然後讀取未覆蓋分支的列表。根據所發現的情況，它會從若干操作中選擇一項：

  • 添加一個為觸達未覆蓋分支而專門構造的新種子
  • 編輯測試框架源碼以調用額外的 API
  • 用某個守衞正在比較的魔術常量自動豐富 AFL 字典
  • 如果只是冷門的錯誤路徑或不值得追查的廠商代碼，就直接跳過這個缺口

時間預算每一輪迭代翻倍：

30s → 60s → 120s → 240s → 480s → 960s（約 32 分鐘/目標）

其思路是早期進行廉價、短時間的輪次（此時有大量唾手可得的覆蓋率可以獲取），後期則進行更長的輪次（此時模糊測試器需要更多時間才能突破某個難以攻克的守衞）。

而正如我手動工作流中的做法，我需要回答這個問題：我們什麼時候停下來？在這裏，循環使用了平台期檢測：一旦連續兩次迭代各自的增益都低於一個可配置的閾值（默認是 1% 的絕對行覆蓋率），循環就判定已經進入收益遞減，隨即繼續推進。這能避免智能體耗費數小時算力去榨取最後那百分之零點幾的覆蓋率。

結構感知模糊測試

AFL 默認的字節級變異器（位翻轉、算術運算、塊拼接）在二進制格式上表現出色，但面對結構化的、基於文本的輸入時就力不從心了。經典的解決方案是為每種格式手寫自定義變異器，但這是一項繁瑣的工作。這一次，我希望流水線替我完成這項工作，因此它內置了四種互補機制來生成結構感知的輸入。

1. 按格式定製的字典與自定義變異器。對於輸入格式可被識別的目標（JSON、XML、regex、PNG、帶長度前綴的二進制 TLV），該 taskflow 內置了預構建的 AFL 字典和 LLVMFuzzerCustomMutator C 文件。JSON 變異器執行 token 拼接和括號配對複製；XML 變異器瞭解標籤、實體以及 billion-laughs token；regex 變異器則攜帶真實的 ReDoS 模式。每個變異器都會把一半的變異操作交還給 AFL 的默認字節變異器，這樣我們就保留了引擎的隨機化，而不是與之對抗。

2. 源級字典。對於流水線無法識別的格式，它會通過掃描目標自身的 .c/.h 文件即時生成一個自定義變異器。它提取字符串字面量和 32 位數值常量（來自 #define、case 和 enum），過濾掉噪聲，並將它們用作拼接 token。其直覺很簡單：解析器所檢查的最有意思的魔法值，通常就寫在它自己的源代碼中的某處。

3. 一個動態生成的、由覆蓋率驅動增強的 AFL 字典。同一組源 token 集合也會在第 1 次迭代之前作為 AFL 經典字典輸出（數值常量同時以兩種字節序給出，這樣無論主機字節序如何，模糊測試器都能滿足針對 4 字節魔法值的 memcmp）。隨後，在每一個覆蓋率步驟之後，流水線會查看未覆蓋行附近的守衞（strncmp、memcmp、case 0xN、== ‘X’），並追加它發現的任何新 token。這個字典確實會朝着模糊測試器尚無法觸及的代碼不斷增長。

4. 一個語料拼接算子。這個智能變異器還可以從語料目錄加載文件，並將其中隨機的子區域拼接到輸入中，這是一種重組風格的算子，而 AFL 自帶的 havoc 在這方面做得並不好。

不斷演進的語料庫

悄悄扼殺模糊測試效率的一個因素，就是丟棄已有的進展。如果每次運行都從原始種子開始，你就要一遍又一遍地重新付出發現相同路徑的代價。

為了避免這種情況，每個測試框架都會獲得一個穩定的語料庫目錄，它能在多次迭代乃至整個測試活動期間持續存在：

<workspace>/corpus/harness_<id>/

在每次迭代結束時，AFL 的隊列會被合併到這個目錄中，並通過afl-cmin運行，以使其規模保持有界。其效果是，昨天發現的有趣輸入會延續到今天的運行中，而上週測試活動中發現的輸入會延續到這一次。如果你停止並重新啓動一次測試活動，你不會丟失任何東西。

分類與漏洞報告

發現崩潰只是工作的一半。任何做過根因分析的人都知道，分類往往是整個過程中最乏味的部分。而這正是智能體大放異彩的另一個地方。

模糊測試循環結束後，會自動運行三個階段。首先，每個崩潰都會用 afl-tmin 進行最小化，在 ASan 下重放以捕獲堆棧跟蹤，並通過 棧頂哈希 進行去重（對頂部規範化幀做哈希，剝離模板、內聯命名空間和 LTO 後綴，使語義相同的崩潰歸併到一起）。其次，將此前已知的崩潰針對當前二進制重放，以確認上游修復是否已解決它們。第三，智能體讀取測試框架源碼和崩潰函數，從公共 API 回溯調用鏈，並撰寫每個崩潰的 markdown 報告。

每份報告會給出以下判定之一：

  • 漏洞
  • 庫加固
  • 測試框架缺陷
  • OOM
  • 超時
  • 斷言失敗
  • 重複

真正的漏洞（可通過公開 API 觸達並利用）與單純的harness_bug（問題出在我們自己的 harness 中，而非庫本身）之間的區分，正是那種過去需要我坐下來手工追蹤代碼才能做出的判斷。每份報告都包含根因分析，附有文件:行號引用、可達性論證、可利用性評估、以統一 diff 形式給出的建議修復，以及迴歸測試草案。

在此澄清一下：建議的補丁被標記為“需要審查”是有原因的。智能體的分析受限於模型對目標代碼的理解，它確實會出錯。請把這些判定視為一份為人類精心準備的起點，而非最終結果。

實時儀表盤

運行一場自主行動卻看不到它在做什麼，這讓人很不踏實，因此該流水線會把所有內容發佈到一個實時 HTML 儀表盤上。一旦你啓動一場行動，它就會在後台自動啓動，監聽端口8765。在 Codespace 中該端口會自動轉發，因此你可以在任意瀏覽器中打開它，在儀表盤上實時觀看行動進展。

該頁面展示的內容包括：

  • 每個 harness 的“運行中”脈衝指示
  • 一張帶內聯迷你走勢圖的覆蓋率趨勢表
  • 崩潰熱力圖
  • 迭代時間線
結論

我啓動這個項目，是出於任何安全研究員都熟知的那些侷限：模糊測試確實有效，但若沒有人工投入就無法規模化，而人工投入正是瓶頸所在。Fuzzing Taskflow 是我嘗試將這一瓶頸向後推移的成果——把重複性的部分（編寫測試框架、閲讀覆蓋率、追蹤覆蓋缺口、分類崩潰）交給 LLM 智能體，同時在智能體的判斷與執行實際工作的工具之間保持清晰的分離。

如果你是 C/C++ 項目的維護者，那麼請試一試。如果你的項目此前從未進行過模糊測試，那麼這個工具將幫助你快速上手。或者如果你的項目曾經進行過模糊測試，那麼這個工具或許能通過提升你的模糊測試覆蓋率來幫助發現新的 bug。

源代碼是開源的，所以如果你遇到任何 bug，請創建 issue。也歡迎貢獻代碼！
