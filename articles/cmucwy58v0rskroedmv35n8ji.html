Anthropic 發佈 Claude Opus 5.5，成本較 Opus 5 降低 40%

內容機器翻譯自第三方媒體（Anthropic），僅供參考，以原文為準。

Anthropic 發佈 Claude Opus 5.5，為 Claude 5.5 系列首個模型，在多數工作上達到 Fable 5.1 水平，典型負載成本較 Opus 5 低 40%。

推薦理由

原文給出定價、基準與安全評測細節，讀者可以據此評估 Opus 5.5 在成本和長任務上的實際變化。

正文

我們推出 Claude Opus 5.5，這是我們全新 Claude 5.5 家族中的首個模型。它在大多數工作上的表現達到 Claude Fable 5.1 的水平，而運行成本比 Opus 5 低 40%。

Claude Opus 5.5 是我們自呼籲 放緩前沿步伐 以來的首個發佈版本。它在發佈前由外部評估方進行了測試，包括 Frontier Design 和 METR。在我們運行的自動化行為審計——即我們所做的最全面的對齊測試——中，Opus 5.5 是我們迄今測試過表現最強的模型。它還配備了我們為最強能力模型所開發的各項防護措施。

以下是你可以從 Opus 5.5 中期待的一些改進：

性能。 Opus 5.5 相較 Opus 5 是一次重大躍升。它是新的領先模型，早期測試者在其最複雜的工作上看到了性能的大幅提升。一位測試者在不到一天內完成了一項 68 萬行的代碼遷移——這項工作原本需要一個工程團隊花費數週。它擅長髮現並修復軟件中的低效問題：當我們要求它縮短一個 Web 應用每個頁面的加載時間時，Opus 5.5 在 40 次中成功了 39 次，而 Opus 5 只做出了較小的改進，且還改變了應用的行為。另一位測試者讓多個 Claude 模型根據單個提示詞構建一款遊戲；Opus 5.5 憑藉其畫面表現和精細度得分高於其他任何模型。

安全性。在我們迄今所有模型中，Opus 5.5 在我們的自動化行為審計——即那套在數千個模擬場景中測試 Claude 的對齊測試套件——上取得了最佳成績。與近期模型相比，它採取難以逆轉的行動或越出既定邊界的可能性要低得多，而且比 Opus 5 更能抵禦提示詞注入。我們還擴展了對齊測試的範圍，覆蓋了更長的任務、不可能完成的任務，以及以真實事件為藍本的場景，不過它仍有侷限。我們評估的完整細節見 Opus 5.5 System Card。

由於 Opus 5.5 在生物學和網絡安全方面與 Claude Mythos 5.1 相當，我們為其部署配備了與 Claude Fable 5.1 類似的防護措施。經過審核的機構今天即可申請我們的 生命科學驗證計劃，以將 Opus 5.5 用於生物學研究。未來幾周內，我們還將擴大 網絡安全驗證計劃的准入範圍，經過驗證的網絡安全從業者將能夠使用 Opus 5.5 開展工作。

成本與速度。Opus 5.5 的推理服務所需算力低於 Opus 5，其定價也反映了這一點。我們的測試顯示，在默認設置下，它在典型工作負載上的成本將比 Opus 5 低 40%。輸入和輸出 token 分別為每百萬 $4 和 $20，比 Opus 5 低 20%。緩存讀取（佔智能體和編程工作成本的大部分）為每百萬 token $0.20，比 Opus 5 低 60%。Opus 5.5 的輸出生成速度也比 Opus 5 快 30% 以上。

除了降價之外，我們還將提高 Pro、Max 和 Team 套餐的五小時使用限額。我們還將為訂閲用户提供一次速率限制重置，你現在可以將其保存下來，並在你選擇的任何時候使用。

溝通能力。 Opus 5.5 的溝通比之前的模型更自然。早期測試者發現它的寫作更清晰、更易於理解，這解決了我們聽到的關於 Opus 5 的一些常見反饋。它把最重要的信息放在前面，其風格使其在長時間會話中成為更好的工作夥伴。正如一位早期測試者所説，“它寫作的方式就像我一樣。”在我們自己的使用中，這讓 Opus 5.5 的工作更易於跟進和檢查——這既是安全方面的好處，也是實用方面的好處。

Claude Sonnet 5.5 和 Claude Haiku 5.5 將在未來幾周內推出，並帶來許多相同的性能、效率和安全性改進。

性能與成本效益

在我們的基準測試中，Claude Opus 5.5 在智能體編程、計算機使用和知識工作方面領先。話雖如此，在這些能力水平上，我們發現基準測試的差距已不再是衡量現實世界差異的可靠指南。在我們自己的使用中，Opus 5.5 與 Claude Fable 5.1 之間的差距比這些分數所顯示的要小。

編程

Opus 5.5 尤其擅長處理長期且龐雜的任務，例如全代碼庫範圍的遷移與審計。一位早期測試者用它審計並修復了一個 200,000 行的代碼庫，耗時不到三小時，而 Opus 5 則用了超過 20 小時，且消耗了 2.5 倍的 token。

在一項內部測試中，我們讓 Opus 5.5 和 Fable 5.1 將 HAProxy（一款廣泛使用的、用於在多台服務器之間平衡網絡流量負載的軟件）從 C 語言翻譯成 Rust。兩個重寫版本都通過了 HAProxy 自身幾乎所有的迴歸測試，但 Opus 5.5 在 9.5 小時內完成，而 Fable 5.1 用了 12 小時，且成本低 51%。

Opus 5.5 以極低的成本在智能體編程方面取得了前沿成果。在 FrontierCode 上，以其默認投入水平，它擊敗了 GPT-6 Astra，而每任務成本僅約為後者的 20%。在 Terminal Bench 4.0 上，它以約 40% 的成本與 Astra 持平，而在 CursorBench 上，它以約三分之一的成本領先 GPT-5.6 Sol 11 分。

最安全的編碼智能體

在自身系統內使用智能體的企業需要知道這些智能體正按預期運行，尤其是當它們自主運行數小時之久時。Opus 5.5 擁有一個會在每個操作執行前對其進行篩查的分類器、一個安全團隊可審計的開源沙箱，以及能在漏洞合併前將其捕獲的代碼審查。

該模型本身也具備更強的防禦能力。在提示詞注入攻擊方面，它在我們測試的每一種場景中都追平或超越了 Opus 5，包括編碼、工具使用、計算機使用和網頁瀏覽。在 AI 安全公司 Gray Swan 運行的一項基準測試中，Opus 5.5 與 Fable 5.1 並列，創下所有受測模型中最低的提示詞注入成功率。

知識工作

Opus 5.5 是一位可靠且嫺熟的研究者。在一項內部測試中，我們要求 Opus 5.5、Fable 5.1 和 Opus 5 僅使用它們在一個財報難以找到的網頁副本上所能找到的信息，撰寫一份關於某公司季度業績的報告。一個自動評分器將每一個數字和引文與來源進行了核對。

在不同的 effort 設置下，Opus 5.5 的報告中 18 份裏有 16 份達到了我們的質量標準，而任何編造的數字或引文都會導致不合格。Fable 5.1 和 Opus 5 在任何一次嘗試中都未能達到這一標準。

它在財務分析和商業工作方面同樣表現出色。投資公司 Walleye Capital 作為早期測試方報告稱，Opus 5.5 在其最低設置下就基本解決了他們的評估套件；在更高設置下，它的表現更加出色，甚至發現了他們評估指令中的一處錯誤並加以糾正。此前沒有任何其他模型發現過這一錯誤。

在另一項測試中，我們讓 Opus 5.5 和 Opus 5 分析兩家虛構的人力資源軟件公司之間的擬議合併。兩者各自在 Excel 中構建了一個財務模型，然後將其轉化為一份高管演示文稿，説明這筆交易按其價格是否合理。兩個模型對這筆交易得出了相同的結論，但 Opus 5.5 的模型更為詳盡，其演示文稿也更易讀，而 Opus 5 的模型則有輕微錯誤。

Opus 5.5 用時 63 分鐘完成，而 Opus 5 用了 93 分鐘，且 Opus 5.5 的製作成本低了 50%。

在知識工作評測中，Opus 5.5 表現優於其他模型，同時使用的 token 更少。在 GDPval-AA v2.1 這一覆蓋 44 種職業的真實工作測試中，Opus 5.5 得分 1846 Elo，領先於 Fable 5.1 和 Opus 5。在默認努力程度（中等）下，Opus 5.5 擊敗了以最高努力程度運行的 GPT-6 Astra，而每任務成本僅約為其五分之一。在衡量業務流程和大規模數據收集的基準測試中，它同樣優於其他模型。

我的發現

額外的下降並不是免費層造成的——而是 0552feb 中的一處迴歸（“將計費週期邊界提取到 periods.py”，標註為“無行為變更”）。

這個 bug

aggregate.monthly_usage 以前做的是半開區間：

start, end = month_start(year, month), next_month_start(year, month)
if start <= e.ts < end:

它現在做的是：

if period.contains(e.ts)

而在 periods.py 中：

@property
def last_day(self) -> datetime:
    return next_month_start(...) - timedelta(days=1)   # 2026-08-31 00:00:00 UTC

def contains(self, ts):
    return self.first_day <= ts <= self.last_day

last_day 是一個午夜時刻的 datetime，而不是一整天。從 9 月 1 日減去一天得到 8 月 31 日，而比較是包含邊界的，因此該週期實際上在 31 日的第一個瞬間就結束了。所有時間戳在當月最後一天午夜之後的事件都會被靜默丟棄——每個賬户每月大約損失一天的使用量。

新的 test_periods.py 無法捕獲這個問題，因為它只檢查 last_day.date()（該值正確地等於 2026-08-31），並在 8 月 1 日 00:00、8 月 15 日 12:00、7 月 31 日和 9 月 1 日測試 contains——它從未在 31 日內的任何時間點進行探測。

額外的損失是計費重構中的一個 bug

免費層級的變更僅佔 acme 8 月降幅中的 $1.50。其餘 $9.92 來自提交 0552feb 中的一個 bug。該提交被標記為“無行為變更”，但它停止統計當月最後一天的使用量。

變更內容

在合併之前，aggregate.py 使用的是半開區間：

start <= e.ts < next_month_start(year, month)    # [Aug 1 00:00, Sep 1 00:00)

重構將其移入 Period.contains，並使區間在錯誤的邊界上閉合：

last_day = next_month_start(...) - timedelta(days=1)    # = 2026-08-31T00:00:00Z
return self.first_day <= ts <= self.last_day

last_day 是一個午夜時間戳，而不是一整天。因此，2026-08-31T00:00:00Z 之後的每個事件都被排除在外。9 月週期從 9 月 1 日開始，所以它也不會納入這些事件。用量不會被移到另一個月；它根本不會被計費。

安全

為前沿發展定節奏

上週，我們的 CEO Dario Amodei 主張，AI 的進展應當有節奏地推進，以便安全實踐始終領先於模型能力。定節奏是一種讓 AI 保持安全、與中國保持競爭力並實現 AI 惠益的方法，尤其是在生物學和醫學等領域。

我們大體上了解當今模型所帶來的風險，並且有充分能力加以管理。然而，隨着能力提升，更嚴重的風險可能迅速出現，我們現在就需要為此做好準備。因此，我們的安全工作同時着眼於兩個時間維度：

針對當前模型的安全實踐。當前這一代模型依賴一套既定的實踐：廣泛的對齊測試、由 METR 和 Frontier Design 等外部機構進行的發佈前評估，以及針對網絡安全和生物學等高風險領域、與每個模型能力相匹配的防護措施。我們在每次發佈時都會完善這些實踐。我們認為，這些實踐足以應對當今模型所帶來的最嚴重風險，也相信它們讓我們對各類嚴重風險有了廣泛——儘管並不完美——的瞭解。

此外，我們會追蹤自身訓練和評估對齊模型的能力，並在我們依據 Responsible Scaling Policy（我們為管理先進 AI 系統帶來的災難性風險而制定的自願性框架）發佈的風險報告中，同時彙報我們的公開模型和內部模型情況。

為未來的模型做準備。我們正在為更先進的模型預先準備訓練和評估流程。我們正在收緊對強化學習所用環境的篩選，因為有缺陷的環境是導致失準行為的主要來源之一。此外，我們正在改進對齊獎勵，並開發自動化流程，以生成用於安全訓練的多樣化新場景。同時，我們正在加強安全與監控，包括一項重點努力：改進基於可解釋性的監控與評估。我們希望這類技術有助於減少我們對審計模型思維鏈、即其在工作過程中寫出的推理內容的依賴。

能力更強的模型——例如那些能夠完全自動化 AI 研究本身工作的模型——需要更高的安全標準。我們呼籲放緩節奏，很大程度上是基於我們預期這類模型可能很快就能被訓練出來。對於這些模型，我們並不假設上述措施本身就能滿足這一安全標準。隨着 AI 能力不斷增強，公共政策應在確保人們所依賴的系統安全方面發揮更大作用。這種能力需要時間建設，而我們已開始搭建支持它的基礎設施，正如“我們必須放緩前沿步伐”一文以及我們近期與Accenture的公告所述；我們預計很快會分享有關這些努力的更多細節。我們還將繼續與政府和行業開展政策討論，包括在監管方式和國際協調方面。

對齊

在我們的主要評估套件中——一項針對 Claude 在近 2,000 個場景下進行評測的自動化行為審計——Opus 5.5 在幾乎所有失準行為的衡量指標上都優於近期任何一款 Claude 模型。在大多數誠實度指標上，它也是我們最強的模型。

尤其是，Opus 5.5 在若干曾導致近期網絡安全事件的行為上相較前代模型有所改善，包括帶有偏見或動機驅動的推理、試圖逃離沙箱，以及在斷定自己處於模擬環境後採取有害行動。在一項旨在測試模型跨越隔離邊界傾向的新評估中，Opus 5.5 試圖繞過邊界的頻率比 Opus 5 或 Claude Mythos 5.1 低約 85%，而且它所做的每一次嘗試都屬於低嚴重度且主動上報。對於在代碼庫和系統中無人值守運行 Claude 的團隊來説，這一點與原始能力同樣重要。

然而，正如我們在近期的對齊評估中所描述的，構建能夠在部署前可靠捕捉每一次失敗的評估，仍是一個尚未解決的問題。我們發現有跡象表明，Opus 5.5 常常懷疑自己正在被評估，這使我們難以評估它在部署所處的各種真實世界環境中將如何行動。隨着這些環境不斷擴展、模型能力不斷提升，我們預計這一挑戰會加劇，除非我們在可解釋性方面取得進展。儘管我們確信 Opus 5.5 在我們能夠衡量的方面展現出廣泛改進，我們仍將自身的對齊工作與下文所述的防護措施配合使用。

防護措施

隨着我們的模型能力日益強大，更嚴格的防護措施是我們防止新能力淪為濫用工具的一種方式。Opus 5.5 是首個在網絡安全、生物學和知識蒸餾方面採用與 Fable 5.1 同類防護措施上線的 Opus 模型，所有這些任務都會透明地回退到另一個模型。

網絡安全。由於 Opus 5.5 具備極強的網絡能力，我們為 Opus 5.5 應用了與 Fable 5.1 類似的網絡安全防護措施。用户將能夠在常規軟件開發生命週期中識別並修復其代碼中的漏洞，但大多數網絡安全任務將被重新路由至 Opus 4.8。

面向網絡防禦者，我們很快將把 Cyber Verification Program 擴展至 Opus 5.5。新計劃將包含三個層級，提供越來越寬鬆的可信訪問權限，其中包括對 Claude Mythos 模型的訪問。Claude Security 現已可用，並可訪問 Claude Mythos 5.1。

生物學。Opus 5.5 在生物學領域能力極強，超越 Opus 5，並在許多工作領域與 Claude Mythos 5.1 持平或更勝一籌。例如，Opus 5.5 在與 Dyno Therapeutics 合作開展的一項長時程分子預測與設計評估中取得了提升，專家紅隊成員將其科學新穎性評為與他們測試過的最佳模型相當。

因此，Opus 5.5 採用了與 Fable 5.1 相同的生物學安全保障措施。若因這些保障措施而無法將 Opus 5.5 用於研發工作，用户可申請我們新推出的 生命科學驗證計劃，該計劃讓經過審核的機構（如學術實驗室、初創公司和製藥企業）獲得專為覆蓋生物學相關全部工作範圍而設計的安全保障。有意向的機構可在此申請。

知識蒸餾

知識蒸餾攻擊是指攻擊者利用數千個虛假賬號以工業化規模提取模型能力，從而帶來安全和國家安全風險。知識蒸餾使惡意行為者能夠在沒有我們為 Claude 內置的安全保障的情況下，打造出能力極強的模型。我們 2026 年 9 月威脅情報報告詳細介紹了我們迄今已檢測並阻止的非法知識蒸餾活動。

Opus 5.5 發佈時即配備保留式思考（preserved thinking），這是我們隨 Fable 5.1 一同推出的反知識蒸餾保障措施。它阻止 API 用户編輯 Claude 此前的上下文，以防其試圖提取 Claude 的推理過程。該措施適用於 2026 年 8 月 31 日或之後創建的 API 賬號下的 Fable 5.1 和 Opus 5.5。我們的 幫助中心文章解釋了這一變更，我們的 保留式思考文檔則展示瞭如何測試和更新你的集成。

數據保留與合規

與之前的 Opus 模型一樣，Opus 5.5 可提供零數據保留。

與 Fable 5.1 一樣，Opus 5.5 也附帶我們的水印措施，以符合歐盟《人工智能法案》的要求，詳見此處。此外，它也不再支持關閉“thinking”模式，如我們在此處所述。

可用性

Claude Opus 5.5 現已在所有平台上線，包括 Amazon Web Services、Google Cloud 和 Microsoft Azure。在 Claude Platform 上，開發者可以通過 claude-opus-5-5 使用。
