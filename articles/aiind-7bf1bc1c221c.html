股價破發、用户抱怨、創始人套現，Anthropic CEO 深夜回應：我從沒想過讓 AI 統治人類

正文

這次發佈有一個明顯的架構變化：Anthropic 沒有讓單個 Agent 包攬所有工作，而是將 Code Review、PR Steward 和 Claude Approvals 拆成三個獨立組件，分別承擔審查、修復和審批職責。它們圍繞同一個 PR 協作，代碼出現問題後可以自動觸發修復，修復完成後再進入相應的審查與審批流程。

其中，Claude Ship 引入的策略驅動審批機制改變了 AI 參與代碼交付的方式。團隊可以通過 YAML 文件定義代碼路徑、變更範圍、審查結果與審批要求之間的關係，系統根據實際修改動態判斷審批條件。Agent 能夠執行哪些操作，也因此有了明確的規則邊界。雷鋒玩

這套架構涉及一個更深層的工程問題：當 AI 開始自主修改代碼，甚至參與決定代碼能否合併，如何避免執行、審查和審批集中在同一個 Agent 手中？Claude Ship 將職責隔離與策略引擎結合，給出了自己的實現路徑。

Claude Ship 將 GitHub PR 作為三個組件共享的工作對象。Diff、Commit、CI 檢查、審查線程和審批結果保留在 PR 中，各個 Agent 根據這些工程狀態開展工作，並將執行結果寫回。這樣，任務上下文不再依賴對話傳遞，代碼版本和操作記錄本身就能承接後續任務。

工作流由 PR 事件推動。PR 創建、分支 Push、檢查失敗以及新增審查意見，都會影響後續執行。團隊可以選擇 Quick、Standard、Deep 三種審查級別，並設置在 PR 創建時、每次 Push 後或人工請求時運行。

Code Review 內部採用 Find、Verify、Rank 和 Post 四階段處理。Find 階段由多個 Agent 並行閲讀 Diff 及周邊代碼，從邏輯錯誤、安全缺陷和邊界條件等角度尋找問題。審查範圍延伸到修改行之外，因為局部代碼能否正常運行，往往取決於調用方、數據流和接口約束。

Verify 階段負責重新檢查候選發現，確認問題能否從實際代碼路徑中得到支持，Rank 階段進行去重和嚴重程度排序，Post 階段將結果寫入 PR，形成行內審查意見和 Check。

這種設計解決了代碼審查中的一個典型問題：模型可以發現可疑代碼，卻未必能判斷它是否構成真實缺陷。獨立驗證能夠過濾一部分缺乏上下文依據的判斷。需要注意，Code Review 採用只讀方式檢查代碼，不負責構建和運行項目，因此仍然需要 CI 提供實際執行結果。

PR Steward 則運行在雲端會話中，處理與當前 PR 有關的 CI 失敗、合併衝突和審查反饋。它能夠修改文件、推送 Commit，並説明每次修改的內容和撤銷方法。對於範圍明確的代碼調整，它可以直接執行，涉及較大的架構取捨時，則會等待開發者決定。

它還有明確的觸發限制：來自 Fork、Bot 創建，以及提交者沒有倉庫寫權限的 PR 默認會被跳過。運行期間，開發者可以通過 @claude 調整任務，或發送 @claude stop 終止執行。

這裏的架構邊界很重要：PR Steward 可以寫入代碼，卻沒有批准和合並權限。它負責產出新的代碼版本，後續審批由獨立機制處理。修復和授權被拆開，避免執行任務的 Agent 同時成為自己的驗收者。

Claude Approvals 的核心是倉庫中的 .claude/approvals.yml 。團隊將審批要求寫成結構化規則，系統根據 PR 修改的文件匹配規則，再計算 Claude 是否可以批准，以及需要多少人工審批席位。

paths 指定規則覆蓋的文件範圍， if 描述規則成立的條件， verdict 決定審批結果。其中， claude 有 approves 、 comments 和 blocks 三種狀態，分別表示允許 Claude 批准、只允許留下審查意見，以及阻止審批。 seats 則規定人工審批人數，還可以限定參與者來自哪個 GitHub Team，或排除 PR 作者。

這套規則採用逐文件評估。系統會檢查每個修改文件適用哪些 Rule，再將結果彙總到整個 PR。如果同一文件匹配多條規則，會保留約束更嚴格的結果，優先級依次為 blocks 、 comments 和 approves 。不同規則要求的人工審批席位也需要分別滿足。

目錄級配置進一步解決了大型倉庫的規則維護問題。系統會從變更文件所在目錄向上查找策略，使用距離文件路徑更近、處於 Enforce 狀態且覆蓋該文件的配置。上層策略可以通過 nested: inherit 繼續約束下層目錄。組織能夠在根目錄維護基礎規則，業務模塊則可以根據自身代碼特點設置局部要求。

條件表達式還可以讀取 PR 的文件數量、Diff 行數、作者、發起者和目標分支等屬性，並支持 ANY 、 ALL 等邏輯組合。這裏有一個細節： pr/diff_lines 統計整份 PR 的變更規模， rule/files_changed 只統計當前規則覆蓋的文件。兩種統計口徑讓團隊可以同時管理整體修改規模和局部模塊的審批要求。

override 則允許在基礎 Verdict 上增加條件分支，系統按配置順序採用首條成立的規則。它可以根據審查結果調整人工審批人數，或者改變 Claude 是否擁有批准權限。

這種策略計算需要考慮模型調用失敗的情況。如果 Override 依賴的分類器沒有返回結果，系統會回到基礎 Verdict，如果分類器出現在 Rule 自身的 if 中卻沒有結果，審批 Check 會失敗。因此，基礎規則需要保留足夠嚴格的審批要求，避免模型調用異常時意外放寬權限。

還有一項關鍵的安全設計：Claude Approvals 從默認分支讀取策略文件。PR 中尚未合併的審批規則修改不會作用於當前 PR，只有規則進入默認分支後才會參與後續評估。這避免了提交者通過待審查代碼修改審批條件，為自己的代碼降低門檻。

Claude Approvals 不能直接讀取 CI 結果，測試和構建仍然需要作為獨立的 GitHub Required Check 運行。它自己的 Check 也需要被配置為 Required Check，才能實際參與合併約束。Observe Mode 則允許團隊先運行策略、觀察審批結果，再決定是否啓用強制檢查。

路徑規則和 PR 屬性能夠描述修改發生在哪裏、規模有多大，卻無法充分表達代碼在語義上發生了什麼。Claude Approvals 通過 Classifier 補充這層判斷。

團隊可以在 .claude/classifiers/ 中創建分類器，通過 def.yml 定義模型、Prompt、輸入參數和輸出範圍。Prompt 負責描述判斷任務， outputs 則限制模型可以返回的結果，例如 low 、 medium 和 high 。策略引擎讀取這些結構化結果，再根據條件決定審批要求。

前者讀取 Code Review 的結果，沒有尚未解決的 Important 級別發現時返回 pass ，仍有此類問題時返回 fail 。後者比較新舊 Diff，將變化歸類為 trivial 、 same_intent 或 different ，判斷後續代碼修改是否延續原來的意圖。
