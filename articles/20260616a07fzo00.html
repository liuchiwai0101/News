從 React Native 到 Flutter，再到近幾年快速升溫的 Kotlin Multiplatform（KMP），行業始終在尋找一個問題的答案：如何在開發效率、原生體驗與長期維護成本之間取得平衡。 而隨着鴻蒙生態的快速發展，以及 AI 編碼工具對軟件開發方式的持續重塑，跨平臺框架正在迎來新一輪範式轉變。過去討論最多的是“一套代碼跑多端”，今天開發者開始關注的是：跨平臺技術如何幫助企業完成生態遷移？AI 是否會削弱跨平臺框架的價值？未來五年，跨平臺開發還會以今天的形態存在嗎？ 圍繞這些問題，InfoQ 對話華爲鴻蒙 KMP 技術負責人謝國。作爲曾經的字節跳動 Flutter 團隊負責人，謝國先後參與過 Flutter 的大規模落地與鴻蒙生態下的 KMP 實踐，親歷了兩代跨平臺技術路線的發展。 在他看來，跨平臺框架正在從“代碼複用工具”演變爲“生態連接器”；而 AI 的出現，也正在重新定義框架本身的價值邊界。 InfoQ：您從字節跳動 Flutter 團隊負責人，到現在在華爲主導鴻蒙上的 KMP 實踐，這一路走來，您對“跨平臺框架到底在解決什麼問題”這件事的理解，有沒有發生過比較大的變化？ 謝國：在字節做 Flutter 的時候，我們當時的核心訴求很直接，就是儘可能消除雙端差異——用一套代碼同時覆蓋 iOS 和 Android，實現降本增效，同時追求渲染一致性和性能表現。 過去更多是在成熟生態中做統一和優化，而面對鴻蒙這樣的新生態，跨平臺框架解決的已經不只是“多端複用”的問題，更承擔着生態遷移和應用落地的重要角色。它更像是一種平滑遷移方案，讓企業現有的移動端資產，尤其是業務邏輯代碼，能夠快速遷移過來，先解決可用性問題，再持續優化體驗和性能。 因此，我的理解也從“技術層面的統一”逐漸轉向“生態層面的連接”。尤其是 KMP，在很多場景下承擔的正是幫助企業將 Android 側的技術資產高效遷移到鴻蒙生態中的角色。 InfoQ：鴻蒙作爲一個全新的操作系統生態，和當年在 iOS/Android 上做框架適配相比，您感受到最大的不同是什麼？是技術層面的，還是更多是生態和協作層面的？ 謝國：最大的不同其實是在生態和協作層面，技術反而只是表象。如果用一個詞來概括，那就是“角色反轉”。 當年做 iOS 和 Android 適配，本質上是在成熟生態中做優化。兩個系統已經建立起完整的技術體系，我們作爲框架開發者，更多是在既定規則下開展工作——Google 和 Apple 定義好了規則，我們需要做的是理解這些規則，並讓框架能夠順利運行。社區有大量參考資料、成熟的 JNI 規範以及完善的 NDK 工具鏈，我們的主要工作是完成不同平臺之間的適配與銜接。 但到了鴻蒙，情況有所不同。作爲一個全新的操作系統生態，鴻蒙面對的是已經發展十餘年的 Android 和 iOS 存量應用生態。藉助跨平臺框架，可以有效降低生態夥伴適配鴻蒙的成本和投入。鴻蒙的發展策略也比較務實：先解決兼容問題，再逐步構建差異化能力。 這種策略決定了我們在進行 KMP 適配時的很多思考方式，也帶來了與以往不同的實踐體驗，主要體現在以下幾個方面：

1. 協作層面的“合力破局”

以前做適配時，我們和手機廠商之間基本沒有直接溝通，更多依賴開源代碼和社區資料完成適配工作。但在鴻蒙生態裏，我們更像是與華爲以及廣大 App 開發者共同推進生態建設的參與者。 當遇到鴻蒙底層的性能瓶頸時，我們會與合作伙伴一起分析問題、解決問題。因爲 KMP 這樣的方案能夠幫助降低開發者遷移成本、豐富鴻蒙應用生態，各方在目標上具有較強的一致性。 這種“你中有我、我中有你”的協作密度，是在成熟生態裏很難看到的。以前我們是“孤獨的適配者”，現在我們是“生態共建者”。

2. 技術層面的“兼容優先”

鴻蒙從一開始就不是希望開發者“二選一”，而是實現“多棲共存”。例如，OpenHarmony 底層兼容 POSIX 接口，這與我們當年在 iOS 上推廣 Flutter 時的環境並不相同。在成熟生態中，操作系統通常不會專門爲某個跨平臺框架調整底層能力；而在鴻蒙生態的發展過程中，系統層也在持續爲跨平臺框架提供更完善的支持。 回到技術本身，這種生態發展階段的差異也直接體現在技術選型上。以前在 iOS 和 Android 生態中，我們更多是在既有規則下開展工作，需要讓 Flutter 引擎適配系統運行機制，有時還需要處理一些平臺能力上的限制，因此始終存在一定的不確定性，很難判斷一次系統升級是否會帶來新的兼容性問題。 調用鴻蒙 API 走的是官方支持的 FFI 路徑。爲了提升整體體驗，系統層面也會持續優化相關鏈路，爲跨平臺方案提供更好的運行環境。 所以總結一下，最大的不同是，我們從“在存量市場裏搶地盤”變成了“在增量市場裏一起開荒”。鴻蒙需要我們的框架來降低開發者遷移成本，而跨平臺技術也需要鴻蒙這樣的新生態來拓展發展空間。這種相互促進的合作關係，是當年那場“三足鼎立”的技術競爭中從未有過的體驗。 InfoQ：Flutter 在鴻蒙上的適配，您們在渲染和性能層面做了哪些比較有意思的探索？有沒有哪個技術決策，讓您覺得“這個思路是對的”？ 謝國：在鴻蒙上做 Flutter 適配，其實是一次很難得的“後發優勢”體驗。因爲鴻蒙是全新的系統，我們不用揹負 Android 碎片化的歷史包袱，可以在底層做很多激進的嘗試。具體來說，有三件事讓我們覺得特別有意思： 1.繞過 Skia，率先使能 Impeller 大家都知道，Flutter 官方在 iOS 上主推 Impeller，以解決“着色器編譯卡頓”問題，但在 Android 上的推進相對緩慢，因爲需要適配大量 GPU 驅動。 在鴻蒙上，我們做了一個較爲激進的技術選擇：直接繞過 Skia（Flutter 默認的渲染引擎），率先在鴻蒙平臺完整使能 Impeller 後端，甚至早於 Flutter 官方在 Android 平臺上的穩定支持。 Impeller 採用預編譯着色器機制，不需要在運行時動態生成 GLSL 代碼並等待驅動編譯。在滑動、轉場等典型場景下，光柵化耗時下降了約 30%，顯著減少了因着色器編譯導致的掉幀現象。 這個決策也讓我更加確信一點：在硬件和系統條件允許的情況下，積極擁抱下一代技術架構，往往能夠獲得更大的優化空間。 2. 外接紋理“零拷貝”：視頻/相機的渲染路徑重構。 這是技術挑戰較大的探索。在傳統 Android 方案中，相機或視頻播放器解碼出一幀數據的路徑爲：GPU/Video Decoder -> 系統內存 -> CPU -> Flutter Engine -> GPU。數據在內存和顯存之間來回拷貝，延遲高且 CPU 佔用飆升。 我們在鴻蒙上利用了 HarmonyOS 的 HDI（硬件設備接口）層，實現了真正意義上的外接紋理零拷貝。具體做法爲：不讓 Flutter Engine 去“拿”數據，而是讓鴻蒙的相機組件直接把數據渲染到一塊共享的 GPU Buffer（圖形處理器緩衝區）裏，然後 Flutter 的渲染後端在合成時直接持有該 Buffer 的句柄，在最後的合成階段（Composition）一次性提交給屏幕。 該機制可比喻爲：以前是“我去倉庫搬貨”（多次拷貝），現在是“貨運火車直接開進車間生產線”（Buffer 流轉）。在視頻通話場景下，視頻畫面可以與 Flutter UI 做到 60 幀的完美同步，無撕裂感。 InfoQ：KMP 在內存管理和 GC 這塊，鴻蒙的環境帶來了哪些新的挑戰？目前的演進方向是什麼？ 謝國：這個問題非常核心，也是我們目前投入精力最多的領域。說實話，這是一場從“享受紅利”到“重造輪子”的艱難旅程。 一、挑戰：從“溫室”到“荒漠” 在 Android 上做 KMP，內存管理基本無感，因爲站在巨人的肩膀上——ART。ART 經過二十多年的工業級打磨，其 GC（垃圾回收）是一個集大成者：分代收集、併發標記、壓縮整理、指針壓縮……開發者只需 new 對象，ART 處理一切，極少出現長時間 STW（Stop The World，暫停所有線程）的情況。 但在鴻蒙生態下，情況完全不同。Kotlin/Native 這種非典型運行時上，底層的 GC 基礎設施尚處於非常早期的階段。目前鴻蒙上支撐 KMP 的併發 GC 算法，與 Android ART 長期演進形成的成熟運行時體系相比，KMP 在鴻蒙生態中的運行時能力仍有較大的優化空間。 當前主要存在以下挑戰： 1. 根集枚舉不精確，無法安全移動對象 ART 能做到精確 GC，在於其知道全局變量、棧幀等根中哪些位置是引用。鴻蒙當前對 KMP 的支持中，GC 無法找到所有的對象指針根（不精確）。不同於保守式 GC 誤判整數爲指針，該不精確性導致更嚴重的問題：GC 無法安全地移動對象。一旦移動某個根未正確更新的對象，指針即錯亂。這直接導致無法實現移動回收（Move GC），內存碎片問題隨程序運行愈發嚴重。

2. 當前 markSweep GC 算法帶來碎片化問題

當前 Kotlin/Native 的 markSweep GC 雖存在類似 TLAB（線程本地分配緩衝區）機制，但現有 Mark-Sweep 與 Freelist 架構在高頻分配場景下易產生碎片。正在推進的 CMC（Concurrent Mark-Copy）方案提供一套完整的併發移動式 GC 解決方案。CMC 使用 Bump Pointer 分配器——分配如移動指針般簡單，分配效率遠高於 Freelist。

3. 沒有指針壓縮

64 位系統下，一個指針佔 8 字節。ART 通過指針壓縮技術將指針壓縮至 4 字節，堆小於 32GB 時基本無感。鴻蒙上目前仍採用標準 64 位指針模型，意味着同樣的業務邏輯下，僅指針數組佔用的內存即爲 Android 的兩倍。在內存本不寬裕的鴻蒙設備上，這幾乎是致命的。 二、演進方向：重構運行時基礎設施 面對這些問題，我們沒辦法等待官方慢慢迭代，所以目前的重心是重構 KMP 在鴻蒙上 GC 依賴的三大基礎設施：

方向 1：推進精確棧映射（Exact Stack Map）

在編譯 Kotlin/Native 到字節碼或機器碼時，額外生成一份“棧映射表”。該表精確記錄每個棧幀中哪些位置是引用、哪些是數值。GC 無需猜測，即可精確回收，同時支持移動式 GC。這是當前優先級最高的任務，沒有精確棧掃描，後續所有優化均爲空中樓閣。 方向 2：升级 CMS GC 为 并发拷贝 CMC 方案（Concurrent Mark-Copy） 在 KMP 的鴻蒙後端推進 CMC 算法的落地。這是一套完整的併發拷貝式 GC 解決方案，而非僅替換分配器。核心設計包括： - 基於 Region 的 Bump Pointer 分配：將堆內存劃分爲多個 Region，每個線程認領一個 Region 作爲私有分配區，分配時僅需移動指針，幾乎無鎖，效率極高。 - 併發標記：在應用線程運行的同時完成對象存活標記。 - 移動整理：將存活對象從零散分佈的 From 區域複製到 To 區域，徹底消除內存碎片。

方向 3：實現指針壓縮

這是相對獨立的內存優化方向。正在鴻蒙的 KMP 上做指針壓縮適配：將堆內存限制在 4GB 以內，所有句柄以 4 字節索引代替 8 字節指針。雖有限制，但在移動端場景下 4GB 通常夠用，換得一半的內存佔用。 該優化與 Moving GC 方案可並行推進，兩者不衝突。目前在鴻蒙 KMP 內存管理上的工作，本質上是將 ART 過去二十年走過的路，以 Kotlin/Native 的方式在鴻蒙上重新走一遍。 InfoQ：您演講裏提到“跨語言調用優化”和“編譯優化”，對普通開發者比較抽象。能不能用一個實際場景來說明，這些優化在用戶體驗上體現在哪裏？ 謝國：一、跨語言調用優化：讓“跨國對話”變成“鄰里串門” 優化前，Kotlin 與 ArkTS 之間的每一次數據傳遞，如同兩個不同語言的外交官談判——中間需要翻譯官將數據序列化爲通用格式（如 JSON 字符串），對方收到後再反序列化。該過程速度慢且 CPU 佔用高。 採取三項措施改變局面：

1.對象免序列化共享方案（通過代理）

優化前：KMP 側解析完一個 FeedItem 對象（包含文本、圖片 URL、點贊數等 10 個字段）後，爲傳遞給 ArkTS，需將該對象整體打包爲 JSON 字符串。一個 Feed 流包含 20 條內容，需打包 20 次、解析 20 次。 優化後：我們實現了一套代理機制——KMP 側對象不出境，而是向 ArkTS 側返回一個“代理對象”。ArkTS 側通過該代理直接訪問 KMP 側對象的字段，如同訪問本地對象。數據無需打包和解包，僅傳遞一個輕量級“引用憑證”。 用戶體驗方面：首屏數據準備就緒至 UI 渲染完成的時間顯著縮短。用戶點擊“點贊”按鈕時，響應從“有點粘滯”變成了“像本地一樣乾脆”。

2. 字符串免拷貝共享方案

字符串是信息流中最頻繁傳遞的數據類型（用戶名、正文、標題）。優化前，每傳遞一個字符串，KMP 側需將 UTF-8 字符串轉換爲 ArkTS 可識別的 UTF-16 字符串，涉及一次完整的內存拷貝。 優化後：KMP 側與 ArkTS 側直接共享同一塊內存，字符串僅存儲一份，雙方通過偏移量和長度讀取。一個包含 20 條內容的 Feed 流，字符串總長度可達數千字符，避免了每次刷新時拷貝數十至數百 KB 內存。 用戶體驗方面：滑動 Feed 流時幀率更穩定。優化前，滑動過程中突然加載新內容時，字符串拷貝導致 CPU 瞬時飆高並掉幀；優化後滑動全程更爲流暢。

3. FFI 代碼生成工具

該優化對開發者不可見，但作爲前兩個優化的基礎設施。手寫 Kotlin 與 ArkTS 之間的 FFI 綁定代碼極其繁瑣、易錯，且難以實現高性能。 我們實現了一套代碼生成工具，其輸入爲 ArkTS 源碼與 ArkTS 裝飾器或源碼註解。工具解析這些信息，自動生成 Kotlin 側的 FFI 代理對象源碼。 與常見跨語言綁定工具不同，該方案無需編寫.def 文件，也不生成 KMP 側的導出代碼、ArkTS 側的聲明代碼或 C/C++橋接代碼。僅生成 Kotlin FFI 代理對象源碼，使 Kotlin 側能夠像調用本地對象一樣調用 ArkTS 側的能力。 無該工具時，人工編寫的綁定代碼性能參差不齊，易遺漏優化點。自動生成保證每條路徑均爲優化後的最優路徑，用戶感知爲“穩定流暢”。 二、編譯優化：讓“工地施工”變成“工廠流水線”

1. LLVM IR Split 编译并行化

Kotlin/Native 編譯爲鴻蒙的.so 文件時，底層依賴 LLVM。傳統編譯方式將整個模塊的 IR（中間表示）作爲一個巨大整體進行優化和編譯，如同單個工人砌整面牆——效率低、耗時長。 優化方案：將 LLVM IR 拆分爲多個獨立的編譯單元，使其並行編譯。一個大型 KMP 模塊的編譯效率可提升 2-5 倍。

2. 模塊化構建技術
