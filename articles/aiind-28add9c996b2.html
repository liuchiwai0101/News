AI 編程導師挑戰低端 Android 手機！不用服務器，Python 和 SQL 直接在瀏覽器裏運行

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

我花了一年時間，看着學生一個接一個地消失。當時我經營着一家編程培訓機構，學生們會進入直播課堂，積極參與，然後突然在上課途中掉線。後來我逐個跟進才發現，幾乎沒有人是主動退出的。他們的網絡連接根本撐不到一節課結束。在一批報名的 80 名學生中，最終只有 6 人畢業。

這段經歷讓我意識到，大多數編程教育平台都建立在四個默認前提之上。這些前提太過普遍，以至於人們幾乎忘了它們只是一些假設：學習者有筆記本電腦、有寬帶網絡、能夠輕鬆閲讀英語，而且付得起訂閲費，或者所在機構已經替他們付了費。

我開發的 Efiwe 平台，就是要打破所有這些假設。它可以直接在智能手機瀏覽器中運行，只需完成一次初始設置，之後就能離線使用。學生提交的代碼也在本地執行，首次加載完成後，不再需要消耗移動數據流量。目前，Efiwe 已被 160 個國家的 22,000 多名學習者使用，並在尼日利亞的拉各斯州、奧貢州，以及印度北阿坎德邦的學校開展了有組織的試點。

這篇文章不討論教學方法，而是討論工程實踐，尤其是那些曾經出過問題的地方。在這個領域，真正棘手的問題並不在於模型質量，而在於存儲、配額、冷啓動和失敗路徑的設計。這些問題也遠不止存在於教育產品中。只要產品面向的是設備性能有限、網絡連接時斷時續的用户，就很可能遇到同樣的挑戰。

為什麼選擇 PWA，而不是原生應用 我們首先要決定的是如何分發產品。開發一款原生 Android 應用似乎是最自然的選擇，但我們最終沒有這麼做，原因有三個。

首先是安裝門檻。即使還沒有下載任何課程內容，從應用商店安裝一個 APK，也往往需要消耗幾十 MB 的流量，而學生可能正精打細算地使用自己的流量套餐。漸進式 Web 應用（PWA）則允許學生點開就開始學習，緩存可以在後台逐步完成，流量開銷也隨之分攤到學習過程中。

其次是更新頻率。我們會持續發佈更新。使用 Service Worker，新版本可以在用户下次訪問時生效。應用商店發佈新版本卻做不到這一點。在那些用户為了節省流量而推遲更新應用的市場中，可能有相當一部分用户仍在運行幾個月前就已經修復過問題的舊代碼。

第三，Web 平台讓我們可以用一套運行時解決代碼執行問題。我們需要學生能夠編寫 Python、SQL、JavaScript 和 HTML，並立即看到運行結果，而且整個過程不能依賴服務器。瀏覽器中的 WebAssembly 讓我們可以一次實現，在各個平台上運行。

我們也考慮過用原生應用外殼包裝一個 WebView。這樣同樣可以使用 Web 運行時，如果加載的是遠程內容，也能解決更新問題。但它解決不了安裝門檻：學生仍然需要先下載 APK，才能開始學習，而這筆流量可能正是他們捨不得花的。對於一個從根本上就是為了降低學習門檻而設計的產品來説，這一點已經足以讓我們作出決定。

這個選擇也有代價：我們必須接受瀏覽器的存儲機制，包括它的配額限制。而我們在生產環境中遇到的大部分麻煩，恰恰都來自這裏。

不依賴服務器執行代碼 通常，評判一道編程題的答案，需要把學生提交的代碼發送到服務器，在沙箱中執行，再把判定結果返回給學生。這意味着每嘗試一次，都要經歷一次網絡往返。在尼日利亞伊傑布奧德的一間教室裏，網絡連接並不穩定，而學生往往需要嘗試十到十二次才能解出一道題。這種模式根本行不通。

所以，我們讓代碼直接在設備上執行。SQL 使用 sql.js，也就是編譯為 WebAssembly 的 SQLite；Python 使用 Pyodide，也就是編譯為 WebAssembly 的 CPython。兩者的體積都不小，初始化也都很慢。如果處理不當，它們都會阻塞主線程，讓頁面卡住。

對於 SQL 題目的判定，我們不會直接比較輸出字符串，而是比較結果的結構和內容。這樣一來，只要題目允許，即使學生使用了不同的格式、別名或列順序，只要查詢正確，就仍然能夠通過。

持久化存儲：為什麼 localStorage 不夠用了 Efiwe 提供 246 種語言的內容。翻譯後的編程題文本會緩存在設備上，這樣選擇約魯巴語或印地語的學生，就不需要每次學習都重新下載相同的內容，而且離線後也能繼續使用翻譯。

最初，我們用 localStorage 來保存這些緩存。後來證明，這是個錯誤的選擇，而且同時暴露了兩個問題。

第一個問題是容量。localStorage 通常對每個源設置大約 5MB 的容量上限，具體限制會因瀏覽器和平台而異。一門包含數百道編程題的課程，即使只緩存幾種語言的翻譯內容，也很容易超過這個限制。一旦超出，寫入操作就會拋出 QuotaExceededError 。如果沒有對每次寫入都做好異常處理，錯誤就可能在意想不到的地方冒出來。

第二個問題更嚴重，也更隱蔽：localStorage 是同步的。每次讀取和寫入都會阻塞主線程。在一台中端筆記本電腦上，這可能只是幾毫秒，沒人會注意。但在一部入門級 Android 手機上，閃存控制器速度慢，CPU 又已經滿負荷運行，啓動時一次較大的同步讀取就可能造成明顯卡頓，而這恰恰發生在最經不起卡頓的設備上。我們花了不少精力優化 JavaScript 代碼體積，卻在存儲層裏悄悄埋下了一個主線程阻塞點。

於是，我們遷移到了 IndexedDB。IndexedDB 是異步的，存儲配額通常根據可用磁盤空間按比例分配，而不是固定的幾 MB，並且可以直接存儲結構化數據，不必經過 JSON 序列化和反序列化。

選擇 IndexedDB 很容易，真正費工夫的是如何讓現有用户平穩遷移，又不丟失數據。已經上線的用户仍然在舊存儲中保存着數據，其中不少人會連續離線好幾天，因此他們什麼時候能運行到新代碼，完全無法預測。如果直接切換，緩存的翻譯和未完成的學習進度就可能悄無聲息地丟失。所以，我們設置了一個雙重讀取的過渡期：先讀取新存儲，如果沒有找到，就讀取一次舊存儲；找到後將數據遷移過去，再刪除舊的鍵。

這個函數里有兩個細節，幾乎就是我們從這次遷移中學到的全部經驗。首先，讀取舊數據的操作被包在異常處理中，因為如果上次會話中斷，導致 localStorage 中的數據只寫入了一部分，那麼 JSON.parse 就可能拋出異常。我們絕不希望一次緩存解析錯誤把整個頁面搞崩。其次，遷移寫入被單獨包在另一個異常處理中，因為設備存儲空間已滿時，讀取可能成功，寫入卻會失敗。這種情況下，正確的做法仍然是先把內容交給學生，下次再嘗試遷移。

將存儲配額問題視為一種必須考慮的故障場景 如果這篇文章只能讓其他工程師記住一件事，我最希望是下面這次事故。

在尼日利亞的試點期間，一位老師反饋説，有些學生在手機上創建賬户後，學習頁面始終無法顯示。賬户創建成功了，登錄也沒有問題，但課程就是加載不出來。屏幕一片空白。
