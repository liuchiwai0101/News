一、先看全景 70 條規則怎麼分層

清單按影響力分 8 類，優先級從上到下遞減：

這個排序背後的邏輯很硬：**一次串行的網絡往返是幾十到幾百毫秒，一次多餘的 re-render 通常不到一毫秒**。瀑布流每多一層就多付一次完整網絡延遲，而你精心 memo 掉的那次渲染，用戶根本感知不到。所以官方原話是「Waterfalls are the #1 performance killer」——先治網絡和包體積，再談渲染。

下面按這個順序逐層拆。

二、消滅瀑布流 每一個多餘的await都在燒錢

2.1 Promise.all 是及格线

最基礎的一條：沒有依賴關係的異步操作絕不串行。

這段是反面示例，三個請求串成三次往返：

const user = await fetchUser()
const posts = await fetchPosts()
const comments = await fetchComments()

改成並行後只付一次往返的時間，官方給的量化收益是 **2-10 倍**：

const [user, posts, comments] = await Promise.all([
  fetchUser(),
  fetchPosts(),
  fetchComments()
])

2.2 部分依賴場景 先啓動再await

真正拉开差距的是「半依赖」场景：profile 依赖 user，但 config 谁都不依赖。多数人会写成两段 Promise.all，结果 profile 白白等了 config。正确做法是**先创建所有 promise，最后统一 await**：

const userPromise = fetchUser()
const profilePromise = userPromise.then(user => fetchProfile(user.id))
const [user, config, profile] = await Promise.all([
  userPromise,
  fetchConfig(),
  profilePromise
])

這樣 config 和整條 user → profile 鏈是並行的，每個任務都在依賴就緒的第一時間啓動。同樣的思路用在 API 路由裏：auth() 和 fetchConfig() 互不依賴，就先把兩個 promise 都啓動，再按需 await，不要讓 config 排在 auth 後面白等一輪。

2.3 defer await 把等待推進真正用到的分支

另一條容易忽視的規則：await 應該出現在**用到結果的分支裏**，而不是函數開頭。比如權限校驗，如果 resource 不存在就直接返回 404，那 fetchPermissions 這次請求就完全不該發生。把 await 後移，走「資源不存在」快路徑的請求一次網絡開銷都不用付。同理，flag && cheapCondition 這種組合條件，先判本地的 cheapCondition，爲 false 就壓根不去 await 遠端的 flag。

2.4 Suspense 讓骨架先上屏

頁面級組件裏 await 一把梭，整個佈局都會被這次取數拖住。官方建議把取數下沉到子組件、外層包 Suspense：

function Page() {
  return (
    <div>
      <Sidebar />
      <Suspense fallback={<Skeleton />}>
        <DataDisplay />
      </Suspense>
      <Footer />
    </div>
  )
}
async function DataDisplay() {
  const data = await fetchData() // 只阻塞这一块
  return <div>{data.content}</div>
}

Sidebar 和 Footer 立即上屏，數據流式補進中間區域。注意清單裏也寫明瞭不適用場景：影響佈局定位的關鍵數據、首屏 SEO 內容、以及快到不值得付出佈局抖動代價的小請求。關於 Suspense 與併發渲染的底層機制，可以搭配我之前寫的 React 18 併發機制詳解 一起看。

三、包體積 一行import偷走你200-800ms

bundle- 類裏最觸目驚心的是 **barrel import** 這條。所謂 barrel 文件就是庫入口那個 export * from ... 的 index.js，流行的圖標庫、組件庫入口動輒上萬個 re-export：

import { Check, X, Menu } from 'lucide-react'
// 实际加载 1583 个模块，dev 慢 ~2.8s，冷启动多付 200-800ms
import { Button, TextField } from '@mui/material'
// 实际加载 2225 个模块

你以爲 tree-shaking 會救你，但清單裏點破了：庫被標爲 external 時打包器根本不做優化；要 tree-shake 就得全量分析模塊圖，build 時間又爆了。解法有兩個：Next.js 13.5+ 直接靠內置的 optimizePackageImports，代碼不用改；其他項目走子路徑直連 import Button from '@mui/material/Button'。官方給的收益是 dev 啓動快 15-70%、構建快 28%、冷啓動快 40%。

受影響的常見庫包括 lucide-react、react-icons、lodash、date-fns、rxjs 等——檢查一下你的項目，大概率中招。

這一類還有三條高價值規則，邏輯一以貫之——**首包只留首屏必需的東西**：

- **重組件動態加載**：- `Monaco`、圖表庫這種 300KB 起步的大件用- `next/dynamic`按需拉，直接改善- `TTI`和- `LCP`

- **第三方庫延後**：analytics、錯誤上報不阻塞交互，- `ssr: false`等 hydration 完了再加載

- **按用戶意圖預加載**：按鈕- `onMouseEnter`/- `onFocus`時- `void import('./monaco-editor')`，等用戶真點開時模塊已經在緩存裏，體感零延遲

另外注意動態導入要保持**路徑靜態可分析**：import(SOME_MAP[key]) 這種寫法打包器猜不出範圍，只能把可能的文件全打進來；改成顯式的 { home: () => import('./pages/home') } 映射表，產物立刻收窄。

四、服務端性能 RSC時代的新坑

server- 类 10 条规则里有三条是 Next.js App Router 项目几乎必踩的坑。

**第一坑：Server Action 忘了鑑權。** `"use server"` 函數會被編譯成公開 endpoint，middleware 和頁面級守衛攔不住直接調用。所以每個 action 內部都必須自帶 `verifySession()` + 權限校驗，這條被標爲 CRITICAL——它不是性能問題，是安全事故。

**第二坑：模塊級變量存請求數據。** 服務端併發渲染時模塊作用域是進程共享的，`let currentUser = null` 這種寫法會讓 A 用戶的數據串到 B 用戶的響應裏。請求級數據一律走 props 或 `React.cache()`，模塊級只放不可變的靜態資源。

**第三坑：RSC 邊界序列化超載。** Server/Client 邊界上所有 props 都會被序列化進 `HTML`，50 個字段的 `user` 對象只用一個 `name` 也全量傳輸。清單的建議是隻傳用到的字段，並且**不要在服務端做 .filter() / .toSorted() 再和原數組一起傳**——序列化按引用去重，新引用意味着同一份數據傳兩遍。

取數方面還有兩條組合拳值得記住。React.cache() 做請求內去重（數據庫查詢、鑑權這類非 fetch 的異步操作收益最大，fetch 本身 Next.js 已自動去重）；跨請求就上 LRU 緩存。嵌套取數則要把依賴鏈塞進每個 item 自己的 promise 裏：

// 反例：一个慢 chat 卡住全部 author 请求
const chats = await Promise.all(chatIds.map(id => getChat(id)))
const authors = await Promise.all(chats.map(c => getUser(c.author)))
// 正解：每个 item 独立成链，互不阻塞
const authors = await Promise.all(
  chatIds.map(id => getChat(id).then(chat => getUser(chat.author)))
)

最後是 after()：日誌、埋點、通知這類副作用放進 after(() => ...)，響應先發出去，副作用在後臺跑。這些能力在 Next.js 15 之後已經穩定，相關背景我在 Next.js 15 如何讓 React 應用更快 裏寫過。

五、re-render優化 一半的useMemo本該刪掉

到了大家最熟的領域，清單反而在潑冷水。15 條 rerender- 規則裏，我認爲最值得內化的是這四條。

**第一條：能推導就別存狀態。** `fullName` 能從 `firstName + lastName` 算出來，就直接在 render 裏算，不要 `useState` + `useEffect` 同步——那會多一輪渲染還容易狀態漂移。這條對應 `React` 官方文檔著名的《You Might Not Need an Effect》。

**第二條：簡單表達式別包 useMemo。** 這是清單裏少見的「反 memo」規則：

// 反例：hook 调用 + 依赖比较的开销超过表达式本身
const isLoading = useMemo(() => {
  return user.isLoading || notifications.isLoading
}, [user.isLoading, notifications.isLoading])
// 正解：直接算
const isLoading = user.isLoading || notifications.isLoading

useMemo 本身有依賴數組比較的成本，包一個布爾運算純屬倒貼。**memo 的對象應該是真正昂貴的計算，而不是所有計算。**

**第三條：絕不在組件內定義組件。** 每次父組件 render 都會產生一個新的組件類型，`React` 視爲不同組件直接**整棵重掛載**——輸入框失焦、動畫重放、`useEffect` 反覆執行，全是它的症狀。想少傳 props 不是理由，老老實實把子組件提到模塊頂層。

**第四条：functional setState 换稳定回调。** `setItems([...items, newItem])` 迫使 `useCallback` 依赖 `items`，回调随状态一起重建；写成 `setItems(curr => [...curr, newItem])` 后依赖数组清空，回调终身稳定，还顺手消灭了 stale closure。

其餘規則可以歸成一句話：**高頻瞬時值用 useRef（鼠標座標、interval 句柄），非緊急更新用 startTransition / useDeferredValue，交互邏輯放事件處理器而不是 effect。** 值得注意的是清單在多處標註：如果項目開了
