GitHub 日韓營銷負責人如何用 GitHub Copilot 把活動運營自動化

內容機器翻譯自第三方媒體（GitHub Blog），僅供參考，以原文為準。

AI 導讀

GitHub 日韓地區營銷負責人 Tomoko Tanaka 分享如何不寫代碼，把活動運營交給 GitHub Copilot 自動化。

推薦理由

作者以自身營銷工作為例，展示了用 Issue、Actions 和 SKILL.md 複用開發者治理流程落地自動化的完整路徑。

正文

我在日本和韓國負責 GitHub 的市場營銷，而活動正是這項工作的核心：面向企業開發者的系列網絡研討會、東京的社區聚會、首爾僅限受邀者參加的高管閉門會。這個市場的開發者當下真正需要什麼？哪些話題值得他們花上一小時？誰又該出現在現場？我很樂意整天琢磨這些問題。

決策之後的事情則是另一回事。一旦活動獲批，一套固定的流程便隨之啓動：

  • 在我們的活動平台上覆制一個落地頁。
  • 生成一組帶 UTM 標記的鏈接：每個渠道一個，每個都按特定格式排好。
  • 起草邀請郵件，並向負責發送的團隊提交請求。
  • 把活動添加到兩個項目看板上。
  • 活動開始前每天早上：下載報名者名單，清理數據，為相關方發佈一條狀態更新。
  • 活動結束後：導出參會者名單，重新整理成可上傳 CRM 的格式，給相應的記錄打上標籤，並撰寫一份報告。

這些任務單看都不難，但每一個都可能讓你貼錯鏈接、漏掉一天，或者拼錯一個活動名稱——而下游有 15 份報告都依賴它。

事情是這樣的：我以前是一名工程師。我的第一份職業是在 Linux 服務器上為企業客户維護數據庫的運轉。雖然我的編碼能力可能已經生疏，但我依然能一眼看出哪條流水線亟待自動化。這正是我用上 GitHub Copilot 的地方，也是你在自己的工作中同樣可以用上它的地方。

所以代碼不是我寫的。我寫下了自己的運維手冊，交給 GitHub Copilot，然後在對話中逐步把自動化搭建起來。如今，一個我過去需要手工花上幾天時間籌備的活動，可以從一個 GitHub Issue 自動完成設置，每天早上自動篩查報名者，並在活動結束後自動清理收尾。

這篇文章將帶你瞭解它是如何運作的，以及為什麼我認為，任何工作涉及跨工具重複性勞動、而這些工具又提供某種可腳本化入口（比如 API，甚至只是一個 CLI）的人，都能照做。

一場活動就是一個 Issue

這個基礎性的想法不能算我原創。GitHub 的市場營銷團隊早已養成了每個項目開一個 GitHub Issue 的習慣。這個 Issue 成為計劃、討論和狀態共同存在的地方。Issue 本來就是我們的工作單元。我所做的，是讓這個 Issue 去幹活。

三個 GitHub 基礎構件支撐起了整個系統：

  • Issue 表單就是申請表。與空白文本框不同，issue 表單呈現的是結構化字段：活動標題、日期、地區、活動名稱、目標受眾。我們為每種活動類型各設一個表單，比如線上研討會和線下活動，它們都接入同一套機制。
  • 標籤就是開關。像 event-setup 這樣的標籤不是標記，而是觸發器。每個自動化工作流都以一個條件開頭，實際上就是説：“僅當此標籤存在時才運行。”
  • 操作就是機器。GitHub Actions工作流在標籤落地時觸發，從 issue 正文中解析出表單字段，然後去執行工作。

倉庫為開發者提供的一切，也免費為我的營銷工作流提供了：歷史記錄、可見性、審查，以及每個決策對應的 URL。

有一件事讓這一切成為可能，而且它與活動本身毫無關係：我們的活動管理平台開放了 API。我們的 CRM 甚至不需要 API；它的官方 CLI 覆蓋了我們所做的全部工作，而且我從未為它配置過 API 密鑰，因為 CLI 通過瀏覽器登錄，並由此處理身份驗證。無論是 API 還是 CLI，要求都是一樣的：一種可腳本化的接入方式。如果你的重複性工作流經某個工具，而該工具提供了活動平台、CRM、表單構建器或分析服務中的任意一種，那麼本文的模式同樣適用於你。

讀到這裏的開發者可能已經在醖釀那個顯而易見的反對意見：這不就是在重複造輪子嗎？營銷自動化平台已經存在，一款好的平台或許開箱就能覆蓋其中一部分需求。但亞太區與其説是一個市場，不如説是一堆截然不同的市場的集合，即便在我自己的團隊內部，工作流也會隨着每個子區域和每個細分市場而變化。同一場網絡研討會，這個月可能用日語為東京舉辦，下個月就用韓語為首爾舉辦，細分市場不同、CRM 中的字段不同、對優質線索的定義也不同。要讓一款打包好的工具吸收所有這些差異，意味着定製預算、諮詢工時，以及等待別人的路線圖。而用現有的工具自己搭建，意味着工作流的改動就是一次 pull request：我描述我想要什麼，一位評審者檢查它，然後它通過開發者用來修改軟件的那套流程合入主分支。

策劃一場活動就是一次對話

這條流水線在 Issue 存在之前就已經啓動。我打開 GitHub Copilot，大致説：“我想在 11 月舉辦一場關於 AI 輔助開發的網絡研討會。”

接下來發生的事情，由我們倉庫根目錄下一個名為 AGENTS.md 的文件所決定。它是我們團隊的操作手冊，用純 Markdown 寫成，定義了活動如何命名、財季如何對應到日期、每個區域使用哪個時區，以及一封好的邀請郵件長什麼樣。GitHub Copilot 讀取它，然後找到一場類似的過往活動，按照我們的命名規則提出一個活動名稱，起草兩個版本的邀請郵件，並向我提出操作手冊中規定要問的問題。

把對話放在流水線的最前端，這本身就是一個設計決策，它一次性解決了兩個問題。如果全部自動化，你就會失去靈活性；哪天你想讓某一場活動稍有不同，僵化的流水線根本沒有地方去表達這種差異。但如果讓人來填寫一切，又會出錯。對話恰好處於兩者之間。GitHub Copilot 遵循模板，因此落到 Issue 裏的數據就是格式正確的正確數據。而正因為它是對話，我可以為這一場活動調整細節，而不會破壞下游的機制。

剛開始時，這段對話發生在 GitHub Copilot CLI 裏，在終端中進行。對我來説這沒什麼問題，但“打開終端”對許多我很想拉進這套工作流的人來説是一道門檻。有了 GitHub Copilot 應用，同樣的對話現在發生在一個普通的桌面窗口裏。入門門檻從“熟悉 shell”降到了“會打字”。

我想把分工説清楚，因為這才是關鍵所在：GitHub Copilot 起草；我來拍板。每一個活動名稱、每一行郵件主題、每一個日期，都要經過我簽字確認後才會推進。對話結束時，GitHub Copilot 會帶着正確的標籤提交 GitHub Issue，從那一刻起，機器就接管了。

一個標籤，一場活動，全流程就緒

當 event-setup 標籤落到 issue 上的那一刻，一個 GitHub Actions 工作流就會接手，並在幾分鐘內完成過去要花我大半天才能做完的事：

  • 在我們的活動平台上覆制一場過往活動，以創建新的落地頁
  • 生成完整的帶 UTM 標記的 URL 集合：每個渠道一個，格式始終一致
  • 將邀請郵件生成為 Word 文檔並提交到代碼倉庫
  • 向負責發送郵件和跟蹤區域營銷的團隊發起請求 Issue
  • 將活動添加到我們的項目看板並填寫相關字段
  • 在 Issue 上回帖發佈一條摘要評論，這樣下一個打開它的人就能在一個地方看到所有信息

報名篩選按計劃運行，而不是靠標籤觸發。每天早上，一個由 cron 觸發的工作流會獲取每個開放活動的最新報名者，並分享整理後的名單。對於僅限邀請的活動，它還會根據我們的標準篩選候補名單（這位報名者是企業客户中的開發者、學生，還是一位非常想參加我們高管簡報會的競爭對手？），之後才會批准任何人。

我最引以為傲的設計決策是一個名為 DRY_RUN 的單一開關，它作為一個設置（用 GitHub 的話説，就是一個倉庫變量）存儲，每個工作流在運行前都會檢查它。把它打開，每個工作流都會走一遍流程，但不觸碰任何外部系統：不創建落地頁，不在其他倉庫提交 Issue，不共享列表。當你是一個把自己的工作自動化的營銷團隊時，你需要一種排練的方式。DRY_RUN 就是排練開關，也正是它讓我從不害怕做實驗。

活動結束後，一個斜槓命令

活動後的工作過去是最糟糕的部分：導出參會者、為 CRM 上傳重新調整列格式、將公司名稱與客户記錄匹配，以及撰寫報告。現在只需兩條命令。

/lead-upload 獲取參會者名單，將其整理成我們的營銷運營團隊進行 CRM 上傳所需的精確格式，提交請求 Issue，並關閉跟蹤 Issue。/event-report 拉取參會指標和調查結果，並將報告作為評論發佈在活動的 Issue 上，回到這個活動所有信息所在的那一個 URL。

這些是 GitHub Copilot agent skills，而這是我最想讓你聽到的部分：一個技能就是一個 Markdown 文件。每一個都是一個 SKILL.md：一份用散文寫成的書面流程，告訴 GitHub Copilot 該做什麼、按什麼順序做、以及要注意什麼。我寫的那些讀起來就像我以前記在腦子裏的操作手冊，因為它們本來就是。

如果你能寫操作手冊，你就能寫技能。

技能也是讓系統保持靈活的關鍵。亞太（APAC）地區沒有兩個市場以完全相同的方式執行後續跟進。受眾不同、細分群體不同、本地慣例不同，而硬編碼的工作流會迫使每個市場都套用同一種形態。用 Markdown 編寫的流程則很靈活：每個市場都能根據自身實際情況調整運行手冊，而無需改動底層的機制。正因如此，活動後的步驟才放在 GitHub Copilot 技能中，而不是固定的流水線裏。

我們在一個方面把技能當作代碼來對待：新技能通過 pull request 提交，並在合併前接受審查，由一個 CODEOWNERS 文件將審查路由給維護者。帶審批流程的營銷自動化。治理也隨平台一併免費獲得了。

內置的護欄讓我可以放手試驗

我自動化了一個涉及客户數據和 API 憑證的工作流，放在全團隊都能看到的倉庫裏，而我自己幾乎沒怎麼寫代碼。六個月前我會説這種組合太魯莽。讓我改變想法的是，我意識到在我介入之前，已經有那麼多護欄就位了。

我搭建的一些護欄：DRY_RUN 開關、每次 pull request 都會運行的測試套件，以及對每項變更的代碼審查。標準的開發者習慣。事實證明，它們對營銷工作的保護和對軟件的保護一樣有效。

但最重要的護欄是隨平台而來的：

  • 帶推送保護的密鑰掃描。對我這個崗位的人來説，最可怕的場景莫過於不小心提交了 API token。GitHub 的推送保護會在密鑰進入倉庫之前就攔截這次推送，而對於 GitHub 自家的 token，即便真有漏網的，也會被自動吊銷。
  • GitHub Copilot 的數據政策。註冊人名單屬於業務數據，固定腳本會以固定方式處理它們。但真正的工作從來不是完全固定的；有些時候我需要一份沒有任何腳本能預料到的一次性數據切分。由於 GitHub Copilot 的商業版方案不會保留提示詞，也不會用它們來訓練模型，我可以直接請求做那次一次性分析，而不必像業界許多人私下做的那樣：把業務數據粘貼到旁邊標籤頁裏開着的隨便哪個消費級聊天機器人裏。模型本身也是如此：我究竟能用哪些模型，是由組織政策決定的，而不是交給我個人判斷，所以即便是一次性實驗，也是在公司已經劃定的邊界內進行。安全的路和便捷的路，這一次難得是同一條路。

技能還帶來了另一個好處，幾乎算是順帶產生的：由於每個流程現在都是一個有名字、固定的工作單元，我可以把模型和任務匹配起來，從我們組織已批准的陣容中挑選。一個快速、便宜的模型負責日常的名單清理；一個更強的模型負責起草營銷文案。

還有一個真實的失敗案例，希望你不要重蹈覆轍：那個早晨篩選工作流曾經悄無聲息地失敗了五天，才有人注意到列表已經過期了。你不監控的自動化，更像是一顆帶延遲的定時炸彈。給每一個定時工作流都配上一種能大聲報錯的方式，這樣你就不會錯過它了。

從一個任務開始

以下是我的建議，來自一個正在康復的手工勞動者，寫給另一個。

挑選你每週重複次數最多的一項任務。然後檢查它所涉及的工具是否提供 API 或 CLI。你可能會驚訝地發現，很多工具都有。

然後構建儘可能最小的版本：一個捕獲輸入的問題表單、一個表示“開始”的標籤，以及一個只完成其中一步工作的 Action。或者直接跳過這些，把你的操作手冊寫成一份 SKILL.md，讓 GitHub Copilot 來執行它。用 dry-run 開關運行，直到你信任它為止。再在此基礎上逐步擴展。

我沒有寫代碼。我只是把已經知道的東西（工作是如何完成的）寫了下來，剩下的就交給平台了。無論你那個版本的早晨登記名單是什麼，它距離自動完成，大概只差一份寫下來的操作手冊。
