正文

分解 RSA-260

過去幾周，Cognition 研究團隊和我一直在優化我們的作業調度器，以更好地利用解耦計算資源。作為概念驗證，同時也因為我過去十年左右一直把因數分解當作愛好，我驅動了一群 Devin 去完成 RSA-260 的因數分解。為此，我的 Devin 們構建了世界上性能最高的 GPU 格篩，使得因數分解的成本比此前公開的最先進水平低 10 倍。以下是分解結果：

RSA-260（一個 260 位數）創下了公開求解的 RSA 因數分解挑戰 中最大數的新紀錄，該挑戰用於評估破解 RSA 密碼系統 的可行性。此前的紀錄 RSA-250 於 2020 年 2 月創下。作為參照，最先進的 RSA 公鑰包含 2048 位（約 617 位十進制數字）的因數分解問題，而 1024 位（約 309 位十進制數字）的 RSA 已於 2013 年被棄用。

下面我會給出一些關於這是如何實現的細節，但有兩個重要結論：

  • 超大規模雲廠商或前沿 AI 實驗室很可能能夠以每個數約 3000 萬美元的成本分解 RSA-1024 數——而且，再稍加優化，成本很可能大幅降低。另一方面，RSA-2048 的難度仍大約是 RSA-1024 的十億倍，並且似乎並未受到這項工作的實質性影響。
  • Devin 是一位足夠強大的軟件工程師，能夠解決計算數論與 GPU 性能工程交叉領域的一個極具挑戰性的問題。我的角色主要是設定優先級、建立基準，並在工作偏離軌道時及時察覺。除此之外，Devin 自主地端到端處理了測量、集群操作和優化。這替代了原本可能需要一支高度專業化的領域專家團隊耗費數月才能完成的工作。

總而言之，密碼分析工作、更廣泛的計算數學、以及很可能大多數大規模科學計算研究的入門門檻，都遠低於過去。在任何可以用編程來解決研究問題的地方，激動人心的工作都在向人們招手；我鼓勵所有人都懷抱雄心，去探索自主軟件工程智能體應用於這些領域時能夠做到什麼！

這是怎麼發生的？

與一些流傳中的説法相反，我並不是通過手工猜測和檢驗 130 位的質數來分解 RSA-260 的。Cognition 也尚未造出數千量子比特的量子計算機。RSA-260 是通過一種面向 GPU 的通用數域篩法（GNFS）新實現來分解的，該實現藉助 Devin 準備並運行。GNFS 是已知對於大約 100 位以上的（大多數）數字最高效的算法，此前多次破紀錄的 RSA 數分解也使用了它。

該實現是對CADO-NFS進行了大幅修改的版本。我基本上沒有報告任何算法層面的進展——在 GPU 上實現格篩法和稀疏線性系統求解，只需要“老派的性能工程”就能利用 GPU 那荒謬的內存系統。

成本估算

總的來説，我估計這次分解大約花費了 4,900 GPU-天，即 13.5 GPU-年，按當前市場價格約合 40 萬美元。更詳細地説，現代 GNFS 實現由幾個順序運行的階段組成：多項式選擇、格篩法和線性系統求解。時間分佈如下：

  • 多項式選擇耗時 643 GPU-天（這個數字異常偏高，基本上是因為操作者能力不足）
  • 篩法耗時 3,813 GPU-天
  • 線性系統求解耗時 467 GPU-天（其中約 7% 因崩潰或被更重要的工作搶佔而未能取得進展）

這是我利用集群個位數百分比的資源做的副業項目，期間還在優化我們的作業調度器，以改善分配、利用 disaggregated compute。這對更大規模的 RSA 實例意味着什麼？

RSA-1024 相當於 309 位數字；按照標準 GNFS 的規模推算，這僅僅比 RSA-260 多出 78 倍的計算量。我估算，按市場 GPU 價格計算，分解 RSA-1024 的成本大約為 3000 萬美元，這可以與實際耗時進行權衡取捨。我確知當前的實現仍然明顯次優；如果進一步的適度工作能將分解 RSA-1024 的成本再降低 2 倍，我不會感到意外。

當然，RSA-1024 不安全這件事並不是新聞。早在 2000 年代中期就有人猜測 NSA 可能具備經濟地攻破 RSA-1024 的能力（參見例如 TWIRL 或 Bernstein 矩陣機）。相反，如下文所述，主要進展是：(1) 分解在成本（美元和時間）上可能更低；(2) 可能有更多方具備執行分解的能力（你只需要足夠的 GPU，而不必製造專用硬件）；以及 (3) 非密碼學研究者現在能夠相對容易地參與加速分解的工作。

最後，我要強調，這些效率提升對使用 GNFS 分解 RSA-2048 規模數字的可行性幾乎沒有影響。

利用閒置算力進行分解

這次分解是在閒置或碎片化算力上以零邊際成本運行的，這些算力原本無法用於其他用途。為什麼會有這樣的算力存在？

我們用於 LLM 訓練和推理的集群包含 NVL72 機架，每個機架名義上由 18 台通過高速 NVLink 互連的計算機組成。LLM 工作負載使用單個機架內的計算機分組，以利用這種高速互連。作業調度器必須解決一個約束優化問題，將工作負載打包進機架。在這種全局分配中，一些機架最終可能會剩下一兩個空閒節點；有時作業會請求備用節點以應對故障轉移，或者作業可能需要偶數台計算機，而某個機架上只有 17 台。對我們來説，這些低效加起來只佔整體算力的個位數百分比。

為了利用這些閒置算力，作為第一步，我改造了我們的作業調度器，讓它以最低優先級將單節點作業填充到其他工作負載周圍。然而，我們還缺少一個穩定的、可隨時被搶佔的單節點工作負載來源。自然，此時我想到了格篩法，它完美契合這種情況。

格篩法在數十億個小型工作單元上具有極佳的並行性，可以一次使用單個節點推進，並且可以安全地被即時搶佔。它也是 GNFS 中計算開銷最大的部分，因此完成篩法就意味着在因式分解上取得了很大進展。然而，此前所有公開的 GNFS 因式分解記錄都只使用 CPU 進行格篩；事實上，由於在 GPU 上高效實現格篩存在挑戰，很長一段時間內人們並不清楚 GPU 格篩在整體上是否更具成本效益。

簡而言之，我所缺的只是一個性能足夠高的 GPU 格篩器，能夠接受分解 RSA-260 所需的參數。那麼，我做了什麼？問 Devin。

使用 Devin 優化 GNFS

太平洋時間 8 月 13 日 0:11:58，我讓 Devin 去為 las（CADO-NFS 的 CPU 格篩器）生成一個可直接替換的替代品。以下是我使用的提示詞：

CADO-NFS 是用於執行 GNFS 的 FOSS 軟件。我希望你開發一個快速的 GPU 格篩器。這在現有技術條件下歷來很困難，因為 CPU 格篩的優化使用了大量條件分支和複雜的內存訪問模式，而且同時精通 GPU kernel 編寫和數域理論的人非常少。然而，GPU 中可用的更高總內存帶寬預示着更高的性能上限。而如今這個交集裏有了你。你有可用的 Modal 訪問密鑰，我授權你使用它們來啓動一台 GPU 機器進行性能測試。獲取 CUDA 工具鏈等並在本地構建；GPU 僅用於性能測試，並在兩次測量之間將其關閉。由此產生的 GPU 格篩器應當可以直接替換 CADO-NFS 的篩器步驟。不斷迭代，直到你超過 CPU 格篩器的性能。

兩小時後，我補充説 glas（當然是 GPU las）應當能夠處理 RSA-250 所用的參數。然後我就去睡覺了。醒來後發現，在又迭代了 7 個小時之後，Devin 已經成功了。

在接下來的一週裏，我驅動 Devin 優化格篩，然後是 GNFS 流程的其餘部分。首先，我會對我們的 GNFS 優化做一個高層次的描述，然後我會描述優化工作流程。

GNFS 優化（高層概述）

在高層上，GNFS 由若干按順序運行的階段組成：多項式選擇、格篩法和線性方程組求解。

多項式選擇確定了算法所運行於的數域。多項式的選擇控制着格篩法步驟上的常數因子加速。因此，通常值得將整體篩法計算中固定比例（約 5%）的算力用於尋找一個“好”的多項式。這裏幾乎沒有技術創新；我們將 CADO 的第一階段多項式選擇適配到了 GPU 上（結果見 gps1），同時還使用了 msieve 經過良好優化的第一階段多項式選擇中的一些內核組件。多項式選擇基本上是高度並行的。

GNFS 計算工作量的主體在於格篩法。格篩法的目標是在 GF(2) 上產生大量（在我們的案例中為 83 億條）稀疏線性關係，這裏（省略一些細節）向量條目表示某個光滑數的素因子分解中素數指數的奇偶性。格篩法同樣可以針對稱為“特殊 q”的工作項高度並行，但每個工作項都需要在一個大數組中的（就我們的目的而言）偽隨機位置執行大量讀/寫操作；處理這一點是優化篩法過程中的主要技術挑戰。

最終，我們將這些關係打包成一個 GF(2) 上的大型矩陣，並使用線性方程組求解來尋找線性相關性。在這個規模下，線性方程組求解通常是分佈式的，並且需要大量通信帶寬；而 Infiniband 和 NVLink 恰好能充分提供這種帶寬。block Wiedemann 算法允許在一定程度上放寬通信約束，而 CADO-NFS 中的特定實現也易於優化並可在 GPU 上運行，我們正是這樣做的。解可以被處理為模 N 的平方同餘式，從而得到因數分解。

總體而言，Devin 幾乎修改了每一部分，包括修改了幾個接口：

  • 一個適配 GPU 的 CADO-NFS 第一階段 polyselect 版本，包含來自 msieve 的組件
  • 一個基於 las 的 GPU 優化格篩
  • 一個經過優化的 CADO 頭部，用於處理工作單元量
  • 並行化並優化的 dup/purge 以及融合 merge/replay 程序
  • 一個新的 GPU 優化 block Wiedemann 實現
  • GPU 加速的 sqrt
  • 相關的運行腳本

CADO-NFS 流水線中唯一未被改動的程序是：cado-nfs.py 本身、polyselect_ropt（第二階段多項式選擇）、makefb 以及 dup1。為了在所需規模的合成輸入上獲得合理的性能，我們甚至不得不優化 fake_rels。

注意：我對這些組件的理解，就好比一箇中級汽車愛好者對汽車部件的理解：知道它們在整體系統中的大致作用、對性能的影響、做出改動時的一些權衡，以及良好的運行和使用方式是什麼樣的——但不瞭解底層的物理原理，也不知道如何從原材料製造這些部件。也就是説，我並不太懂底層的數學。我可以告訴你，多項式選擇為格篩產出提供了一個常數因子；但我無法告訴你多項式在篩選中是如何使用的。在這個領域，我遠非專家！

優化工作流程

我同時驅動了多個 Devin。在項目為期 3 周的時間裏，我平均同時運行 3 個 Devin 會話，最多時達到 18 個。這些會話大致分為兩類：

  • 迭代優化單個組件——設計並運行實驗、解讀結果、選擇目標改進項、實施改進，然後重複
  • 在集群上管理端到端的因式分解運行——檢驗整條流水線及配套腳本，找出最重要的低效環節（錯誤、利用率、性能）以供進一步優化

特別是，Devin 處理了以下工作中的很大一部分：

  • 為篩法和線性系統求解選擇和調優參數（儘管使用的是我不得不幫忙搭建的基準測試設備）
  • 生成/優化多項式選擇（同樣，難度各不相同）
  • 運行迭代優化循環
  • 調試（自然是少不了的）
  • 設置並優化處理腳本
  • 在集群上編排大規模計算

我每隔幾個小時與這個優化循環交互一次，其間穿插着與其他 Devin 會話溝通以處理我的日常工作。

Devin Cloud 對這種工作流來説尤其方便：會話是持久化的，且獨立於我的電腦，並行化簡單直接，沙箱機制可防止獨立工作流之間相互干擾，會話還能自主運行數週。我們早已知道 Devin 在 GPU 編程、實驗以及面向 ML 相關負載的集群管理方面很高效，但格篩法和 GNFS 相當不同；我發現 Devin 在這裏的泛化能力令人印象相當深刻。

Devin 還需要我（或其他人類）做什麼？

Devin 成功優化並執行了一條複雜的計算數論流水線，其規模此前需要相當多的人類專業知識才能完成。但我不能聲稱 Devin 是在整條端到端流水線上自主迭代的。想想它究竟需要我做什麼，這很有意思。

不知何故，答案似乎是：還是很多。回想起來，Devin 聲稱我在 233 個用於因式分解的會話中的 192 個裏，通過 3,328 條消息發送了 82,702 個詞（502,887 個字符）（總計 14,450 ACU）。其中，Devin 自身啓動了 101 個子會話，有 36 個完全沒有我的介入。

Devin 需要我來承擔執行功能，與它討論並檢驗它正在做的事情是否合理，具體包括：

  • 設定目標層級，並讓 Devin 保持在恰當的範圍內
  • 識別出 Devin 何時在做無用功並加以糾正（“你不需要做那個測量”）
  • 識別出 Devin 工作流程中反覆出現的低效（“你可以把這部分設置工作攤銷掉”）
  • 指出尚未嘗試的方向（“確保 GPU 永遠不會因 CPU 而阻塞”，“你能在這裏用 NVLink SHARP 嗎？”）
  • 整理實驗框架和結果（“用這種方式做測量，在這裏找之前的結果，不要每次都搞出新的、無法比較的方法”）
  • 捕捉 Devin 何時過早放棄某個方向

雖然事後看來，我似乎提供了一些具體的技術洞見，但我最大的貢獻大概在於手把手促成了統一的一套測量結果、基準和性能估算器的建立，而這些顯然不會自行拼裝成型。這使 Devin 能夠更輕鬆地運行和理解測量，也讓我能夠了解進展的程度以及哪裏還需要更多改進。

退一步説，我還想強調，這項工作沒有 CADO-NFS 是不可能完成的。CADO-NFS 是 GNFS 的一個先進、穩健的開源實現，曾被用於此前的許多紀錄，也被因數分解愛好者社區所使用。它提供了所有相關技術、流水線各階段及其接口，以及一個參考 CPU 實現。藉助這些，我可以讓 Devin 集群大致獨立地優化各個程序，並將輸出與原始版本進行比較。與許多其他情況一樣，我相信人類對問題的工程化分解對於讓智能體取得進展至關重要。

事實上，我注意到代碼庫離上游 CADO-NFS 越遠，智能體就越困惑。這可以歸因於複雜性的累積，但我也在想，CADO-NFS 在預訓練中的存在是否也與此有關。

雜感

這裏發生的事情讓我感到奇怪。成果上署着我的名字，但我並不清楚該如何在我自己、Devin、硬件以及整個外部世界之間分配功勞。

對於編程任務，我把當前的模型和智能體大致看作一台縫紉機或織布機。我以某種方式推動它運轉；顯然沒有我它就無法發生，但我也不是用手在投梭。很難確切説清我的角色是什麼，儘管我確信它並非無足輕重。從某種輕率的意味上説，用 Devin 做這件事與原本可能發生的情況並沒有太大不同：我與一個遠比我龐大、其精確運作機制對我而言晦澀難解的物質系統發生了交互，能量被耗散，結果隨之產生。

另一方面，某種明顯全新的東西正在發生。從第一次提示詞到找到 RSA-260 的因子，大約過去了三週。這一速度體現出一種能力過剩，其程度我們才剛剛開始探索。我認為我們不應迴避這種探索。尤其是，如果一個難題可以通過“單純的編程”來解決，那麼立刻嘗試似乎就是值得的。

過去幾天裏，我們還看到了一些令人印象深刻的數學成果宣稱，其中包括對某個千禧年大獎難題的宣稱解答。我對人類理解力的流失有一些擔憂。如果我自己動手做這件事，我本可以對 NFS 或 GPU 編程有更多瞭解，但即便如此，大概也比完全不用 Devin 時學到的更多。即便技術使我們能夠或激勵我們放棄人類理解，如何在全球範圍內分配資源以維持人類理解，似乎仍是一個重要問題。與此同時，這些工具或許能讓我們選擇在何處深入理解最有價值，探索到任何個體此前都無法企及的更遠處，並擴大能夠做出有意義貢獻的人群。我認為這項工作在兩個方向上都是一個例證。

線性代數

去重/清除/合併/篩選端到端耗時 4 小時（此前一次運行在進行了 2 小時後崩潰），在一台 192 vCPU 節點的 176 個線程上完成，生成了一個 656,182,601 x 656,182,189 的矩陣，非零元素數為 98,431,741,898，密度為每行 150。我們曾對最優合併做過一些考量，並在篩選過程中調整了目標密度，但最終落在接近 150 的位置。

我們在篩選進行的同時優化了線性代數。優化過程頗為動盪，因為我們同時協同優化了矩陣參數、求解器佈局，以及針對推測性最終矩陣特性的代碼目標。對於具有代表性的測試輸入，我們最終收斂到幾個使用優化後的 fake_rels 形成的矩陣。這又反過來影響了篩選：線性代數性能的變化（以及偏離試驗篩選產出估計）數次微調了關係目標。我不清楚我們距離整體最優還有多遠，但當一次 48 小時的線性代數運行似乎觸手可及時，我停止了優化。
