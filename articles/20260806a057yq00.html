適用對象：Codex 及各類編程智能體（coding agent）

如果你剛接觸 Codex 或編程智能體，這份指南能幫你更快拿到更好的結果。它覆蓋了讓 Codex 在 CLI、IDE 擴展 和 ChatGPT 桌面端 上更高效的那些核心習慣——從提示詞與規劃，到驗證、MCP、技能（skills）和定時任務。

把 Codex 用好的關鍵，是別把它當成一次性助手，而是當成一個可以長期配置、持續培養的「隊友」。

一個有用的心智模型：先爲任務準備好正確的上下文，用 AGENTS.md 沉澱長期有效的指引，把 Codex 配置成貼合你工作流的樣子，通過 MCP 接入外部系統，把重複性的工作固化成技能，再把穩定的工作流自動化。

強烈建議：上下文與提示詞

即便你的提示詞不夠完美，Codex 本身已經強到能直接派上用場。你常常只需把難題丟給它、幾乎不做額外配置，就能拿到不錯的結果。清晰的 提示詞（prompting） 不是拿到價值的必要條件，但它確實能讓結果更可靠——尤其是在大型代碼庫或高風險任務裏。

如果你在一個龐大或複雜的倉庫裏工作，最大的提升點就是：給 Codex 提供「針對這個任務的正確上下文」，以及「你希望它做什麼」的清晰結構。

一個穩妥的提示詞默認應包含四部分：

- **上下文（Context）：**哪些文件、文件夾、文檔、示例或報錯與這個任務相關？你可以用- `@`提及特定文件作爲上下文。

- **約束（Constraints）：**Codex 應該遵循哪些標準、架構、安全要求和約定？

- **完成標準（Done when）：**任務完成前什麼必須爲真？比如測試通過、行爲改變、或某個 bug 不再復現。

這能幫助 Codex 保持範圍聚焦、減少假設，產出更易審查的工作成果。

根據任務難度選擇推理強度（reasoning level），並測試哪種設置最適合你的工作流。不同用戶、不同任務，最優設置各不相同。

- **Medium / High（中 / 高）：**用於更復雜的改動或調試

- **Extra High（超高）：**用於漫長、自主性強、重度推理的任務

想要更快地提供上下文，可以在 ChatGPT 桌面端裏用語音聽寫功能，直接說出你希望 Codex 做什麼，而不是打字。

複雜任務先規劃

如果任務很複雜、含糊不清，或者很難描述清楚，就讓 Codex 在動手寫代碼之前先規劃。

以下幾種方式都很好用：

**使用 Plan 模式：** 對大多數用戶來說，這是最簡單也最有效的方式。Plan 模式讓 Codex 先收集上下文、提出澄清問題，並在動手前形成更完善的計劃。用 `/plan` 或 `Shift`+`Tab` 切換。

**讓 Codex 反過來採訪你：** 如果你對想要的東西有一個模糊的概念，但說不清楚，就讓 Codex 先向你提問。告訴它去挑戰你的假設，在寫代碼之前把模糊的想法變成具體的方案。

**使用 PLANS.md 模板：** 對於更進階的工作流，你可以配置 Codex 在執行週期較長或多步驟的任務時，遵循一個 `PLANS.md` 或執行計劃模板。詳見 執行計劃指南。

用 `AGENTS.md` 讓指引可複用

一旦某種提示詞模式奏效，下一步就是別再手動重複它。這就是 AGENTS.md 的用武之地。

可以把 AGENTS.md 理解爲給智能體看的開放式 README。它會自動加載進上下文，也是沉澱「你和你團隊希望 Codex 在這個倉庫裏怎麼幹活」的最佳位置。

CLI 裏的 /init 斜槓命令，是在當前目錄快速生成一份 AGENTS.md 起手的命令。它是很好的起點，但你應當編輯生成的結果，使其貼合你團隊真實的構建、測試、審查和發佈代碼的流程。

你可以在不同層級創建 AGENTS.md：放在 ~/.codex 的全局 AGENTS.md 用於個人默認配置，倉庫級文件用於共享標準，子目錄裏更具體的文件用於局部規則。如果存在離當前目錄更近的更具體文件，則以該文件的指引爲準。

保持實用。一份簡短而準確的 AGENTS.md，勝過塞滿模糊規則的長文件。先從基礎開始，只有在發現重複的失誤後，才追加新規則。

如果 AGENTS.md 開始變得過大，保持主文件精簡，把規劃、代碼審查、架構等任務相關的具體說明，用單獨的 markdown 文件來引用。

當 Codex 犯了兩次同樣的錯誤時，讓它做一次覆盤（retrospective），並更新 AGENTS.md。指引應始終基於真實痛點、保持實用。

配置 Codex 以保持一致性

配置是讓 Codex 在不同會話和不同界面上行爲更一致的主要手段之一。例如，你可以爲模型選擇、推理強度、沙箱模式、審批策略、配置文件和 MCP 設置定義默認值。

*圖片來源：Pexels*

一個不錯的起始模式是：

- 把个人默认值放在 `~/.codex/config.toml`（ChatGPT 桌面端中**Settings > Configuration > Open config.toml**）

- 把倉庫特定的行爲放在 `.codex/config.toml`

- 命令行覆蓋只用於一次性場景（如果你用 CLI 的話）

config.toml 是你定義持久化偏好的地方，比如 MCP 服務器、多智能體設置和功能開關。特定配置文件的覆蓋項，存放在獨立的 $CODEX_HOME/profile-name.config.toml 文件裏。

Codex 自帶運行級沙箱（operating level sandboxing），有兩個關鍵開關可由你控制。審批模式（approval mode）決定 Codex 何時請求你的許可來運行命令；沙箱模式（sandbox mode）決定 Codex 能否在目錄中讀寫、以及智能體能訪問哪些文件。

如果你剛接觸編程智能體，請從默認權限起步。默認情況下保持審批和沙箱收緊，只有在需求明確後，才爲可信倉庫或特定工作流放寬權限。

注意，CLI、IDE 擴展和 ChatGPT 桌面端共享同一套配置層。更多內容見 示例配置 頁面。

儘早爲你的真實環境配置 Codex。很多「質量問題」其實是「配置問題」——比如工作目錄錯誤、缺少寫入權限、模型默認值不對，或缺少工具與連接器。

用測試和審查提升可靠性

不要止步於「讓 Codex 改個東西」。該讓它建測試時就建測試、跑相關的檢查、確認結果，並在你接受之前審查工作成果。

Codex 可以幫你跑完這一整套循環——但前提是它知道「好」長什麼樣。這個指引可以來自提示詞，也可以來自 AGENTS.md。

Codex 不該只是生成代碼。在正確的指令下，它還能幫你 **測試它、檢查它、審查它**。

用 MCP 接入外部上下文

當 Codex 需要的上下文存在於倉庫之外時，就用 MCP。它讓 Codex 接入你已經在用的工具與系統，你就不用反覆把實時信息複製粘貼進提示詞。

模型上下文協議（Model Context Protocol，MCP） 是一個把 Codex 連接到外部工具和系統的開放標準。

在以下情況使用 MCP：

- 你希望 Codex 使用某個工具，而不是依賴粘貼的指令

Codex 同时支持 STDIO 和 Streamable HTTP 服务器，并支持 OAuth。

在 ChatGPT 桌面端，進入 **Settings > MCP servers** 即可查看自定義和推薦的服務器。很多時候，Codex 可以幫你安裝所需的服務器——你只需要開口問。你也可以在 CLI 裏用 codex mcp add 命令，通過名稱、URL 等細節添加你的自定義服務器。

只在工具能打通真實工作流時才添加。不要一開始就接入你使用的每一個工具。先從一兩個能明顯消除你經常做的人工循環的工具開始，再逐步擴展。

把可重複的工作固化成技能

一旦某個工作流變得可重複，就別再依賴長提示詞或反覆的來回拉扯。用一個 技能（skill） 把指令、上下文和支持邏輯打包進一份 SKILL.md 文件，讓 Codex 始終如一地應用。技能在 CLI、IDE 擴展和 ChatGPT 桌面端都通用。

讓每個技能只聚焦於一件事。從 2 到 3 個具體用例起步，定義清晰的輸入和輸出，並寫好描述——說清這個技能做什麼、何時使用它，包括用戶真正會說的那些觸發短語。

不要一開始就試圖覆蓋所有邊界情況。先從一個有代表性的任務做起，把它打磨好，再把這個工作流固化成技能並持續改進。只有當腳本或額外資源確實能提升可靠性時，才把它們包含進來。

一個好經驗：如果你一直在複用同一段提示詞，或一直在糾正同一個工作流，那它大概就該變成一個技能了。

$skill-creator 技能是搭建第一個技能版本的最佳起點。在迭代期間，先讓它保持本地。當準備好廣泛分享時，再把它打包成 插件（plugin）。技能描述是最重要的一部分之一——它應當說清技能做什麼、何時使用。

個人技能存放在 $HOME/.agents/skills，團隊共享技能可以簽入倉庫內的 .agents/skills。這對新成員 onboarding 尤其有幫助。

用定時任務處理重複工作

一旦某個工作流穩定了，你就可以讓 Codex 在後臺替你定時運行它。在 ChatGPT 桌面端，定時任務（scheduled tasks） 讓你爲週期性工作選擇項目、提示詞、節奏和執行環境。

從 **Scheduled** 頁面創建一個定時任務。選擇項目、提示詞、節奏，以及任務是在專用的 Git worktree 中運行還是在你的本地環境中運行。提示詞可以調用技能。瞭解更多關於 Git worktrees 的內容。

一個有用的原則：技能定義「方法」，定時任務定義「節奏」。如果一個工作流還需要大量人工干預，就先把它變成技能。一旦它變得可預測，再把它排期就能省時間。

把定時任務用於反思和維護，而不只是執行。回顧最近的對話、總結反覆出現的痛點，並隨着時間持續改進提示詞、指令或工作流配置。

管理長週期對話

對話會隨時間累積上下文、決策和行動，因此管理好它們對質量影響很大。

ChatGPT 桌面端允許你置頂（pin）對話並創建 worktree。如果你用 CLI，這些 斜槓命令 特別有用：

- `/experimental`：切換實驗性功能，並寫入你的- `config.toml`

- `/fork`：在保留原始記錄的前提下，創建一個新對話

- `/compact`：當對話變長、你想要一份早期上下文的摘要版本時使用。Codex 也會自動壓縮對話

- `/agent`：當你在並行運行多個智能體、想在活動線程間切換時使用

- `/apps`：在 Codex 里直接使用 ChatGPT 应用

一個連貫的工作單元，對應一個對話。如果工作仍是同一問題的一部分，留在同一個對話裏往往更好，因爲它保留了推理軌跡。只有當工作真正分叉時，才 fork。

用 Codex 的 子智能體（subagent） 工作流，把邊界清晰的工作從主線程中卸載出去。讓主智能體聚焦核心問題，把探索、測試或分流類任務交給子智能體。

常見錯誤

初次使用 Codex 時，有幾個常見錯誤要避免：

- 把長期有效的規則堆進提示詞，而不是移入 `AGENTS.md`或技能

- 不告訴智能體如何最好地運行構建和測試命令，導致它看不到自己的工作成果

- 在還不瞭解工作流之前，就給 Codex 你電腦的完全權限

- 不使用 Git worktree，就在同一批文件上跑實時任務

- 把 Codex 當成需要一步步盯着的東西，而不是讓它和你的工作並行

- 整個項目只用一條對話，而不是「一個連貫結果對應一條對話」。這會讓上下文臃腫，長期結果變差
