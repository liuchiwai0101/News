很多人問我：TypeScript 究竟能給 React 項目帶來什麼？看完這個調色板與成員表格的實戰拆解，你會發現——

開局一張圖：爲什麼 TypeScript 是大型項目的剛需

那句“ts 適合大型項目開發，代碼量大，成員多”雖然簡短，但點出了核心痛點。在多人協作、組件複用頻繁的場景裏，靠人腦記憶 props 名稱和類型遲早會出事。TypeScript 最大的價值不是多寫幾個類型註解，而是**建立起一套“數據模型先行”的開發紀律**。

下面我們以一個包含「調色板」和「成員列表」的 Demo 爲例，把零散的代碼筆記串成一套可落地的架構思路。

一、先把數據模型“拎”出來：model 層

你一定見過這樣的場景：一個 User 對象的結構散落在十幾個文件裏，後端改了字段，前端要全局搜索逐個替換。把數據模型集中管理，問題就迎刃而解。

#### 顏色模型：Color

// model/color.ts
export interface Color {
  red: number;
  green: number;
  blue: number;
}

這個接口看似簡單，卻承擔着“顏色數據契約”的角色。無論在 ColorBrowser 還是 ColorPicker 中，只要引用 Color，就能保證大家對顏色的理解完全一致——RGB 三個通道，值都是 number，範圍 0~255（邏輯上我們還要約束）。

#### 成员模型：MemberEntity

// model/member.ts
export interface MemberEntity {
  id: number;
  login: string;
  avatar_url: string;
}

MemberEntity 直接對應 GitHub 風格的用戶數據。**把實體定義獨立成文件，前端就有了自己的“數據字典”** ，接口聯調時看一眼 model 目錄就知道數據結構長什麼樣。

小貼士：

type和interface在這裏都能用，但 interface 更具擴展性，也更符合面向對象建模的習慣。

二、接口請求也模塊化：api 層

有了模型，我們自然希望獲取數據的方法也能“開箱即用”，並且返回類型與模型嚴格匹配。這就是 api 目錄的意義。

// api/memberApi.ts
import { type MemberEntity } from "../model/member";
export const getMembersCollection = (): Promise<MemberEntity[]> => {
  return new Promise((resolve) => {
    setTimeout(() => {
      resolve([
        {
          id: 1457912,
          login: "brauliodiez",
          avatar_url: "https://avatars.githubusercontent.com/u/1457912?v=3"
        },
        {
          id: 4374977,
          login: "Nasdan",
          avatar_url: "https://avatars.githubusercontent.com/u/4374977?v=3"
        }
      ])
    }, 500)
  })
}

這裏有幾個亮點值得記住：

- **返回類型明確標註爲**，調用方用- `Promise`- `await`拿到的直接就是- `MemberEntity[]`，智能提示一步到位。

- 通過 `setTimeout`模擬異步請求，**所有異步行爲都封裝在 Promise 中**，與真實`fetch`或`axios`調用可以無縫切換。

- 獨立的 `api`目錄讓接口方法集中管理，後期更換數據源只需修改這一處。

三、狀態提升與組件拆分：ColorPicker 實戰

#### App.tsx：狀態的“中央廚房”

import { useState } from 'react'
import { type Color } from './model/color';
function App() {
  const [color, setColor] = useState<Color>({
    red: 20,
    green: 240,
    blue: 180
  });
  return (
    <>
      <ColorBrowser color={color} />
      <ColorPicker color={color} onColorUpdated={setColor} />
    </>
  )
}

這裏直接 ** useState**  顯式指定了泛型，賦予

color 明確的類型。setColor 作爲更新函數傳給 ColorPicker，形成了典型的**狀態提升**——子組件通過回調改變父組件狀態，自己只負責展示和交互。

#### ColorPicker：如何“精確更新”對象屬性

interface Props {
  color: Color;
  onColorUpdated: (color: Color) => void;
}
const ColorPicker: React.FC<Props> = (props) => {
  return (
    <div>
      <input
        type="range"
        min="0"
        max="255"
        value={props.color.red}
        onChange={event => props.onColorUpdated({
          ...props.color,
          red: +event.target.value,
        })}
      />
      {props.color.red}
      {/* green、blue 同理 */}
    </div>
  )
}

注意 onChange 中的两个细节：

- **不可变更新**：- `{ ...props.color, red: 新值 }`创建一个新的- `Color`对象，符合 React 的 immutable 原则。

- `+event.target.value`快速轉數字- `event.target.value`是字符串，前面加一個- `+`就能轉成 number。這是非常實用的取巧寫法，比- `parseInt`更簡潔。

金句：寫 TypeScript 組件時，Props 接口就是你給隊友看的使用說明書——傳什麼，怎麼傳，一目瞭然。

#### ColorBrowser：純展示，類型即文檔

interface Props {
  color: Color
}
const ColorBrowser: React.FC<Props> = (props) => {
  const divStyle: React.CSSProperties = {
    width: "11rem",
    height: "7rem",
    backgroundColor: `rgb(${props.color.red},${props.color.green},${props.color.blue})`
  }
  return <div style={divStyle} />
}

React.CSSProperties 也是一個隱形的類型保障，如果你不小心把 width 寫成了 wdith，編譯階段就會報錯。這讓我想起一句話：**類型系統就像一位不知疲倦的 Code Review 同事，24小時在線。**

四、異步數據與列表渲染：MemberTable

const MemberTable: React.FC = () => {
  const [memberCollection, setMemberCollection] = React.useState<MemberEntity[]>([])
  React.useEffect(() => {
    (async () => {
      const members = await getMembersCollection();
      setMemberCollection(members);
    })()
  }, [])
  return (
    <table>
      <thead>...</thead>
      <tbody>
        {memberCollection.map((member) => (
          <MemberRow key={member.id} member={member} />
        ))}
      </tbody>
    </table>
  )
}

這裏有幾個關鍵知識點：

-

<code>useState<MemberEntity[]></code>

-

**類型安全地 map 渲染**：`memberCollection`已經是`MemberEntity[]`，所以 map 回調中的`member`會自動推斷爲`MemberEntity`，無需額外標註。

#### 为什么 useEffect 不能直接是 async 函数？

如果讓你憑直覺寫，你大概率會這樣：

// ❌ 错误写法
React.useEffect(async () => {
  const members = await getMembersCollection();
  setMemberCollection(members);
}, []);

但 React 會給你一個警告，或者至少讓你心裏沒底——**因爲  useEffect 的回調函數期望返回一個清理函數（或 undefined），而 async 函數永遠返回一個 Promise**。React 拿到一個

Promise 根本不知道怎麼處理，既不會幫你 await，也沒法把它當作清理函數去執行。說白了就是 **類型不匹配**：你給我個 Promise，我要的是函數，咱倆聊不到一塊兒去。

#### IIFE 如何巧妙地繞過限制？

解決辦法就是：**外層保持普通函數（返回 void），內部再“寄生”一個異步函數讓它立即跑起來**。

React.useEffect(() => {
  // 1. 外层是一个普通箭头函数，返回 undefined → React 满意
  (async () => {
    // 2. 这是一个异步 IIFE，立刻执行
    const members = await getMembersCollection();
    setMemberCollection(members);
  })(); // 3. 注意末尾的 ()，定义完就调用
}, []);

這裏 (async () => { ... }) 定義了一個異步函數表達式，而後面的 () 當場調用了它，所以稱爲**立即執行的異步函數表達式（IIFE）** 。 這樣一來：

- React 只看外層的普通函數，它啥也沒返回，完全符合規範；

- 異步數據請求在 IIFE 裏照常運行，拿到結果後通過 `setState`更新視圖；

- 整個流程異步不阻塞渲染，組件可以先用空數組渲染，數據回來後再更新。

#### 這個寫法還有什麼門道？

- `[]`空依賴數組- `useEffect`只在組件- **掛載時**執行一次，相當於- `componentDidMount`。非常適合做首屏數據請求。

- **錯誤處理**：實際項目中 IIFE 裏最好加- `try/catch`，否則請求一旦失敗，錯誤會吞沒在 Promise 裏。改進寫法：

useEffect(() => {
  (async () => {
    try {
      const members = await getMembersCollection();
      setMemberCollection(members);
    } catch (err) {
      console.error('获取成员列表失败', err);
    }
  })();
}, []);

- **清理函數**：如果請求在組件卸載前還沒完成，理想情況下應該取消它（例如用 AbortController）。這個示例簡單，所以沒處理，但你需要知道——- **依賴外部的異步操作，永遠要考慮“組件沒了但數據還在路上”的情況**。

#### 有沒有更“優雅”的替代方案？

IIFE 在 React 17/18 中依然很常用，但現在你偶爾也會看到這種寫法：

const fetchData = async () => {
  const members = await getMembersCollection();
  setMemberCollection(members);
};
useEffect(() => {
  fetchData();
}, []);

本質是一樣的：把異步邏輯提到 useEffect 外面定義，內部直接調用。有些人覺得這樣更清晰，不過要注意 fetchData 在依賴變化時是否需要加進依賴數組。而 IIFE 的好處是**把邏輯緊密包裹在 effect 內部，一眼就能看出它在幹嘛**，無副作用往外泄露變量。

#### 小坑提醒：MemberRow 的隱式 any

MemberRow 没有定义 Props 类型：

const MemberRow = (props) => { ... }

在嚴格的 TS 配置下這會報錯（參數隱式 any）。更好的做法是：

interface MemberRowProps {
  member: MemberEntity;
}
const MemberRow: React.FC<MemberRowProps> = ({ member }) => (
  <tr>
    <td><img src={member.avatar_url} style={{ maxWidth: '10rem' }} /></td>
    <td><span>{member.id}</span></td>
    <td><span>{member.login}</span></td>
  </tr>
)

如此一來，任何使用了 MemberRow 的地方都會受到類型約束，徹底消滅“傳錯屬性名”的隱患。

五、架構小結：model 與 api 的分層哲學

回顧整個項目目錄：

src/
├── model/
│   ├── color.ts
│   └── member.ts
├── api/
│   └── memberApi.ts
├── components/
│   ├── ColorBrowser.tsx
│   ├── ColorPicker.tsx
│   └── MemberTable.tsx
└── App.tsx

**model 層定義“長什麼樣”，api 層定義“從哪來”，組件層只負責“怎麼展示與交互”** 。這種分層讓前端項目擁有了類似後端的可維護性，新同事接手時，先看 model，再看 api，最後看組件，路徑清晰。

金句：架構的本質不是讓代碼能跑，而是讓你的意圖能被其他開發者（包括三個月後的自己）瞬間理解。

寫在最後

從一個小小的 Color Picker 到模擬數據請求的成員表格，我們看到 TypeScript 在 React 項目中不是“多寫幾個類型”那麼簡單。它倒逼我們提前思考數據結構、規範接口格式，最終通過 model 和 api 的分層，把零散的邏輯編織成一張強壯的安全網。

如果你還在猶豫是否在團隊中推行 TypeScript，不妨從今天這組代碼開始嘗試——把 model 和 api 先抽出來，讓類型幫你寫文檔。很快你會發現，**曾經那些深夜排查的 “undefined” 錯誤，不過是少寫了一個接口定義罷了**。
