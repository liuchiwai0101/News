剛剛，ChatGPT Pro 額度官宣翻倍，但免費重置可能要沒了

內容機器翻譯自第三方媒體（愛範兒 · InfoQ · cnBeta.COM），僅供參考，以原文為準。

正文

10 月 29 日，OpenAI 產品負責人 Tibo 宣佈，從即日起，Pro 100、Pro 200、Pro 500 以及 Business Premium 套餐的使用限制全面翻倍。

其中還有一項重要説明：OpenAI 聽取用户反饋後，決定不再削減 Pro 200 的使用額度，因此該套餐的 ChatGPT Work 和 Codex 使用量將維持原有水平。與此同時，Dots 目前仍將繼續享有擴容額度，而且其使用量與賬户默認額度相互獨立，不計入默認額度。

這項調整實際上回應了此前 Pro 訂閲體系調整引發的爭議。OpenAI 此前推出 500 美元的 Pro 500，並調整 200 美元 Pro 套餐的權益，原有 Pro 200 用户曾面臨部分使用額度下調的預期。此次公告撤回了相關削減安排，意味着用户反饋確實影響了最終政策決定。

後續，有用户進一步詢問，Pro 500 是否意味着可以獲得相當於 Plus 套餐 50 倍的使用量，Tibo 直接回答“Yes”。這也體現出 OpenAI 正在進一步拉開不同付費層級之間的使用額度差距，為高強度 AI 編程和工作流用户提供更大的使用空間。

社區對此並非一邊倒地叫好。部分 Pro 用户歡迎額度擴容，但也有 200 美元 Pro 用户指出，自己此前已經享有較高額度，此次只是撤回了原定的削減計劃，並沒有獲得真正意義上的新增權益。

“我很高興其他 Pro 檔位以及低額度套餐的用户拿到了實打實的額度上漲，這些才是真正的優化。但把取消原定降額這件事，打包算進 28 天改進計劃裏，對外宣傳成全面翻倍升級，這有誤導之嫌。坦白説，對於一直在跟進這件事、並且依賴官方公告做規劃的用户而言，這種説法實在讓人難以接受。”有用户説道。

與此同時，一些 Plus 用户對本次調整沒有覆蓋低價套餐表達不滿，認為 OpenAI 正在進一步拉大不同付費層級之間的使用體驗差距。

除了提高額度，Tibo 還強調，OpenAI 會繼續推出更好的模型和效率優化，讓用户隨着時間推移獲得更多實際使用量。值得注意的是，這次調整屬於 OpenAI 為期 28 天的產品改進計劃中的第 25 天。Tibo 隨後還開玩笑稱，OpenAI 正在從“重置額度公司”畢業，轉向“Token 公司”。

OpenAI 負責 Codex 和 ChatGPT 產品的 Andrew Ambrosino 也表示，團隊已經啓動一輪密集改進，重點解決應用簡潔性和性能問題，並由他親自負責。

這意味着 OpenAI 並不打算只依靠擴大套餐上限解決用户需求，而是希望同時提高模型能力、推理效率和單位算力的產出。對於越來越依賴 Codex 的開發者而言，能否獲得穩定、充足的使用額度，已經成為影響訂閲決策的重要因素。

除了 OpenAI，過去一年，Anthropic 也頻繁調整 Claude Code 的使用限制，甚至經歷了從收緊到擴容、再到部分回收的過程。

2026 年 3 月，Anthropic 曾收緊免費、Pro 和 Max 用户在高峯時段的 5 小時使用額度；5 月與 SpaceX 達成算力合作後，又將 Claude Code 的 5 小時額度翻倍，並取消 Pro 和 Max 套餐的高峯期額度削減。與此同時，公司還曾將 Claude Code 周度額度臨時提高 50%，但在 9 月結束促銷後，僅保留了比原始水平高 25%的永久額度。

對額度調整的不滿，也引發了用户對訂閲權益的訴訟。

Anthropic 的 Max 5x 和 Max 20x 套餐分別宣傳提供 Pro 套餐 5 倍和 20 倍的使用量，但這一倍率實際上指每個 5 小時會話窗口內的使用量，而非每週累計使用量，用户同時還受到周度總量限制。今年 9 月，一批用户因此對 Anthropic 提起集體訴訟，認為相關限制沒有在購買過程中得到充分、醒目的説明，導致實際使用體驗與購買預期存在差距。

AI 編程工具的額度問題並非簡單的套餐定價問題。隨着 Agent 逐漸接管更多開發任務，後台自動執行、任務調度和多智能體協作也開始消耗大量算力，甚至出現用户沒有直接感知到任務，卻已經消耗了不少使用額度的情況。

今年 6 月，OpenAI 的 Codex 就曾出現過類似問題。當時，不少用户發現，原本需要一週才能消耗完的使用額度，突然在一兩天內就被用完。部分 200 美元 Pro 用户表示，過去需要連續工作一週才能用完的額度，後來一天就可能消耗殆盡。

Tibo 隨後解釋，問題與後台工作量異常有關：自動代碼審查和輔助子智能體有時會比預期更頻繁地運行，甚至重複執行任務，或者在發生錯誤後過度重試，導致不必要的算力消耗。此外，Codex 儀表盤還曾顯示一些實際上並未計入用户賬單的活動，進一步加劇了用户對額度異常消耗的困惑。

為此，OpenAI 組織了緊急排查，成立專項團隊調查問題，部署修復並重置所有用户的使用額度，同時增加後台使用量監控，以便更早發現類似問題。Tibo 還表示，團隊會為用户額外補充一次額度重置，以彌補此前異常消耗造成的影響。

Anthropic 的 Claude Code 也被發現存在類似問題，只不過消耗發生在一個更加不起眼的環節。

8 月 15 日，一名開發者在 Anthropic 的 Claude Code GitHub 倉庫提交 Issue，要求官方提供一個正式開關，允許用户關閉子智能體狀態摘要，而不必犧牲整個子智能體功能。

問題出在 Claude Code 的後台狀態刷新機制。當用户啓動多個子智能體時，系統會定期調用模型，為每個活躍智能體生成一條簡短狀態提示，例如當前正在執行什麼任務。按照開發者對 Claude Code 內部請求的分析，這項機制默認每隔 30 秒觸發一次，每次都會重新提交子智能體的完整對話歷史及工具定義，交給模型生成摘要。最終輸出通常只有幾十個 Token，主要用於更新界面中的狀態文字，同時幫助用户和 Claude Code 掌握各個後台智能體的工作進展。

開發者對一次持續 4 小時、啓動 27 個子智能體的會話進行了抓包分析。在 1496 次 API 請求中，有 339 次屬於 agent_summary，佔全部請求的 22.7%；這部分請求產生約 6276 萬原始 Token，佔總原始 Token 的 22.2%。按照 Opus 5 的緩存讀取、緩存寫入和輸出價格進行加權後，其成本仍佔整個會話約 18%。

另一名開發者在使用 4 個子智能體進行 1 小時 45 分鐘測試時，也發現了類似問題。其中，一個長期運行的智能體上下文規模達到約 38 萬 Token，103 次狀態摘要請求產生 2180 萬緩存讀取 Token，佔整個會話緩存讀取量的 26%，但最終輸出僅約 2100 個 Token。按照該開發者的測算，僅這個智能體用於生成狀態提示，每小時就可能產生約 4500 萬緩存讀取 Token。

更麻煩的是，這些後台請求設置了 skipTranscript: true ，通常不會進入常規會話轉錄文件。因此，依賴會話記錄統計消耗的第三方工具可能低估實際 Token 使用量。用户看到的是智能體狀態欄裏不斷變化的幾個詞，背後卻可能發生了大量上下文讀取。
