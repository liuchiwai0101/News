關於本教程：本教程基於一次真實的多後臺微前端落地經驗抽象而成，去除了所有項目專屬信息。所有踩坑、決策點都是實戰沉澱，不是 API 文檔複述。讀完後你應該能：判斷自己是否需要微前端，搭出一套同棧多後臺的 qiankun 方案，知道哪些坑必踩、哪些坑可繞。

目錄

第一部分：決策篇

1. 什麼是微前端

微前端是一種**把一個大型前端應用拆成多個獨立可部署單元、運行時聚合**的架構模式。

類比後端微服務：

**核心特徵**：

- 子應用**獨立開發、獨立構建、獨立部署**

- 子應用對外暴露統一的**生命週期接口**（mount / unmount）

- 主應用負責**路由調度**和**外殼渲染**

- 用戶感知是**一個完整的網站**

微前端不是"前端微服務"的簡單類比——它

只在瀏覽器一側完成聚合，沒有跨網絡通信，所以性能損耗遠小於微服務。

2. 微前端能解決什麼問題

微前端的五個典型適用場景：

**一句話畫像**：當你發現自己想說"我希望把 X 和 Y 當成兩個獨立的項目維護，但用戶看起來還是一個網站"，你就該考慮微前端了。

3. 你是否真的需要微前端

微前端不是免費午餐。它帶來三種成本：

- **沙箱開銷**：JS 沙箱、樣式隔離都有運行時損耗

- **調試複雜度**：跨應用問題排查比單體困難得多

- **部署鏈路變長**：dev / preview / prod 都要跑通

引入前先問自己三個反問：

反問 1：我的項目真的有多個獨立業務邊界嗎？
  └─ 如果只是想做"代碼拆分"，路由懶加載 + monorepo 就夠了
反問 2：我的團隊規模真的需要解耦嗎？
  └─ 5 人以內的單團隊通常用不到，直接 monorepo 反而更順手
反問 3：我真的需要獨立部署嗎？
  └─ 如果所有應用註定一起發版，微前端只增成本

**替代方案對比**：

判斷標準：如果你的痛點只是"單倉庫太大"或"構建太慢"，先試 monorepo，它成本低得多。微前端是最後的選擇。

4. 框架方案對比

主流微前端框架四象限對比：

**本教程選 qiankun**，因爲：

- 同棧和跨棧都能 hold 住，遷移成本最低

- 幾乎所有踩坑都能 Google 到答案，社區資料密度最高

- 沙箱機制完善，遺留改造場景安全感強

如果你的場景是**全棧統一 Vite 7+** 、**對 bundle 體積極度敏感**，可以考慮 Module Federation。其餘情況 qiankun 是穩妥選擇。

5. 示例項目場景

教程貫穿一個虛構的"企業內部管理平臺"：

admin-shell  （主应用 / Shell / 容器）
├── /              门户首页（子应用入口卡片）
├── /orders/*      子应用 app-orders（订单管理）
└── /users/*       子应用 app-users（用户管理）

技术栈：React 19 + Vite 7 + TypeScript + Tailwind CSS + Shadcn UI（**同栈场景**）。

版本口径：本教程与配套模板的验证基线是React 19 / Vite 7 / qiankun 2.x。曾尝试 Vite 8 +@vitejs/plugin-react6，但与 qiankun 生态(尤其 Vite 插件)依赖不稳,实测回退到 Vite 7 + plugin-react 5 才稳。升级 Vite 大版本前务必重跑 dev/preview/prod 全流程。

跨棧場景（如主應用 React + 子應用 Vue）的關鍵差異會在對應章節標註。

第二部分：心智模型

6. qiankun 是怎麼跑起來的

完整加載流程：

子應用靜態資源 (app-orders)主應用 (admin-shell)瀏覽器子應用靜態資源 (app-orders)主應用 (admin-shell)瀏覽器用戶訪問 /orders/list路由匹配 activeRule "/orders"fetch 子應用 entry HTML返回 index.html解析 HTML，抽出 script/link加載 JS chunk / CSS返回資源沙箱中執行子應用腳本拿到子應用 export 的 bootstrap/mount/unmount調用 mount(container)子應用渲染到

注意箭頭方向：**主應用主動 fetch 子應用資源**，子應用是"被動"的。

7. 一句話心智

子應用的代碼是被主應用 fetch 過來，在主應用的 origin 裏執行的。

這句話是後面所有決策的根。它推導出：

把這兩條記牢：

JS 在主應用 origin 跑，靜態資源走子應用 origin。它們不是同一回事。

8. 三角色職責

Shell 是"外殼/遙控器"，業務永遠在子應用裏。

Shell 一旦開始寫業務代碼，微前端架構就開始爛。

9. 三個高頻誤解

**誤解 1：以爲是 iframe 那種隔離**

qiankun 的子應用是**真實跑在主應用 DOM 裏的 React 應用**，不是 iframe。所以：

- 沒有跨 frame 通信問題

- 沒有獨立的 history（共用瀏覽器 history）

- 但也沒有 iframe 那種"什麼都隔離"的天然安全感

**誤解 2：以爲子應用靜態資源走主應用 origin**

子應用的 HTML 入口、JS chunk、CSS、圖片都是**從子應用 origin 加載的**。所以：

- 子應用部署側必須配 CORS（允許主應用 origin 來 fetch）

- 子應用靜態資源 URL 必須是**絕對路徑**，否則會被錯誤地拼到主應用 origin（第 19 節詳解）

**誤解 3：以爲 dev 跑通就等於 prod 跑通**

qiankun + Vite 場景下，dev 和 prod 的行爲差異**遠大於普通 SPA**：

- CSS 注入路徑不同（dev 是 JS 注入 style 標籤，prod 是 link 標籤）

- 靜態資源解析路徑不同（dev 走 Vite dev server，prod 走絕對 URL）

- 樣式隔離效果不同（見第 17 節）

**所以必須 dev → preview → prod 三步都跑通**，詳見第 20 節。

進階：從硬編碼 registry 演進到 manifest 動態發現。本節的registry.ts是最好教學的入門形態,但當子應用變多、由不同團隊獨立部署時,“主應用改一行代碼才能上一個子應用”會變成瓶頸。

配套模板已經升級成manifest 發現:子應用各自帶一份app.json(title/icon/category/order),主應用啓動時fetch('/manifest.json')動態註冊,清單經 zod 校驗、圖標走白名單、activeRule撞保留前綴(/__sso、/api、/assets、/apps)會被攔。這樣“上一個子應用 = 傳一個文件夾 + 重建 manifest”,主應用零改動。

詳見第 24 節與模板的src/features/micro-apps/registry.ts。

15. 接入第一個子應用

假設你已經有一個獨立運行的 Vite + React 子應用 app-orders，下面是接入 qiankun 的**最小改動**。

**第一步：裝插件**

pnpm add -D vite-plugin-qiankun-lite

早期教程用的是

vite-plugin-qiankun，但它长期未维护、对新版 Vite 适配差。这里改用维护中的分支：它用vite-plugin-qiankun-lite命名 ES export桥接 qiankun 生命周期，不再需要renderWithQiankun/ 内联 IIFE /window.proxy，对 Vite 7+ 更友好。主应用仍用经典qiankun(registerMicroApps/start),无需改动即可加载 lite 子应用。

**第二步：改 vite.config.ts**

import react from '@vitejs/plugin-react'
import qiankun from 'vite-plugin-qiankun-lite'
// 若主应用域名开了 Cloudflare Rocket Loader,会改写 <script> type 让内联脚本不执行,
// 给所有 script 加 data-cfasync="false" 让它跳过(没用 Cloudflare 可删)
function disableCloudflareRocketLoader(Plugin {
  return {
    name: 'cf-rocket-disable',
    enforce: 'post',
    transformIndexHtml(html) {
      return html.replace(/<script\b(?![^>]*\bdata-cfasync=)/g, '<script data-cfasync="false"')
    },
  }
}
export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '')
  const appName = env.VITE_APP_NAME || 'app-orders'
  // 同源部署:生产挂到主应用同源路径前缀(如 /apps/orders/),资源走绝对路径且免 CORS;
  // 跨域部署则填子应用自己的绝对 URL。开发/独立 preview 用 '/'。见第 19 节
  const publicBase = mode === 'production' ? env.VITE_PUBLIC_BASE || '/' : '/'
  return {
    base: publicBase,
    // lite 用命名 export 桥接生命周期,不再需要 useDevMode
    plugins: [react(), qiankun({ name: appName }), disableCloudflareRocketLoader()],
    server: {
      port: 5173,
      cors: true,
      headers: { 'Access-Control-Allow-Origin': '*' },  // dev 跨域
    },
    preview: {
      port: 4173,
      cors: true,
      headers: { 'Access-Control-Allow-Origin': '*' },  // preview 也要单独配
    },
  }

⚠️ 判斷“是否被主應用接管”用自寫的

isInShell()，不要依賴插件 helper 的。原因:helper 在頂層求值的標誌,在子應用__POWERED_BY_QIANKUN__main的真實 realm 裏可能拿到undefined。可靠做法是:主應用注入過 props 就算被接管,mount 之前按當前路徑前綴兜底判斷(見第四步的subAppContext)。

**第四步：改路由 basename（用函數延遲求值）**

// app-orders/src/app/routes.ts
import { createBrowserRouter } from 'react-router'
import { isInShell } from '@/shared/auth/subAppContext'
// 必须是函数 — basename 在 mount 时才求值。否则模块初始化早于主应用注入,
// 独立运行会拿到错误的 basename。
export function createRouter(const basename = isInShell() ? import.meta.env.VITE_APP_BASENAME || '/orders' : '/'
  return createBrowserRouter(routes, { basename })
}

isInShell() 放在子應用的 subAppContext 裏（第 18 節會給完整實現），核心是不依賴插件 helper：

// app-orders/src/shared/auth/subAppContext.ts(节选)
let providedByShell = false
export function setSubAppContext(next: SubAppContext) {
  Object.assign(ctx, next)
  providedByShell = true
}
export function isInShell(if (providedByShell) return true                 // 主应用注入过 props = 被接管
  if (typeof window === 'undefined') return false
  return window.location.pathname.startsWith(import.meta.env.VITE_APP_BASENAME || '/orders')
}

/orders必须和主应用注册子应用时的activeRule（manifest 里的activeRule/VITE_APP_BASENAME）完全一致。不一致 = 子应用所有内部链接 404。

**第五步：部署 —— 優先同源，跨域兜底**

**方案一：同源部署（推薦）** 。把子應用部署到主應用**同源**的路徑前綴下,比如主應用在 `https://console.example.com`,子應用就放在 `https://console.example.com/apps/orders/`,manifest 的 `entry` 指向它。子應用 `VITE_PUBLIC_BASE=/apps/orders/`(末尾帶斜槓)。這樣:

- 子應用資源走**同源絕對路徑**,**完全免去 CORS**

- 只需 SPA fallback:把 `/apps/orders/*`都 rewrite 到该子应用的`index.html`

同源是真實項目收斂到的形態——它繞開了第 19 節那一整套跨域 + 絕對 URL 的麻煩,部署鏈路最簡單。

**方案二:跨域部署**。子應用部署在獨立域名時,`entry` 與 `VITE_PUBLIC_BASE` 填子應用的絕對 URL,並在託管平臺同時配兩件事:

// 以 vercel.json 为例，其他平台思路一致
{
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "Access-Control-Allow-Origin", "value": "*" },
        { "key": "Access-Control-Allow-Methods", "value": "GET, OPTIONS" },
        { "key": "Access-Control-Allow-Headers", "value": "Content-Type" }
      ]
    }
  ],
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

跨域方案裏**兩件事缺一不可**，少一件都會讓生產環境的某個邊界場景掛掉。能同源就別跨域。

第四部分：進階決策

17. 樣式隔離怎麼選

qiankun 的 sandbox 首先是 **JS 沙箱**；樣式隔離是 sandbox 裏的額外選項。不要把 start({ sandbox: true }) 理解成“已經開啓樣式隔離”——它只是開啓 JS 沙箱，CSS 仍然會在同一個頁面環境裏生效。

**決策樹**：

**爲什麼同棧共用設計系統場景通常不開樣式隔離**：

- 主題切換天然同步（``全局生效）

- CSS 變量共享，無需手動同步

- 減少 qiankun 改寫 CSS 的開銷

**但「不開隔離」有個必踩的坑：子應用的全局樣式會泄漏進外殼**。

不開 qiankun 樣式隔離 ≠ 子應用樣式不會污染主應用。子應用自己的 index.css 裏那些**頂層全局規則**——html / body / #root 的 reset、* { ... } 通配、:root { --background: ... } 整套色板——在 qiankun 模式下會**直接掛到主應用文檔上**，蓋掉 shell 的全局樣式。

真實項目的解法是兩層（配套模板已內置）：

- **作用域化**：子應用根節點包一層- `.subapp-root`，- `index.css`裏的基礎樣式全部限定在- `.subapp-root`內,不寫裸- `*`/- `body`。

/* index.css:始终加载,只作用于子应用自己的子树 */
.subapp-root, .subapp-root *, .subapp-root *::before, .subapp-root *::after {
  border-color: var(--border);
  outline-color: color-mix(in oklch, var(--ring) 50%, transparent);
}

- **全局樣式只在獨立運行時注入**:把- `html / body / :root`這類頂層全局樣式和完整色板抽到單獨的- `standalone.css`,由- `main.tsx`- **僅在獨立運行時**動態- `import`(見第 15 節- `bootstrapStandalone`)。qiankun 模式下這些由 shell 提供,子應用不再注入,自然不污染。

/* styles/standalone.css:仅 if (!isInShell()) 时动态 import */
html, body, #root { min-height: 100vh; }
body { background-color: var(--background); color: var(--foreground); }
:root { --background: oklch(1 0 0); --foreground: oklch(0.145 0 0); /* ...完整色板 */ }
.dark { --background: oklch(0.145 0 0); /* ... */ }

多個子應用共用一個 shell 時,把

.subapp-root改成各自唯一的類名,避免互相覆蓋。

**dev 和 prod 行爲差異（必須知道）** ：

dev 跑通 ≠ prod 跑通。這是後面"dev → preview → prod 三步法"（第 20 節）的根本原因。

18. 共享登錄態的三種方案

**決策樹**：

**推荐：方案 B**——`props` 透传 token getter（不是裸 token）。

// 主应用 register.ts
const subAppProps = {
  getAccessToken: async () => await authStore.getState().getToken(),
  getUser: async () => authStore.getState().user,
  onLogout: () => authStore.getState().logout(),
}
registerMicroApps(
  microApps.map((app) => ({
    ...app,
    container: '#subapp-viewport',
    props: subAppProps,
  })),
)

**爲什麼是 getter，不是裸 token**：

- token 會過期、會刷新，**每次取最新**纔不會用到舊值

- 函數引用穩定，token 字符串變了也不用重新 register

**子應用側統一 context 模塊**（避免 props 滿項目飛）：

update钩子也要setSubAppContext——qiankun 在某些重新激活场景会调update而不是mount。如果只在mount里赋值，update之后 token getter 会变成旧引用。

19. Vite 子应用的 publicPath 陷阱

**這是 Vite + qiankun 幾乎人人必踩的坑**，單獨成節講清。

**現象**：

dev 模式聯調通過，生產構建後控制檯報：

GET http://localhost:3000/assets/index-xxx.js  net::ERR_ABORTED 404
TypeError: Failed to fetch dynamically imported module
single-spa minified message #31

注意 URL：瀏覽器去**主應用 origin**（3000）取了**子應用的 JS chunk**。

**根因**：

Vite 生產產物裏的 import() 動態導入路徑是**根相對**的：

<!-- 子应用 dist/index.html -->
<script>import('/assets/index-xxx.js')</script>

被 qiankun 加载时，/assets/index-xxx.js 会以**当前文档 origin**（主应用）拼接成绝对 URL → 拼出来是主应用 origin → 404。

**解決方案**：把 `base` 設爲子應用的**絕對 URL**

// app-orders/vite.config.ts
export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '')
  const publicBase = env.VITE_PUBLIC_BASE || '/'
  return {
    base: publicBase,
    // ...
  }
})
# .env.local（本地 preview 时）
VITE_PUBLIC_BASE=http://localhost:4173/
# .env.production（部署时）
VITE_PUBLIC_BASE=https://app-orders.example.com/

末尾

必須帶斜槓，少一個斜槓路徑會拼錯。

這樣構建產物變成：

<script>import('http://localhost:4173/assets/index-xxx.js')</script>

完全絕對路徑，跟當前文檔 origin 無關。

**爲什麼 webpack 沒這個問題**：

webpack 有运行时变量 __webpack_public_path__，qiankun 注入 __INJECTED_PUBLIC_PATH_BY_QIANKUN__ 让子应用动态修改。Vite 没这套机制，只能在构建时硬编码 base。

結論：所有 Vite 子應用都必須用環境變量驅動base。同源部署時設爲同源路徑前綴(如/apps/orders/)即可——它本身就是“跟當前文檔 origin 無關的絕對路徑”,還順帶免了 CORS;跨域部署時才需要設成完整絕對 URL。兩種都記得末尾帶斜槓。

20. 部署纪律：dev → preview → prod

**爲什麼不能直接推生產**：

dev 和 prod 行爲差異大（見第 17 節 CSS 注入路徑、第 19 節 publicPath）。直接推生產等於把調試現場放到雲上——慢且貴。

**三步法**：

第 2 步是大多數人會跳過的，但它**必不可少**——publicPath、樣式隔離、CSS 注入路徑，這三個問題都在 prod 模式纔會顯形。

**新子應用接入驗收清單**：

- 子應用獨立運行 `pnpm dev`能正常訪問

- 子應用獨立運行 `pnpm preview`能正常訪問

- 主應用 dev + 子應用 dev，聯調能加載

- **主應用 dev + 子應用 preview，聯調能加載（關鍵！）**

- 切換主題，主子應用同步變色（如果有主題切換）

- 路由切換不報 `single-spa #31`錯誤

- 子應用刷新頁面不 404（SPA fallback 生效）

- 網絡面板裏所有 chunk 都從子應用 origin 加載
