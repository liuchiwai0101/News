生產級 AI：隱性故障、工程落地與智能體治理

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

在 InfoQ 近期舉辦的一場題為 《生產環境中的 AI：哪些會失效、哪些能正常運行，以及由誰審批上線？》 的網絡研討會上，一個由資深工程實踐者組成的小組深入剖析了部署智能體系統過程中遇到的各類現實難題。本次研討會由 Hien Luu 主持，嘉賓包括來自 ThoughtWorks 的 Zichuan Xiong 和 Prem Chandrasekaran 、隱私領域專家 Katharine Jarmul 以及金融 AI 從業者 Lan Chu 。

Luu 在開場時指出了三個核心驅動因素：AI 的失效模式與傳統軟件不同，它會生成看似合理但不準確的結果，而不是直接崩潰；編碼智能體生成生產代碼的速度已經超過了人類的代碼評審速度；敏感數據有了新的泄露途徑，包括提示詞、上下文窗口以及檢索到的文檔。

ThoughtWorks 託管服務 AI 運維負責人 Xiong 強調了 LLM 流水線中普遍存在的“語義漂移”問題。他描述了一個文本轉 SQL 的翻譯智能體如何頻繁地混淆特定領域的概念，例如將銷售領域和客服支持領域的“會員”視為同一概念，從而在下游業務分析中產生不易察覺的錯誤，而這些錯誤卻能繞過常規的鏈路追蹤檢測。

同樣，Chu 分享了一個由金融合規系統中的“嵌入漂移”引發的嚴重故障。在部署了一個基於向量相似度閾值來攔截違規投資建議的智能體後，底層嵌入模型的一次後台更新改變了向量距離分佈。這導致線上流量中的誤報和漏報率急劇飆升，而與此同時，所有基礎設施健康檢查卻完全顯示為綠色（正常）。

此外，Chandrasekaran 指出 RAG 流水線可能會在無意中檢索到敏感文檔，而 Jarmul 則提到模型本質上會記憶訓練數據，可能被用來去匿名化信息或泄露 API 密鑰。Chandrasekaran 還提到了 GitSpawn 漏洞，説明惡意倉庫配置能夠在執行常規命令時觸發未授權代碼運行。

隨着編碼助手生成的生產代碼數量日益龐大，傳統的人工代碼評審流程正面臨難以持續的瓶頸。ThoughtWorks 技術與商業服務負責人 Chandrasekaran 強調，逐行的人工代碼評審無法跟上高速發展的智能體產出。工程團隊必須在 CI/CD 流水線中實現戰術層面的風格和語法檢查自動化，人工審查只聚焦高層架構、業務意圖以及非功能性需求。

Xiong 補充説，團隊必須將工作“左移”，在拉取請求生成之前就在 harness 層面評估意圖。Chandrasekaran 還強調了 變異測試 的再度興起，認為這是一項關鍵實踐。通過引入刻意的代碼變異，團隊可以驗證自動化測試套件是否真正校驗了底層邏輯，而不只是單純滿足表面的代碼覆蓋率指標。

在評估智能體系統時，Chu 強調，評估體系應當作為長期持續運轉的基礎設施，而不是發佈前一成不變的檢查清單。有效的評估需要在 span 級別進行持續的在線追蹤、日誌過濾，並使用 LLM 對故障模式進行分類，從而使團隊能夠將生產環境中的邊緣案例反饋到離線基準測試套件中。

為了應對隱私和安全風險，Jarmul 警告不要依賴提示詞工程來進行系統防禦。她主張進行系統性的紅隊測試、持續的威脅建模、為自主智能體定義嚴格的功能範圍，並提升可觀測能力，以便處理更大的事件量。為了限制自主智能體行為的影響範圍，Chandrasekaran 建議將每個 AI 智能體都視為一名新入職的工程師來管理。

企業應當為智能體分配獨立的非人類身份，實施分級訪問控制，區分只讀操作與可回滾的寫入操作，對第三方 MCP 依賴項進行版本管理，並且把 API 密鑰嚴格隔離在沙箱內，脱離智能體運行環境。歸根結底，工程、安全、隱私團隊負責驗證安全防護機制，但部署審批仍是一項戰略性的業務決策。
