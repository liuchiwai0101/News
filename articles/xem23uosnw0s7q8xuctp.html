React Compiler 迁移 Rust：构建更快但社区担忧可维护性

www.infoq.cn· 8月15日 周六 · 查看原文 ↗
本文為原文轉錄（繁體中文，簡體已自動轉繁），版權歸原媒體所有；內容機器翻譯自第三方媒體，僅供參考，以原文為準。

React 是 Meta 開源的用戶界面構建庫，目前已將 React Compiler 的 Rust 移植版本合併到主代碼倉庫中。這一舉措旨在提升構建速度，並加強與更廣泛的基於 Rust 的 JavaScript 工具鏈之間的集成。

React Compiler 過去被稱爲 React Forget，它會自動爲組件和 Hooks 添加緩存優化，因此開發者不再需要手動調用 useMemo 和 useCallback。此次 Pull Request 將該編譯器從 TypeScript 重寫爲 Rust，團隊在 PR 中將其描述爲“一個實驗性的、正在開發中的移植版本”。

性能是此次改動最受關注的數據。作爲一個可直接替換的 Babel 插件，Rust 版本的運行速度大約比原 TypeScript 版本快 3 倍，而獨立的轉換邏輯在部分情況下最高可達到 10 倍提升，不過序列化開銷會拉低實際使用中的收益。根據 Rust Bytes Newsletter 的介紹，所有 1,725 個測試樣例均通過，中間狀態與 TypeScript 版本幾乎逐字節匹配。這一成果通過使用 arena 分配以及基於索引的數據結構重建內部實現而達成。

最明顯的收益出現在編譯器不再作爲插件運行之後。由於此前 React Compiler 是通過 Babel 轉換運行的，打包工具每次構建都會承擔這部分開銷；而將 Rust 版本直接集成到 Vercel 的 Rust 打包器 Turbopack 中，則可以消除這一成本。Vercel 工程師 Andrew Imm 表示，在使用公司自研的大規模 Next.js 應用 v0 進行測試時，這一改動帶來了超過 40% 的編譯速度提升。他指出，之前的 SWC 插件路徑受到了較長的 WebAssembly 冷啓動影響。

Next.js 官方賬號則表示，在其測試應用中，路由編譯速度提升範圍爲 20% 到 50%，實驗性支持將在 Next.js 16.3 中推出。

此次移植大量依賴大語言模型完成機械性工作，人類工程師則主要負責架構設計和代碼審查，這也成爲外界討論的焦點。在 Hacker News 上，一位讀者歡迎向編譯型語言遷移，但警告稱：“償還認知債務將會非常痛苦，無論最終哪個團隊長期維護這套代碼。”另一位用戶則將這一做法與類似的 Bun 項目進行了比較，同時也質疑了在此類項目中使用 LLM 的長期影響：

繼 Bun 之後，這是又一個通過大量使用 LLM 進行移植的高關注度項目。

非常好奇這些重寫最終會如何發展。

LLM 構建出來的基礎是否足夠可靠，可以在其上繼續構建和迭代？還是說，這會導致項目最終變得無法維護，因爲沒有人真正理解實現細節？

同一討論中的另一位用戶提醒說：“僅僅因爲某些東西是用 Rust 編寫的，並不意味着它就是優秀的 Rust。”因爲模型可能會爲了滿足借用檢查器的要求而選擇使用 RefCell，並將潛在問題推遲到運行時才暴露。

現有用戶基本不會受到此次變化的影響。公開 API 仍保持類似 Babel 的形式，因此升級目標是直接替換，保持現有配置不變：對於剛開始使用該編譯器的團隊，可以參考 React 的介紹文檔和漸進式採用指南，其中說明了如何排除不符合要求的代碼，因此整個代碼庫無需一次性完成修改。

這次重寫也符合 Rust 在前端工具領域持續擴張的趨勢。SWC 已遷移到官方 Rust 編譯器，Oxc 將其作爲可發佈的 crate 引入，而 Rspack 2.1 則提供了原生支持。不過，並非所有集成都順利完成；Rolldown 維護者 Boshen 表示，團隊已經撤回了其在 Rolldown 和 Vite 中的 Rust React Compiler 集成，以便先進行“去除垃圾化（de-slopify）”處理，儘管早期結果顯示性能最高提升可達 2 倍。

該 Rust 移植版本位於 React monorepo 中，可以通過 React Compiler 工作組持續跟蹤其進展。
