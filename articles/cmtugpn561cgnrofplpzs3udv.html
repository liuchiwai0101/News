Mistral 覆盤用 AI Agent 遷移 40000 行 Fortran 77 到 C++ 的經驗

內容機器翻譯自第三方媒體（Mistral AI：News（網頁）），僅供參考，以原文為準。

Mistral 幫助一家歐洲能源運營商將 40,000 行 Fortran 77 代碼遷移到 C++。瞭解這一過程是如何完成的，以及值得借鑑的經驗教訓。

遺留科學代碼庫歷經數十年不斷累積，當最初的作者離開後，代碼中藴含的知識便難以恢復。此外，使用沒有活躍開發者生態的語言，意味着錯失在他人工作成果之上繼續構建的機會。Mistral 幫助一家歐洲能源運營商將 40,000 行 Fortran 77 代碼遷移到 C++，這是一個物理計算密集型的油藏模擬器，沒有測試套件，也沒有集中式文檔。

在遺留代碼現代化中，超越單純的代碼翻譯。

將語法從一種語言翻譯到另一種語言，在很大程度上已是一個被解決的問題。讓任何近期發佈的模型將一段代碼從一種並非完全冷門的語言翻譯成另一種語言，通常只需幾次迭代就能收斂到可接受的結果。然而，將整個系統從過程式語言遷移到面向對象的 C++，會帶來架構重構的需求，這使得任務變得並不簡單。

Fortran 77 於 1977 年標準化，正如其名稱所示，用其編寫的代碼直接反映了當時的種種限制：沒有模塊、沒有命名空間、沒有結構化類型。狀態存儲在 COMMON 塊中——即整個程序共享的全局內存。變量根據首字母隱式確定類型，因此拼寫錯誤的名稱會靜默地創建一個新變量，而不是引發編譯器錯誤。

舉一個簡單但具有説明性的例子：下面是一階泰勒展開的一種實現。輸入和輸出是 COMMON 塊中的全局變量，IC 之所以是整數，僅僅是因為它的名字以 I 到 N 之間的字母開頭。變量名相當晦澀，因為其長度被限制在 6 個字符以內。

SUBROUTINE GASDEN INCLUDE 'common.h' DO 10 IC = 1, NCELL10 RHOG(IC) = ROG(IV) + DROG(IV)*(P(IC)-PTAB(IV)) END

在 C++ 中，開發者可以利用顯式類型、編寫面向對象的代碼，並通過返回值返回結果，而不是寫入全局變量：

double gasDensity(const GasProperties& gas, double pressure) { size_t i = lookup(gas.pressure, pressure); return gas.density[i] + gas.slope[i] * (pressure - gas.pressure[i]);}

分散的 COMMON 數組變成了一個單一的 GasProperties 參數，網格循環被移到了調用方，因此不存在逐行對應的關係可供核對——這正是驗證遷移工作困難的原因所在。

這些結構性差異，加上需要集成 PetSc 等現代科學計算框架的要求，在遷移開始之前就引發了一些重要問題：

  • 如何證明遷移後的代碼庫在數值上與舊代碼一致

  • 如何將遷移拆分成可管理的多個部分

  • 如何最好地利用自主智能體來加速這一過程

在遷移舊代碼之前構建一個對等性測試框架。

在放開智能體之前，我們需要一種方法來證明兩套代碼庫是一致的。這裏的“一致”指的是輸出在數值上完全相等——既包括最終結果，也包括油藏工程師在客户端標記的一組關鍵中間點。

我們增加了：

  • 用於導出 Fortran 代碼庫狀態的子程序

  • 一個用於將檢查點加載到 C++ 中的測試框架

  • Skill.md 文件，用於引導智能體正確使用這些工具

在遷移工作流中，智能體成功地對 Fortran 代碼庫進行了插樁以轉儲狀態快照，並使用 C++ 測試框架驗證了遷移模塊的正確性。

先構建這部分測試平台對項目來説是一項淨收益投資：它讓長時間的智能體運行更加安全，而且數值一致性是一個易於驗證且極具説服力的論據，能夠證明一段代碼已成功遷移。我們認為這應該是任何代碼現代化項目的首要步驟之一。

下面的示例説明瞭這一點。我們首先在 Fortran 代碼中插入了一行，用於轉儲 RHOG 變量的值（本次運行中為 42.71834），然後在測試遷移後的 C++ 模塊時，將該值用作參考檢查點。

使用 AI 智能體來理解和記錄遺留代碼庫。

該項目的文檔散落在舊版 PDF 和 Fortran 代碼中埋藏的註釋裏，而整個工作最大的附帶成果之一，就是將這些文檔整理對齊，並移到代碼旁邊。

幸運的是，像 Fortran 這樣的過程式代碼有一個便利特性：整個程序可以繪製成一棵單一的調用者-被調用者樹。我們通過自定義解析器解析代碼庫生成這棵樹，然後使用 Vibe CLI 派生出上百個智能體來為其編寫文檔。每個智能體都可以通過文檔庫和 Mistral OCR 拉取相關的 PDF。

從樹的葉子節點開始向上推進，每個節點都會派生一個子智能體來為其編寫文檔，並向原始倉庫發起一個 PR。一個審查智能體按 cron 計劃循環運行，查找新開的 PR，進行審查並在必要時安排修復任務。

利用 AI 智能體實現代碼現代化。

在第一次嘗試中，我們給了智能體完全的自主權：每個 Fortran 子程序對應一個智能體，各自在一週內獨立地將其函數翻譯成 C++。結果雖然可用，但稱不上代碼現代化。COMMON 塊變成了一對一的全局結構體。GOTO 驅動的控制流原封不動，沒有被重構為循環或提前返回。這看起來像是用 C++ 語法重打的 Fortran，而不是現代化的代碼。

第二次嘗試中，我們通過給智能體賦予結構而非僅僅自主性來解決這個問題：一個規劃者、一個編碼者、一個測試者和一個代碼質量審查者協同處理每個模塊。代碼質量相比第一次嘗試有了顯著提升。但源代碼的複雜度最終還是讓智能體難以招架。它們會遇到一個 bug，嘗試幾次修復後便停滯不前，而當時沒有人可以介入幹預。

我們最終找到了一個折中方案：由人類操作一個由編碼者、測試者和審查者智能體組成的工作流，逐模塊遷移代碼庫。這既保留了第二次嘗試的代碼質量，又增加了人工檢查點，以便在智能體卡住時為其解圍。下一節將詳細介紹這一工作流。

運行結構化的 AI 智能體工作流，以完成複雜的代碼遷移。

在代碼庫完成文檔化、對等性測試框架就緒之後，剩下的有趣部分就是調優：我們究竟能給智能體多大自主權，同時仍能產出可合併的代碼。我們嘗試了兩個極端，從完全自主運行到嚴密監督的人工會話。下面的結構化工作流就是我們針對這一用例最終確定的方案。

我們與客户的油藏工程師合作，利用調用者-被調用者關係樹來識別獨立模塊——即規模可控的自包含子樹（根據經驗，少於約 10,000 行 Fortran 代碼）。每個模塊都經過相同的工作流：

  1. 生成目標 C++ 架構。

  2. 與油藏工程師一起審查該架構。

  3. 獲批後，將其拆分為一個任務隊列。

  4. 為每個任務運行一個實現子工作流：規劃 → 實現 → 測試 → 重複。

  5. 由人類審查生成的 PR，並提出修改意見，直到合併為止。

認識到 AI 輔助遺留代碼現代化的侷限性。

第一個衝刺週期覆蓋了核心功能：30 萬行代碼中的 4 萬行。該 Fortran 代碼庫是自包含且可運行的，這是一個有利的起始條件。依賴外部系統、缺乏可運行基線或包含未在任何文檔中記錄的物理知識的遷移，會帶來本文未討論的額外挑戰。

應用三項原則來現代化複雜的遺留系統。

這個項目的三條經驗應該適用於任何大型遺留系統遷移。

  1. 在編寫遷移代碼之前先構建一致性測試框架——數值一致性是證明模塊已完成的最廉價、最有説服力的方式。

  2. 在依賴智能體之前先把文檔整理好，因為你無法遷移沒人能讀懂的代碼。

  3. 在這種規模下，帶有審查關卡的結構化工作流勝過完全自主和純手動操作。
