阶段 1：分析并优化 bundle（Phase 1: Analyze and optimize the bundle）

優化的第一步，是搞清楚你到底給用戶發了什麼。

在動代碼之前，先看 bundle，從中找出最值得優先優化的地方。

- 給構建加一個 bundle analyzer 來可視化包體：

- **Webpack**：- `webpack-bundle-analyzer`

- **Vite**：- `vite-bundle-analyzer`或- `rollup-plugin-visualizer`

- analyzer 會給你一個交互式的 treemap，告訴你哪些包/文件佔了最多空間。

你經常會發現：某個“大依賴”（通常是第三方庫）喫掉了很大一塊體積——這能立刻幫你明確“先優化誰”。

從這張圖可以看出：一些 node modules 佔了很大一部分體積，hero 圖片也不小。好消息是，我們的 src 目錄佔比很小。

优化构建（Optimizing build）

-

**確認生產環境啓用了 JS 和 CSS 的壓縮（minification）。**現代構建工具大多在 production 模式默認開啓，但你最好確認“真的有生效”。壓縮會移除空白、縮短變量名，並做其他轉換，顯著減少文件體積。

-

**開啓代碼分割（code splitting），按路由/功能把 bundle 拆成更小的 chunk。**與其把所有代碼打成一個巨大的 JS 文件，不如只給當前頁面發必需的代碼，其餘按需加載。 這個項目使用 TanStack Router，所以我們會按路由拆分。這樣後續就可以很容易對不常訪問的路由做懶加載導入。

原文示例（節選，按可讀性整理）：

// vite.config.ts
export default defineConfig({
	build: {
		outDir: "dist",
		emptyOutDir: true,
		sourcemap: true,
		minify: true,
		cssMinify: true,
		terserOptions: {
			compress: false,
			mangle: false,
		},
	},
	// ...
	// tanstackRouter({
	//   target: 'react',
	//   autoCodeSplitting: false,
	// }),
});

组件懒加载（Lazy load components）

當我們放大 bundle analyzer 裏 src/components 的區域，可能會發現：某些組件佔了不少體積。

這時就可以通過懶加載來優化：確保它們只在用戶真的導航到需要它們的頁面/路徑時纔會被 import。

// MovieList.tsx
import { lazy } from "react";
const MovieCard = lazy(() => import("@/components/MovieCard"));

阶段 2：优化 React 代码（Phase 2: Optimizing React code）

在 React Compiler 出現之前，你必須手工找出性能瓶頸，然後通過 useMemo / useCallback 等手段做記憶化（memoization）來優化組件。

但現代 React 開發已經有了 React Compiler，它可以自動處理大量性能優化。

除此之外，新的性能監控工具（例如自定義的 React Performance tracks）也讓“到底發生了什麼”更透明，你不必再靠猜測來判斷哪些組件渲染慢。

在開始優化之前，我們先看一下當前可用的工具。

1) React 19 Performance tracks

React 19 引入了自定義的 Performance tracks。它把性能分析能力直接集成進 Chrome DevTools 的 Performance 面板，讓你能定位真實的渲染瓶頸，而不是憑感覺猜哪個組件慢。

它會展示每個組件在 React 生命週期四個階段中分別花了多少時間：

- blocking

- transition

- suspense

- idling

trace（追蹤）能把“長任務（long tasks）”關聯回具體組件的工作和 hook 邏輯，從而快速隔離：昂貴的渲染路徑、不必要的重複計算、以及可避免的重複渲染。

2) React Compiler

React Compiler 改變了我們今天看待記憶化的方式。

在它出現之前，開發者往往需要手動：

- 用 `React.memo`包裹组件

- 用 `useMemo`/`useCallback`包裹回调或计算

來避免不必要的重新渲染。

這種方式容易出錯，而且需要你花大量精力判斷“到底哪些組件需要記憶化”。即便手工做了記憶化，也很容易漏掉真正慢的部分。

React Compiler 會作爲 Babel 插件接入構建流程，自動分析組件，並基於 Rules of React 施加記憶化。

它理解 React 的渲染行爲，能做出比手工優化更“聰明”的決定，在很多情況下甚至能超過人肉優化。

要開始使用它，先安裝 compiler 並把它加到 Babel 配置中：

npm install -D babel-plugin-react-compiler@latest

然後更新 Vite 配置（原文示例）：

// vite.config.js
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
export default defineConfig({
	plugins: [
		react({
			babel: {
				plugins: ["babel-plugin-react-compiler"],
			},
		}),
	],
});

現在，當你在 React Profiler 裏打開組件，會注意到：被 compiler 自動記憶化的組件旁邊會出現一個 ✨ 標記：

3) React Profiler

雖然它出現很久了，但仍然非常有用：你可以用它理解組件重渲染的次數，以及到底哪些組件在重渲染。

本文也會把它與 React Compiler、Performance tracks 一起用，來找到真正慢的組件。

改进点（Improvements）

#### 1) 让 React Compiler 负责记忆化

有了 React Compiler，你不必手动到处加 useMemo / useCallback。

它可以自動減少不必要的重渲染和重複計算，你就能把注意力放在“真正需要改的代碼問題”上。

#### 2) 清理 <code>useEffect</code>

useEffect 很容易導致不必要的重渲染。

能不寫就儘量不寫；必須寫時，確保 effect 正確清理，並且不會造成無限的 state update。

作者在另一篇文章裏更深入討論了最常見的 useEffect 錯誤：blog.logrocket.com/15-common-u… 。

#### 3) 清理函數定義

一個常見錯誤是：在組件函數體裏定義一些“其實不屬於這裏”的函數（比如純工具函數）。

問題在於：每次組件渲染，這些函數都會被重新創建——即便它們的實現根本不變。這會給 JS 引擎帶來不必要的工作。

把工具函數挪到組件外，或放到單獨的工具文件裏：

const formatRuntime = (minutes: number) => {
	const hours = Math.floor(minutes / 60);
	const mins = minutes % 60;
	return `${hours}h ${mins}m`;
};

#### 4) 懶加載組件

用戶一開始看不到的大組件，是懶加載的絕佳候選。

像視頻播放器、圖表、富文本編輯器這類組件，會讓初始 bundle 變大，即便大多數用戶從來不會用到它們。

React 通过 React.lazy + Suspense 让这件事很容易：

- 用 `React.lazy()`替代普通 import，讓組件只在需要時加載

- 用 ``包起来，在加载期间展示 fallback UI（比如 spinner / skeleton）

它和“按路由分割”的 code splitting 配合尤其好：只有用戶訪問某個頁面時才加載對應代碼。

import { lazy, Suspense } from "react";
const MovieCard = lazy(() => import("@/components/MovieCard"));

#### 5) 列表虚拟化（Virtualized lists）

渲染包含大量 DOM 節點的長列表，是非常常見的性能問題。

多數用戶甚至不會把列表滾到最底部，你卻爲看不見的內容做了很多渲染工作。

列表虛擬化的思路是：只渲染屏幕可見的部分（再加一點 buffer）。用戶滾動時，元素在 DOM 中被動態添加/移除——列表看起來完整，但性能更好。

像 react-window（更輕量）或 react-virtualized（功能更豐富）這樣的庫，可以很容易實現它。

你會看到：應用的重渲染次數下降了，峯值也變低了，最大一次渲染爲 13.1ms：

阶段 3：把工作移到服务端（SSR）（Phase 3: Moving to the server）

客戶端渲染（CSR） 往往會更慢，因爲用戶經常會在瀏覽器下載並執行 JS、再去請求數據期間，看到空白屏或 loading spinner。

這種延遲是 LCP 不佳的主要原因之一，會導致“元素渲染延遲（element render delay）”。

服務端渲染（SSR）通過在服務端先把數據取好、生成 HTML，再把頁面發給瀏覽器來解決這個問題。

用戶能立刻看到真實內容，而 JS 在後臺加載並 hydration。

采用框架（Adopting a framework）

你當然可以自己搭 SSR，但像 Next.js、Remix、或 TanStack Start 這樣的框架會讓事情更容易，也更適合生產環境。

TanStack Start 還支持 streaming SSR：服務端可以在生成 HTML 的同時就開始往瀏覽器發送，而不是等整頁渲染完再一次性返回。

遷移到框架通常意味着要改路由與數據獲取方式，但性能收益巨大。

你不只是在微調客戶端代碼，而是在改變頁面“何時、在哪裏”渲染：數據在組件渲染前就已經在服務端準備好，從而顯著降低 LCP。

Server functions

在 TanStack Start 中，你可以通過 server function 在服務端獲取數據。

本文把原本在客戶端 useEffect 中的數據請求遷到服務端，寫成 server function。

原文“前後對比”代碼（按可讀性整理）：

// Before: data-fetching in useEffect
useEffect(() => {
	async function fetchPopularMovies(const token = import.meta.env.VITE_TMDB_AUTH_TOKEN;
		if (!token) {
			setError("Missing TMDB_AUTH_TOKEN environment variable");
			setLoading(false);
			return;
		}
		setLoading(true);
		setError(null);
		try {
			const response = await fetch(API_URL, {
				headers: {
					accept: "application/json",
					Authorization: `Bearer ${token}`,
				},
			});
			if (!response.ok) {
				throw new Error(`Failed to fetch movies: ${response.statusText}`);
			}
			const data = (await response.json()) as TMDBResponse;
			setMovies(data.results);
		} catch (error) {
			setError((error as Error).message);
		} finally {
			setLoading(false);
		}
	}
	fetchPopularMovies();
}, []);
// After: Data-fetching in TanStack Start Server Function
export const getMovies = createServerFn({
	method: "GET",
}).handler(async () => {
	try {
		const response = await fetch(`${API_URL}/popular`, {
			headers: {
				accept: "application/json",
				Authorization: `Bearer ${token}`,
			},
		});
		if (!response.ok) {
			throw new Error(`Failed to fetch movies: ${response.statusText}`);
		}
		const movies = await response.json();
		return { movies };
	} catch (error) {
		const errorMessage = error instanceof Error ? error.message : "Unknown error occurred";
		throw new Error(`Movies fetch failed: ${errorMessage}`);
	}
});

阶段 4：静态资源与图片优化（Phase 4: Asset and image optimization）

圖片往往是拖慢 LCP 的最大因素。

下面是一些常用的優化圖片/視頻資源交付的技巧。

使用 CDN（CDN usage）

把本地的大資源（例如 hero 背景）搬到 CDN（如 Cloudinary、Cloudflare），減少你自己應用服務器的壓力。

很多 CDN 還能自動做圖片優化：對支持的瀏覽器下發 WebP/AVIF，併爲老瀏覽器回退到 JPEG/PNG。

把大資源放到 CDN 也會減少應用服務器負載，並降低 bundle 體積。

标记优先级（Priority tagging）

並不是所有圖片都同等重要。

瀏覽器無法自動判斷：哪些圖片對首屏至關重要，哪些在首屏之外或某些 Tab 裏用戶可能永遠不會打開。

你需要明確告訴瀏覽器：

- 對首屏關鍵圖片使用 `fetchpriority="high"`

- 對其餘圖片使用 `loading="lazy"`

原文示例（按可讀性整理）：

<!-- Hero banner 是最高优先级，因此 fetchPriority=high -->
<img
	src="https://res.cloudinary.com/dubc3wnbv/image/upload/v1760360925/hero-background_ksbmpq.jpg"
	fetchpriority="high"
	alt=""
/>
<!-- Movie Card 图片懒加载 -->
<img
	src={movie?.poster_path ? TMDB_IMAGES_ASSET_URL + movie?.poster_path : "/placeholder.svg"}
	alt={movie?.title}
	loading="lazy"
/>

预加载关键资源（Preloading critical resources）

現代框架（比如 TanStack Router）可以自動預加載路由。

例如用戶把鼠標懸停在鏈接上時，就可以提前加載下一頁的代碼和數據，等用戶真的點下去時，導航會顯得“瞬間完成”。

// router.tsx
const router = createTanStackRouter({
	routeTree,
	scrollRestoration: true,
	defaultPreload: "intent",
});

你也可以預加載重要的 CSS 和字體，讓它們立即開始下載，而不是等到之後才被瀏覽器“發現”。

這樣可以減少 layout shift，並避免未樣式化內容閃爍（FOUC）。

// __root.tsx
links: [
	{ rel: "preload", href: appCss, as: "style" },
];
