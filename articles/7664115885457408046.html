别再写 useMemo 了——2026 年这 5 个 React 性能优化已经是反模式

本文為原文轉錄（繁體中文，簡體已自動轉繁），版權歸原媒體所有；內容機器翻譯自第三方媒體，僅供參考，以原文為準。

打開任何一個AI輔助開發的React項目，你大概率會看到同樣的畫面：useMemo、useCallback、React.memo鋪天蓋地，彷彿不寫就會崩。

但2026年了，React Compiler已經正式落地。**你手動寫的那些"優化"，很多不但沒用，還在拖慢你的代碼。**

先說結論：爲什麼要改

React Compiler（隨React 19正式推出）做了一件事：**在編譯階段自動分析組件，在表達式級別做細粒度memoization。**

這意味着：你手寫的useMemo、useCallback、React.memo——編譯器都能自動做，而且做得更細、更準確。

手動寫的問題在於：

ESLint React v5.3已经加了 no-unnecessary-use-memo 和 no-unnecessary-use-callback 规则——**官方工具链都在告诉你别写了。**

下面逐個看5個已經變成反模式的"優化"。

反模式1：useMemo包裹所有計算

最常見的AI生成代碼模式：

function UserList({ users, filter }) {
  const filteredUsers = useMemo(() => {
    return users.filter(u => u.name.includes(filter));
  }, [users, filter]);
  const sortedUsers = useMemo(() => {
    return [...filteredUsers].sort((a, b) => a.name.localeCompare(b.name));
  }, [filteredUsers]);
  const stats = useMemo(() => ({
    total: sortedUsers.length,
    active: sortedUsers.filter(u => u.active).length,
  }), [sortedUsers]);
  return <div>{/* ... */}</div>;
}

**三個useMemo做了一件事：過濾+排序+統計。**

React Compiler會自動分析這段代碼的依賴關係，在users或filter沒變的時候跳過所有計算。你手寫三個useMemo，其實在做編譯器已經做了的事，同時還增加了：

- 三個依賴數組的維護成本

- 三個閉包的內存開銷

- 讓代碼可讀性下降一半

**2026年的寫法：**

function UserList({ users, filter }) {
  const sorted = users
    .filter(u => u.name.includes(filter))
    .sort((a, b) => a.name.localeCompare(b.name));
  const stats = {
    total: sorted.length,
    active: sorted.filter(u => u.active).length,
  };
  return <div>{/* ... */}</div>;
}

乾淨、直接、編譯器自動優化。

**唯一例外：** 如果你的計算確實很重（比如對10萬條數據做複雜聚合），並且你能用`React DevTools Profiler`證明它是瓶頸——那保留useMemo。但99%的場景不是這樣。

反模式2：useCallback包裹所有傳給子組件的函數

function Dashboard(const [count, setCount] = useState(0);
  const handleClick = useCallback(() => {
    setCount(c => c + 1);
  }, []);
  const handleReset = useCallback(() => {
    setCount(0);
  }, []);
  const handleExport = useCallback(() => {
    exportData(count);
  }, [count]);
  return (
    <>
      <Button onClick={handleClick} />
      <Button onClick={handleReset} />
      <ExportButton onClick={handleExport} />
    </>
  );
}

這段代碼有三個問題：

- **useCallback本身不阻止子組件重渲染**——除非子組件用了- `React.memo`

- 沒有React.memo的情況下，useCallback做的事就是"穩定引用"——但React Compiler已經能自動判斷哪些組件需要跳過

- `handleExport`的依賴數組裏有- `count`，每次count變化它都會重建——useCallback完全沒起作用

**更直接的問題是：AI工具特別愛生成useCallback。** 因爲訓練數據裏大量"React性能優化最佳實踐"文章都在教"傳給子組件的函數一定要useCallback"。這個建議在2023年可能有道理，在2026年就是噪音。

**2026年的寫法：**

function Dashboard(const [count, setCount] = useState(0);
  return (
    <>
      <Button onClick={() => setCount(c => c + 1)} />
      <Button onClick={() => setCount(0)} />
      <ExportButton onClick={() => exportData(count)} />
    </>
  );
}

反模式3：React.memo包裹每個導出組件

const UserCard = React.memo(function UserCard({ user, onSelect }) {
  return (
    <div onClick={() => onSelect(user.id)}>
      <Avatar src={user.avatar} />
      <span>{user.name}</span>
    </div>
  );
});

React.memo的邏輯是：props沒變就跳過渲染。問題是：

- **React Compiler已經在做同樣的事**，而且粒度更細——它可以跳過組件內部的部分表達式，不需要跳過整個組件

- React.memo**每次渲染都要做props淺比較**——如果props經常變，這個比較本身就是白白浪費

- **和useCallback配套纔有意義**——但如果你已經不寫useCallback了，React.memo也沒必要了

**一條很好判斷的規則：** 如果你的組件渲染成本低於props淺比較成本（大部分簡單組件都是這樣），React.memo就是負優化。

**2026年的寫法：** 直接導出，不包裹。

function UserCard({ user, onSelect }) {
  return (
    <div onClick={() => onSelect(user.id)}>
      <Avatar src={user.avatar} />
      <span>{user.name}</span>
    </div>
  );
}

反模式4：useEffect + useState做數據獲取

這可能是最根深蒂固的反模式，也是AI生成代碼最愛寫的模式：

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);
  useEffect(() => {
    let cancelled = false;
    setLoading(true);
    
    fetchUser(userId)
      .then(data => {
        if (!cancelled) {
          setUser(data);
          setLoading(false);
        }
      })
      .catch(err => {
        if (!cancelled) {
          setError(err);
          setLoading(false);
        }
      });
    
    return () => { cancelled = true; };
  }, [userId]);
  if (loading) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;
  return <div>{user.name}</div>;
}

**25行代碼做一件事：獲取數據。** 而且還有這些隱患：

**2026年的写法（用TanStack Query）：**

function UserProfile({ userId }) {
  const { data: user, isPending, error } = useQuery({
    queryKey: ['user', userId],
    queryFn: () => fetchUser(userId),
  });
  if (isPending) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;
  return <div>{user.name}</div>;
}

或者用React 19的use：

function UserProfile({ userPromise }) {
  const user = use(userPromise);
  return <div>{user.name}</div>;
}

**從25行到3行。** 自動處理競態、緩存、去重、後臺刷新。

**這不是風格偏好，是架構級的差距。** useEffect做數據獲取在React官方文檔裏已經被標註爲不推薦。

反模式5：過度拆分組件"優化性能"

我見過的一個極端案例：一個表單頁面被拆成了47個組件——每個輸入框一個組件、每個標籤一個組件、每個校驗提示一個組件。理由是"避免整個表單重渲染"。

**這是對React渲染機制的誤解。**

組件拆分不等於性能優化。每多一個組件，React就多了：

- 一次reconciliation比较

- 一個Fiber節點

- 一次props序列化和比較

**合理的拆分標準應該是：**

**真正該做的性能優化是狀態下沉（state co-location）：** 把state放到真正需要它的組件裏，而不是提升到父組件然後靠拆分來避免重渲染。

// ❌ 状态提升 + 过度拆分
function Form(const [name, setName] = useState('');
  const [email, setEmail] = useState('');
  return (
    <>
      <NameInput value={name} onChange={setName} />
      <EmailInput value={email} onChange={setEmail} />
    </>
  );
}
// ✅ 状态下沉，各管各的
function Form(return (
    <>
      <NameInput />
      <EmailInput />
    </>
  );
}
function NameInput(const [name, setName] = useState('');
  return <input value={name} onChange={e => setName(e.target.value)} />;
}

速查表：2026年React性能優化決策

**判斷標準就一條：先用React DevTools Profiler跑一遍。沒有證據證明是瓶頸的，就別優化。**

升級React Compiler的最小步驟

如果你的項目還沒啓用React Compiler：

npm install react-compiler-runtime
npm install -D babel-plugin-react-compiler

Babel配置加一行：

{
  "plugins": [
    ["babel-plugin-react-compiler", {}]
  ]
}

Vite用戶：

// vite.config.js
import { reactCompiler } from 'react-compiler-runtime/vite';
export default {
  plugins: [reactCompiler()],
};

啓用後，可以逐步刪掉不必要的useMemo/useCallback/React.memo。不用一次性全刪——編譯器和手動優化可以共存，只是手動的部分變成了冗餘代碼。

別讓AI替你做決定

這篇文章本質上在說一件事：**不要因爲AI生成了useMemo，你就不敢刪它。**

AI代碼生成器的訓練數據裏充滿了2020-2024年的"最佳實踐"文章。那些文章在當時是對的——React沒有編譯器，手動memoization是唯一選擇。但2026年了，工具變了，實踐也要變。

用AI寫代碼沒問題。但Review的時候，你需要知道什麼該留、什麼該刪。
