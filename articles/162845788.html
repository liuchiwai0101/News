我們產品裏有一個"結構化信息提取"模塊：用戶上傳一段非結構化文本（合同片段、招聘需求、商品描述等），模型需要提取出指定字段並以 JSON 返回。聽起來簡單，但實際跑起來合格率只有 61%——格式錯誤、字段遺漏、類型混亂，各種問題。

排查後發現不是模型能力問題，是 Prompt 設計問題。接下來兩週我做了 10 輪迭代實驗，把合格率拉到 94%。這篇文章是實驗過程的完整記錄，包括每一輪的假設、改法、數據和反思。

實驗設置

**任務**：從非結構化文本中提取結構化字段，返回嚴格 JSON。

**評測集**：500 條標註數據，覆蓋合同、招聘、商品三個場景。合格標準 = JSON 可解析 + 所有必填字段存在 + 字段類型正確 + 值與標註一致。

**模型**：主力用 GPT-5.6 Terra（均衡型，速度和效果折中），關鍵場景對比 Claude Fable 5 和 GPT-5.6 Sol。通過魔芋AI（moyu.info）調用，它同時支持 GPT 和 Claude 全系，換模型只改一個參數，省得維護多套 SDK。

**控制變量**：每輪只改 Prompt 的一處，其他不變，跑完 500 條再統計。

**Prompt v0**（最初版本）：

實驗 6：字段說明細化 + 約束邊界

**假設**：部分字段類型錯誤是因爲描述太模糊。

**改動**：每個字段加更詳細的約束說明。

需要提取的字段：
- title: 字符串，合同/文件的標題或類型名稱，如"採購合同""租賃合同"
- amount: 數字，金額數值，只保留數字不要單位（58000元→58000）
- party_a: 字符串，甲方全稱，如文本中無甲方則填null
- party_b: 字符串，乙方全稱，如文本中無乙方則填null
- date: 字符串，日期，格式YYYY-MM-DD，如"2024年3月15日"→"2024-03-15"
        如文本中無日期則填null

**结果**：合格率 89.0%（+1.7%）

**反思**：提升幅度變小了，說明 Prompt 文本層面的優化接近天花板。但"只保留數字不要單位"這條消除了 amount 字段大量的類型錯誤。

**假設**：GPT-5.6 Terra 可能不是這個任務的最優模型。

**改動**：同一 Prompt 在三個模型上跑完整 500 條評測集。

實驗 9：添加錯誤處理指令

**假設**：模型遇到信息缺失時行爲不確定，導致類型錯誤。

**改動**：明確告訴模型遇到缺失字段怎麼處理。

特殊情況處理：
1. 如某字段在文本中找不到，該字段值填null，不要編造
2. 如日期格式不完整（如只有"2024年3月"），date填"2024-03-01"，取該月第一天
3. 如金額有多種表述（如"約5萬"），amount取最接近的整數（50000）
4. 如甲方或乙方有多個，只取第一個

**结果**：合格率 92.7%（+3.3%）

**反思**：這輪提升超出預期。之前很多"類型錯誤"本質是模型遇到邊界情況時的行爲不確定——它不知道該怎麼辦就隨便編一個。明確邊界行爲後，錯誤率大幅下降。

實驗 10：自驗證機制

**假設**：模型輸出後不檢查，錯誤直接流出。

**改動**：在 Prompt 末尾加一句自驗證指令。

輸出前請自行檢查：
1. 所有必填字段是否都存在
2. amount是否爲純數字
3. date是否爲YYYY-MM-DD格式
4. party_a和party_b是否爲字符串或null
如不符合，請修正後再輸出。

同時代碼層面加一道後校驗：

import json
from datetime import datetime
REQUIRED_FIELDS = ["title", "amount", "party_a", "party_b", "date"]
def validate_extraction(result: str) -> tuple[bool, str]:
    """提取结果后校验"""
    try:
        data = json.loads(result)
    except json.JSONDecodeError:
        return False, "JSON解析失败"
    
    # 必填字段检查
    for field in REQUIRED_FIELDS:
        if field not in data:
            return False, f"缺失字段: {field}"
    
    # 类型检查
    if not isinstance(data["amount"], (int, float)):
        return False, "amount不是数字"
    
    # 日期格式检查
    if data["date"] is not None:
        try:
            datetime.strptime(data["date"], "%Y-%m-%d")
        except ValueError:
            return False, "date格式错误"
    
    return True, "ok"

彙總：10 輪迭代數據

經驗總結

**1. 先看錯誤分佈，再定優化方向。** 不要盲目改 Prompt，先把 500 條跑一遍，統計錯誤類型佔比。我們的前 3 輪改的都是"JSON 不可解析"，因爲它佔比最大。等它降到 0 再攻下一個。

**2. API 參數比 Prompt 文字有效。** `response_format` 比寫 10 遍"只輸出JSON"都管用。能用 API 層面解決的別靠 Prompt。

**3. few-shot 對齊的是粒度不是格式。** 給示例不是教模型寫 JSON，而是告訴它"金額取數字還是帶單位""日期怎麼格式化"這種提取粒度問題。

**4. 邊界行爲要顯式聲明。** 模型遇到信息缺失時的默認行爲不可預測，必須在 Prompt 裏寫清楚"找不到填null"。這單獨一步漲了 3.3%。

**5. 不要只靠模型，加代碼校驗。** Prompt 內自驗證 + 代碼層後校驗 + 自動重試，三道防線缺一不可。模型永遠有翻車的時候，代碼兜底是最後一道保險。

**6. 模型選型要分場景。** 我們的最終方案是高價值任務用 Claude Fable 5，普通任務用 GPT-5.6 Terra，通過魔芋AI統一調用。選 Terra 而不是 Sol 是因爲信息提取不需要旗艦級推理能力，Terra 的均衡性正好匹配，成本只有 Sol 的三分之一。如果預算敏感，還可以把低優先級任務切到 DeepSeek V4-Flash，合格率會降幾個點但成本降一個數量級。
