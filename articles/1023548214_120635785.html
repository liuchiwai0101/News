**導讀**

過去一年，很多人都在聊 Agent。

會寫代碼的 Agent、會操作瀏覽器的 Agent、會調用工具的 Agent、會自動執行任務的 Agent，聽起來都很強。

但真正落地時，問題也很明顯：

同一個任務，每次都要重新解釋一遍流程。 同一套經驗，不同 Agent 之間很難複用。 同一個項目，換個工具、換個模型，之前沉澱的規則就失效了。 一個團隊內部積累的操作規範、測試流程、排查經驗，很難變成 Agent 穩定可調用的能力。

所以，Agent 真正缺的可能不是更大的模型，而是一套能把“經驗”封裝起來的標準。

這也是 Agent Skills 這個開放標準值得關注的原因。

Agent Skills 是一個輕量級、通用、模型無關的 AI Agent 技能開放格式。它的核心不是再造一個複雜框架，而是用一個簡單的目錄和一個 SKILL.md 文件，把某類任務的流程、規則、腳本、模板和參考資料封裝成一個可複用的技能包。官方規範中，一個 Skill 至少包含 SKILL.md，並可選包含 scripts/、references/、assets/ 等目錄。(**Agent Skills****[1]**)

對於測試開發、自動化測試、AI 測試平臺、企業內部 Agent 落地來說，這件事非常關鍵。

因爲它意味着： 我們可以把測試用例評審、接口自動化生成、日誌分析、故障排查、報告生成、RAG 測評、UI 自動化腳本規範，逐步封裝成 Agent 可以穩定調用的技能。

這可能是 Agent 從“聰明的聊天助手”走向“可靠的工程協作者”的關鍵一步。

**一、爲什麼 Agent 需要 Skill 標準**

很多團隊在使用 AI Agent 時，最開始都會經歷一個階段：

感覺什麼都能做。 寫代碼可以，生成測試用例可以，分析日誌可以，寫報告也可以。

但用久了之後，問題就來了。

你會發現 Agent 的表現非常依賴上下文。

你告訴它“按照我們公司的測試規範寫用例”，它可能並不知道規範是什麼。 你告訴它“按照我們項目接口風格生成 Pytest 腳本”，它可能不知道你們的斷言規範、目錄結構和公共方法。 你讓它“幫我審覈測試用例”，它可能只會泛泛地說覆蓋率不足、邊界值不足，而不是按照你們真實評審會的標準逐條檢查。

這就是 Agent 落地最大的矛盾：

模型越來越強，但組織內部的經驗沒有被結構化封裝。

過去我們靠人傳人。 師傅帶徒弟，組長講規範，評審會上反覆糾正。

到了 Agent 時代，這些經驗不能只停留在人的腦子裏，而應該沉澱成 Agent 可讀取、可執行、可複用的技能。

Agent Skills 解決的就是這個問題。

它不是教模型變聰明，而是把“怎麼做某類任務”變成標準化資產。

**二、Agent Skills 到底解決了什麼問題**

Agent Skills 可以理解爲：

給 AI Agent 使用的“技能說明書 + 工具包 + 參考資料 + 執行腳本”。

它重點解決四類問題。

**1. 可複用性**

以前你每次都要在 Prompt 裏寫：

請按照以下規則生成測試用例…… 請參考以下接口規範…… 請輸出 Markdown 表格…… 請不要遺漏邊界值、異常流、權限控制……

這些內容一旦變成 Skill，就不需要每次重複輸入。

Agent 只要識別到任務匹配，就可以加載對應 Skill。

例如：

用戶說：“幫我審覈一下這份測試用例。” Agent 自動觸發 test-case-review Skill。 然後按照固定標準檢查字段完整性、步驟連貫性、邊界覆蓋、異常流、預期結果、可執行性。

這就把一次性的 Prompt，變成了可長期複用的能力模塊。

**2. 可分享性**

一個好的測試用例審覈 Skill，不應該只在一個人的電腦裏有用。

它應該可以被團隊共享。 可以進入代碼倉庫。 可以版本管理。 可以評審。 可以迭代。 可以在多個 Agent 工具之間遷移。

Agent Skills 採用純文本文件組織，非常適合 Git 管理。官方也強調，Skills 可以把專業知識、流程和團隊上下文打包成可版本控制、按需加載的目錄。(**Agent Skills****[2]**)

這對企業內部非常重要。

因爲很多 AI 落地失敗，不是因爲模型不強，而是因爲企業內部知識沒有被工程化管理。

**3. 上下文效率**

Agent 最大的成本之一是上下文。

如果每個任務都把所有規範、所有文檔、所有工具說明一次性塞進去，模型很快就會被大量無關信息淹沒。

Agent Skills 的核心設計是“漸進式披露”。

也就是：

先加載最少的信息，用來判斷要不要觸發技能。 觸發後再加載主要操作說明。 真正需要時，再讀取更詳細的參考資料、模板或腳本。

官方文檔把這個過程分成 Discovery、Activation、Execution 三個階段：啓動時只加載名稱和描述，任務匹配後加載完整 SKILL.md，執行時再按需使用腳本、模板和參考文件。(**Agent Skills****[3]**)

這非常符合真實工程場景。

因爲一個成熟團隊可能會有幾十個甚至上百個技能，但每次任務只需要其中一兩個。

**4. 執行可靠性**

只靠自然語言 Prompt，Agent 很容易“理解對了，但執行偏了”。

比如你讓它生成接口自動化腳本，它可能每次目錄結構不同、斷言方式不同、命名風格不同。

如果 Skill 裏明確寫好：

使用 Pytest 請求層統一走 api_client.py斷言必須包含狀態碼、業務碼、核心字段 測試數據放在 data/禁止在用例中硬編碼 Token 生成後必須運行格式檢查和單測

Agent 的執行穩定性就會明顯提高。

這就是 Skill 的價值：

不是讓 Agent 自由發揮，而是讓 Agent 在清晰邊界內工作。

**三、一個 Skill 的標準結構是什麼**

按照 Agent Skills 的規範，一個技能本質上就是一個目錄。

典型結構如下：

test-case-review/

├── SKILL.md

├── scripts/

│ └── validate_cases.py

├── references/

│ ├── review-rules.md

│ └── boundary-checklist.md

├── assets/

│ └── output-template.md

其中只有 SKILL.md 是必需的。

其他目錄都是可選的。

**1. SKILL.md**

這是技能的入口文件。

它包含兩部分：

第一部分是 YAML 前置元數據。 第二部分是 Markdown 指令主體。

Agent 會先讀取元數據，判斷這個 Skill 是否適合當前任務。

任務匹配後，再讀取 Markdown 主體，按照裏面的步驟執行。

**2. scripts/**

這個目錄用於存放可執行腳本。

例如：

測試用例格式校驗腳本 接口文檔解析腳本 日誌清洗腳本 性能數據統計腳本 Markdown 報告生成腳本 Excel 轉換腳本

當一個任務裏有固定、重複、容易出錯的處理邏輯時，就不應該每次都讓 Agent 現場寫代碼。

更好的方式是把腳本沉澱到 scripts/ 中，讓 Agent 直接調用。

**3. references/**

這個目錄用於存放詳細參考資料。

例如：

測試用例評審規則 接口錯誤碼說明 數據庫表結構說明 業務狀態機說明 質量准入標準 團隊代碼規範 發佈流程說明

這些內容不一定每次都需要加載。

只有當 Agent 遇到相關問題時，再按需讀取。

這就是漸進式披露的核心思想。

**4. assets/**

這個目錄用於放模板、示例、圖片、配置文件等靜態資源。

例如：

測試報告模板 缺陷分析模板 用例評審輸出模板 性能壓測報告模板 接口自動化項目模板 數據清洗配置模板

對於輸出格式要求很強的任務，assets/ 非常有用。

因爲“給模板”通常比“用語言描述格式”更穩定。

**四、SKILL.md 爲什麼是整個標準的核心**

SKILL.md 是 Agent Skills 的灵魂。

一個技能能不能被正確觸發，主要看 description。 一個技能能不能穩定執行，主要看 Markdown 指令主體。 一個技能能不能長期維護，主要看它是否足夠清晰、剋制、可驗證。

一個典型的 SKILL.md 可以這樣寫：

name: test-case-review

description: Use this skill when reviewing software test cases, checking case completeness, boundary coverage, step consistency, expected results, exception scenarios, and execution feasibility. Use it when the user asks to review, optimize, audit, improve, or validate test cases, even if they do not explicitly mention "test case review".

license: MIT

compatibility: Python 3.10+, Markdown input, optional Excel parsing

metadata:

author: QA Team

version: "1.0"

Test Case Review Skill

When to use

Use this skill when the user provides test cases and wants review, optimization, scoring, rewriting, or coverage analysis.

Workflow

1. Identify the business module and test objective.

2. Check whether each case has clear preconditions, steps, data, and expected results.

3. Review normal flow, exception flow, boundary values, permissions, data consistency, and concurrency scenarios.

4. Mark vague, duplicated, unexecutable, or low-value cases.

5. Output review comments and optimized examples.

Output format

Case ID | Problem | Risk | Suggestion | Optimized Version |

---|---|---|---|---|

Gotchas

- Do not only give general advice.

- Do not ignore expected results.

- Do not treat UI interaction steps as business verification points.

- Do not add unrealistic scenarios that cannot be executed.

這個文件看起來並不複雜，但它解決了三個關鍵問題：

什麼時候用。 怎麼執行。 輸出成什麼樣。

這就是 Agent Skill 和普通 Prompt 最大的區別。

普通 Prompt 是一次性的。 Skill 是可沉澱、可複用、可驗證的。

**五、漸進式披露：Agent Skills 最重要的設計**

Agent Skills 最值得關注的設計，不是目錄結構，而是漸進式披露。

簡單說，就是不要一開始把所有信息都塞給模型。

而是分層加載。

**第一層：元數據層**

只加载 name 和 description。

這部分非常短，通常只有幾十到一百多個 token。

作用只有一個：

判斷當前任務是否需要這個技能。

例如：

name: api-test-generator

description:UsethisskillwhengeneratingAPItestcasesorPytestautomationscriptsfromSwagger,OpenAPI,Postmancollections,orinterfacedocumentation.

Agent 看到用戶說：

“幫我根據 Swagger 生成接口自動化用例。”

就能判斷這個 Skill 可能有用。

**第二層：指令層**

當 Skill 被激活後，Agent 纔讀取完整的 SKILL.md。

這裏可以包含：

任務目標 執行步驟 輸入輸出要求 異常處理 注意事項 示例 驗證方式

官方建議將主要說明控制在合理範圍內，並把詳細資料放到 references/ 中。規範中也明確建議 SKILL.md 主體保持在 500 行以內，詳細參考材料拆到獨立文件。(**Agent Skills****[4]**)

這非常重要。

因爲 Skill 不是文檔倉庫。

它應該像一個“任務操作手冊”，而不是一本百科全書。

**第三層：資源層**

只有在需要時，Agent 才加載：

腳本 模板 詳細規範 示例文件 錯誤碼說明 項目配置

例如：

用戶只是讓 Agent 粗略評審測試用例，就不需要加載完整企業級測試規範。

但如果用戶問：

“這個預期結果爲什麼不合格？”

Agent 就可以读取 references/review-rules.md。

如果用戶要求：

“幫我生成最終評審報告。”

Agent 再读取 assets/review-report-template.md。

這樣做的好處是：

上下文更省。 觸發更精準。 執行更穩定。 維護也更清晰。

**六、Agent Skills 和 MCP 有什么区别**

很多人看到 Agent Skills，第一反應是：

這和 MCP 有什麼區別？

這個問題非常關鍵。

簡單理解：

MCP 更像是 Agent 連接外部工具和數據源的協議。 Agent Skills 更像是 Agent 執行某類任務的方法包。

MCP 解決的是“能調用什麼”。 Skills 解決的是“怎麼把事情做好”。

舉個例子。

如果你希望 Agent 能訪問數據庫、調用瀏覽器、讀取 GitHub、操作 Jira，那麼 MCP 很合適。

但如果你希望 Agent 知道：

查詢用戶表時必須過濾軟刪除數據 生成測試報告必須包含風險等級 接口自動化腳本必須複用公司封裝的請求方法 缺陷分析必須先看日誌再看鏈路追蹤 生產數據庫只允許只讀查詢

這些就更適合放在 Skill 裏。

兩者不是替代關係，而是互補關係。

一個成熟的 Agent 工程體系，大概率會是：

MCP 負責連接工具。 Skills 負責封裝流程。 RAG 負責補充知識。 Agent 負責理解目標、規劃步驟和執行任務。

可以用一張圖理解：

用戶任務

↓

Agent 理解意圖

↓

匹配 Skill

↓

讀取任務流程 / 規則 / 模板

↓

通過 MCP 調用工具

↓

執行腳本 / 查詢數據 / 生成結果

↓

驗證輸出

↓

返回結果

所以，MCP 讓 Agent 有手有腳。 Agent Skills 讓 Agent 知道應該怎麼幹活。

**七、測試開發團隊可以怎麼用 Agent Skills**

對於測試開發團隊來說，Agent Skills 的價值非常直接。

因爲測試團隊有大量標準化、流程化、可複用的工作。

這些工作過去靠文檔、培訓、評審和經驗傳遞。

現在可以逐步沉澱成 Skill。

**1. 測試用例生成 Skill**

適用場景：

根據需求文檔生成測試點 根據 PRD 生成測試用例 根據頁面截圖生成 UI 測試點 根據用戶故事補充異常流 根據狀態機補全業務路徑

Skill 中可以定義：

用例字段標準 功能流分析方法 邊界值設計規則 異常場景清單 權限場景清單 輸出模板 評審檢查項

**2. 測試用例審覈 Skill**

適用場景：

審覈已有測試用例 檢查用例是否可執行 檢查預期結果是否明確 檢查是否遺漏邊界值 檢查異常流和權限場景 檢查用例是否重複或低價值

這類 Skill 很適合測試團隊內部推廣。

因爲測試用例評審是高頻任務，而且不同組長的評審標準經常不一致。

把評審經驗沉澱成 Skill，可以大幅提升團隊一致性。

**3. 接口自動化生成 Skill**

適用場景：

根據 Swagger 生成接口用例 根據 OpenAPI 生成 Pytest 腳本 根據接口文檔補充斷言 生成請求參數組合 生成異常參數測試 生成接口自動化項目結構

Skill 中可以明確：

目錄結構 命名規範 公共請求方法 認證方式 斷言標準 數據驅動格式 失敗重試策略 報告生成方式

**4. UI 自动化生成 Skill**

適用場景：

根據頁面結構生成 Playwright 腳本 根據業務流程生成 Selenium 腳本 根據頁面元素生成 POM 對象 補充等待策略和斷言 優化定位器穩定性

Skill 中可以寫清楚：

優先使用哪類定位方式 禁止使用脆弱 XPath 如何處理異步加載 如何封裝 Page Object 如何設計斷言 如何處理失敗截圖和日誌

**5. 缺陷分析 Skill**

適用場景：

分析 Bug 根因 整理缺陷覆盤 根據日誌判斷問題鏈路 從錯誤堆棧提取關鍵信息 輸出開發可讀的缺陷描述

Skill 中可以定義：

先看現象，再看影響範圍 先確認環境，再確認數據 先定位入口，再定位調用鏈 輸出必須包含復現步驟、實際結果、期望結果、影響範圍、初步判斷 禁止直接給結論，必須標明證據來源

**6. 性能測試分析 Skill**

適用場景：

分析壓測結果 定位吞吐瓶頸 分析響應時間分佈 識別錯誤率變化 生成性能測試報告 給出容量評估建議

Skill 中可以封裝：

TPS、RT、P95、P99、錯誤率分析方法 應用、數據庫、中間件、網絡層排查路徑 壓測數據清洗腳本 報告模板 容量預估模型

**7. AI 系统测评 Skill**

適用場景：

測評大模型輸出質量 測評 RAG 問答準確性 測評智能體任務完成率 測評多模態識別效果 分析幻覺、拒答、魯棒性、安全性

這對 AI 測試開發尤其重要。

因爲 AI 系統測試不是簡單點點頁面，而是要圍繞準確性、一致性、魯棒性、可解釋性、延遲、成本、安全邊界等指標做系統評估。

這些規則非常適合 Skill 化。

**八、一個測試用例審覈 Skill 應該怎麼設計**

如果我們要給測試團隊做一個 test-case-review Skill，可以按下面這個思路設計。

**1. description 要写准**

很多 Skill 失敗，不是因爲指令寫得不好，而是因爲 description 寫得太差。

比如：

description: Review test cases.

這個描述太弱了。

Agent 很難判斷什麼時候該觸發。

更好的寫法是：

description: Usethisskillwhenreviewing,auditing,scoring,optimizing,orrewritingsoftwaretestcases.Checkcompleteness,stepconsistency,inputdata,expectedresults,boundaryvalues,exceptionflows,permissions,dataconsistency,concurrencyrisks,andexecutionfeasibility.Useitwhenevertheuserprovidestestcasesandasksforrevieworimprovement,eveniftheydonotexplicitlysay"test case review".

這個描述包含三類信息：

技能做什麼。 什麼時候使用。 哪些間接表達也要觸發。

這比簡單寫“審覈測試用例”可靠得多。

**2. 指令主體要像評審清單**

測試用例審覈不是讓 Agent 自由點評，而是要讓它按照固定維度檢查。

可以設計成這樣：

Review Checklist

- [ ] 是否有明確測試目標

- [ ] 是否有前置條件

- [ ] 是否有測試數據

- [ ] 操作步驟是否連續

- [ ] 預期結果是否可驗證

- [ ] 是否覆蓋正常流

- [ ] 是否覆蓋異常流

- [ ] 是否覆蓋邊界值

- [ ] 是否覆蓋權限場景

- [ ] 是否覆蓋數據一致性

- [ ] 是否存在重複用例

- [ ] 是否存在無法執行的用例

- [ ] 是否存在描述模糊的步驟

清單比長篇描述更適合 Agent 執行。

因爲它能降低遺漏概率。

**3. 一定要写 Gotchas**

Gotchas 是 Skill 裏最值錢的部分。

因爲它記錄的是 Agent 最容易犯錯的地方。

例如：

Gotchas

- 不要只給“覆蓋不足”這類泛泛建議，必須指出具體缺失場景。

- 不要把“頁面展示正確”當成唯一預期結果，必須補充業務狀態、數據變化或接口返回。

- 不要只檢查正常流程，必須檢查異常流、邊界值和權限控制。

- 不要生成無法執行的用例，例如依賴不存在的數據或無法構造的狀態。

- 不要忽略併發、重複提交、冪等性和數據一致性問題。

- 如果用例步驟跳躍，必須指出缺失步驟。

- 如果預期結果不可觀察，必須要求補充可驗證依據。

這部分比“請認真審覈”有用得多。

因爲它把經驗裏的坑直接寫出來了。

**4. 輸出格式必須固定**

輸出格式越明確，結果越穩定。

例如：

Output Format

總體結論

- 完整性評分：

- 可執行性評分：

- 風險覆蓋評分：

- 主要問題：

詳細評審

用例編號 | 問題類型 | 當前問題 | 風險影響 | 修改建議 | 優化示例 |

---|---|---|---|---|---|

遺漏場景補充

場景類型 | 建議補充用例 | 設計原因 |

---|---|---|

最終建議

用 3-5 條總結該用例集下一步如何優化。

這樣輸出之後，測試組長可以直接拿去評審，測試同學也能按表修改。

**5. 驗證循環要寫進去**

一個好的 Skill 不應該只讓 Agent 生成結果，還要讓 Agent 自查。

例如：

Validation

Before final response:

1. Check whether every issue has a specific case reference.

2. Check whether every suggestion is executable.

3. Check whether expected results are observable.

4. Check whether missing scenarios are relevant to the business.

5. Remove generic advice that does not help improve the test cases.

這一步非常關鍵。

因爲很多 Agent 輸出看起來很完整，但實際充滿套話。

驗證循環就是爲了逼它從“寫得像”變成“真的有用”。

**九、Agent Skills 的最佳实践**

想把 Skill 寫好，不能只靠感覺。

下面這幾條是比較適合工程團隊落地的原則。

**1. 不要讓 Skill 變成百科文檔**

Skill 不是知識庫。

不要把所有資料都塞進 SKILL.md。

SKILL.md 應該只放：

什麼時候用 怎麼做 注意什麼 輸出什麼 如何驗證

詳細資料放到 references/。

模板放到 assets/。

腳本放到 scripts/。

這樣 Skill 才能保持輕量。

**2. 只寫 Agent 不知道的內容**

很多人寫 Skill 時，喜歡解釋大量通用知識。

比如：

“測試用例是軟件測試中的重要資產。” “接口測試用於驗證系統接口是否符合預期。” “性能測試可以發現系統瓶頸。”

這些內容對 Agent 沒有太大價值。

Skill 裏應該寫的是：

你們團隊的字段規範。 你們項目的斷言要求。 你們業務的特殊狀態。 你們評審時最常見的問題。 你們平臺的目錄結構。 你們內部工具的調用方式。 你們不允許出現的錯誤。

Skill 的價值不是常識，而是經驗密度。

**3. 粒度要像函數一樣**

一個 Skill 不要太大，也不要太小。

太小的問題是：

一個任務需要連續觸發多個 Skill，Agent 容易混亂。

太大的問題是：

觸發不精準，執行步驟太長，結果變得不可控。

比較好的粒度是：

一個 Skill 解決一類明確任務。

例如：

test-case-review：审核测试用例api-test-generator：生成接口自动化用例performance-report-analysis：分析性能测试报告bug-root-cause-analysis：分析缺陷根因rag-evaluation：评估 RAG 系统效果

這就像寫函數。

一個函數只做一件相對完整的事。

**4. 優先寫流程，不要只寫結論**

不好的 Skill 是這樣寫的：

“生成高質量測試用例。”

好的 Skill 是這樣寫的：

先識別業務對象。 再拆分主流程。 再補充異常流。 再設計邊界值。 再檢查權限。 再補充數據一致性。 最後按模板輸出。

Agent 需要的不是口號，而是路徑。

尤其在測試開發場景裏，過程比結果更重要。

因爲測試設計本身就是一套方法論。

**5. 脆弱任務必須寫死步驟**

有些任務容錯率低，必須寫得非常明確。

比如：

數據庫遷移 生產環境變更 批量刪除數據 自動發送郵件 修改 CI/CD 配置 執行壓測任務 發佈前質量門禁

這類 Skill 不能寫得太開放。

應該明確：

先生成計劃 必須二次確認 必須備份 必須 dry-run 必須限制範圍 必須記錄日誌 必須驗證結果 禁止自動執行高風險操作

越脆弱的任務，指令越要具體。

**6. 高頻邏輯要沉澱成腳本**

如果你發現 Agent 每次都在重複寫同一段代碼，就應該把它變成腳本。

例如：

解析 Excel 用例 檢查用例字段缺失 統計接口覆蓋率 生成 Markdown 報告 清洗 JMeter 結果 分析慢 SQL 解析錯誤日誌 檢查 OpenAPI 字段

讓 Agent 每次臨時寫腳本，穩定性一定不如調用一個經過驗證的腳本。

所以，成熟 Skill 的結構應該是：

自然語言負責判斷和編排。 腳本負責穩定執行。 模板負責規範輸出。 參考資料負責補充細節。

這纔是工程化。

**十、真正落地前，必須注意的風險**

Agent Skills 雖然很有價值，但不能只看好處。

因爲 Skill 本身也會帶來新的風險。

尤其是當 Skill 可以執行腳本、調用工具、訪問文件或操作外部系統時，它就不再只是“提示詞”，而是具備了真實執行能力。

近期已有研究開始關注 Agent Skills 的安全問題，包括技能生命週期、權限邊界、惡意技能檢測、社區技能風險等方向。相關論文指出，Agent Skills 的風險不僅來自代碼，也可能來自 SKILL.md 中的自然語言指令、權限設計和分發機制。(**arXiv****[5]**)

企業落地時，至少要注意五件事。

**1. 不要隨便安裝陌生 Skill**

第三方 Skill 可能包含惡意腳本、隱蔽指令或過度權限要求。

安裝之前要檢查：

它會讀取哪些文件 它會調用哪些工具 它是否聯網 它是否執行 Shell 命令 它是否請求敏感權限 它的腳本是否可讀 它的來源是否可信

Agent Skill 本質上是一種可執行能力包。

不能像複製普通 Prompt 一樣隨便複製。

**2. 高風險 Skill 要做權限隔離**

例如：

數據庫操作 Skill 郵件發送 Skill 代碼提交 Skill 雲資源操作 Skill 生產環境運維 Skill 批量文件修改 Skill

這些必須限制權限。

建議做到：

只讀優先 最小權限 沙箱運行 關鍵操作二次確認 操作前生成計劃 操作後生成審計記錄

**3. Skill 要做版本管理**

不要讓團隊成員各寫各的 Skill。

否則很快就會出現：

同名 Skill 行爲不同 舊版本規則還在使用 不同項目標準衝突 輸出模板不一致 腳本沒人維護

建議把 Skill 放進 Git 倉庫。

每次修改走 Review。

這和維護測試框架、自動化平臺、公共組件是一樣的。

**4. Skill 要有評估集**

一個 Skill 寫完後，不是能觸發就算成功。

要設計一組測試問題來驗證它。

比如 test-case-review Skill，可以准备 20 个查询：

10 個應該觸發。 10 個不應該觸發。

應該觸發的例子：

“幫我看看這批用例有沒有問題。” “這些測試點覆蓋完整嗎？” “幫我優化一下登錄模塊測試用例。” “評審一下這份 Excel 裏的用例。” “預期結果是不是寫得太簡單了？”

不應該觸發的例子：

“幫我解釋什麼是測試用例。” “幫我寫一篇測試用例教程。” “測試用例和測試計劃有什麼區別？” “幫我做一個測試崗位學習路線。” “測試用例管理工具有哪些？”

這樣才能判斷 description 是否寫得準確。

**5. 不要把 Skill 當萬能藥**

Skill 解決的是“經驗封裝”和“流程複用”。

但它不能替代：

業務理解 工程判斷 權限治理 數據質量 工具穩定性 組織流程 質量文化

如果底層流程本身混亂，Skill 只會把混亂自動化。

所以企業做 Agent Skills，第一步不是寫文件，而是梳理流程。

先把人的最佳實踐說清楚，再把它變成 Skill。

**十一、寫在最後**

Agent Skills 這個標準真正有意思的地方在於：

它把 Agent 能力建設，從“調 Prompt”推進到了“建資產”。

Prompt 是臨時表達。 Skill 是長期能力。

Prompt 更像一次對話。 Skill 更像一個模塊。

Prompt 依賴個人經驗。 Skill 可以團隊共享。

Prompt 很難評審。 Skill 可以版本管理。

Prompt 很難複用。 Skill 可以跨工具遷移。

對測試開發團隊來說，這件事尤其值得重視。

因爲測試工作天然包含大量流程、規範、模板、檢查項和經驗。

測試用例怎麼設計。 接口自動化怎麼生成。 UI 自動化怎麼封裝。 性能報告怎麼分析。 缺陷根因怎麼定位。 AI 系統怎麼測評。 發佈質量怎麼把關。

這些都可以逐步 Skill 化。

未來，一個優秀測試團隊的核心資產，可能不只是自動化框架、測試平臺和用例庫，還會包括一套穩定、可複用、可審計的 Agent Skills。

到那個時候，AI Agent 才不只是一個會聊天的助手，而是一個真正理解團隊流程、遵守工程規範、能穩定交付結果的數字化協作者。

真正的 Agent 工程化，可能就是從一個 SKILL.md 開始的。
