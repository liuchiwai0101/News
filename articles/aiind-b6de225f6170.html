黃德幾：Anthropic上市為AI大模型定調 - 20261111 - 經濟

內容機器翻譯自第三方媒體（明報 · 香港經濟日報 · 信報網站 · IT之家 等6家），僅供參考，以原文為準。

正文

Anthropic 最近 詳細介紹瞭如何將其單體代碼倉庫從 Git 遷移至 Scion 。Scion 是一套將代碼倉庫操作移至服務器端的源代碼管理系統，使用內容尋址存儲和分層緩存來支持智能體與 CI 工作負載。該設計犧牲了離線獨立性，換取更少的本地數據和共享基礎設施。

Anthropic 在 10 月 13 日發佈的工程文章中表示，單日合併變更數從 5 月的約 2500 個增長到了 9 月的 3 萬多個。其 CI 系統每天大約執行 2500 萬次檢出，而單體代碼倉庫主分支的歷史記錄接近 100GB，壓縮後的工作副本也超過 25GB。該公司此前使用淺克隆、稀疏檢出、Promisor Remote、倉庫快照以及數百個 Git 鏡像，但隨着合併頻率不斷提高，這些方案的運維難度也越來越大。

圖片 2026 年 1 月至 9 月，Anthropic 單體代碼倉庫每天合併的變更數量。（ 來源 ）

Scion 將提交、合併、變基、歷史記錄和代碼追溯查詢都放在服務器端執行。客户端只維護容量受限的對象緩存，虛擬化檢出則按需實體化文件。工具還可以通過 API 查詢差異並執行部分寫入操作，無需檢出代碼。

Scion 變更集會記錄相對於其第一個父變更集發生變化的文件，並使用內容尋址指針引用 Blob 存儲中經過壓縮的文件內容。創建變更集與更新引用彼此分離，因此接收變更集不需要跨服務器協調。對於歷史記錄和代碼追溯查詢，Scion 會構建名為“派生數據”的附加結構。這些數據根據父變更集遞歸計算，可以提前生成，也可以按需生成。由於實現位於服務器端，派生數據可以獨立演進，而無需修改客户端。

圖片 Scion 變更集記錄發生變化的文件及其內容引用；樹結構由服務器單獨派生。（ 來源 ）

執行檢出時，客户端會直接請求缺失的不可變樹和 Blob，而不再協商生成自定義 Packfile。節點本地守護進程會在不同任務之間共享緩存對象，並從區域緩存中獲取數據；區域緩存再從權威服務器獲取數據，後者由 Spanner 和雲存儲提供支持。區域緩存會直接以守護進程使用的存儲格式流式傳輸對象，因此無需針對每次請求執行增量壓縮。

各層都公開相同的檢出協議 RPC，但 Anthropic 會強制規定調用順序，以隔離故障，防止區域緩存失效時大量請求壓垮權威服務器。稀疏檢出和虛擬化檢出只會請求實際需要的對象。

Anthropic 報告稱，每一層的緩存命中率都超過 99%，CPU 和內存基礎設施佔用僅為此前 Git 鏡像的二百分之一，CI 與研究任務的檢出速度則提升了兩個數量級。這些結果由 Anthropic 根據其內部工作負載得出，並不是與 Git 進行對比的通用基準測試。

InfoQ 此前曾報道 Uber 的 GitFarm 。GitFarm 在不替換源代碼管理系統的情況下，將標準 Git 操作集中到服務器端。Scion 更進一步，改變了底層數據模型。其設計也建立在已有成果之上：Anthropic 在 10 月 15 日的一次更新中明確表示， Mononoke 及其 Bonsai 數據模型 率先採用了 Scion 所使用的許多技術。

Anthropic 提醒，Scion 並不是通用的 Git 替代品。它需要配套的代碼審查、代碼搜索和 CI 系統，而該公司的這些實現都經過了高度定製。Anthropic 建議將其中一些設計理念引入現有 Git 平台，例如完備的服務器端 API 和更高效的獲取協議。

對於架構師而言，最重要的啓示是：當工作負載發生變化時，需要重新考慮計算工作應該在哪裏執行。代碼倉庫查詢不一定需要本地檢出，不可變對象也可以通過緩存共享。這些做法能夠減少重複工作，但 Scion 依賴服務器的可用性，而且所需的系統集成工作也相當龐大。
