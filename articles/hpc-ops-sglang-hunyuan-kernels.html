HPC-Ops × SGLang：腾讯混元高性能 Attention、Router GEMM 与 MoE 内核

HPC-Ops（https://github.com/Tencent/hpc-ops）是專爲 LLM 推理設計的開源算子庫，已部署於騰訊混元的大規模生產服務中。其核心算子 Dynamic Attention 和 Fused MoE 在混元在線推理中發揮關鍵作用，最高可將 Hy3 模型的 TPOT 降低 48.8%。目前，HPC-Ops 的 Attention、Router GEMM 和 MoE 算子已集成至 SGLang 主分支，將這些生產驗證的優化帶給開源服務社區。

本文將介紹 HPC-Ops 三大算子的設計思路及其與 SGLang 的集成方式，並展示 H20 上的算子基準與服務結果，同時包含 H200 驗證數據。這些優化針對 NVIDIA Hopper GPU（SM90），已在 Qwen3、Hy3 和 LongCat 工作負載上驗證通過。

亮點速覽

- **Attention：**在 H20 上，HPC-Ops 动态调度比静态 split-KV 方案快 2.95 倍，平均比 FlashInfer 和 FlashAttention 中最优方案快 2.25 倍。在 H200 上，集成 Hy3-FP8 路径配合 FP8 KV cache，输出吞吐提升 3.7–5.9%。

- **Router GEMM：**在 H20 上，HPC-Ops 比 FP32 cuBLAS 快 1.30–3.22 倍，最大绝对误差仅 0.00177，优于 TF32 cuBLAS 的 0.06464。在 H200 LongCat-Flash 验证中，速度提升 4.31 倍。

- **MoE：**在 H20 上，HPC-Ops 在 TP8/EP1 配置下平均加速 1.08 倍，在 TP1/EP8 配置下加速 1.21 倍。在 Qwen3/H200 测试中，最高比 Triton 快 4.21 倍。

- **端到端服务：**8×H20 + Hy3-FP8 配置下，同时启用 HPC-Ops Attention 和 MoE，TPOT 在 batch 4–64 时降低 15.1–48.8%，TTFT 在 batch 4–16 时降低 3.3–6.0%。

MoE 模型服務中的三大熱點路徑

生產級 MoE 服務通常包含混合長度 Attention、精度敏感的路由以及稀疏專家執行，負載分佈不均。HPC-Ops 針對每個階段提供專用算子：負載感知的 Attention 調度、精度感知的 Router GEMM，以及減少 gather 開銷的融合 MoE 流水線。

Attention：混合長度 decode 的負載均衡

在 decode 階段，每個新 token 需要關注完整 KV cache，工作量隨序列長度線性增長。靜態 split-KV 調度難以應對混合長度批次，而 HPC-Ops 採用持久化內核，根據實際 KV 長度動態分配任務，實現近乎完美的負載均衡。

Router GEMM：精度與吞吐的平衡

路由器精度直接影響 MoE 模型質量。HPC-Ops 將 FP32 權重分解爲兩個 BF16 分量，通過兩次 BF16 GEMM 恢復低階尾數精度，同時利用 Tensor Core 加速，誤差遠低於 TF32 cuBLAS。

MoE：降低小專家 GEMM 周圍開銷

decode 時每個專家僅處理少量 token，傳統 MoE 路徑存在大量 gather、kernel launch 和 HBM 往返開銷。HPC-Ops 通過融合流水線顯著減少這些開銷。

端到端性能驗證

在 8×H20 上启用 HPC-Ops Attention 和 MoE 后，Hy3-FP8 模型 TPOT 大幅下降；LongCat-Flash-Lite-FP8 模型输入吞吐提升 5.5–6.1%。
