團隊分享提升 Agent Harness Token 效率的提示詞

內容機器翻譯自第三方媒體（Eric Zakariasson），僅供參考，以原文為準。

AI 導讀

一份公開提示詞用於優化 LLM Agent Harness，目標是在不降低任務質量的前提下降低每任務的價格加權 token 成本。某團隊一輪改動（提示詞精簡、工具卸載、緩存佈局、稀疏行號、子智能體調優）將整體 token 成本降低約 7%，且質量無損。提示詞強調按任務而非按請求計量，並建議先映射 harness、測量基線，再按優先級實施改動。

推薦理由

來自 Cursor 團隊經驗的完整 agent harness 降本 prompt，給出實測數字、執行順序和常見陷阱，可直接複用。

正文

這裏有一個提示詞，可以基於我們在 cursor 學到的東西來改進你的智能體框架。請享用

提升這個智能體框架的 token 效率

你正在處理一個 LLM 智能體框架：系統提示詞、工具定義、請求組裝、上下文緩存、壓縮與檢索，以及工作如何在各個智能體之間拆分。讓智能體的運行更便宜，同時不讓它把活幹得更差。

• 目標：降低每個已完成任務的按價格加權的 token 成本。 - 約束：任務質量沒有可測量的下降。

按任務衡量，而不是按請求衡量。每一輪都會重新發送前綴（工具、指令、設置，以及到目前為止的對話），所以一個能縮小每個請求但會增加輪數的改動，反而可能更貴。按計費類型對 token 加權：輸出、未緩存輸入和緩存輸入的定價差別非常大。

按這個順序來做：先梳理框架並測量基線，對機會點排序，直接做那些可以安全做的改動，把其餘的放到開關後面或寫成提案，然後彙報。

下面的數字來自某個團隊的生產級編程智能體及其多智能體實驗。用它們來判斷量級，而不是當作目標。這一輪改動（提示詞精簡、工具卸載、緩存佈局、稀疏行號、子智能體調優）讓該團隊的整體 token 成本降低了約 7%，且質量沒有損失。那些更大的百分比只適用於每項改動所觸及的那部分請求。

原則

  1. 改變的是 harness 發送的內容，而不是模型有多努力。不要要求模型節省 token。一個告訴其模型"注意節省 token、不要浪費"的 harness 發現，模型變得不願承擔有雄心的任務，有時還會退出，説自己不該浪費 token。 2. 有能力的模型需要的是定義，而不是命令。那些"不要""你必須""重要"的清單，以及針對舊模型習慣的防範措施，通常都可以用對每個工具功能的平實描述來替代。有一個團隊用這種方式削減了大約三分之二的系統提示詞，而更短的提示詞在多個模型家族中都奏效。只針對模型無法知道的內容（產品、環境、用户的流程）以及你在對話記錄中見過的怪癖進行指示。 3. 靜態上下文是留給大多數輪次都需要的內容的。其他一切都應該在需要時可被發現。更少的前置上下文也意味着更少令人困惑或相互矛盾的信息。 4. 要預期刪減會勝出。為較弱模型編寫的護欄、變成瓶頸的協調步驟，以及針對模型如今已能自行完成的行為所寫的提示詞，全都在消耗 token。 5. 真實使用情況説了算。評測是快速的替代指標，但它們偏向難題，會錯過真實請求的構成。
  1. 梳理 harness 並測量基線

查找：

• 請求在哪裏組裝、系統提示詞以及工具 schema。如果某個框架或 SDK 負責構建請求，找到它在消息順序、緩存控制和工具加載方面的鈎子。 - 工具結果的格式化方式，以及歷史記錄如何保存、裁剪或摘要。 - 子智能體或並行智能體如何生成（如果有的話）。 - 使用了哪些模型和提供商 API。從提供商的文檔中，獲取提示詞緩存行為（自動或顯式斷點、TTL、最小可緩存長度）以及輸出、未緩存輸入和緩存輸入的價格。 - 現有的日誌記錄、token 核算和評測。

如果這套運行框架沒有按計費類型和緩存命中來記錄每個請求的 token 用量，先把這個補上。後面的一切都依賴它。

然後渲染幾個真實請求（來自日誌，或通過運行代表性任務），用模型的 tokenizer 或 API 的 usage 字段統計每個部分的 token 數。產出：

• 按來源 × 計費類型的成本佔比。來源包括：系統提示詞、工具定義、技能/規則/集成描述、用户消息、文件讀取、搜索結果、命令及其他工具輸出、歷史記錄、摘要、子智能體。 - 每個請求的靜態 token 數、緩存命中率，以及每個任務的輪次。 - 按工具統計：至少調用一次該工具的運行佔比，以及其錯誤率。

要閲讀渲染後的請求，而不只是模板。重複內容、泄漏的易變值以及順序錯亂的塊，只有在那裏才會顯現出來。

按支出佔比 × 可削減比例 ÷ 質量風險，對各項優化機會排序。

  1. 系統提示詞與注入的上下文

為每條指令打上標籤：

• 保留：模型無法推斷的產品或環境知識、針對該模型對話記錄中出現的怪癖的修復，以及某個模式所依賴的規則。 - 改寫：把命令和強調語氣改寫為平實的描述。把提醒改寫為約束條件："不要 TODO，不要部分實現"比"記得完成實現"效果更好。把模糊的數量改寫為區間："生成 20-100 個任務"比"生成許多任務"能激發出雄心大得多的行為。 - 刪除：能力強的模型默認就會做的事、針對你尚未從該模型觀察到的行為的防範措施、重複工具描述的文本，以及可能與用户請求相矛盾的語句。被訓練為將系統指令置於用户消息之上的模型，會站在系統提示詞一邊。 - 移動：把任何按用户或按請求變化的內容（日期、環境、倉庫狀態、技能或子智能體列表、用户規則）移到緩存邊界之後的 user 角色設置消息中。

用同樣的方式審查其他注入的上下文。隨着模型不斷進步，這些數據背後的團隊刪掉了目錄樹、預檢索的代碼片段、附件文件的壓縮副本、每次編輯後注入的 lint 錯誤、對短文件讀取的強制擴展，以及每輪工具調用次數上限。他們保留了少量高價值的事實：操作系統、倉庫狀態，以及打開或最近查看過的文件。

對於開放式工作，跳過檢查清單。模型會優化清單上列出的項目，並降低其他一切事項的優先級。

  1. 工具定義

工具 schema 會隨每個請求一起傳輸。除核心工具集之外，大多數工具在不到 20% 的對話中才會被用到，而將它們移出靜態上下文後，工具描述 token 減少了 60%。對集成類工具（例如 MCP server）採取同樣做法--上下文中只保留名稱，完整 schema 放在每個 server 一個文件夾中，由智能體用 grep 或 jq 搜索--在使用這些工具的會話中，總 token 減少了 46.9%。

• 保留在靜態上下文中：高頻工具（對編碼智能體而言：read、search、edit、shell）、模型即使不存在也會嘗試調用的工具，以及某個模式所依賴的工具。 - 其餘全部外置：只留一個名稱或一行提示，讓完整 schema 可按需發現。將相關工具分組，使其一起加載，並把狀態（例如"需要重新認證"）放在智能體能看到的對方。 - 精簡保留部分：描述行為和參數，去掉使用説教。 - 通過測試幾種配置並跟蹤 token、成本、延遲、工具調用錯誤和任務成功率，來確定拆分方式。

  1. 緩存佈局

對每個請求進行排序，使可複用的前綴儘可能長：

工具定義 → 系統指令 → 【斷點】 → 設置消息（技能、子智能體、規則、環境）→ 【斷點】 → 對話

• 保持前綴在各輪之間逐字節一致。使用確定性的工具順序和序列化方式，把時間戳和 ID 放在邊界之後，並且不要重寫更早的消息，除非是在進行壓縮時。 - 如果服務商支持顯式斷點，就使用它們。否則依賴自動前綴緩存，把穩定部分放在最前面。遵守 TTL 和最小長度規則。 - 在對話中途切換模型會丟棄緩存（緩存是按模型和服務商分別存儲的），並且會把一段並非由它撰寫的歷史交給新模型。當需要換用另一個模型時，把它作為子智能體在全新上下文中運行。

顯式斷點，加上把每次請求的設置移到斷點之後，將冷緩存未命中減少了 20%。

  1. 工具結果以及運行期間添加的其他上下文

• 大型輸出（命令、集成、日誌）：將其寫入文件並返回路徑、大小和一小段尾部內容。智能體可以自行 tail、grep 或按範圍讀取以獲取更多信息。截斷會丟失數據，而內聯則會讓後續每一次請求都變得臃腫。長時間運行的終端會話也應同樣處理。 - 高容量格式：留意每一行或每一項上重複出現的開銷。在讀取文件時每隔 10 行編號一次，而非每行都編號，可將緩存讀取的 token 減少 1.6%，且不影響引用準確率。每個編號要花費 3-5 個 token，而智能體每次會話要讀取數萬行。同時還要檢查重複的絕對路徑、冗長的 JSON 鍵名、ANSI 轉義碼、進度條以及重複的表頭。 - 良好的檢索能節省探索輪次。在 grep 之外加入語義搜索，可將代碼庫問答準確率平均提升 12.5%，並減少用户所需的迭代次數。 - 工具錯誤會浪費 token，並在上下文中留下令人困惑的殘留物。對預期錯誤進行分類（無效參數、意外環境、提供商錯誤、超時、用户中止），將未知錯誤視為框架缺陷，並按工具和按模型跟蹤錯誤率。沿着這一思路做一次集中優化，可將意外工具錯誤減少 10 倍。

  1. 長時間運行：壓縮、子智能體與模型混用

• 壓縮：保持摘要提示詞簡短、摘要緊湊，延續計劃狀態和剩餘任務，並將完整歷史保存到文件中，讓智能體可以搜索摘要中遺漏的細節。一個經過訓練、能從一行提示詞進行自我摘要的模型，寫出了約 1k token 的摘要，其壓縮錯誤率僅為多千 token 提示詞（產生 5k+ token 摘要）的一半。未經訓練的模型可能需要更多引導，所以要測試你能壓縮到多短。使用更昂貴的摘要模型帶來的差異微乎其微。 - 草稿本和運行筆記：重寫它們，而不是追加。對於同一環境中的重複工作，一個由智能體維護、帶行數預算、在啓動時加載的小型筆記文件，是縮短後續運行時間的一種有前景的方式。 - 子智能體：全新的上下文讓父智能體保持精簡，但隔離會增加協調成本（重複或過時的工作）。如果模型已經會自行委派任務，就移除推動它這樣做的提示詞。讓子智能體返回簡短的交接內容：做了什麼、發現、顧慮和偏差。只有當用户或運行框架要求時，子智能體才應使用不同的模型。 - 模型組合：在大型多智能體運行中，工作節點使用了至少 69% 的 token，在大多數運行中超過 90%。前沿規劃器搭配廉價工作節點，能以約八分之一的成本達到前沿模型包辦一切的效果。規劃器的選擇仍然會改變工作節點的開銷。一個自身成本較低的規劃器，其工作節點使用的 token 卻多了數倍，整體運行成本反而更高。要衡量整棵調用樹。 - 路由和推理力度：將簡單輪次發送給更便宜的模型或更低的推理力度，只有在更強的模型明顯更好時才升級。以這種方式構建的路由器在用户滿意度上匹配或超越了單一前沿模型，成本降低了 41-68%。 - 推理連續性：如果 API 返回推理項（包括加密的），在後續輪次中將其傳回，並在它們丟失時發出警報。丟棄它們會讓一個推理模型在編碼基準測試上損失 30%，而且它還會消耗 token 來重建自己的計劃。

  1. 讓 harness 適配每個模型

要適應每個模型訓練時所採用的方式，而不是強行讓所有模型都套用同一種形態。如果你已經為某個相似的模型調好了 harness，就從那個版本開始。

• 編輯格式：使用模型訓練時所採用的格式（例如 patch 風格或搜索替換）。不熟悉的格式會額外消耗推理 token，並導致更多錯誤。 - Shell 或工具：shell 優先的模型會退回到 cat 或內聯腳本。以工具的 shell 等價物來命名工具（例如 rg），如有需要可加上："如果某個操作已有對應工具，優先使用該工具而不是 shell 命令（例如用 read_file 而不是 cat）。" - 字面程度：有些模型家族會嚴格按字面執行指令，另一些則能容忍不精確。有些模型會對被強調的措辭產生過度反應。對於字面型模型，去掉大寫和強調。 - 觸發條件：有些模型在被告知何時使用之前會忽略某個工具。字面型觸發語有效："在實質性編輯之後，使用 檢查最近編輯過的文件是否有 linter 錯誤。如果你引入了任何錯誤，在你能輕鬆弄明白如何修復的情況下修復它們。" - 進度更新：如果模型通過推理摘要來報告進度，讓它們保持在 1-2 句話，説明新發現或策略變化，並刪除關於回合中途發消息的指令。 - 值得專門寫一行的小毛病：隨着上下文填滿而含糊其辭或拒絕（"上下文焦慮"）、過早宣佈完成、停下來請求許可，以及調用不存在的工具。

把每一條新增的指令都與你所修復的對話記錄行為對應起來。當模型發生變化時重新審查，因為某個版本需要的指引對下一個版本來説可能是累贅。

  1. 驗證

• 離線：在改動前後運行一組固定的真實任務，最好取自真實使用場景，並按照用户實際的寫法來表述（簡短且含糊）。對比任務成功率、token、成本、每任務成本、輪次和工具錯誤。不要上線會降低成功率的改動。 - 在線，如果你有用户：對每項改動或小批量改動做 A/B 測試。主要指標是每個已完成任務的成本。護欄指標是任務成功信號、工具調用錯誤、延遲、每任務輪次和緩存命中率。對於編碼智能體，一個好的成功信號是智能體編寫的代碼隨時間推移的存活量。一般來説，要看用户的下一條消息是繼續推進還是報告問題。 - 只有在成本下降且沒有任何護欄指標出現超出噪聲的退化時才上線。記錄無顯著結果。

哪些直接改，哪些先提議

• 直接改，每項各自一個可回滾的提交：token 與緩存遙測、確定性序列化和工具順序、把易變內容移出緩存前綴、顯式緩存斷點、把大輸出寫入文件而不是截斷、把正在被丟棄的推理項傳回，以及修復反覆出現的工具錯誤。 - 放在開關後面以便測試：系統提示詞修改、工具卸載、輸出格式變更、壓縮變更和子智能體提示詞。 - 僅提議：更換所用模型、路由、推理投入默認值，或工作在各智能體之間的拆分方式。

陷阱

• 要求模型使用更少的 token 或做更少的事。 - 截斷工具輸出。 - 丟棄推理項以節省輸入 token。 - 緩存前綴中存在易變內容，或工具順序在請求之間發生變化。 - 在第一輪就卸載模型需要的工具，或模型嘗試調用時該工具已缺失。 - 大量強調的提示詞（MUST、NEVER、IMPORTANT、全大寫），尤其是對字面理解的模型。 - 強制使用比模型訓練時更簡潔的輸出格式。更少的輸出 token 可能意味着更少的思考，結果更差。 - 優化原始 token 數量而非成本，按單次請求而非按任務優化，或優化評測而非真實使用。 - 在對話中途切換模型以省錢。 - 添加會變成瓶頸的協調層。

彙報以下內容

  1. 框架圖和基線：按來源 × 計費類型劃分的成本，並標出最大的來源。 2. 一份按優先級排序的變更清單：層級、變更內容、預估節省額及估算方式、質量風險、如何驗證，以及如何回滾。 3. 你所做的變更，包括一份系統提示詞 diff，每一行都附上保留、重寫、刪除或移動的理由。 4. 針對已標記變更的測試計劃。 5. 缺口：任何你未能找到或衡量的內容。
