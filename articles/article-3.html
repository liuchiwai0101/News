**本地可復現的 Agent 自進化閉環**

讓 Agent 構建 Agent 只是 PenguinHarness 的第一步，PenguinHarness 更長遠的目標，是希望每個人都能在本地擁有自進化 Agent。

構建 Agent 是從 0 到 1，優化 Agent 是從 1 到 100，其中需要跨越許多挑戰。

「Chaning agents is easy; improving them is hard.」

在一次關於自進化的討論中，鄭耀威曾提出這樣的觀點：Agent 本質上就是一堆代碼和文件，修改它很容易，讓他變好卻很難。大模型本就已經是自帶隨機性的概率函數，Agent 則更是一個充滿了不確定性的自主系統。要想做好 Agent 自進化，那麼必須要有一個可靠的「尺子」，也就是評估系統。

ReAct 論文作者姚順雨曾言，評估是大模型的下半場。對於 Agent 自進化，這句話同樣成立，一套好的評估基準是自進化的根本。

爲了探索準確的評估方式，鄭耀威帶領團隊花費了半年多時間。最大的障礙是，現有的評估大多隻有測試集，而沒有訓練集。如果在測試集上跑自進化，很難區分 Agent 到底是背會了答案，還是真正產生了進化。

爲此，團隊甚至親手做了一套新的評估基準 ——GDPevo，專門用於測試 Agent 自進化能力，覆蓋醫療、金融、法律等六大真實場景。通過劃分訓練 / 測試集，確保 Agent 進化時不會「偷看答案」。

PenguinHarness 吸納了 GDPevo 的核心思想，把 Agent 的評估和優化凝練爲了開箱即用的 Skills。在調用 Skill 以後，PenguinHarness 就會啓動多個智能體，配合完成 Agent 的調優流程，也就是「自進化」。

試想這樣一個場景：做一個 Agent 幫你更準確的預測球賽、提出投資策略、處理電商售後，但是這個 Agent 一開始準確率並不高。過去，你需要通過手動調整提示詞，搭建工作流來提高精度，而現在，PenguinHarness 可以自動幫你完成 Agent 調優。

通過視頻可以看出，PenguinHarness 完成了多次迭代，Agent 的分數從優化前的 53 分，提升到了優化後的 95 分。使用 DeepSeek V4 Flash 正式版，整個過程只花了 0.5 元的 Token。

這背後是一套多智能體的協作流程。PenguinHarness 首先生成一個負責出題的 Benchmark Builder，圍繞目標能力生成一系列題目和答案對，通過反覆測試來校準題目難度。

進入優化階段後，三個承擔不同角色職責的 Agents 會組成一個自進化閉環，反覆進行下面四步過程：

1. 組織評測：Optimizer Agent 按照題目數量和運行次數，組織多個 Evaluator Agents 並行評測；

2. 獨立打分：每個 Evaluator Agent 啓動一個獨立的被測 Agent 解答題目，並且根據只有 Evaluator 才能看到的 Rubrics 打分，將分數返回給 Optimizer Agent；

3. 分析優化：Optimizer Agent 彙總評測結果，通過查看和分析軌跡，定位失分原因，修改被測 Agent 的提示詞、Skill 或者配置，生成候選的下一版被測 Agent；

4. 驗證迭代：Evaluator Agent 對候選版本重新評測，Optimizer Agent 根據結果決定是否接受候選版本，再進入下一輪迭代。

從一次性交付走向持續進化，這就是 PenguinHarness 對下一代 Agent Harness 給出的回答。

**和自進化 Agent 之間的契約**

爲了讓 Agent 自進化跑得更 “穩”，PenguinHarness 設計了一套框架必須遵守的 “契約”。

這份契約規定了 Agent 自進化的邊界在哪裏，我們在這裏挑幾個重點來講。

1. 限定 Agent 的修改範圍爲提示詞和 Skills，不能觸及 Harness 內核。這是爲了防止 Agent 在進化過程中產生安全風險，例如破壞了原有的權限審計規則。好的 Agent 建立在安全之上。

2.Agent 自進化要有快照和回滾能力，如果產生了負面作用，框架要有能力將 Agent 版本回退到之前的狀態。

3. 目標 Agent 在進化過程中只能看到題目，不能看到 Rubrics。這是爲了防止 Agent 走捷徑，通過背會答案或者迎合打分器來取得更高分數，防止 Reward Hacking 現象。

4. 所有的優化流程都要形成文件記錄，用戶有權限去審計優化過程，提供自進化的可解釋性。

這套契約也被 PenguinHarness 形式化爲了一份 “CONTRACT.md” 文件，方便複製和分發。
