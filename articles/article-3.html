「我們刪除了 80% 的 Claude Code 系統提示，這是我們從編寫系統提示詞、Skill 和 Claude.MD 中學到的。」

本週五，Claude Opus 5 正式上線，Anthropic 技術團隊成員 Thariq Shihipar 立即發帖，向我們介紹了新一代大語言模型之上，工程方面的趨勢變化。

Anthropic 自己發現，在 Claude Opus 5 這種新一代強推理模型發佈後，舊的提示詞工程範式可能已經過時，甚至在起反作用。

簡單來說，就是**模型越強，就越不需要「保姆式」指導**，冗長的手寫規則除了浪費 token，還有可能會讓效果變差；新的 Claude.md 應該保持絕對的精簡，高績效團隊控制在 60 行以內，通常絕不要超過 300 行；大砍系統提示詞之後，可以把那些特定任務的上下文交給 Skill。

可見，隨着大模型的參數化知識和推理能力越來越強，提示詞工程也要向整體架構的高度轉變。

這讓我們不由得感嘆，時代變了。

**讓我們看看 Anthropic 自己是如何解釋的**

Anthropic 此前介紹過如何爲新一代 Claude 5 模型編寫提示詞，以及如何與模型迭代協作、在過程中逐步明確真正想構建的東西。

但當用戶向 Claude 發送一條消息時，提示詞只是模型所獲上下文中的一小部分。上下文中的絕大部分內容，來自系統提示詞、Skills、CLAUDE.md 文件、記憶以及其他來源，這稱爲**上下文工程（context engineering）**。無論你是在使用 Claude Code，還是在構建自己的 Agent，它都會顯著影響最終產出的質量。

與提示詞不同，上下文通常用於多個請求，因此不可能寫得那麼具體。

那麼，在根本不知道用戶會輸入什麼提示詞的情況下，該如何爲 Claude 編寫這類通用的提示和指導？

隨着 Claude 自身能力的演進，這件事的難度可能超出預期。

最近，Anthropic 就發現面向新一代 Claude 模型的提示方式出現了一次很大的躍遷：對於 Claude Opus 5、Claude Fable 5 這類模型，**團隊刪掉了 Claude Code 系統提示詞中 80% 以上的內容，而在編碼評估上沒有觀察到任何可測量的性能損失**

以下是 Anthropic 在爲這一新世代模型編寫提示時總結出的經驗，以及開發者可以如何用它來更新自己的上下文工程實踐。**這些最佳實踐已被沉澱進 claude doctor**—— 在 Claude Code 中使用 /doctor 命令，就能自動把 Skills 和 CLAUDE.md 文件調整到合適的規模。

**给 Claude 松绑**

總體來看，Anthropic 發現自己對 Claude Code 施加了過多約束，系統提示詞如此，CLAUDE.md 文件和 Skills 同樣如此。

舉個例子，團隊翻閱內部使用 Claude Code 的對話記錄時，常常在同一次請求中看到互相矛盾的指令。系統提示詞、Skills 和用戶請求彼此打架，一邊說「酌情保留文檔」，另一邊卻寫着「禁止添加註釋」。

一般來說，Claude 能夠讀懂用戶的真實意圖並給出正確答案，但它必須先在這些重疊、衝突的指令之間反覆權衡，才能決定該怎麼做。

這些約束在過去確實是必要的，它們用來規避最壞情況。但團隊後來發現，其中很多都可以刪除，轉而讓模型依據周邊上下文和自身判斷力行事。

此外，Claude Code 如今擁有的工具也多得多。過去 Claude 主要依賴 CLAUDE.md 作爲記憶、信息和指引的來源。而現在有了記憶、artifacts 和 Skills，Claude 可以藉助它們創造出跨會話加載與共享上下文的新方式。

**昔與今**

過去的一些上下文工程「最佳實踐」，如今已經淪爲誤區。

**昔：給 Claude 定規則 → 今：讓 Claude 自行判斷**

Claude Code 剛推出時，Anthropic 團隊必須確保它不會踩到最壞情況的雷區，比如刪除文件。這意味着要給出一些語氣很強、但並不總是成立的指令。

例如，系統提示詞裏曾經寫着：

寫代碼時默認不寫註釋。絕不要寫多段式 docstring 或多行註釋塊 —— 最多一行短註釋。除非用戶明確要求，否則不要創建規劃、決策或分析類文檔 —— 依據對話上下文工作，而不是根據中間文件。

但對某一類提示詞而言，這條指令是錯的。就文檔而言，用戶可能有自己的偏好，某些特別複雜的代碼，也確實需要多行註釋塊來說明。

話雖如此，在沒有這些護欄的情況下，舊模型寫出的註釋在很多場景下都是錯的，團隊只能接受這種取捨。而新模型判斷力更好，無需顯式規則也能把這類決策處理得很妥當。

在新的系統提示詞中，寫法變成了：

寫出的代碼要讀起來像它周圍的代碼：匹配其註釋密度、命名方式和慣用寫法。

**昔：給 Claude 舉例子 → 今：設計好接口**

關於工具使用，過去的第一準則是：給 Claude 提供使用示例。但在最新的模型上，Anthropic 團隊發現示例反而會把模型約束在某個特定的探索空間裏。

與其堆砌示例，不如多花心思在工具、腳本和文件的設計上，即 Claude 能拿到哪些參數？這些參數如何才能更具表達力？

以 Todo 工具爲例，僅將狀態列爲待處理、進行中和已完成三個枚舉值，就能提示 Claude 如何使用該工具。而「始終只保留一項處於進行中狀態」這條說明，則清晰界定了所期望的行爲。

**昔：一股腦全寫在前面 → 今：漸進式披露**

由於 Claude Code 聚焦於編碼，其系統提示詞裏塞進了關於代碼評審和驗證的詳盡說明。這些內容並非總能用上，但一旦用上就至關重要。

如今，Claude Code 已經非常擅長漸進式披露 —— 在恰當的時機加載恰當的上下文。比如，團隊把驗證和代碼評審拆成了獨立的 Skills，供 Claude Code 按需調用。

漸進式披露不只適用於 Skills，也適用於工具。部分工具採用「延遲加載」：Agent 必須先通過 ToolSearch 檢索出完整定義，才能調用。這樣就能提供更多工具（比如 Task 類工具），而它們在被真正需要之前不佔用任何上下文。

同樣的思路也適用於開發者自己的 CLAUDE.md 和 SKILL.md。一個常見的誤解是，必須把所有可能用到的實踐一股腦塞進這些文件，否則 Claude 就找不到。實際上，請考慮構建一棵文件樹，讓它們在合適的時機被加載。

**昔：反覆強調 → 今：簡潔的工具描述**

早期的 Claude 模型有時需要重複指令，也更傾向於聽從上下文窗口末尾而非開頭的內容。於是系統提示詞裏既有對工具的引用，工具描述中又有一套說明。

Anthropic 發現這些重複內容完全可以刪掉：把工具的使用說明放進工具描述裏，而不是系統提示詞中。

**昔：把記憶寫進 CLAUDE.md → 今：自動記憶**

過去，用戶被鼓勵用 # 快捷鍵把內容自動寫入 CLAUDE.md，以此保存到 Claude 的記憶中。

而現在，Claude 會自動保存與當前工作以及與用戶相關的記憶。

**昔：簡單的規格文檔 → 今：豐富的參考材料**

在 plan 模式下，Claude Code 一直高度依賴 markdown 格式的計劃文件。把計劃存成文件，便於 Claude 在需要時回查。另一條類似的最佳實踐，是把規格文檔存放在代碼庫中，供 Claude 在長週期項目中隨時參考。

但 Anthropic 發現，Claude 已經能夠駕馭複雜得多的參考材料。除了簡單的 markdown 文件，Claude 還可以引用由我們新的 artifacts 功能生成的 HTML artifact。

開發者也可以用代碼本身作爲參考材料。一份規格說明可以是一套詳盡的測試用例，也可以是另一個代碼庫中某個待移植的函數。

評分標準（rubric）是另一種形式的參考材料。藉助評分標準，Claude 可以通過動態工作流、並派生出驗證者智能體（verifier agents），來嘗試還原並校驗開發者在某個領域中的品味（比如，什麼樣的 API 設計纔算好設計）。

**落到你自己的上下文裏**

把上面這些串起來，在實際組裝上下文時應該是什麼樣子？

**系統提示詞**

系統提示詞與產品語境高度綁定。它告訴 Claude 自己身處什麼產品、在做什麼事。對 Claude Code 而言，你基本不會去改動它；但如果你在構建自己的智能體框架（agent harness），這裏值得你投入大量精力。

**CLAUDE.md**

保持 CLAUDE.md 輕量：簡要說明這個倉庫是做什麼的，然後把大部分 token 花在代碼庫中的「坑」上。比如，團隊可能把所有類型定義集中放在一個大文件裏，別處一概沒有 —— 這類信息才值得寫。避免陳述那些 Claude 只要看一眼文件結構或倉庫就能知道的「顯而易見」的事。

更細的內容用漸進式披露來處理。比如，如果有若干套獨特的工作驗證流程，就做成一個驗證 Skill，然後在 CLAUDE.md 中引用它。

**Skills**

把 Skills 看作輕量級指南，讓 Claude 在需要時能找到信息。除非是極其關鍵的領域，否則不要把它們寫得過度約束。

對於篇幅較長的 Skill，儘可能採用漸進式披露，即拆成多個文件，分而治之。

Skills 最能發揮價值的地方，是承載那些屬於開發者本人、其團隊或其產品所特有的觀點、知識和最佳實踐。

**參考材料**

可以用 @ 提及文件，把它們作爲參考材料引入。參考材料讓 Claude 能夠查閱當前計劃的深層細節。

這些材料可以是規格文件、設計稿，甚至是整個代碼庫。總體而言，優先選擇以代碼形式存在的文件，它們能給 Claude 提供清晰、高保真的指令，而且用的是它非常熟悉的語言。舉例來說，一份 HTML 設計稿的效果，通常會好過對設計的文字描述或一張截圖。

**試着做減法**

在系統提示詞、Skills 和 CLAUDE.md 之間，開發者或許也需要像 Anthropic 一樣做一輪簡化。新推出的 claude doctor 命令可以自動幫助完成這件事。
