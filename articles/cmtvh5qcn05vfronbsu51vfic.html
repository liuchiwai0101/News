Hugging Face 用 Gradio Workflow 重建 Workflow1111，復刻 AUTOMATIC1111 主要功能

內容機器翻譯自第三方媒體（Hugging Face），僅供參考，以原文為準。

AI 導讀

Hugging Face 發佈 Workflow1111，用 gr.Workflow 以 73 個節點、11 條媒體管線重建 AUTOMATIC1111 的大部分功能，覆蓋文本生成圖像、高清修復、圖生圖、prompt matrix、VLM 反推提示詞、檢測生成 inpaint 蒙版、ControlNet 式預處理器、背景移除、PNG Info 和圖生視頻。

推薦理由

原文展示用 Gradio Workflow 重建 AUTOMATIC1111 主要功能的具體做法，並給出 REST 與 MCP 入口，讀者可評估它與 ComfyUI 的取捨。

正文

在上一篇文章中，我們構建了五個小型gr.Workflow圖，並暗示了要構建像 AUTOMATIC1111 的stable-diffusion-webui那樣複雜的東西需要什麼。在這篇文章中，我們將帶你瞭解Workflow1111，在這裏我們將 AUTOMATIC1111 的大部分功能集重建為單個工作流畫布。Workflow1111 是一個由十一條媒體流水線組成的圖，使用七十三個節點構建。它彙集了用於文生圖、高分辨率修復、圖生圖、提示詞矩陣網格、VLM 反推、檢測到局部重繪蒙版、ControlNet 風格標註器、背景移除、PNG Info 存儲以及圖生視頻的 SOTA 模型。

你可以使用 Hugging Face 賬户登錄或提供訪問 token 來運行這些流水線中的任意一條。登錄後，模型調用將使用你自己的配額。

👉 試用 Workflow1111，或複製該 Space 並開始為你的用例重新接線。

讓我們走一遍畫布。

畫布上有什麼

所有媒體流水線都由我們上一篇帖子和官方指南中介紹的同樣四種算子類型構建而成。畫布上的每個節點封裝一個算子，算子的輸入和輸出就變成你連接邊的端口。作為四種算子類型的快速參考：fn是一個 Python 函數，model是通過InferenceClient調用的模型，space是另一個 Gradio Space，dataset是 Hub 數據集中的一行。

讓我們逐一來看這些流水線。

文生圖

這是核心流水線。它具備你在 A1111 的 txt2img 標籤頁中會看到的那些控件：負面提示詞、步數、CFG、種子、寬度和高度，外加一個用於選擇 checkpoint 的model_id字段。提示詞首先經過一個提示詞構建器fn節點，該節點會追加所選風格預設並清理文本，然後進入一個model節點，通過 Inference Providers 調用 checkpoint。一個後處理fn節點在輸出時將生成參數寫入 PNG 的元數據中，這正是 PNG Info 流水線之後讀取回來的內容。

高分辨率修復

在 Automatic1111 中，高分辨率修復首先對 txt2img 的輸出進行放大，然後運行第二次去噪。在這裏，它改為一個兩節點的繞行。文生圖的結果進入一個帶有精修指令（“增強精細細節和微觀紋理，保持構圖完全一致”）的FLUX.1-Kontextmodel節點，返回時變得更清晰、更大。

圖生圖

同一個 Kontext 節點同時充當圖生圖標籤頁。上傳一張圖片，描述你想要的改動，它就會返回編輯後的圖像。

讓 LLM 來寫提示詞

從一個粗略的提示詞開始，比如“暴風雨中的燈塔”。這條流水線會把它發送到一個 Qwen3-4Bmodel 節點，再由一個小型 fn 節點把回覆整理成一份乾淨的標籤列表，上限為四十個：“stormy sea, wet rocks, dramatic composition, low angle shot, volumetric lighting, ominous tone”。你可以把任意擴散模型節點連接到這個輸出上來渲染圖像。

與 ComfyUI 不同，這裏不涉及自定義節點。在 Gradio 工作流中，LLM 和擴散模型都只是同一畫布上的普通 model 算子。

把圖像讀回成提示詞

這就像 AUTOMATIC1111 的 Interrogate 按鈕，只不過由 VLM 而非 CLIP 來執行解讀。Qwen2.5-VL 看着一張夜市照片，寫出一段可能生成它的提示詞。一個 ViT 分類器節點讀取同一張圖像並返回標籤：restaurant 51.9%、tobacco shop 15.6%、toyshop 9.1%。

兩個節點使用相同的圖像輸入，因此 gr.Workflow 會並行運行它們，你大約只需運行一個節點的時間就能得到兩個答案。

檢測到修復掩碼

AUTOMATIC1111 需要你手動繪製修復掩碼。而這條流水線則通過檢測器自動生成掩碼。DETR 在一張街景照片中檢測到六個對象（三個人、一隻狗、一輛自行車和一輛汽車），隨後工作流分為兩條分支：一條將檢測到的邊界框繪製在原圖上，另一條將它們轉換為掩碼，供下游的修復流水線使用。

繪製和掩碼生成均在本地通過 Pillow 和 NumPy 完成。只有檢測調用需要離開本機。

提示詞矩陣

這類似於 AUTOMATIC1111 的提示詞矩陣。一個基礎提示詞"一棵孤零零的橡樹"通過一個 fn 節點與四個後綴（日出時分、雷暴中、銀河之下、秋霧中）組合，每個變體分別送入各自的文生圖節點。最後一個節點將四張結果拼接成一張聯繫表。

gr.Workflow 沒有循環操作符，因此四個文生圖節點並排排列在畫布上。由於它們處於相同的依賴深度，因此並行運行，四張圖像同時開始生成。

放大與背景移除

這就像 Automatic1111 裏的 Extras 標籤頁。有兩個放大節點，它們走的是不同的路徑。第一個是本地Lanczos重採樣，在一個fn節點中完成，無需網絡調用，速度與 Pillow 縮放一樣快。第二個是AuraSR ×4，它是畫布上的第一個space節點：它會調用 Hub 上的一個Space，並把結果當作任何其他節點輸出一樣處理。

背景去除的工作方式也是如此。BRIA RMBG-2.0是另一個space節點，因此整個模型都存在於它自己的 Space 中，而這個畫布只是調用它。

標註員

Canny、線稿、素描、luma-depth 和色調分離，這些通常是你在 Automatic1111 的 ControlNet 擴展中才能獲得的前置處理器。而在這裏，每一個都是一個用純 NumPy 編寫的 fn 節點，背後沒有任何模型。在一張預加載的建築立面示例照片上，每個標註器在 CPU 上大約需要半秒鐘。

該應用中有 36 個算子節點，其中 32 個是 fn 節點，而這 32 箇中有 22 個完全在進程內運行，無需網絡調用。如果你斷網，大約三分之二的畫布仍能正常工作。由於這些只是普通的 Python 函數，你還可以直接測試它們，無需畫布、服務器或 GPU。

PNG 信息

AUTOMATIC1111 會把生成詳情存儲在 PNG 的 parameters 文本塊中，PNG Info 標籤頁會將其讀回。Workflow1111 也是如此。文生圖流水線上的後處理節點負責寫入這些元數據，而這條流水線會將其讀回，包括提示詞、負面提示詞、步數、CFG、種子、圖像尺寸和模型。

圖生視頻

PNG Info 讀取的那個圖像節點同時也饋送給一個 Wan 2.2 I2V A14B 節點，由它將其動畫化；在演示示例中，一隻沉睡的狐狸醒來並開始活動。這裏沒有第二個上傳框，因為一個參考節點可以饋送給任意多個下游流水線，所以一次上傳就能在同一畫布上既讀取其元數據又被動畫化。

在自己的 GPU 上運行模型

到目前為止，每一次模型調用都發生在別人的硬件上，通過 Inference Providers 或一個 Space。這正是你無需自己的 GPU 就能構建並運行 Workflow1111 這類東西的原因。

不過，一個 fn 節點本質上就是 Python，因此它同樣可以在本地加載模型並在你自己的 GPU 上運行。FastVideo/fastvideo-fasth3-preview 就是一個 gr.Workflow 應用，正是這麼做的。它運行 FastH3，這是 MiniMax-H3 的四步蒸餾版本，並在 ZeroGPU 上生成帶配樂的視頻。

整個應用歸結為一個綁定函數：

@spaces.GPU(duration=get_duration, size=GPU_SIZE)
def _generate(prompt_embeds, text_token_tags, height, width, num_frames, seed):
    ...

gr.Workflow(bind={"generate": generate, "status": status}).launch()

ZeroGPU 會在函數需要時為其分配一塊 GPU，調用結束後再釋放。gr.Workflow 無需瞭解這些細節，它只需調用 fn 節點即可。

這也不僅限於 Spaces。把 bind= 指向一個加載本地 checkpoint 的函數，在你自己的機器上運行 .launch()，Workflow1111 畫布就能驅動你自己的 GPU。

每個輸出都是一個 API

畫布上的每個輸出節點都會變成一個 REST 端點，無需手寫任何路由。Workflow1111 暴露了其中九個：/image、/edited_image、/generated_prompt、/recovered_prompt、/detected_objects、/x_y_grid、/upscaled_local、/annotator_map 和 /png_info。

from gradio_client import Client

client = Client("ysharma/Workflow1111", oauth_token="hf_...")

image, params, hires = client.predict(
    "a red fox in a snowy pine forest",  # Prompt
    "",                                  # Negative prompt
    "Cinematic",                         # Style preset
    "enhance fine detail",               # Hires refine instruction
    api_name="/image",
)

這些相同的端點同時也是 MCP 工具。用 mcp_server=True 啓動（指南），每個輸出節點都會作為一個工具出現，供 AI 助手調用。把 Claude Code、Cursor 或任何 MCP 客户端指向該服務器 URL：

{
  "mcpServers": {
    "workflow1111": {
      "url": "https://ysharma-workflow1111.hf.space/gradio_api/mcp/",
      "headers": { "X-HF-Token": "hf_..." }
    }
  }
}

現在，智能體可以在一個更大的任務中把生成圖像、讀回提示詞或運行檢測作為步驟來執行，無需任何膠水代碼。每個調用方都在 X-HF-Token 請求頭中發送自己的 token，因此該 Space 本身不持有任何 token。

它與 ComfyUI 的定位對比

AUTOMATIC1111 給了我們功能清單，但真正被拿來和 Gradio Workflow 這款工具比較的是 ComfyUI，因為兩者都是節點圖。對於很多人想要構建和發佈的東西，gr.Workflow 覆蓋了相同的範圍。

  • 一個節點可以是你並不擁有的硬件。它可以通過 Inference Providers 運行，調用 Hub 上的任意 Space 或任意 API，或者從數據集中拉取。Workflow1111 就是這樣在沒有自己的 GPU 的情況下運行的。
  • 每個輸出都會變成一個帶類型的 REST 端點。這些端點由該圖生成。
  • 訪客可以用自己的身份運行工作流。開啓 OAuth，分享公開 URL，任何人都可以登錄並使用該應用，無需安裝任何東西。
  • 在同一畫布上混合模型和模態。擴散模型、LLM、VLM、檢測器和視頻模型都可以成為同一個工作流的一部分。
  • 需要自定義的東西？寫一個函數。自定義節點就是一個 Python 函數，所以它能做 Python 能做的任何事。

結果就是一個多模型流水線，人們可以在瀏覽器中打開、登錄、立即使用，並從代碼中調用。

構建你自己的

Workflow1111 有 73 個節點，但它最初只是這樣：

import gradio as gr

def your_function(text: str) -> str:
    pass

gr.Workflow(bind=[your_function]).launch()

bind= 將你的函數變成節點，edges= 將它們連接起來，.launch() 在瀏覽器中打開畫布，讓你可以在那裏繼續編輯。準備好之後，gradio deploy 會把整個東西放到一個 Space 上。gr.Workflow 指南 有完整的細節，包括 JSON schema 和每一種算子類型。

如果你想從已經能用的東西開始，打開 Workflow1111，點擊 Duplicate，然後從十一條流水線中選一條來修改：刪除節點、替換模型、重新連接流程。如果你想從更小的開始，上一篇博文 裏有五個工作流，每個大約一分鐘就能跑起來。

無論你構建了什麼，都把它發到 X 上並 @@gradio。我們很樂意幫你推廣你的工作流。
