字節新規：限制使用Claude、Codex等外部AI工具

內容機器翻譯自第三方媒體（鈦媒體 · cnBeta.COM），僅供參考，以原文為準。

正文

Anthropic 最近完成了一項頗具代表性的工程改造：一個起初沒有 Rust 開發者的團隊，藉助 Claude，將公司的 Messages API 從 Python 遷移到了 Rust。據 Anthropic 平台工程負責人 Katelyn Lesse 透露，改造後相關服務的 CPU 資源消耗減少了約 40%—50%，首 Token 延遲也改善了約 10%—20%。

在這個項目中，Claude 承擔了大量代碼編寫工作，而人類工程師主要負責系統架構、遷移策略和驗證方案。一個原本需要大量人工編碼的複雜項目，如今可以藉助 AI 完成。那麼， 當 AI 已經能夠承擔如此複雜的開發任務，軟件工程師還能做什麼？又該如何證明自己的價值？

Katelyn 對此頗為樂觀。10 月 26 日，Katelyn 在 X 上發表了一篇題為《The new set of problems for engineers to solve》（《工程師需要解決的一組新問題》）的長文。文中她提到：對於軟件工程師而言，現在是一個絕佳的時代。 AI 雖然正在改變工程師的工作方式，但也帶來了一批過去不曾面對的工程難題。

這種樂觀並非沒有理由。當 Agent 不再只是回答問題、執行簡單任務，而是開始長時間自主運行、彼此協作，甚至參與複雜的科研和工程項目時，現有的軟件基礎設施、身份認證與授權、安全隔離以及監控機制，都面臨新的挑戰。

在 Katelyn 看來，這些挑戰也意味着新的工程需求，正是軟件工程師接下來值得投入精力的方向。對於那些正在思考自身職業價值的工程師而言，這或許提供了另一種看待未來的角度。

一個負責統籌工作的 Agent，可以將任務分配給多個子 Agent；不同 Agent 可以分別承擔執行、檢查、評分等工作，再將結果彙總。隨着任務變得複雜，參與協作的 Agent 數量可能不斷增加，部分任務甚至需要持續運行數小時或數天。當成千上萬個 Agent 同時運行時， 現有的基礎設施能否高效地管理這些工作負載？

Katelyn 提到了 Kubernetes。作為廣泛使用的容器編排平台，Kubernetes 可以管理應用部署、擴縮容和故障恢復。它既能運行無狀態應用，也支持有狀態工作負載，但 Agent 的運行特徵給現有管理方式提出了新的要求。

Katelyn 將 Agent 描述為一種需要隔離、具有獨立狀態，通常以單個實例運行的工作負載。與傳統在線服務相比，Agent 的運行模式存在明顯差異。它可能連續執行復雜任務，也可能長時間等待模型推理、工具調用或其他 Agent 返回結果。如果每個 Agent 始終佔用獨立運行環境，資源利用率可能很低；但如果在空閒時釋放資源，又需要解決狀態保存、快速恢復和重新調度的問題。 如何在啓動速度、狀態持久化、隔離強度和資源成本之間取得平衡，成為 Agent 基礎設施的新挑戰。

圍繞這些問題，新的技術方案也在不斷出現。Katelyn 提到，一些 AI 基礎設施公司已經開始開發新的文件系統和沙箱服務，谷歌團隊也在構建名為 Agent Substrate 的新運行時環境。不過，在她看來，如何為大規模 Agent 提供高效、可靠的運行環境，仍有許多問題需要工程師解決。

當它們開始訪問代碼倉庫、調用外部服務、修改文件，甚至將任務交給其他 Agent 時，另一個問題隨之出現：這些 Agent 究竟應該擁有多大的權限？

Katelyn 在文章中明確區分了兩個概念：身份認證（Authentication）和授權（Authorization）前者回答“你是誰”，後者則決定“你能做什麼”。對於前者，軟件行業已經有較成熟的工作負載身份（Workload Identity）、短期證書等技術可以借鑑；真正複雜的是，當 Agent 開始代表用户長期執行任務，甚至自主創建子 Agent 時，權限應該如何分配和傳遞。

目前，許多 Agent 實際上是在代表人類用户工作。它們使用用户的身份和憑據訪問不同系統，代替用户執行操作。問題是，當某個文件被修改、某項操作被執行時，系統如何區分，這究竟是用户本人所為，還是 Agent 代替用户完成的？

當 Agent 開始長時間自主運行，授權問題還會變得更加棘手。例如，用户授權一個 Agent 持續數週處理開發任務，Agent 又將部分工作委託給子 Agent。此時，子 Agent 能否繼承原有權限、繼承多少、授權有效期如何確定，都需要重新設計。尤其是當 Agent 準備執行超出用户最初預期的操作時，系統還必須判斷是否需要人類再次確認。

Katelyn 特別提到了代表用户行事（On-Behalf-Of，OBO）模式。傳統的 OBO 授權模式可以讓服務代表用户訪問其他資源，但 Agent 的自主性和任務持續時間，使權限委託變得更加複雜。系統不僅需要確認 Agent 代表誰執行操作，還需要明確授權範圍、委託鏈條以及權限撤銷後的處理方式。

更復雜的情況是，如果未來的 Agent 不再依賴人類用户的身份，而是擁有自己的獨立身份，應該如何為它們分配權限？當多個 Agent 需要相互協作，一個 Agent 向另一個 Agent 發出請求時，後者又該如何確認對方的身份、判斷這項請求是否獲得授權？這些問題目前仍缺少成熟的解決方案，仍是工程師需要解決的新問題。

安全隔離：Agent 被攻擊後，如何限制風險擴散？ 過去幾個月，尤其是最近幾周，軟件漏洞接連暴露，出現的速度甚至超過了行業修復漏洞的速度，其中不少涉及大量系統賴以運行的關鍵基礎軟件。

Katelyn 指出，當成千上萬個 Agent 持續運行，不斷編寫、執行不可信代碼，並讀取來源不可信的內容時，基礎軟件中尚未修復的漏洞可能帶來更大的安全風險。因此，如何加固操作系統內核、瀏覽器、運行時環境和常用軟件庫，成為軟件工程師需要解決的重要問題。

假設一個 Agent 在執行任務時讀取了包含惡意指令的網頁或文件，並受到提示詞注入攻擊。如果它只是獨立運行，風險可能侷限於當前任務；但如果它需要與其他 Agent 協作，惡意內容就可能通過通信傳遞給其他 Agent，甚至進入共享記憶，影響之後的任務。

這時，攻擊的影響範圍（Blast Radius）就成為一個必須認真考慮的問題：如果第一個 Agent 被攻破，整個多 Agent 系統中究竟有多少部分可能受到牽連？在她看來，強隔離的執行環境是重要的基礎。

實際上，早在 9 月 13 日，Katelyn 就曾專門撰文討論 Agent 的安全架構，提出將 Agent 的“大腦”與“雙手”分開。

所謂“大腦”，包括負責模型調用、工具調用和用户交互的 Agent Harness，以及需要持久保存的會話狀態和訪問憑據。這些組件應當運行在沙箱之外的可信基礎設施中。而作為“雙手”的沙箱，則負責執行 Agent 生成的代碼和命令，處理可能包含惡意內容的外部數據。

這套架構的關鍵，是讓不可信代碼始終運行在權限受限的環境中。Agent 需要訪問外部服務時，由沙箱外的可信代理完成憑據注入和訪問控制，避免敏感密鑰直接暴露給沙箱內的代碼。即使 Agent 遭遇提示詞注入或執行惡意代碼，攻擊者能夠接觸的資源也受到限制。

如何識別 Agent 是在努力完成任務，還是已經失控？ 即使有了隔離措施，工程師仍然面臨另一個問題：如何及時發現 Agent 已經出現異常？
