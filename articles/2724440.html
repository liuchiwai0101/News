最近，我在處理基於 OpenAPI schema 生成的 API 請求和響應類型時，發現使用 TypeScript 的**條件類型**，我的 fetch 邏輯能夠根據調用的路徑和 HTTP 方法自動推斷出適當的參數和響應類型，這很酷。我試圖在文檔中查找更多信息，但發現它們實際上並沒有深入講解這種類型推斷，所以我想我應該更廣泛地分享一下這個很酷的特性。

type GetReturnType = Type extends (...args: never[]) => infer Return ? Return : never;我将向你展示 TypeScript 如何通过 extends 和 infer 关键字的强大功能，巧妙地从复杂的嵌套结构中提取类型。

我爲本文整理了一個簡化的 API schema，你可以在 GitHub 上探索它 — 以及所有代碼，都是實時可運行的。通過從倉庫中按 . 鍵啓動 GitHub Codespace，這樣你就能看到所有內容的實際運行效果。

請注意，本文假設你對 TypeScript 中的泛型有一些基礎瞭解！

將條件類型想象成 TypeScript 中的小 if 語句："如果滿足這個條件，就是*這種*類型，否則就是*那種*類型。" 語法看起來很像 JavaScript 的三元運算符，它在諸如爲可能根據傳入內容返回不同返回類型的函數編寫類型時很有用：

type myFn = (arg: SomeType | OtherType) => arg extends SomeType ? string : number;你可能在类型声明中熟悉 extends，我们会说"这个类型 X 继承自另一个类型 Y"。当在类型声明内部使用时，extends 不像一个语句，而是一个问题。"schema[P][M] 是否继承自这个对象？"

如果 extends 條件爲真，TypeScript 返回問號 ? 後面的類型。如果爲假，則返回冒號 : 後面的類型。

infer 允許我們提取類型如果你查看 TypeScript 條件類型文檔，infer 只有幾個小例子。例如，這裏是他們建議用它來獲取函數返回類型的方法：

type GetReturnType<Type> = Type extends (...args: never[]) => infer Return ? Return : never;
type Num = GetReturnType<() => number>; // type Num = number
type Str = GetReturnType<(x: string) => string>; // type Str = string
type Bools = GetReturnType<(a: boolean, b: boolean) => boolean[]>; // type Bools = boolean[]

我認爲這並沒有充分展現這個小關鍵字的強大之處。你實際上是在對 TypeScript 編譯器說，"*你*告訴我這是什麼類型，我不想把整個類型都寫出來"。當我們處理許多具有相同屬性不同組合的不同類型時，這變得*真的*很有用。

開始之前：使用 VSCode 調試 TypeScript 類型的技巧

我經常希望 TypeScript 有一個類型調試器，這樣你就可以在編譯時準確地看到編譯器在特定行上的想法，就像你可以用運行時值做的那樣。在沒有這個的情況下，我傾向於通過將類型分配給類型變量並在 VSCode 中懸停它們來調試/測試我的類型，看看 IntelliSense 如何評估它。這就是我在整篇文章中測試我們創建的類型時要做的。

type MyComplexType<T,Q> =  {....}
type test = MyComplexType<"test value", "another test value">

這裏是場景：我們正在用 TypeScript 構建一個觀鳥網站，它顯示不同鳥類的信息，讓你跟蹤你發現的鳥類目擊記錄。有一個前端和一個用於獲取數據的 API。

我們希望確保我們發出的請求包含正確的參數，然後我們希望能夠以類型安全的方式使用我們獲得的返回數據。爲此，我們需要一些 API 類型。

我們有一個 API 規範可以用來構建，它準確告訴我們請求需要哪些參數，以及響應返回什麼。出於本文的目的，這是一個非常簡化的 API 規範。

我們運行了一個腳本來自動爲該規範生成類型，生成的接口給了我們所有的路徑、它們允許的方法，以及這些方法的參數和響應類型。

我們生成的 API 類型看起來像這樣：

要進行 API 調用本身，我們通常會使用原生的 fetch 函數。但這本身不會對我們創建的那些類型做任何事情。

const rsp = await fetch('<https://api.example.com/bird/12>');
const data = await rsp.json(); // 此时不知道这是什么类型

fetch 不是一個泛型函數，所以我們不能傳遞類型註解來說明請求和響應的形狀：

await fetch(....) // 你不能這樣做我們*可以*告訴 fetch 它返回什麼類型，但這非常冗長和不便（而且每次使用時都必須這樣做）：

import schema from './api'
[...]
const rsp = await fetch('<https://api.example.com/birds/12>')
const data = await rsp.json() as schema['/bird/{birdId}']['get']['response']['content']

當然，我們可以提取這些類型，這樣就不必如此冗長了，但是我們需要爲每個想要的響應類型都這樣做。

type ListBirdsResponse = paths['/birds']['get']['response']['content'];
type GetBirdResponse = paths['/bird/{birdId}']['get']['response']['content'];
type AddSightingResponse = paths['/users/{userId}/sightings']['post']['response']['content'];
// 我已经觉得无聊了。

所以，如果我們想要在參數和響應中更容易的類型安全，我們需要構建某種圍繞 fetch 的包裝器來編碼類型信息。由於我們有 API schema 的生成類型，我們可以讓 TypeScript *告訴我們*類型，而不是每次都指定它們：它可以**僅從 API 調用的路徑和方法推斷參數和響應類型。**

我們將構建一個 createFetcher 函數，它接受一個路徑和一個 HTTP 方法，並返回另一個函數，該函數確切地知道它期望什麼參數，以及你得到什麼返回類型。

我們稱返回函數的函數爲高階函數。

function createFetcher(path, method) {
    return async (params) => { // ... }
}
const getBird = createFetcher('/birds/{birdId}', 'get')
const data = await getBird({ path: { birdId: 12 } })

向 getBird 傳遞錯誤的參數 — 或不夠的參數 — 將導致一些友好的錯誤：

const data = await getBird({});
// Argument of type '{}' is not assignable to parameter of type 'Params<"/birds/{birdId}", "get">'.
// Property 'path' is missing in type '{}' but required in type '{ path: { birdId: number; }; }'.ts(2345)

懸停在 data 上將給我們響應類型：

const data: {
    id?: number;

爲了給我們這些請求和響應的正確類型，我們的 createFetcher 函數需要知道：

第一個很容易：我們可以在定義此函數的文件中導入 API schema 的類型，所以它會在作用域內。

對於第二和第三點，我們將向函數傳遞兩個**類型參數**，一個用於路徑 P（例如 /birds/{birdId}），一個用於方法 M（例如 get）。

import { schema } from './api'
function createFetcher<P, M>(path: P, method: M) {
    return async (params) => { // TODO }
}

在 API schema 中包含着嵌套對象，使用路徑作爲鍵，然後方法作爲這些嵌套對象的鍵：

export interface schema {
        '/birds/{birdId}': {
            get: {
            parameters: {
              query?: {
              [...]

我们需要明确告诉 TypeScript 第一个类型参数 P（上面例子中的 /birds/{birdId}）是我们 schema 的键，第二个类型参数 M（例子中的 get）是 schema[P] 的键。我们用 extends 来做这件事。

import { schema } from './api'
function createFetcher<P extends keyof schema, M extends keyof schema[P]>(path: P, method: M) {
    return async (params) => { // TODO }
}

注意：這不是條件類型，即使我們使用了

extends關鍵字：它實際上是一個帶有約束的類型參數。這個上下文中的extends如果你有任何面向對象編程經驗，或者在 JS 中使用過類，可能會很熟悉：T extends X意味着"類型T包含類型X的屬性"，約束限制了可以傳入的類型種類。

上面的代碼告訴 TypeScript **它應該能夠對**我們給它的類型參數**做什麼樣的事情**。例如，我們可以使用它們在我們的 schema 中查找嵌套類型，因爲我們特別告訴 TypeScript P 指的是 schema 的鍵，M 指的是 schema[P] 對象的鍵。

此時我們沒有給它*特定的*路徑或方法，而是說"我們在這裏傳入的任何路徑都應該有效，因爲它是 keyof schema"。如果我們嘗試將此類型用於 schema 中不存在的東西，編譯器會給我們一個錯誤。

const wrong = createFetcher('cheese', 'get');
// error: Argument of type '"cheese"' is not assignable to parameter of type 'keyof schema'.ts(2345)

我們的 createFetcher 函數將在底層使用 fetch。（注意：出於本文的目的，我們不擔心錯誤處理，但通常我會在這裏用 try/catch 包裝 fetch 並確保任何錯誤都得到適當處理。）

function createFetcher<P extends keyof schema, M extends keyof schema[P]>(path: P, method: M) {
    return async params => {
        const baseUrl = '<https://api.example.com>';
        const fetchUrl = new URL(path, baseUrl);
        const options: RequestInit = {
            method: method as string
        };
        const data = await fetch(fetchUrl, options);
        return await data.json();
    };
}

注意這裏我們需要顯式地將我們的 method 參數（M extends keyof schema[P]）轉換爲字符串，以便將其分配給 RequestInit 中的 method 屬性（它期望一個字符串）。即使我們知道它是一個字符串，但從技術上講，M 可能不是字符串（*我們*知道它不會是，但 TypeScript 編譯器不知道。）

**這個 fetch 還不能工作**，因爲我們正在用路徑的模板字符串版本（例如 `/birds/{birdId}`）進行獲取。我們需要從請求的參數中獲取路徑值，但首先我們需要知道我們期望什麼參數（以及我們是否期望任何參數）。

現在我們需要定義我們的 Params 類型，它屬於我們返回的部分應用函數中進行實際獲取的參數：

function createFetcher<P extends keyof schema, M extends keyof schema[P]>(path: P, method: M) {
    return async (params?: Params) => { ... // 获取逻辑 }
}
// type Params = ???

我們將此參數標記爲可選的，因爲某些請求可能具有可以完全省略的參數（例如帶有可選搜索查詢參數的"列出所有鳥類"請求）。

就像 createFetcher 函數一樣，Params 類型也需要知道它正在處理什麼 schema、路徑和方法，以便告訴我們該路徑和方法組合的正確參數。所以這將具有與 createFetcher 完全相同的類型參數。

type Params

= {};这里是生成的 schema 类型中我们参数的几个例子：

"/birds/{birdId}": {
    get: {
    parameters: {
      path: {
        birdId: number
      }
    }
    ...
  }
},
"/users": {
  post: {
    requestBody?: {
      content: {
        name?: string
        email?: string
        favouriteBirdIds?: number[]
      }
    }
    ...
  }
}

所有路徑 + 方法組合都在我們的規範中定義了 parameters，但它們可能實際上沒有在請求中使用。在 POST /users 的例子中，query?: never 意味着沒有查詢，你可以完全省略該字段。

requestBody.content 可以包含任意键/值对，就像 POST /users 那样，或者在没有主体的请求中，requestBody 字段应该完全省略（就像 GET /birds/{birdId} 那样，它在生成的类型中有 requestBody?: never）。

我們希望確保在我們不同的請求中捕獲各種參數組合，而不讓你必須顯式提供不需要的字段。我們想要*自動*做到這一點。

這裏是重點：我們現在將以**依賴於 P 和 M 的值**的方式從 API 規範中獲取各種參數的類型。

首先，我們必須用 extends 檢查我們的類型是否包含我們正在尋找的字段，然後我們使用 infer 關鍵字從條件類型中獲取那些嵌套類型。然後我們可以在從條件返回的分支的類型中**使用這些推斷的類型**。

type Params<P extends keyof schema, M extends keyof schema[P]> = schema[P][M] extends {
    parameters: {
        query?: infer Q;
        path?: infer PP;
        requestBody?: { content: infer RB };
    };
}
    ? {
          query: Q;
          path: PP;
          requestBody: RB;
      }
    : never;

注意我們的 requestBody 實際上是一個嵌套對象 — 你可以遍歷對象直到找到要推斷的屬性，這很巧妙。

最後，如果條件*不*匹配，我們返回 never，因爲條件賦值時你總是必須有兩個分支，即使你知道你的類型將始終匹配你正在評估的條件，第二種情況永遠不會發生。

never說："這不應該發生"。與undefined（意味着"這個值還沒有初始化"）不同，never告訴 TypeScript 編譯器這裏永遠不會有值，如果有，就出了問題。如果我們嘗試給類型爲never的東西賦值，編譯器會對我們大喊大叫。

我們可以通過爲特定路徑和方法聲明類型來測試它：

type GetBirdParams = Params<'/birds/{birdId}', 'get'>;在 VS Code 中悬停在这上面它会给我们：

type GetBirdParams = {
    query: undefined;
    path: {
        birdId: number;
    };
    requestBody: undefined;
};

現在讓我們將這個 Params 類型放入 createFetcher 中，看看我們的編譯器說什麼。

function createFetcher<P extends keyof schema, M extends keyof schema[P]>(path: P, method: M) {
    return async (params?: Params<P,M>) => { ... }
}
const getBird = createFetcher("/birds/{birdId}", "get")
getBird({ path: { birdId: 1 }})

不幸的是，最後一行給我們一個類型錯誤：

Argument of type '{ path: { birdId: number; }; }' is not assignable to parameter of type '{ query: undefined; path: { birdId: number; }; requestBody: undefined; }'.
Type '{ path: { birdId: number; }; }' is missing the following properties from type '{ query: undefined; path: { birdId: number; }; requestBody: undefined; }': query, requestBody

嗯。path 字段是正確的，但似乎我們仍然必須顯式提供 query 和 requestBody 字段來讓 TypeScript 滿意。它們是 undefined 因爲 /birds/{birdId} 在 schema 中沒有查詢字符串或請求主體，但我們在 Params 中將這些字段聲明爲非可選的。

我們將修復它，使這些參數中不需要的任何字段都用 ? 標記爲**可選**。我們可以通過檢查哪些參數是未定義的，並在最終結果中使它們可選來做到這一點。我將爲我們的 Params 創建一個包裝器類型來做這件事，並將原始 Params 重命名爲 ParamsInner。

type ParamsInner<P extends keyof schema, M extends keyof schema[P]> = schema[P][M] extends {
    parameters: {
        query?: infer Q;
        path?: infer PP;
    };
    requestBody?: { content: infer RB };
}
    ? {
          query: Q;
          path: PP;
          requestBody: RB;
      }
    : never;
export type Params<P extends keyof schema, M extends keyof schema[P]> = (unknown extends ParamsInner<P, M>['query'] ? { query?: never } : { query?: ParamsInner<P, M>['query'] }) & (unknown extends ParamsInner<P, M>['path'] ? { path?: never } : { path: ParamsInner<P, M>['path'] }) & (unknown extends ParamsInner<P, M>['requestBody'] ? { requestBody?: never } : { requestBody: ParamsInner<P, M>['requestBody'] });

這裏我們有三個條件類型的**聯合**。如果一個字段返回爲 unknown（因爲我們的路徑 + 方法組合沒有它），我們用類型 never（因爲它永遠不應該存在）將其標記爲**可選**。

如果我們提取的參數上存在 requestBody 或 path，我們將使必要的字段成爲必需的。query 即使存在也應該仍然是可選的，因爲查詢參數可能是可選的（例如可選搜索過濾器）。

這裏有一個陷阱：確保使用

unknown extends而不是extends unknown。[unknown](https://www.typescriptlang.org/docs/handbook/2/functions.html#unknown)是[any](https://www.typescriptlang.org/docs/handbook/2/functions.html#unknown)的类型安全等价物。因为它在类型层次结构的顶部，每个类型都继承自unknown，但unknown只能继承自它自己。

如果你颠倒这个extends语句的顺序，你最终会在这种情况下得到所有返回为never的东西（例如ParamsInner['query'] extends unknown将始终为真，即使它有值）。

現在讓我們確保我們的類型看起來正確：

const getBird = createFetcher('/birds/{birdId}', 'get');
getBird({ path: { birdId: 1 } });
