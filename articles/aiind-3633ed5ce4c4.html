AI 能否取代滲透測試？Cloudflare 的答案是：必須套上測試框架

內容機器翻譯自第三方媒體（InfoQ），僅供參考，以原文為準。

正文

Cloudflare 將前沿 AI 模型置於一個受控測試框架中，用於探測其 Web 應用防火牆（WAF），並以遭到攔截的攻擊為起點，讓模型生成和改進新的變體。

在 45 個場景中，該系統生成了 1,107 次嘗試，經過人工篩選後留下了 49 項發現。這項測試最終促成了 Cloudflare 託管規則集的三項變更。

實驗從 WAF 已經攔截的攻擊載荷開始。模型並非反覆重放固定測試用例，而是根據此前嘗試得到的響應，提出對編碼方式、載荷位置或交付方式的修改。模型無法訪問 Cloudflare 的 WAF 規則、源代碼或內部安全信號，因此從模型的角度來看，這實際上是一場黑盒測試。

Cloudflare 不希望交給模型處理的部分由一個 Python 測試框架負責。它負責構造和重放 HTTP 請求、維護場景狀態、實施限制並收集響應。一次模型調用負責提出下一個變體，另一次模型調用則審查由此產生的響應，使後續嘗試能夠動態調整，同時又不讓模型直接控制請求的執行。

一項 SSRF 測試展示了這種反饋循環的工作方式。測試器不斷改變某個雲元數據地址的表示方式和出現位置，嘗試了十進制、八進制及其他形式。最終，一個使用十進制表示方式的請求遭到攔截。在下一次嘗試中，模型保留了相同的請求結構，但將該地址改為末尾帶點的表示形式；這一次，客户端遇到的是重定向，而不是 WAF 攔截。Cloudflare 保留了這一結果以供調查，而沒有將其視為攻擊已經成功的證據。

這種區分在大規模測試中被證明非常重要。在記錄的 1,107 次變體嘗試中，有 607 次形成了經過篩選後的結果集：其中 558 個請求被 WAF 攔截，49 項發現被認為與進一步的修復工作相關。49 項發現中有 48 項涉及命令注入或服務端請求偽造（SSRF）。

人工審查仍是最終的驗證環節。審查人員會檢查請求是否真正到達目標、是否仍具有惡意性、是否明確未被攔截、是否屬於 WAF 的職責範圍，以及能否安全復現。保留下來的案例隨後會被重新執行，並作為修改規則、規範化處理或其他緩解措施的候選項進行評估。

這項工作促成了 Cloudflare 託管規則集的三項變更：新增兩項檢測規則 SSRF - Obfuscated Host 和 SSRF - Restricted Protocol，並改進了現有的 SSRF - Cloud 規則。

相同的測試框架模式也出現在其他安全工程實踐中。 Cloudflare 的漏洞發現測試框架 將漏洞發現與獨立驗證分離，而 Google Mandiant 的 智能體漏洞發現測試框架，則讓多個專業智能體依次完成源代碼分析、假設生成和驗證，之後才將發現交給人工審查人員。

其他系統採用了不同的術語，但遵循類似的發現與驗證模式。 OpenAI 的 Codex Security 會為代碼倉庫構建威脅模型、搜索漏洞，並嘗試在隔離環境中復現候選漏洞，然後再提出修復方案供人工審查。 Google 的 PageBreak 同樣側重於驗證 AI 生成的漏洞假設是否確實可以利用，部分目的是避免大量看似合理但未經驗證的發現淹沒安全團隊。

這些系統的共同點是圍繞模型構建的測試框架：限制執行、保存狀態、驗證發現，並將概率性的探索轉化為現有安全工作流可以使用的證據。
