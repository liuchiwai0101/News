2）先只用函数组件 + useState + useEffect

別急着碰 Redux、Router、Context，一上來就全堆進去，心智負擔會明顯上升。你只需要搞清楚：

3）對“頁面結構”保持一點點潔癖

新人寫 React 時，我最常看到的問題不是 API 不會，而是：所有東西擠在一個組件裏。

在代碼評審裏，我會要求拆出這些：

- `SearchBar`：只關心輸入和觸發查詢

- `ProductList`：只負責列表展示

- `Pagination`：只管分頁邏輯- 頁面組件只做一件事：把這些組件串起來。

你可以把這個階段看成“React 最小可用技能”：只要你能獨立構建這樣的頁面，你在大部分團隊裏已經能開始接簡單需求，而不僅僅是做教程裏的練習題。

我給新人的 Hook 學習順序，非常功利：

1）<code>useState</code>：別把所有東西都塞成一個大對象

在真實項目裏，經常看到這樣的寫法：

const [state, setState] = useState({ loading: false,

list: [],

page: 1,

keyword: ''

});

改的時候既費力，也容易出錯。更好的方式往往是拆開：

const [loading, setLoading] = useState(false);const [list, setList] = useState([]);

const [page, setPage] = useState(1);

const [keyword, setKeyword] = useState('');

是，多了幾行，但可讀性和可維護性高很多，也利於新人理解“狀態變化”。我在團隊裏做代碼審查時，每週至少會讓 3～5 個新人把“一坨 state”拆開。

2）useEffect：只回答一個問題——這個副作用，依賴的是什麼？

- 無限循環請求接口

3）自定義 Hook：只解決“重複邏輯”問題

到了 2025–2026 年，大部分成熟團隊已經把頁面裏常見的異步請求、分頁、表單操作，用自定義 Hook 封裝得很完備了，比如：

- `useRequest`：统一处理 loading、error、retry

- `usePagination`：處理當前頁、總頁數、頁碼切換- 你一開始不必研究這些封裝的“哲學”，你只需要學會從業務中抽取： - 頁面 A 和頁面 B 都有加載狀態、錯誤提示、數據列表，邏輯大差不差，就可以考慮抽一個 - `useList`。

落到 React 上，其實就是這些小地方：

- 組件命名 - `List`、- `Box`、- `Item`這種命名，過幾周後你自己都看不懂。- 改成 - `CourseList`、- `CourseCard`、- `FilterPanel`，對未來接手的人非常友好。

- Props 設計 - 真實項目裏，最常見的“祕密 Bug”，往往來自 props 設計過度靈活。 - 比如一個組件同時支持 - `value`和- `defaultValue`，同時還要支持受控和非受控，邊界邏輯非常容易出錯。新手階段，更穩妥的方式是：儘量收斂組件的用途，用幾個清晰的 props 做事情。

- 錯誤處理 - 在教程裏，大家常常忽略錯誤處理；在真實項目裏，錯誤處理質量，常常影響用戶是否願意繼續用你的產品。 - React 有 Error Boundary，可以捕捉子組件的渲染錯誤。如果你在自己的項目裏主動加上這一層，而不是等線上白屏了再補，面試時講這樣的經驗，可信度會比“我看過很多源碼”高太多。
