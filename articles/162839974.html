React 19 Compiler 深度实战：当 React 亲手取代 useMemo

React 19 早已不再是新聞，但它搭載的 React Compiler（前身 React Forget）纔是真正改變遊戲規則的東西。從 2024 年 React Conf 上首次公開，到 2025 年 10 月發佈 1.0 穩定版，再到 2026 年全面進入生產的主流隊列——這套編譯時優化工具經歷了從「要不要用」到「不用會虧」的轉變。

React Compiler 的核心邏輯可以概括爲一句話：**自動追蹤組件依賴關係，在編譯階段完成 useMemo/useCallback 級別的優化**。

傳統 React 開發中，開發者需要手動判斷哪些計算需要緩存、哪些回調需要穩定引用。這個過程不僅心智負擔重，而且容易出錯——少寫一個 useMemo 可能導致不必要的重渲染，多寫一個又可能因爲依賴數組寫錯而產生過期的閉包。

React Compiler 通過靜態分析你的 JSX 和 Hook 調用，自動推斷出組件中哪些值是「派生」的、哪些函數需要穩定引用，然後在編譯產物中自動插入等效的 memoization 代碼。

React Compiler 的編譯流程分爲四個階段：

**第一階段：AST 解析與 IR 構建。** Compiler 首先將你的 React 組件代碼解析爲抽象語法樹，然後構建一箇中間表示（IR）。這個 IR 專門爲 React 組件設計，能夠表達 JSX 元素、Hook 調用、條件渲染、循環等 React 特有的語義。

**第二階段：依賴圖分析。** 在 IR 層面，Compiler 構建一個完整的依賴圖。它會追蹤每個變量的來源——是 props、state、context，還是從其他變量派生而來。對於每個函數，它會分析函數體內引用了哪些外部變量，以及這些變量的穩定性。

**第三階段：Memoization 決策。** 基於依賴圖，Compiler 做出 memoization 決策。核心規則是：如果一個值的計算成本較高（如數組的 map/filter 操作、對象字面量），且其依賴在多次渲染間可能不變，就自動緩存它。如果一個函數被作爲 props 傳遞給子組件，就自動用 useCallback 包裹。

**第四階段：代碼生成。** 最後，Compiler 將優化後的 IR 轉回 JavaScript 代碼。生成的代碼會包含自動插入的 useMemo、useCallback 調用，以及必要的依賴數組。

手動寫 useMemo 時，開發者需要自己指定依賴數組。這有兩個常見問題：一是依賴數組可能遺漏，導致緩存未正確失效；二是依賴數組可能過度指定，導致緩存過於頻繁地失效。

React Compiler 不存在這兩個問題。它通過靜態分析精確地知道每個值的真實依賴，生成的依賴數組永遠是正確的。此外，Compiler 還能做一些開發者手動做不到的優化，比如對 JSX 元素進行 memoization——這在手動編碼中幾乎不可能做到。

首先確保你的項目已經升級到 React 19 和對應的構建工具版本：

npm install react@19 react-dom@19
npm install -D @vitejs/plugin-react@6  # 如果使用 Vite

Vite 8 內置了 Rolldown（Rust 寫的 bundler），打包速度提升 50% 以上。@vitejs/plugin-react v6 將 Babel 替換爲 Oxc——又一個 Rust 寫的轉譯器，編譯速度提升 10-20 倍。

在 Vite 項目中，啓用 React Compiler 只需在 vite.config.js 中添加配置：

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
export default defineConfig({
  plugins: [
    react({
      babel: {
        plugins: [['babel-plugin-react-compiler', { target: '19' }]],
      },
    }),
  ],
});

對於 Next.js 16 用戶，Compiler 已經默認啓用。Next.js 16 使用 Turbopack（Rust 打包器）作爲默認構建工具，啓動速度提升 87%，生產構建秒級完成。

**第一步：刪除手動 memoization。** 啓用 Compiler 後，第一步是系統性地刪除項目中的 useMemo、useCallback 和 React.memo。這不是必須的——Compiler 能夠識別已有的 memoization 並跳過重複優化——但刪除它們能讓代碼更簡潔，也避免了手動優化與自動優化之間的潛在衝突。

**第二步：運行 Compiler 的 lint 規則。** React Compiler 附帶了一套 ESLint 規則，能夠檢測出可能違反「React 規則」的代碼——比如在條件語句中調用 Hook、在循環中使用 Hook 等。這些規則在 Compiler 啓用後尤爲重要，因爲違反規則的代碼可能導致 Compiler 無法正確分析。

npm install -D eslint-plugin-react-compiler

在 .eslintrc.js 中添加：

module.exports = {
  plugins: ['react-compiler'],
  rules: {
    'react-compiler/react-compiler': 'error',
  },
};

**第三步：逐步驗證。** 不要一次性遷移整個項目。建議按路由或功能模塊逐步遷移，每遷移一個模塊就運行一次完整的測試套件和性能基準測試。

**問題一：Compiler 報「無法分析」錯誤。** 這通常是因爲組件中使用了 Compiler 無法靜態分析的動態模式，比如動態生成的 Hook 名稱、在條件分支中調用 Hook 等。解決方法是重構這些代碼，使其符合 React 的規則。

**問題二：性能反而下降。** 在極少數情況下，Compiler 的自動 memoization 可能導致性能下降。這通常發生在組件的渲染成本極低、但 memoization 的比較成本較高時。可以通過 React DevTools 的 Profiler 定位問題，然後使用 `'use no memo'` 指令選擇性禁用 Compiler。

React Server Components 從「爭議特性」變成了「默認選項」。Next.js 15、React Router v7、TanStack Start 都已經深度集成 RSC。流式渲染配合 RSC，讓首屏體驗有了質的變化。

RSC 的核心思想是：組件在服務端渲染，只將渲染結果（而非組件代碼）發送到客戶端。這意味着組件可以使用服務端資源（數據庫、文件系統），而不會增加客戶端的 JavaScript 體積。

React 19 新增了多個實用的 Hook：

- **useActionState**：管理表單提交狀態，替代了手動管理 loading/error 的模式。

- **useFormStatus**：在表單內部獲取父表單的提交狀態，無需 prop drilling。

- **useOptimistic**：實現樂觀更新，在服務端響應之前就更新 UI，提升交互體驗。

- **useStream**：專門處理 AI 流式響應，配合 RSC 實現實時 AI 交互。
